# e2e metrics-server preload fails on a cache miss beside cert-manager

**Event:** the kindnet or Calico e2e lane fails on `main` or in the merge queue at "Preload metrics-server image onto kind nodes", or at any pre-pull step, with `does not provide the specified platform` or `still does not export`.

The lane failed at the metrics-server preload whenever the `metrics-server-images-m2-v0.8.1` cache missed while the cert-manager cache hit.
Three merge-queue runs failed this way on 2026-10-30, when the cache download died on `Egress is over the account limit`: [41107804578](https://github.com/actions-gateway/github-actions-gateway/actions/runs/41107804578), [41108123126](https://github.com/actions-gateway/github-actions-gateway/actions/runs/41108123126) and [41112785824](https://github.com/actions-gateway/github-actions-gateway/actions/runs/41112785824).
A dispatch of unfixed `main` with only the metrics-server key bumped, [41337555013](https://github.com/actions-gateway/github-actions-gateway/actions/runs/41337555013) on 2026-11-01, failed the same way with no throttling, so the failure follows the cache state, not the egress limit.

**Mechanism, reproduced 2026-11-01 on Docker 29.4.1 and 29.6.2 (docker-in-docker, containerd store).** metrics-server v0.8.1 shares 9 of its 13 uncompressed layers with the cert-manager v1.20.2 images under different compressed blobs.
After `docker load` of the cert-manager images, a metrics-server pull fetches 4 layers and skips the 9 whose snapshots exist, so their blobs never reach the content store ([moby/moby#52193](https://github.com/moby/moby/issues/52193), open).
`docker save --platform` then refuses the image, and a plain `docker save` exits 0 with a 12 KB archive holding no layers, which `docker load` accepts and which fails the same way on every later run.
That second half is why a fix in `kind-load-image.sh` alone would have poisoned the cache on the first cold run that passed.
Whether the cert-manager tar came from Docker 28's classic store or from the containerd store makes no difference, and neither does the Docker version between 29.4.1 and 29.6.2.
So the earlier non-reproduction on a developer host's 29.6.2 was not a version fix; what about that host's state let the save pass was not checked.

**Mitigation.** [`backfill-image-content.sh`](../../scripts/fetch/backfill-image-content.sh) probes the platform export and, on that error, runs a `FROM <image>` BuildKit export on the daemon's own builder, which fetches the missing blobs into the content store the daemon shares, leaving the image ID unchanged.
`prepull-manifest-images.sh` runs it on the miss path before writing the tar, and `kind-load-image.sh` runs it before retrying a refused save.
`--output type=cacheonly` fetches nothing, so the export is written and discarded.

**Not covered.** The self-hosted Kata lane skips these caches and always takes the pull path, so it meets the shared-layer pull on every run if its daemon uses the containerd store; whether the BuildKit fetch there reaches the registry mirror has not been measured.
`prepull-image-cached.sh` still saves without the backfill; whether its one image, the buildkit builder, shares layers with anything loaded before it has not been checked.
