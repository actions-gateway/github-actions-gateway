# e2e metrics-server preload fails when its cache restore is throttled

**Top of queue per [flakes-first rule](../development/maintaining-backlog.md#flake-fixes-go-first).**

The kindnet e2e lane fails at "Preload metrics-server image onto kind nodes" whenever the `metrics-server-images-m2-v0.8.1` cache restore fails, and the merge queue evicts whatever PR is in the candidate.
Three merge-queue runs failed this way on 2026-10-30, every e2e failure in the 40 most recent `merge_group` runs of `e2e-test.yml`: [41107804578](https://github.com/actions-gateway/github-actions-gateway/actions/runs/41107804578) (18:32 UTC), [41108123126](https://github.com/actions-gateway/github-actions-gateway/actions/runs/41108123126) (18:34) and [41112785824](https://github.com/actions-gateway/github-actions-gateway/actions/runs/41112785824) (19:08).
Each of the three logs shows the same sequence:

1. `actions/cache` logs `Cache hit for: metrics-server-images-m2-v0.8.1`, stalls partway through the 20 MB archive (at 79% and 83% in the two runs checked), then logs `##[warning]Failed to restore: Egress is over the account limit.` and `Cache not found for input keys: metrics-server-images-m2-v0.8.1`.
   The "hit, then not found" is one failed download, not two lookups.
2. `scripts/fetch/prepull-manifest-images.sh` takes the cold path and pulls `registry.k8s.io/metrics-server/metrics-server:v0.8.1`.
   In run 41112785824 the pull lists only 4 of the image's 13 layers.
3. `scripts/e2e/kind-load-image.sh` runs `docker save --platform linux/amd64` and the daemon answers `no suitable export target found: image with reference registry.k8s.io/metrics-server/metrics-server:v0.8.1 was found but does not provide the specified platform (linux/amd64)`.

Runs whose cache restore succeeds pass, which is why the lane looks intermittent: it fails exactly when the cache download fails.
The runner in run 41112785824 is Docker 29.4.2 on the containerd image store (`driver-type: io.containerd.snapshotter.v1`).

**Why the save rejects a just-pulled image.** The 9 layers the pull never listed are exactly the 9 leading layers metrics-server v0.8.1 shares with `quay.io/jetstack/cert-manager-controller:v1.20.2`: the distroless base, measured by comparing the two amd64 configs' `rootfs.diff_ids` from the registries.
The job `docker load`s the cert-manager images from their own cache a few steps earlier, so those layers are already unpacked.
On the containerd store a pull skips downloading a layer whose unpacked snapshot already exists, which leaves the compressed blobs the metrics-server manifest names absent from the content store, and `docker save --platform` then counts that platform as not provided.
That is upstream [moby/moby#52193](https://github.com/moby/moby/issues/52193): the same error after a same-platform pull, attributed by a maintainer to moby#49784 and to [containerd/containerd#8973](https://github.com/containerd/containerd/issues/8973), which its reporter says is now resolved.

What is and is not measured.
The layer overlap, the 4-of-13 pull listing, and the error text are from the CI logs and the registries.
The CI sequence did **not** reproduce locally on Docker 29.6.2 (containerd store): after `docker load` of a cert-manager-controller tar, the metrics-server pull and `docker save --platform linux/amd64` both exit 0.
Either 29.6.2 carries the upstream fix or the CI cert-manager tarball matters: its cache entry was created 2026-10-24 00:13 UTC, when `main` still ran Docker 28.0.4's classic store (#2169 dates the move to the containerd store between 2026-10-24 and 2026-10-27), so it likely holds uncompressed layers, which the local tar did not.
Neither has been checked.
[#2169](https://github.com/actions-gateway/github-actions-gateway/pull/2169)'s passing cold path was Calico, whose images share no layers with anything loaded earlier.

**Why it can recur on its own.** A failed job never saves its cache, so the only way out is a run whose restore succeeds.
And any run where metrics-server is cold while cert-manager is present (a `METRICSSERVER_VERSION` bump, a key bump, cache eviction) takes the same path regardless of the egress limit.
That last claim is inferred from the mechanism above, not observed.

**Fix candidates, none yet proven against Docker 29.4.2:**
- In `kind-load-image.sh`, when `docker save --platform` fails with this error, fall back to exporting the image without the daemon's content store, for example by having the kind nodes pull it themselves (`ctr -n k8s.io images pull --platform`), which reintroduces a registry pull but only on this path.
- On the cold path in `prepull-manifest-images.sh`, pull each image before any cached image sharing its layers is loaded, so its blobs are fetched rather than skipped.
  This needs the metrics-server prepull to run before cert-manager's, and fails again if both are cold.

Done means a fix that passes a `workflow_dispatch` of `e2e-test.yml` with the metrics-server cache key bumped (forcing the cold path) and the cert-manager cache warm, which is the exact state of the failing runs.

Related, measured locally on Docker 29.6.2 only: `prepull-manifest-images.sh`'s cold path runs `docker save` without `--platform`, and on the containerd store that fails for `cert-manager-controller:v1.20.2` (`unable to create manifests file: NotFound: content digest … not found`), while metrics-server's CI cold path saved cleanly.
A cold cert-manager pull, as on a `CERTMANAGER_VERSION` bump, may fail at the prepull step for that reason.
