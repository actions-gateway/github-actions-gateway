# Validate five AGC run and recovery state leads from the security audit

**Leads, not confirmed vulnerabilities.** Source supports each path and something outside the repository decides the outcome, so none has a severity.
[Each lead, with evidence, blockers and a validation plan](../plan/security-audit-2026-11.md#agc-run-and-recovery-leads):

- AGC re-runs and force-cancels whatever run its namespace ConfigMaps and pod annotations name; docs/design/05-security.md line 200 describes only the pod annotation and says a run ID cannot be substituted (needs validation).
- One repository's OOM-killed jobs can fill the per-set failure ledger and withhold automatic re-runs for every repository on the RunnerSet (needs validation).
- Throughput sizing profile derives the worker memory limit from job-controlled peak usage with no maxRequests clamp, so the limit can exceed the operator's envelope and may ratchet (needs validation).
- Tenant-chosen workerImage host (and registry redirects) steer AGC GETs to in-cluster 443/6443 endpoints off the egress proxy, with the outcome reported in RunnerSet status (needs validation).
- AGC run-status, re-run and force-cancel errors carry the raw upstream body into logs, and run-status and re-run errors into a tenant-namespace Event, bypassing SanitizeBody (needs validation).

The first decides the most: the controller re-runs or force-cancels whatever run its namespace ConfigMaps and pod annotations name, so anyone who can write those steers an installation-token call.

**Measure:** each lead's local test in the plan doc is an envtest or unit case that needs no cluster; who can write the tenant ConfigMaps and pod annotations in a real install is the owner-observed half.

**Done when** each lead is either confirmed and fixed, refuted with the measurement recorded, or written into `05-security.md` as an accepted residual with its bound.
The plan doc gives each one a bounded local test and the fact an owner has to observe.
