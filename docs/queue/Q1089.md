# `TestHandleEviction_RunNeverConcludingIsSurfaced` measures the host

**Event:** `TestHandleEviction_RunNeverConcludingIsSurfaced` or `TestHandleEviction_UnreadableConclusionWithholdsThenSurfaces` fails on `main`: an attempt-count mismatch, or a hang where the loop's select finds no ready case. → top of Queue, escalated.

The test set `EvictionRerunWindow: 50ms` and `EvictionRerunRetryInterval: 5ms`, drove `handleEviction` against a real `httptest.Server` answering 403, and asserted `calls > 1` ("the window must span several refused attempts").
Nothing in that assertion was about the retry loop.
It was about whether two loopback HTTP round trips plus goroutine scheduling fit inside 50ms of wall clock, which is a property of the host.

**Observed 2026-09-09 (Q1078).** A `make check` failed it with `"1" is not greater than "1"` while the box was at load average 82.64 on 18 cores and the gate fan-out took 424s.
The same tree passed the same test twice afterwards, with no code changed between the three runs.
CI never saw it: `git log -S` on the `50 * time.Millisecond` literal returns only #1010, which introduced it (Q503/Q510), and #1515 (Q811), neither widening it for a flake.
CI's runners are 2-vCPU, so the margin there was not obviously better than a loaded dev Mac's.

**The fix.** Both timers the re-run loop selects on now come from nil-defaulted seams (`rerunWindowC`, `rerunRetryC`), and the test fills them: the handler closes the window on the attempt it wants to be the last, and every earlier wait fires immediately, so exactly one select case is ever ready at a pass and the assertion is an exact count the handler decided, which is the shape the neighbouring `TestHandleEviction_RetriesUntilTheRunConcludes` already had.
Production behaviour is unchanged; with both seams nil the loop is `time.NewTimer` plus `time.After` as before.
The second site carrying the identical 50ms window (the Q811 unreadable-conclusion test) is repaired the same way, and its `gets > 1` is now an exact count too.
Measured 2026-09-16: 200 consecutive `-race` runs green at load average 82.21, the load the original failure was taken at, and each test now takes ~0.01s instead of racing 50ms of wall clock.

**Seaming the window bypasses the production timer, so it needs its own cover.** Once both tests fill the seams, nothing exercises `startRerunWindow`'s real branch: replacing it with a channel that never fires leaves the whole provisioner package green.
`TestHandleEviction_TheUnseamedWindowCloses` closes that, with the seams nil and a real 50ms window, asserting the `EvictionRerunFailures` counter alone and never an attempt count.
That is not this row's defect reintroduced: it needs the window to close eventually, which 50ms of wall clock always delivers, rather than N round trips to fit inside it.
Measured both ways: the test itself runs in 0.05-0.07s intact, and goes red at 60.05s against the broken branch, where it falls through to the detached context's API budget instead.

**Sweep.** The idiom is an assertion that a counter exceeded a number inside a real deadline the test set.
The repo's Go tests hold 43 `Greater`/`GreaterOrEqual` assertions, of which roughly 14 to 21 take a counter as their subject depending on how the subject is matched.
This is not a census: every one read is sound, but not all 43 were classified, and the first pass reported seven from a regex narrow enough to miss the one in the file this row edits.
The sound ones fall into two shapes, a signal-decided count behind an `assert.Eventually` or a fake clock's `Advance` (the `cmd/agc/internal/listener` cases, [`ipranges_test.go`](../../cmd/gmc/internal/controller/ipranges_test.go)), and a stub-decided one where the handler chooses when to stop refusing ([`eviction_scaleset_internal_test.go`](../../cmd/agc/internal/provisioner/eviction_scaleset_internal_test.go), and `TestHandleEviction_DrainedRunStillReRuns` in this row's own file).
One genuine instance turned up, in another module, and is filed as Q1111.
