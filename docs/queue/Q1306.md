# Tie the Helm version to the Kubernetes floor

`helm template` checks `kubeVersion` against the version Helm was built for, so each floor raise also raises the Helm that can render the charts, and nothing here connects the two.
Q1284 met this when the e2e runner image's Helm v3.16.3 refused the 1.35 floor.
`validate-cluster-test.sh` holds the charts and the node image to the floor, but neither `HELM_VERSION` in `scripts/dogfood/e2e-runner/Dockerfile` nor the `3.20` in `scripts/ci/check-tools.sh` is asserted.

The hosted lanes have the same gap by another route: `azure/setup-helm` runs with no `version:`, so it floats to `latest`.
On a failed lookup it falls back to v3.18.4 (read from the action's source at the pinned SHA, not triggered), whose client-go is 0.33, so `manifest-validate`, `publish` and the e2e suite would fail with `chart requires kubeVersion`, which reads as a chart bug.

A Helm pin in `scripts/ci/pins.env` could serve both, and the choice is open.
Done when raising the floor past what the pinned or baked Helm renders goes red before a release candidate finds it.
