# `MaxWorkersCeiling` breached its 20s wait on a spent broker session

**Event:** `TestAGC_PodProvisioning_MaxWorkersCeiling` breaches its 20 s wait again on `main`, or any test in the `cmd/agc` integration suite breaches a wait with no matching `AcquireJob` in the log.

`TestAGC_PodProvisioning_MaxWorkersCeiling` failed on `main` in [integration-test run 32934660757](https://github.com/actions-gateway/github-actions-gateway/actions/runs/32934660757), 2026-08-26 05:39 UTC on `ubuntu-latest`: `Condition never satisfied` after 20.38 s at [pod_provisioning_test.go](../../cmd/agc/internal/controller/integration/pod_provisioning_test.go), on "a runner pod should be created once the maxWorkers ceiling is lifted".

**The cause, measured 2026-09-03 and fixed the same day.** The test enqueued its second job onto the session that had acquired the first one.
`AcquireJob` spends that session's single-use JIT agent whether or not the provisioning after it succeeds, so the listener DELETEs it and opens a fresh one (Q114) the moment the ceiling drop returns; `brokertest.Server` queues jobs per session ID and re-offers nothing, so the job waited in a queue no listener polls again.
`enqueueJobOnOwnerSession(…, nil, …)` picks any session active at that instant, which is a narrower fact than *will still be polled*.

Two direct measurements settle it.
Forcing the second job onto the acquiring session reproduces the CI failure exactly: same assertion, 20.52 s against CI's 20.38 s, and no second `AcquireJob` at all (`acqDelta=0`) — which is what the CI log shows too, since the `Q247` WARN that accompanies every acquire never reappears in the 20 s window.
And the gate meant to pace the test against the ceiling cycle was vacuous: it waited on "no `job-*` Secret exists", which is equally true before the provisioner stages one, and it returned in 4.8 ms and 55.7 ms over two runs having never observed a Secret.
That is what left everything downstream racing a job still being provisioned.

Neither candidate the original row offered was the cause.
The wait is not tight: the test completes in 0.47-0.63 s against its 20 s budget, so raising it would have moved the threshold and left this intact.

**What shipped.** The vacuous gate is now `WaitForSessionDelete` on the acquiring session, a listener-produced event that can only follow provisioning, with the Secret assertion after it as a point-in-time check.
The second enqueue excludes that session.
The same idiom is swept: the Q260 late-redelivery test carried it unreported and is fixed here too; `q422_quota_admission_test.go` enqueues repeatedly on one session and is safe, because its deliveries are rejected before `AcquireJob` and so spend no agent.
The rule is in [testing.md § Avoiding shared-stub flakes in the AGC suite](../development/testing.md#avoiding-shared-stub-flakes-in-the-agc-suite), and the general form of the vacuous wait in [§ A negative assertion must be able to fail for only one reason](../development/testing.md#a-negative-assertion-must-be-able-to-fail-for-only-one-reason).

**What this does not cover.** The stub's per-session queue is the fidelity gap underneath: a real broker re-offers an undelivered message when its session dies, and `brokertest` strands it.
Any future test can walk into the same trap.
[Q1049](Q1049.md) owns that.
