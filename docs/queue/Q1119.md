# E2E_V2_ProxyConnectWorks 502s the CONNECT tunnel, evicting a queued PR

`E2E_V2_MultiGateway [It] E2E_V2_ProxyConnectWorks: a workload pod reaches GitHub through the v2 EgressProxy` (`[real-github-egress]`) failed in the merge group and the queue evicted the PR.
It is the e2e lane's only failure: `70 Passed | 1 Failed | 0 Pending | 7 Skipped`.

## Measured 2026-09-16

[#1877](https://github.com/actions-gateway/github-actions-gateway/pull/1877) was enqueued at 16:56:07Z, its `e2e (calico)` merge-group run failed at 17:07, and `github-merge-queue[bot]` removed it at 17:13:38Z.
`cmd/gmc/test/e2e/v2_multigateway_test.go:212` asserted `Succeeded` and got `Failed`, after eight identical attempts:

```
curl: (56) CONNECT tunnel failed, response 502
HTTP_CODE=000
```

The base is not broken: the other six `e2e (calico)` merge-group runs in the window all succeeded, [#1943](https://github.com/actions-gateway/github-actions-gateway/pull/1943) among them, nine minutes earlier on the commit #1877 was queued on top of.

The PR's own diff cannot plausibly reach this assertion: it bumps `github.com/prometheus/client_model` 0.6.2 to 0.6.3 and the `google.golang.org/protobuf` vendor files under it.
That is a generated metric-type schema, and the failing path is an HTTP CONNECT tunnel to GitHub.
**Not yet settled by measurement** — no rerun has been taken, so "unrelated" remains a reading of the diff rather than a demonstration.

## Why it is worth a row rather than a rerun

A merge-group-only test that fails on external network reachability spends a full queue cycle per occurrence and evicts a PR whose own gates were all green, and `[real-github-egress]` says the dependency is real GitHub rather than the fake.
Settle the cause first (rerun the lane on the same head; if it passes, the 502 is environmental), then decide whether the assertion needs a retry budget, a clearer failure that distinguishes proxy-side from upstream-side 502, or demotion out of the merge-group gate.

## Notes

Eight attempts already happen inside the test, so a naive retry loop is not the fix; the attempts all failed the same way within the window.
Capture the EgressProxy's own logs in the failure output, so a future occurrence says whether the proxy refused the tunnel or the upstream did.
