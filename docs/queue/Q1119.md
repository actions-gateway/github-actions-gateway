# Both ProxyConnectWorks specs 502 the CONNECT tunnel, in both CNI lanes

`E2E_V2_MultiGateway [It] E2E_V2_ProxyConnectWorks: a workload pod reaches GitHub through the v2 EgressProxy` (`[real-github-egress]`) failed in the merge group and the queue evicted the PR.
It is the e2e lane's only failure: `70 Passed | 1 Failed | 0 Pending | 7 Skipped`.

## Measured 2026-09-16

[#1877](https://github.com/actions-gateway/github-actions-gateway/pull/1877) was enqueued at 16:56:07Z, its `e2e (calico)` merge-group run failed at 17:07, and `github-merge-queue[bot]` removed it at 17:13:38Z.
`cmd/gmc/test/e2e/v2_multigateway_test.go:212` asserted `Succeeded` and got `Failed`, after eight identical attempts:

```
curl: (56) CONNECT tunnel failed, response 502
HTTP_CODE=000
```

The base is not broken: the other six `e2e (calico)` merge-group runs in the window all succeeded, [#1943](https://github.com/actions-gateway/github-actions-gateway/pull/1943) among them, nine minutes earlier on the commit #1877 was queued on top of.

The PR's own diff cannot plausibly reach this assertion: it bumps `github.com/prometheus/client_model` 0.6.2 to 0.6.3 and the `google.golang.org/protobuf` vendor files under it.
That is a generated metric-type schema, and the failing path is an HTTP CONNECT tunnel to GitHub.
**Settled by rerun 2026-09-16 23:03Z.** The same test on the same PR passed in the merge group after the branch was replayed onto current `main`, with no change to the assertion or to the code under it, and #1877 merged.
A test that passes on rerun with no code change is a flake by the repo's own definition, so the 502 was environmental and the bump was never implicated.

## It recurred the same day, on main, in the other CNI lane

**Measured 2026-09-17 by sweeping both lanes rather than one.** The reading above is scoped to `e2e (calico)` merge-group runs, which structurally cannot see a kindnet lane or a push to `main`, and both happened five hours later.
Run [35156765438](https://github.com/actions-gateway/github-actions-gateway/actions/runs/35156765438), the `e2e / e2e` kindnet lane on `push main` at 2026-09-16 22:24Z, failed *two* `[real-github-egress]` specs at once on the same signature, over 27 attempts of `CONNECT tunnel failed, response 502` reporting `HTTP_CODE=000`:

- `E2E_GMC_TenantProvisioning_ProxyConnectWorks` (`cmd/gmc/test/e2e/provisioning_test.go:350`), the v1 proxy path
- `E2E_V2_ProxyConnectWorks` (`cmd/gmc/test/e2e/v2_multigateway_test.go:212`), this row's own spec

That is 38 minutes before the 23:03Z rerun the section above reads as a settle, so the rerun establishes that the branch is clean and establishes nothing about the rate.

**It is not the first pair either.** [q300-gmc-kindnet-e2e-flake.md](../plan/q300-gmc-kindnet-e2e-flake.md) triaged the identical two-spec 502 on 2026-07-14 and assigned it a class at `docs/plan/q300-gmc-kindnet-e2e-flake.md:256:502s to real GitHub are the external-egress class, not the dataplane class` on that page.
Its triage row closes `docs/plan/q300-gmc-kindnet-e2e-flake.md:21:watch for recurrence before filing separately` there, so this row is that separate filing and the recurrence it waited for, rather than a first sighting.

## Why it is worth a row rather than a rerun

A merge-group-only test that fails on external network reachability spends a full queue cycle per occurrence and evicts a PR whose own gates were all green, and `[real-github-egress]` says the dependency is real GitHub rather than the fake.
The class is settled; what is left is the cost and the refusing hop.
Three occurrences have now spent a queue cycle, a `main` build and a second `main` spec between them.

**Settled 2026-09-17: the diagnostic first, and nothing else yet.** Three answers were on the table and the row already rules one out itself: eight attempts happen inside the test and all eight failed the same way inside the window, so a retry budget is a wider race rather than a fix.
Demotion out of the merge-group gate is the expensive answer: `[real-github-egress]` says the dependency is real GitHub, which is exactly the coverage a merge-group gate is there to hold.
That leaves the third, and the recurrences make it urgent rather than making demotion decidable: three occurrences still cannot say whether the proxy refused the tunnel or the upstream did, which is the fact either other answer needs.

**Corrected 2026-09-17.** This paragraph first argued demotion down on the ground that one eviction does not buy it, which read the occurrence as isolated.
The count is three across both CNI lanes and both trigger events, and the July pair was already triaged in the tree.
The answer is unchanged; the reason given for it was wrong.
