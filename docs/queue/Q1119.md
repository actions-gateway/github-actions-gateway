# Both ProxyConnectWorks specs 502 the CONNECT tunnel, in both CNI lanes

**Event:** either proxy-CONNECT spec fails again on `curl: (56) CONNECT tunnel failed, response 502`, in either CNI lane, on a PR, a merge-group entry or a push to `main`.
Read the `EGRESSPROXY CONNECT ATTRIBUTION` banner in that run's failure output first: it names the refusing hop, which is the fact the three occurrences below could not supply and which both remaining answers need.

`E2E_V2_ProxyConnectWorks: a workload pod reaches GitHub through the v2 EgressProxy` (`[real-github-egress]`) failed in the merge group and the queue evicted the PR.
It is the e2e lane's only failure: `70 Passed | 1 Failed | 0 Pending | 7 Skipped`.

## Measured 2026-09-16

[#1877](https://github.com/actions-gateway/github-actions-gateway/pull/1877) was enqueued at 16:56:07Z, its `e2e (calico)` merge-group run failed at 17:07, and `github-merge-queue[bot]` removed it at 17:13:38Z.
`cmd/gmc/test/e2e/v2_multigateway_test.go` asserted `Succeeded` and got `Failed`, after eight identical attempts:

```
curl: (56) CONNECT tunnel failed, response 502
HTTP_CODE=000
```

The base is not broken: the other six `e2e (calico)` merge-group runs in the window all succeeded, [#1943](https://github.com/actions-gateway/github-actions-gateway/pull/1943) among them, nine minutes earlier on the commit #1877 was queued on top of.

The PR's own diff cannot plausibly reach this assertion: it bumps `github.com/prometheus/client_model` 0.6.2 to 0.6.3 and the `google.golang.org/protobuf` vendor files under it.
That is a generated metric-type schema, and the failing path is an HTTP CONNECT tunnel to GitHub.
**Settled by rerun 2026-09-16 23:03Z.** The same test on the same PR passed in the merge group after the branch was replayed onto current `main`, with no change to the assertion or to the code under it, and #1877 merged.
A test that passes on rerun with no code change is a flake by the repo's own definition, so the 502 was environmental and the bump was never implicated.

## The diagnostic, measured and shipped

**The row's asserted gap was half real.** It reads as though neither spec captured anything proxy-side.
Reading the 2026-09-16 job log directly (`gh run view --job 104998010114 --log`) says otherwise: the v1 spec's `DumpProvisioningDiagnostics` dumps every pod in the namespace, so it caught **nine** `upstream dial failed` lines across both proxy replicas, every one reading `dial tcp 172.182.252.137:443: i/o timeout`.
The v2 spec caught none, since it dumps its AGC Deployments alone.
So the capture was missing for v2 and already present for v1, and the v1 evidence answers the row's own question outright: the proxy accepted the destination and its TCP dial did not complete, which is not a refusal by the proxy.

**What kept it from being read that way is a second mechanism giving the wrong answer confidently.** The runner-host GitHub preflight (Q352) scored the two identical failures in that one run in opposite directions: `BLOCKED (HTTP 403; x-ratelimit-remaining=0)` on the v1 failure and `REACHABLE (HTTP 200 in 164ms)` on the v2 failure minutes later.
`BLOCKED` prints *infrastructure, not a product regression.
Re-run the job.*, which is what made this look settled.
Neither verdict is wrong about the question that probe asks; neither can answer this one, because a 403 arrives through a completed TCP connection and the failure is a dial that never completed.
[Q1126](Q1126.md) owns that defect: it is a different mechanism in a different file, and no one fix closes both.

**What shipped.** `DumpEgressProxyDiagnostics` runs from both specs' `AfterEach`, gated on a failure and the `real-github-egress` label, reads each proxy replica's log individually, and stamps an `EGRESSPROXY CONNECT ATTRIBUTION` banner with one of four verdicts: `NO-EVIDENCE`, `PROXY-NOT-REACHED`, `PROXY-REFUSED`, `UPSTREAM-DIAL-FAILED`.
Its pod selector is read off the Deployment's own `.spec.selector.matchLabels` rather than assumed: v1 selects `app: actions-gateway-proxy` and a v2 `EgressProxy` selects `actions-gateway.com/egress-proxy: <name>` with no bare `app` key at all (Q582), so a hardcoded label finds nothing on the other version and scores `NO-EVIDENCE`.
Scoring is a pure function over log text, so every verdict is driven by a unit test, including the two that say the banner attributes nothing.
A classifier returning one verdict always reddens four of the seven arms.
The rule is in [testing.md § EgressProxy CONNECT attribution](../development/testing.md#egressproxy-connect-attribution-q1119).

## Why it is parked rather than closed

A merge-group-only test that fails on external network reachability spends a full queue cycle per occurrence and evicts a PR whose own gates were all green, and `[real-github-egress]` says the dependency is real GitHub rather than the fake.
Three occurrences have now spent a queue cycle, a `main` build and a second `main` spec between them.

The two answers left both need the same fact, and the diagnostic is what produces it rather than what settles it.
Eight attempts already happen inside the test and all eight failed the same way inside the window, so a retry budget is a wider race rather than a fix.
The row ruled that out and it stays ruled out.
Demotion out of the merge-group gate is the expensive answer: `[real-github-egress]` says the dependency is real GitHub, which is exactly the coverage a merge-group gate is there to hold, so it is worth paying only against evidence that the refusing hop is one this repo does not own.
The next occurrence carries that evidence in its banner.

**Corrected 2026-09-17.** An earlier revision argued demotion down on the ground that one eviction does not buy it, which read the occurrence as isolated.
The count is three across both CNI lanes and both trigger events, and the July pair was already triaged in the tree.

## Notes

`i/o timeout` on a dial to a GitHub address is where the existing evidence stops, and it is consistent with the SYN being dropped before it left the node and with it being lost past the node.
`UPSTREAM-DIAL-FAILED` names that as the open question rather than answering it; separating the two needs something outside the proxy's egress NetworkPolicy reaching the same address in the same window, which nothing captures today.
