# Reaped Pending worker force-cancels a run with a job still running

A scale-set worker reaped at `pendingPodDeadline` has its own run force-cancelled even where another job of that run is running on a live worker of the set.
The stranded-job branch of the same handling declines in that case, because the cancel would end the running job (Q1235, `cmd/agc/internal/provisioner/abandoned_scaleset.go:227:if ok && workers.runStarted(job.RunID, inFlight) {`).
The direct branch, where the reaped pod's own run is the one cancelled, has no such check.

Measured 2026-11-27 on the unit-test fake of GitHub, with a throwaway test on `newAbandonedScaleSetFixture`: `job-a` and `job-b` are in flight for run 111, `job-b`'s worker has started `job-b`, and `job-a`'s worker is reaped while `Pending`.
`RecoverAbandonedScaleSetWorker` posts `/repos/myorg/repo-a/actions/runs/111/force-cancel`.
The existing `TestStrandedJob_Q1235_SparesARunWithAJobRunning` covers only the shape where another worker's runner took the reaped pod's job.

Not measured: what the force-cancel does to the running job at GitHub.
That it ends every job of the run is the claim Q1235 acted on, and [Q1246](Q1246.md) owns its measurement on a live multi-job run.
This row is separate from Q1246: it is the code path that already takes the cautious answer on one branch and not the other.
It is also separate from Q1398, which is about which run a disruption before the start names.

The check can see only jobs on this set's workers.
A job of the run on another `RunnerSet`, or on a GitHub-hosted runner, is invisible to `runStarted` on both branches, and reading the run's jobs from GitHub before cancelling is what would cover it.

**A fix:** apply the `runStarted` check to the pod's own run before `forceCancelInBackground`, on the reaper seam and the scan seam, and leave the job to GitHub's unstarted-job timeout as the stranded branch does.
Hold it until Q1246 says whether the timeout spares the running jobs, since [Q1248](Q1248.md) records that as unmeasured too.
