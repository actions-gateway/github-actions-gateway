# Nothing fails a job that reads a pins.env key in run: without loading it

CI jobs read their tool pins from `scripts/ci/pins.env` through a `pins` step running `scripts/ci/load-pins.sh` (Q1166).
An expression reads a pin as `steps.pins.outputs.<KEY>`, and actionlint rejects that reference in a job with no `pins` step, so the expression half is gated.
A `run:` step reads `$KIND_VERSION` straight from the environment, and nothing checks that the job loaded it: a job that gains a pin read and forgets the `pins` step expands it to empty.

What empty does depends on the consumer (measured 2026-10-24):

- **A `*_SHA256` fails closed.** `scripts/fetch/download-verified.sh` exits 2 with a usage line on an empty digest.
- **`CALICO_VERSION` does not.** `scripts/e2e/kind-with-registry.sh:38:CALICO_VERSION=${CALICO_VERSION:-v3.31.5}` falls back on empty as well as unset, so an unloaded pin silently runs that hardcoded default, which nothing bumps.

Today there are no instances: the review of PR #2113 scanned every job at `a048b02` and found no `run:` read of a `pins.env` key without a `pins` step, where the same scanner flagged 54 reads on `main` before the move.
The gap is the next edit that adds one.

A gate would list the keys in `pins.env`, find each workflow job whose `run:` bodies reference one, and require a step with `id: pins` before the first such step.
`scripts/ci/workflow-step-body.sh` already extracts a step's `run:` body.
The `kind-with-registry.sh` fallback is a second, independent fix: reading `pins.env` there, or failing on an empty `CALICO_VERSION`, would remove the stale default whatever the gate does.
