# No gate requires a row deletion to ride its own docs(queue): commit

`queue.py metrics` attributes a removal per row, reading the closure verb off the `docs(queue):`/`docs(status):` line that names it.
A `git rm` committed inline with the work carries no such line, so the row falls to the residual however clearly the PR describes it.

**Measured 2026-09-12** at `32312254e`, after the Q959 re-vendor: 28 of 214 removals classify as `removed`.
Twenty of those have a deletion commit with no `docs(queue):`/`docs(status):` line at all.
`fix(coverage): force a fresh pass over the uncacheable package (Q992) (#1844)` is the shape, and Q1003, Q1040 and Q1042 closed the same way.
The other eight do carry a row line, but one naming other rows, which the walk declines rather than spending on whichever rows the diff holds.

The isolated row commit is already what [`session-backlog`](../development/skills.md#session-backlog) asks for and what `CLAUDE.md` states, and nothing checks it: `check-queue-rules.py` scores the store's tree at base against head, so commit shape is outside every rule it has, and the repo has no commit-message gate of any kind.

The rung is the question, not the rule.
A `--staged` check cannot see it, because staging is one tree and the defect is which commit the deletion lands in.
So this is a pre-push or CI walk over the branch's own commits, which is a rung this repo has never used for anything.
Weigh that against leaving the residual: 28 of 214 is a 13% unread rate on a metric nobody gates on, and the verb is advisory.
