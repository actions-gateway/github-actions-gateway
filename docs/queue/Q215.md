# Ship the in-cluster worker cache as a reference architecture

A tenant asked for an in-cluster cache on 2026-10-27, which fired this row's trigger, and the design is settled and spiked in [q215-worker-cache.md](../plan/q215-worker-cache.md).
The untrusted-PR tenant is the case it exists for: under the tight egress posture `actions/cache` has no store to reach, and a cache shared across jobs is a poisoning vector unless the server enforces GitHub's ref scope.

What is built: the opt-in `cache-runner` target in the root `Dockerfile`, which patches `Runner.Worker.dll` so actions take `ACTIONS_RESULTS_URL` from the pod, with a build check that fails when a runner bump moves the literal, published, signed and scanned on each release as the seventh first-party image.
The spike ran it on kind against real GitHub with falcondev-oss's cache server: save, restore and artifacts all worked through the in-cluster server, GitHub's cache held nothing, and a sibling branch could not restore the entry.

What is left, in order:

1. **Close the tokenless blob transport.** falcondev v9.8.0 authenticates its three `CacheService` calls by the job's token, but the upload URLs they hand out carry no secret beyond a 10-digit ID, and a `PUT` with no credential writes the entry (measured 2026-10-27, [the residuals](../plan/q215-worker-cache.md#the-write-path-is-a-contract)).
   Upstream #299 tracks the maintainer's fix, a per-upload token in the URL, and phase 1 waits for a release carrying it while steps 2 to 6 are built.
   A GAG-owned signing proxy in front of the server would ship sooner, and is declined: it is a security component to own and then retire once #299 ships.
   Bump the pin from 9.8.0 in the same step, and re-read the residuals if that release is the Rust rewrite.
   [Our comment on #299](https://github.com/falcondev-oss/github-actions-cache-server/issues/299#issuecomment-6458898702) promises to re-run the save and restore checks on that release and report back there if anything breaks.
2. **A `deploy/gha-cache/` base** shaped like `deploy/registry-mirror/`: the server pinned by digest, its Service, the two NetworkPolicies from the spike, an `emptyDir` default and a persistent overlay.
3. **An operator page** under `docs/operations/` and a runner template library entry, saying that the image is opt-in and that a pod running it without `ACTIONS_RESULTS_URL` loses cache and artifacts.
4. **Validate on the untrusted pull requests profile** (Kata, tight egress): the server answers from a worker, `*.blob.core.windows.net` does not.
5. **Measure a fork pull request's scope**, which the spike could not: its saves must land in `refs/pull/<n>/merge` and a push to the base branch must not restore them.
6. **Eviction**: set `CACHE_CLEANUP_OLDER_THAN_DAYS` to GitHub's 7 days, and pick a default for `CACHE_MAX_SIZE_BYTES`, which caps the whole server rather than GitHub's 10 GB per repository.

The server goes in the tenant namespace, so the tenant's `ResourceQuota` pays for it; the shared and platform-operated modes in [tenancy modes](../plan/q215-worker-cache.md#tenancy-modes) are [Q1225](Q1225.md).
The patch itself is temporary; [Q1224](Q1224.md) retires it once upstream takes an override.
