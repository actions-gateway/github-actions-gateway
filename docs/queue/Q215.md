# Worker cache backend (actions/cache + Docker layer cache)

**Demand:** an in-cluster cache ask.
**Event:** a tenant loses its working `actions/cache`, which is the *tenant* path and not this repo's own CI.

The reading was ambiguous until 2026-08-26 and is now fixed, because an ambiguous trigger is a standing query nobody can re-run.
The trigger is about the capability GAG offers a tenant, and that capability works today: the tenant egress proxy's implicit GitHub allowlist carries `*.blob.core.windows.net`, the Azure-blob store the Actions cache runs on (`githubEgressFQDNs` in `cmd/gmc/internal/controller/egressproxy_fqdn.go`).
So `actions/cache` reaches its store on the proxy form, and the gap is local rather than absolute.

[Q408](Q408.md) Phase 1 did **not** fire this.
It gated every `actions/cache` step and `GHA_CACHE` to `runner.environment == 'github-hosted'` in this repo's own `e2e-reusable.yml`, which is GAG dogfooding the untrusted-PR posture on its self-hosted lane, not a tenant losing anything.
Settled in [release-1.7.md](../plan/release-1.7.md#q215s-trigger-has-not-fired-and-the-row-now-says-which-reading-it-takes).

One asymmetry to know before re-reading this: the direct-egress form admits GitHub CIDRs, and the Azure blob store is not among them, so a tenant on that form has no working `actions/cache` now and never did.
The trigger reads on the proxy form because that is where the capability exists to lose.

The design question the row exists for is unchanged: the read-only mirror role cannot hold a read-write cache.
