# Plan shared docs when one backlog row is split across parallel PRs

When one row is split into parallel streams, every stream edits the same append-only docs, so the PRs conflict pairwise from the start and must merge one at a time with a rebase between each.
[parallel-dispatch.md](../development/parallel-dispatch.md) covers spacing items that edit the same registry file, and that a stream is defined by its docs as well as its code, but says nothing about a single row split across streams, where the overlap is built in by the split itself.

**Measured on Q1322 (2026-11-10).** The row was split into four streams with one PR each (#2294, #2295, #2296, #2297).
Before the first merge, `merged-set-lint.py --pairs` found all six pairs conflicting, all in docs: `docs/operations/upgrade.md`, `docs/releases/v2.0.0.md`, `docs/queue/Q1322.md` (its "N of the eight remain" line), and for some pairs `docs/plan/security-audit-2026-11.md`.
The merges then cost 7 rebase cycles: 3 for #2294, 2 for #2295, 2 for #2297.
Each cycle was a draft, a rebase, `make check`, a force-push, a reviewer range-diff re-check and a fresh CI run of about 20 to 25 minutes.
One of those rebases also produced Go that git merged without a conflict and that did not compile (a duplicated import in `cmd/gmc/cmd/wiring_test.go`), which `make check` caught before the push.
The shared summary sentences had to be reserved for whichever PR merged last, which the dispatcher could not know in advance, so the closing edits went out in a separate brief after the third merge.

**Done when** the playbook says what a dispatcher does when it splits one row across streams, measured on the next split rather than asserted.
Two candidate remedies are unmeasured, and either could be wrong:

- **One row per stream.** Each PR deletes its own row file, which removes the shared counter line and the last-merger closing step.
- **Per-stream slots, or a final docs PR.** Each shared doc gets one slot per stream before workers start, or the upgrade and release-note entries all land in one docs PR after the code PRs merge.

The second trades the conflict for a docs PR that can only be written after every code PR has merged, which may cost more wall clock than the rebases did.
If neither beats accepting the serial merges, the outcome is a sentence in the playbook that states the cost up front, so the dispatcher can tell the maintainer before the batch starts.
