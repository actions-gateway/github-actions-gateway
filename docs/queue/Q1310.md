# deps-sync can leave go.sum untidy after go work sync moves an indirect

`make deps-sync` is the documented remedy for a dependency change, and once it left a tree that `make tidy-check` rejects.
Measured 2026-11-07 on the `golang.org/x/net` v0.60.0 → v0.62.0 bump that became #2273: `go get` in `api`, `cmd/agc`, `cmd/gmc` and `tools`, then `make deps-sync` (exit 0), then `make tidy-check` failed with one line of drift:

```
diff --git a/cmd/proxy/go.sum b/cmd/proxy/go.sum
+golang.org/x/sys v0.49.0/go.mod h1:hNLxWAXmnKAxqDtdwIYC4bM9oQPEecfsnNMuSxOs3og=
```

`cmd/proxy` was not one of the modules bumped by hand; its `x/sys` requirement moved because the bump raised it workspace-wide.
The tidy-check run wrote the missing line itself, and a re-run of `vendor-check`, `tidy-check` and `third-party-notices-check` passed with it committed.
The same flow passed `tidy-check` twice the same day on a k8s.io v0.37.2 bump that moved no indirect into an un-bumped module.

**The mechanism is unverified.** `scripts/go/vendor-sync.sh` runs `scripts/go/go-work-tidy.sh` and then `go work sync`, and the likely cause is that order: `go work sync` raises a module's requirement after that module was tidied, leaving its `go.sum` short of the new version's `go.mod` hash.
Reproduce it before fixing: on a branch, bump an indirect in one module so that `go work sync` carries it into a module not bumped by hand, run `make deps-sync`, and confirm `make tidy-check` goes red.
If that reproduces, the candidate fix is a second tidy pass after `go work sync` in `vendor-sync.sh`, proved by the same reproduction going green.

What it costs by hand: one extra gate run and an amend, because `tidy-check` catches it locally and in CI.
It costs more on the bot path: `.github/workflows/dependabot-go-sync.yml` runs `make deps-sync` and pushes whatever changed, with no `tidy-check` in between, so a Dependabot bump that hits this drift goes red on CI's `tidy-check` straight after the sync commit, and only a human can repair that branch.
