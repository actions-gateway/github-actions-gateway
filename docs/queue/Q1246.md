# Measure what a run force-cancel does to a multi-job run's healthy jobs

The never-started handling force-cancels the whole workflow run (`forceCancelAbandonedRun`, `POST …/actions/runs/{id}/force-cancel`), then a deferred `rerun-failed-jobs` re-runs it once capacity returns (Q691).
Nobody has measured what that does to a multi-job run, a matrix above all: the co-running jobs that were healthy, and which of them the deferred re-run then restarts.
Q1230 would route every never-started preemption and eviction victim through this path, and under `priorityTiers` oversubscription that is the common case rather than the stuck-Pending exception, so the blast radius decides whether Q1230's routing is safe.

1. Whole-run blast radius.
   Read from source and from the API being run-scoped; unmeasured for a multi-job run.
   The Q683 measurement (run 31022925992) was a single-job run, and no doc covers the multi-job case (searched `04-operational-flows.md`, the Q645 and Q766 plan docs and `troubleshooting.md` for "matrix", "other jobs" and "whole run").
2. Changing the routing inverts a merge-group-only e2e.
   `E2E_AGC_PreemptedWorkerIsRecovered` (`cmd/gmc/test/e2e/worker_preemption_test.go`) holds a classic worker Pending and asserts refused-then-accepted `rerun-failed-jobs` exactly once.
   The envtest `TestAGC_Preemption_ScaleSetWorker_IsRecovered` and about 20 unit fixtures with no container start record would change with it.
3. What the current routing costs, read from source and not measured: the classic re-run window (`defaultEvictionRerunWindow`, 15 minutes) starts at detection plus the retry delay.
   GitHub's told-nothing cancel landed at T0+15m14s from the acquire (Q676, run 30914399921).
   So today's re-run of a never-started victim usually lands about 15 minutes late rather than never.

Measure with a probe arm on a run of two or more jobs, one held never-started while the others run: force-cancel the run, record each job's conclusion, then call `rerun-failed-jobs` and record which jobs it re-queues.
