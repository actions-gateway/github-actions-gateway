# Abandoned arm withholds runs GitHub's unstarted-job timeout cancelled

Since Q1232, the scale-set abandoned arm reads the run before force-cancelling.
It withholds a run concluded `cancelled` on an attempt the failure ledger does not hold as GAG's, as `run_cancelled` with `cause="abandoned"` (`cmd/agc/internal/provisioner/abandoned.go:109:	if run.status == runStatusCompleted && run.conclusion == runConclusionCancelled &&`).
The conclusion does not say who cancelled, so the check also catches GitHub's own ~15-minute unstarted-job timeout.
That timeout lands before the `pending_deadline` reap whenever `pendingPodDeadline` is set past ~15 minutes, which the CRD godoc recommends for slow GPU pools.
Such a job is then left for a manual re-run instead of the capacity-gated automatic one.
The withhold is the safe direction (a user's cancel is never undone), and the case is documented as a known behaviour in the troubleshooting runbook and the metrics reference.
The fix is to tell a timeout cancel from a user's or a concurrency group's, and re-run only the former.
Unmeasured: what the run or job object carries that separates the two.
Candidates are the cancel time against the job's queue time, or a job-level field.
Whether the timeout concludes the whole *run* `cancelled`, rather than only the job, is also unmeasured; it rests on the runbook's own claim.
Measure on a live run first, against a `ScaleSet` set whose `pendingPodDeadline` is past 15 minutes.
Do not build on a timing heuristic before that.
Whether `main` before Q1232 re-ran such a run is unmeasured too: it registered the re-run only on a 2xx force-cancel, and what GitHub answers a force-cancel of a concluded run has not been probed.
Filed from the independent review of #2196.
