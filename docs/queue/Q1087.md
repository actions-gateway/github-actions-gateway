# Bind a gate-labelled row to its release plan in both directions

Nothing checks that a row claiming to block a release is known to that release's plan, or that a blocker the plan names carries the label.
Measured 2026-09-08 across 205 rows: three carry a gate label, and two rows that are a release's actual content, [Q273](Q273.md) and [Q264](Q264.md), the `v1alpha1` and classic removals named in [v2-ga.md](../plan/v2-ga.md#phase-3--the-storage-advance-and-the-coupled-removals) Phase 3 — carried none, so a query for what blocks `v2.0.0` returned one row of the four.
A third gap in the same audit was a row whose body said one release owed part of it while its label named another, with the owing release's plan naming it nowhere.

`check-release-ladder.sh` is the neighbour and does not cover this: its three assertions bind the ladder's *punted* table to `status:`, never a gate label to a plan.
`roadmap-check` rule 7 is the only existing linkage and fires only for a row also carrying `feature` or `security`, which is deliberate ([why](../development/maintaining-backlog.md#a-gate-label-and-its-roadmap-bullet-are-two-commits-and-the-first-one-is-red)) and leaves every `debt`, `ci`, `tests` and `milestone` blocker unbound.

Two assertions, each the other's direction:

1. A row labelled `X.Y-gate` is named by release `X.Y`'s plan.
2. A row a release plan names as gating is labelled `X.Y-gate`.

**The hard part is the mapping from a label to a plan doc, and it is where this can go wrong quietly.** `1.8-gate` reaches `release-1.8.md` by construction, but the ladder's `2.0` rung is `v2-ga.md` and its `1.9` rung is `release-1.9.md`, so the rule cannot be a filename template.
Read the mapping off the ladder table, which already states it, rather than deriving it: a template silently passes every release whose plan is named the way it guesses.

Direction 2 needs a definition of *names as gating* that a plan can express, since a plan doc mentions many rows.
The existing vocabulary is the gating-versus-rides split in [release-1.8.md](../plan/release-1.8.md), which is prose and a table column rather than a marker.
Settle that before building: the cheap form may be a `<!-- gates -->` marker like the roadmap's `<!-- q: -->`, and that is a change to how plans are written, not only a checker.

**Lands in the same script as [Q965](Q965.md), and is not that row.** Q965 is a defect in the existing punted-table parsing: `back_word` matches a literal plural, so a revived count of one reads ungrammatically.
This row adds an assertion that does not exist yet, over a different part of the page: the rung table rather than the punted table.
They are worth doing together because both touch `check-release-ladder.sh` and the second would otherwise re-read the same page a third way, but neither blocks the other and Q965 is `S` against this `M`.

The inversion the gate needs: a fixture row labelled `2.0-gate` that no plan names must go red, and a fixture plan naming a gating row that carries no label must go red.
An empty-result grep cannot be either, since it passes equally when the rule works and when the query matches nothing.
