# A patch line's e2e leg dispatches from main, not the candidate

`dispatch_e2e_run` defaults `E2E_DISPATCH_REF` to `main` (scripts/dogfood/validate-release.sh:510), so the e2e matrix leg runs `main`'s copy of `e2e-test.yml` and its test code against the candidate's GAG runners.
For a minor cut from `main`'s head those are near enough the same tree.
For a patch cut off an older tag they are not, and Q879 made validating a patch line compulsory, so the case now happens by design rather than never.

Decide what a patch line should dispatch, and whether the default should be the candidate's ref rather than `main`.

**The row's own counter-argument does not survive reading its citation, groomed 2026-09-17.** It said the tension is "already documented" at release.md's *A release line carries its own validation harness*, so pinning the dispatch to the candidate is not obviously right either.
That paragraph argues the opposite way: `docs/operations/release.md:1288:the gate runs *the scripts in your checkout* against *the artifacts of the tag*`, and the line under it says a `release-X.Y` branch "inherits whatever harness that commit had".
Checkout-wins is therefore the documented posture, and `E2E_DISPATCH_REF` defaulting to `main` is the one leg that breaks it rather than the one leg that follows it.

**What is genuinely open** is whether that posture reaches a *dispatched workflow ref* at all, which release.md never says: `validate-release.sh` and the dogfood scripts under it are local files a checkout supplies, and `e2e-test.yml` plus its test code are fetched by ref at dispatch time, so nothing in the runbook has ruled on the third case.
Whoever settles it starts from the full paragraph rather than the row's summary of it.

Unmeasured: nobody has run the gate on a patch line.
The mechanism above is read off the source, not observed, and no patch release has ever been cut here (all seven stable tags are `.0`).
Surfaced by the review of #1788.

**Ask:** whether the *checkout-wins* posture release.md states for `validate-release.sh` is meant to reach a dispatched workflow ref as well.
No measurement can answer it, since no patch release has ever been cut here, and the runbook has never ruled on the third case.
Both readings ship a working gate; they differ in what a patch line's e2e leg is evidence *about*.
