# `status.withheldCapacity` freezes on an idle set until the 10h resync

Found by the `v1.7.0-rc.1` capacity leg, which failed on it 2026-08-29 ([release-1.7.md](../plan/release-1.7.md#candidate-validation)).

The listener records an advertisement on **every poll** (`scaleSetCapacityFunc` calls `rec.record(adv)` and `ScaleSetMetrics.SetCapacityWithheld`), but status is written only by the reconcile goroutine, which reads `rec.last()` in `applyAdvertisedCapacity`.
The two are decoupled on purpose: a poll that wrote status directly would race every other status write.

Nothing requeues on an advertisement changing.
`RequeueAfter` is assembled from `reapAfter` (0 with no worker pods), `capacityRequeue` (`applyWorkerCapacityConditions` returns 0 with nothing pending or starting), a baseline recheck that applies only while `mux.ActiveCount() < spec.maxListeners`, and a proxy-share recheck that applies only to a projected share.
An idle set satisfies none, so `RequeueAfter` is 0 and the only fallback is controller-runtime's default `SyncPeriod`, which this project does not configure: **10 hours**.

So once a set goes idle, `status.withheldCapacity` and `status.advertisedCapacity` hold whatever the last reconcile wrote, for up to 10 hours, while Prometheus carries the live value.

**Measured.** After the release gate restored the e2e tenant's `ResourceQuota` to 6 pods with 1 in use, `withheldCapacity[quota]` still read 2 and `advertisedCapacity` 0 more than 30 minutes later, on an AGC that had been Running 60m with 0 restarts.

This inverts what the field is for.
Q721 added it so a tenant can read why intake is throttled **without** Prometheus; a reader who cannot see the metric is exactly the reader who gets the stale answer, and the answer says intake is throttled when it is open.

Fix candidates, unmeasured: requeue when `rec.record` observes a changed advertisement, or fold a bounded re-check into `RequeueAfter` whenever withholding is non-zero.
The second is cheaper and self-limiting, since a set withholding nothing needs no poll.

**A second, separable defect is in the gate.** [`validate-release.sh`](../../scripts/dogfood/validate-release.sh)'s `capacity_leg` waits 300s for the rung to release by polling that status field, and supplies no demand that would trigger a reconcile.
On a drained post-suite cluster there is none to be had, so the leg can only pass if some unrelated event fires a reconcile inside the window.
Fixing the controller closes both; fixing only the gate (assert on the metric, or drive a reconcile) leaves the operator-facing defect live.
