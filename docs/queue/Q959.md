# Queue metrics report zero completions because removals name no verb

`queue.py metrics` splits throughput from garbage collection by matching `complete|prune|merge|defer` in the subject of the commit that deletes an item, and falls back to `removed` when none is present.
Measured 2026-08-23 over the store's whole history: of 86 removals, 81 classify as `removed` and 5 as `merge`, so the summary reads `completed 0` and `pruned 5` for a repo that has shipped 239 filed items.
Zero throughput is not an imprecise reading, it is an inverted one, and the prune ratio derived from it is meaningless.

Two candidate fixes, and the choice is the work.
Either the convention gets enforced, which needs a gate on the deleting commit's subject rather than on the tree, and the gate has to accept `retire` as well, since [the flake lifecycle](../development/maintaining-backlog.md#retiring-a-flake-watch-row) sends rows to the ledger under that word and `maintaining-backlog.md` never told anyone to write a verb at all.
Or the verb is abandoned as the signal and closure is derived instead, which is available here: a flake row that lands in `flake-watch-retired.md` retired, an item whose ID appears in a merged PR's body shipped.

Note that `queue.py` is [vendored byte-identical from the skill](../development/maintaining-backlog.md) and never edited here, so a fix to the matcher belongs upstream and only the convention half is this repo's to change.
