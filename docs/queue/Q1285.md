# Check other tightened CEL rules for the 1.31/1.32 status-write refusal

Whether any other CEL or schema rule tightened this cycle has this exposure is unchecked.
Karl gated the check on `v2.0.0` on 2026-11-04 ("Karl gates the check"), because a hit freezes a stored gateway's status on versions the charts still allow, and the same fix is cheap while the release is open.

The measurement that makes it worth checking is the `spec.tracing.endpoint` rule, before it gained an `oldSelf` clause.
With a bad value already stored, the apiserver refused a status write on envtest 1.31.0 and 1.32.0 and accepted it on 1.33.0, 1.34.1 and 1.35.0, because ratcheting misses the status subresource on the older two.
With a real reconcile on 1.32.0, the reviewer's fresh gateway got its Deployment, 0 conditions and 31 reconcile errors in 25 seconds, while a control got 11 conditions.

Edits to the spec and metadata passed on every version, so a test of those cannot find this, and `ENVTEST_K8S_VERSION` and the e2e node image are both 1.35, so no gate here can see it.
A rule is exposed only if an object stored before the rule can fail it and a controller writes that object's status.

To reproduce, store a failing value with the rule removed from the CRD, restore the rule, and write status under `make -C cmd/gmc test-integration ENVTEST_K8S_VERSION=1.32.x`.
`TestV2_Tracing_StoredBadEndpointKeepsWorking` is the worked example.

Done when every rule tightened since the last release is listed with its result, and an exposed rule has the `optionalOldSelf` clause or a stated reason to go without.
Raising the floor past 1.32 ([Q1284](Q1284.md)) would also retire this, and that row is not a reason to skip the list.
