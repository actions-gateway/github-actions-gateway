# `head_snapshot` crashes on any unstaged deletion of a tracked file

`head_snapshot()` documents itself as counting "the current working tree", and it enumerates from `git ls-files`, which reads the **index**.
A file deleted on disk but not yet staged is therefore listed and then opened, and the open raises.

Measured 2026-08-24 two ways.
Deleting `docs/queue/Q719.md` with plain `rm` failed `make check`'s `claude-usage-test` with `FileNotFoundError` at claude-usage/compute_metrics.py:968, reached from `test_snapshot_reports_the_census_and_the_vendor_context`.
Deleting an unrelated tracked file (`docs/development/kind-iteration.md`) reproduced it identically, so this is not about the queue: any unstaged deletion does it.

CI never sees it, because CI runs against committed state, and staging the deletion clears it.
What it costs is a local `make check` run for whoever holds an unstaged deletion, which is the ordinary state of a session part-way through completing a backlog item.

Either skip a listed path that no longer exists, or enumerate from the working tree so the docstring and the behaviour agree.
Prefer the second: a census that silently omits deleted-but-staged files is a different wrong answer, and the docstring already says which tree it means.
Found while working Q719; out of that item's scope, filed rather than fixed.
