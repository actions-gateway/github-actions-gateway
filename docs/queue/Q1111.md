# webhookretry's budget test measures the host, not the retry loop

**Event:** `TestRetryOnTransientWebhookError_BudgetSurfacesLastError` or `TestRetryOnTransientWebhookError_TheUnseamedBudgetExpires` fails on `main`: an attempt-count mismatch, or the unseamed loop outliving its 30s guard. → top of Queue, escalated.

The test gave the retry loop a 50ms wall-clock budget and asserted `calls > 1` ("it should have retried before giving up").
Nothing in that assertion was about the retry loop.
`retryOnTransientWebhookError` stops once its deadline has passed, so the assertion asked whether a second closure call plus one 1ms gap fit inside 50ms of wall clock, which is a property of the host.
A first call descheduled past 50ms returns after one attempt and reads `1 > 1`.
It was found by the idiom sweep that closed Q1089, the same shape in `cmd/agc`, and has **never been observed failing**: it is parked here on the strength of the class, not a sighting.

**The fix.** The loop's two clock reads now come from nil-defaulted seams (`webhookRetryNow`, `webhookRetryAfter`), and the test fills them through `pinRetryClock`: every gap fires at once, and time stands still until the op moves it to the end of the budget on the attempt it wants to be the last.
Exactly one select case is ever ready at a pass, so the assertion is an exact count the op decided.
Widening the budget would only have been a wider race.
Production behaviour is unchanged: with both seams nil the loop reads `time.Now` and `time.After` as before, and `deadline.Sub(time.Now())` is what `time.Until(deadline)` computes.

**Seaming the clock bypasses the production deadline, so it has its own cover.** `TestRetryOnTransientWebhookError_TheUnseamedBudgetExpires` runs with the seams nil and a real 50ms budget, asserting the surfaced error alone and never an attempt count or the retry banner, behind a 30s guard.
It needs the budget to elapse eventually, not any number of attempts to fit inside it.

**Measured 2026-10-09 by deleting the mechanism.** Bypassing the seam in `retryNow` turns the pinned test red at `expected: 3, actual: 3431018` after 5.04s; freezing `retryNow`'s production branch turns the unseamed test red at its 30s guard.
The sibling `TestRetryOnTransientWebhookError_RidesOutTransientStall` (5s budget, `calls == 3`) was already sound and is unchanged: the op decides when to stop refusing, and the budget only has to not expire.
