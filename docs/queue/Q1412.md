# Measure how often real nodes end a memory kill Error, not OOMKilled

The reporter writes nothing on a container that ended with exit code 137 and a reason other than `OOMKilled`: [the rule](../plan/q1403-oom-kill-reporter.md#the-rule) counts it "among those it may be of, and nothing is written on it".
The runtime does end some memory kills that way, so on a real node such a kill goes unreported.

The oom-reporter's kind e2e lane now kills again when its hog ends that way, up to three hogs a limit, and logs `kill N of 3 is not counted` for each one it does not count.
That keeps the lane from failing a merge on the runtime's answer, and it also hides how often the runtime gives it.

**Measured 2026-11-26 on a local kind cluster** (`kindest/node:v1.35.5`, Docker Desktop, host load about 22): of 20 memory kills read, one ended `Error`, 137.
Its two siblings, killed the same second right after the agent restarted, ended `OOMKilled` and were answered.
Its agent had recorded the kill without reading the container's cgroup (`"inferred":3`, no container ID), so only the status could name the container, and the status named none.
On the hosted runner the lane's container case failed 2 of its first 2 runs with no condition, both before the test said how the hog ended, so whether those two were `Error` is not known; the 5 runs since all passed (run 45896584667, attempts 1 to 5).

Nothing has read the rate on a real node.
Count it on the dogfood cluster: containers that ended 137 against those of them that ended `OOMKilled`, beside the agents' report ConfigMaps for the same kills.
A rate well above the lane's would say the reporter needs to answer such a container, as `Unknown` or by its counters, which the rule does not do today; the lane's `kill N of 3` lines are a second reading of the same rate.
The duplicate search flags Q1403, which built the reporter and this lane and is closed by the same PR, and Q1410, which asks where the reporter lives, not what it answers.
