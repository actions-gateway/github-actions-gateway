# Decide what the OOM reporter does with a 137 not called OOMKilled

The reporter writes nothing on a container that ended with exit code 137 and a reason other than `OOMKilled`: [the rule](../plan/q1403-oom-kill-reporter.md#the-rule) counts it "among those it may be of, and nothing is written on it".
The runtime does end some memory kills that way, so the oom-reporter's kind e2e lane, which `e2e-gate` requires on any merge touching the reporter, can fail a merge that changed nothing about it.

**Measured 2026-11-26 on a local kind cluster** (`kindest/node:v1.35.5`, Docker Desktop, host load about 22): of 20 memory kills read, one ended `Error`, 137.
Its two siblings, killed the same second right after the agent restarted, ended `OOMKilled` and were answered.
Its agent had recorded the kill without reading the container's cgroup (`"inferred":3`, no container ID), so only the status could name the container, and the status named none.
On the hosted runner the lane's container case failed 2 of its first 2 runs with no condition, both before the test said how the hog ended, so whether those two were `Error` is not known.
The 5 runs since, with that diagnostic, all passed (run 45896584667, attempts 1 to 5): 5 of 7 hosted runs in all.

**Ask:** which of these, none chosen here:

- The lane fails on it, as now, and the hosted rate decides whether the lane stays required.
- The lane accepts either end for the container case: the condition, or a hog that ended 137 with another reason and none.
- The reporter answers such a container `Unknown`, so the lane can require a condition every time.
- The reporter answers it by the counters, as it does an `OOMKilled` one, which the rule does not do today.
