# Retype the `actions-gateway.com` validating webhooks onto `v2`

The five validators in `cmd/gmc/internal/webhook/v2alpha1/` are typed on `api/v2alpha1`, and their `+kubebuilder:webhook` markers name `versions=v2alpha1` alone.
`v2.0.0` deletes that package and stops serving both `v2alpha1` and `v2beta1`, so by the tag they must be typed on `api/v2` with rules naming `v2`.
The hazard is a rule left naming a removed version: it matches nothing, so validation stops without an error.
`make webhook-versions-check` (Q1068) now fails that state, so the retype cannot be skipped at `v2.0.0` either way.

**It gates the 1.9 tag, now that Q413 has landed (#1999).** Decided in two steps: on 2026-09-29, when Q1068 was worked, to retype in 1.9 rather than inside the removal PR; and on 2026-09-30 to make it a `1.9-gate`.
Review of that PR showed that 1.9 otherwise had no gating row left, so a preference would have missed the tag.
Retyped in 1.9, the `v2`-typed validators run through the whole 1.9 release, which exists to be the rollback point for the `v2.0.0` upgrade.
Left to the removal PR, they first run in `v2.0.0` itself, beside the storage migration and four removals.
The removal PR is forced to retype anyway, since deleting `api/v2alpha1` breaks the build, so this row is about when the retype runs, not whether.

**The retype is not a type swap, because 1.9 still serves `v2alpha1` and `v2beta1` and the hub stays `v2beta1`** (Q413).
A rule naming only `v2` makes the apiserver's default `matchPolicy: Equivalent` convert every `v2alpha1` and `v2beta1` write to `v2` before admission, through the hub.
Two checks then see less than they do today, and each must be rebuilt from a conversion annotation for the 1.9 window:

- **The `EgressProxy` alias rule (Q1085):** reject a newly added `CiliumFQDN`/`CalicoFQDN`, and admit one already stored with a warning.
  `v2` has no enum value for either, so `api/v2/conversion.go` (#1999) shows the mode as `FQDN` and carries the alias in `conversion.actions-gateway.com/egress-policy-mode`.
  A validator reading only `spec.egressPolicyMode` would admit every new alias and warn about none.
- **The `RunnerSet` scale-set label-uniqueness check**, which is a no-op for Classic sets.
  `v2` has no `acquisitionProtocol` field.
  The `v2alpha1` → hub conversion carries it in `conversion.actions-gateway.com/acquisition-protocol`, and `TestRunnerSetConversion_KeepsV2alpha1Annotations` in `api/v2/conversion_test.go` pins that it reaches the `v2` view.
  What is unmeasured is the live apiserver path, which the envtest below covers; if the annotation were dropped there, every Classic set would be checked as ScaleSet.

Both rebuilds are deleted again at `v2.0.0` along with the versions they serve, and the row accepts that cost for the soak.

**Do not add versions to the rules instead of retyping.** Q1068 refuted that fix: a rule naming the request's own version stops the conversion, so a `v2beta1` object would reach a handler typed for another version.
`runtime.DecodeInto` then fails, and under `failurePolicy: Fail` every write is rejected.

Done when all five rules name `v2` and the handlers are typed on `api/v2`.
Two envtest cases must also go red when their annotation is ignored: a `v2alpha1` write adding an alias, and a `v2alpha1` Classic `RunnerSet` sharing a first label with a ScaleSet set.
