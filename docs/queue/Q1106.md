# A test probe lands in the live workflows dir and races concurrent gates

**Event:** any gate that enumerates `.github/workflows/` fails on a file it cannot open, naming `zz-uses-pinned-test-probe.yml` or any other `zz-*` probe.

`make check` failed on `gate-needs-check` with no code change, and passed on a re-run of the same tree:

```
pathfilters: open .github/workflows/zz-uses-pinned-test-probe.yml: no such file or directory
check-gate-needs: could not read the jobs of zz-uses-pinned-test-probe.yml
```

**The mechanism, measured 2026-09-13.** [check-uses-pinned-test.sh](../../scripts/ci/check-uses-pinned-test.sh) line 43 points `PROBE` at `$REPO_ROOT/.github/workflows/zz-uses-pinned-test-probe.yml`, inside the real workflow tree rather than a scratch dir, and creates and removes it during the run.
`check` fans its gates out through `run-parallel.sh`, so `scripts-test` (which runs that suite) and `gate-needs-check` execute at the same time against the same directory.
`check-gate-needs.sh` lists the directory, then opens each file it found; the probe can be deleted in the gap, and the open fails on a path the listing had just returned.

The suite needs the probe there on purpose: it asserts the file is what `path-filters` selects, which is a claim about the real workflow tree.
So the fix is not simply to move it.
Either the probe's window has to be invisible to a concurrent reader, or a reader has to tolerate a workflow disappearing between the listing and the open, which is a property `check-gate-needs.sh` wants anyway: the directory is not locked and any gate reading it races every other writer.

**Why it is worth fixing rather than re-running.** It reddens a branch for a reason that has nothing to do with the branch, which is the failure mode that costs the most: the first read is "what did I break", and the answer is nothing.
It is not local to one workstation either, since CI runs the same fan-out.

**What has not been established.** How often it fires.
It was seen once, in one run, and the timing depends on how the two gates interleave.
It has also not been reproduced deliberately; the mechanism is read off the two scripts and the failure text, and a reproduction would pin the window's width.

Note the failure names `pathfilters`, not the probe's author, so the gate that reports it is not the gate that wrote the file.
Anything else enumerating that directory concurrently can fail the same way.
