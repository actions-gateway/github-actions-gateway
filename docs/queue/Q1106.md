# A test probe lands in the live workflows dir and races concurrent gates

**Event:** any gate that enumerates a `.github/workflows/` directory fails on a file it cannot open or cannot parse, naming `zz-uses-pinned-test-probe.yml`. → top of Queue, escalated.

**The mechanism, reproduced 2026-09-16.** The row was filed with it read off the two scripts, and the reproduction changed the fix.
[check-uses-pinned-test.sh](../../scripts/ci/check-uses-pinned-test.sh) created and removed an untracked tag-pinned workflow inside the root `.github/workflows/` while `make check` fanned out.
Driving a reader in a loop against a churning probe produced three distinct failures, not the one the row asserted:

| Class | What the reader sees | Measured under churn |
|---|---|---|
| Vanish | the path the listing returned is gone by the open | `check-gate-needs.sh` 4/40, `check-uses-pinned.sh` 2/20, `actionlint` 1/20 |
| Presence | the probe *is* a tag pin, so rejecting it is correct | `check-uses-pinned.sh` 12/20 |
| Torn read | the file is opened mid-write and parses short | `actionlint` 1/20, `"jobs" section is missing` |

The `check-uses-pinned.sh` split reconciles: 12 plus 2 is the 14 of 20 runs that failed.
Its rate is the one with power behind it; the single-figure rates are one or two events each, and a second 20-run pass at the root read `check-gate-needs.sh` at 0/20, so that reader's exposure is real but its rate here is not a number to quote.

The probe's window is **1.43 s**, one sample from one suite run, opening about 6 s in.
`check-gate-needs.sh` takes 1.49 s and `check-uses-pinned.sh` 2.40 s, so a reader is comparable in width to the window rather than dwarfed by it.

**A second unprovoked sighting, 2026-09-16.** Reported by the session holding Q1102 on `claude/elegant-lumiere-0a91c8`; their measurement and their log, not one taken here.
It is the missing-file class and not the torn read: `pathfilters: open <abs path>/.github/workflows/zz-uses-pinned-test-probe.yml: no such file or directory`, then `check-gate-needs: could not read the jobs of ...`, then `make[1]: *** [gate-needs-check] Error 2`.
An ordinary `make check` on an unrelated docs-and-scripts change, not a driven reproduction, which is the whole of what it establishes and the one property the churn harness above structurally cannot: the class fires on its own.
Two sightings three days apart, in sessions that had never spoken.

The failing run spanned roughly 10:06:47 to 10:11:52 PDT over 59 commands, `gate-needs-check` itself taking 6 s, and a clean re-run of the same tree finished 10:22:04.
**No load reading was taken at failure time**, and the nearest one is 40 minutes later, so nothing here says what the host was carrying during the window.
Whether a sibling lane was running its own `make check` is likewise unmeasured rather than absent.

`gate-needs-check` was the only failure: `actionlint`, `path-filters-check`, `uses-pinned-check` and `gate-lists-check` all passed in the same fan-out.
That is luck rather than structure, and the churn rates above are what say so, since each of those readers has been driven red by the same probe.
`scripts-test` passed too, both `check-uses-pinned-test` and `check-gate-needs-test` inside it, with the probe visibly in play (`selection includes an untracked workflow ... yes`).
So the suite that plants the probe and the suite that tests the reader were both green while the real gate reading the real directory went red.
Log line order is not evidence of sequencing here, because `run-parallel` buffers per command and position reflects flush order.

The original's quoted text renders the path relative and this one renders it absolute, which is transcription rather than a second call path: `pathfilters` prints the path it was handed, and [check-gate-needs.sh](../../scripts/ci/check-gate-needs.sh) builds `WF_DIR` from an absolute `REPO_ROOT`, as did the reproduction here.

This sighting is `gate-needs-check` reading the probe in the **root** directory, which the fix moves out of.
It is evidence about the pre-fix world and about frequency, and it is not evidence that the fix works.

**One reader failed quietly rather than loudly, and so appears in no count.** [workflow-acting-steps-test.sh](../../scripts/ci/workflow-acting-steps-test.sh) also enumerates the root directory, and greps each file it globbed.
A probe that vanishes mid-loop makes `workflow_acts` read the file as not acting rather than error on it, so that reader returns a clean verdict having failed to read what it was pointed at.
Nothing reports it, and it could never have appeared in a flake count.
Found while checking a coupling raised by the lane adding `withheld-runs-watch.yml`, whose own conclusion was negative.

**Why reader tolerance could not be the whole fix.** The row offered it as the property `check-gate-needs.sh` wants anyway, and it is.
But `actionlint` walks the directory itself inside a third-party binary, so no tolerance written here reaches it, and the torn read is not an `ENOENT` any tolerance would recognise.
`check-uses-pinned.sh` cannot take it either: its own group 2 asserts that an unreadable file is exit 2, which is the fail-closed property the gate exists for.

**What shipped.** The probe moved to `cmd/gmc/.github/workflows/`, which is in this gate's selection and in no other reader's, so it is still an untracked workflow in the real tree; and it is SHA-pinned, so a concurrent `uses-pinned-check` sees a legitimate file.
`check-gate-needs.sh` skips a workflow that vanished between the listing and the open and reports the count, while a file still present and still unreadable stays a refusal; that half guards against every other writer of the directory, not just this probe.
Group 4's end-to-end assertion became: the default run stays green and its own scanned-file count rises by exactly one, which is what says the untracked file reached the scan rather than only the listing.

Post-fix, the same churn harness against the relocated probe: `check-uses-pinned.sh` failed once in 20, and `check-gate-needs.sh` and `actionlint` did not fail.
**Those last two carry no denominator on purpose.** Neither reader looks under `cmd/gmc/`, so no state of the world reachable from where they were pointed would have reddened them.
Writing them `0/20` would read as twenty trials that could have gone the other way, and a constructed zero has none; the qualifying sentence does not travel when the number gets quoted, which is how the figure would end up meaning more than it does.
What that run confirms is the relocation, not any tolerance.
What tests the tolerance is [check-gate-needs-test.sh](../../scripts/ci/check-gate-needs-test.sh), where a stubbed reader reproduces the state a vanish leaves behind; deleting the tolerance turns that case red and leaves its control, a file still present and still unreadable, green.

**Parked rather than closed because of that 1/20.** It is `check-uses-pinned.sh` racing its own suite on the vanish path, which its fail-closed design forbids it from tolerating; separating a default-selected path that disappeared from an explicitly named path that never existed is its own change and is filed separately.
