# The merge drivers resolve nothing on GitHub, where the merges happen

Four files are routed to a merge driver so concurrent PRs appending entries merge as a set rather than by line position, and `maintaining-backlog.md` already records that the drivers cannot help GitHub, which cannot see a clone's config.
What was never measured is the cost, which lands on exactly the batches the routing exists to serve: of seven PRs open together on 2026-08-18, five conflicted on a routed file under a `merge-tree` with every driver disabled — `scripts/README.md` in five of them and `mk/gate-lists.mk` in four — so each has to rebase behind the one before it, at a full CI cycle each.
The trap is that no clone can see it: with the drivers configured every one of those merges resolves clean, and `mergeStateStatus` reported `CLEAN` for all eight PRs on one reading and `UNKNOWN` for all fourteen on another, never the conflict.
Only `git -c merge.<name>.driver=false merge-tree` shows the state GitHub will act on, so a session that trusts either signal rebases when it is told to rather than when it is needed.
The measurement is the deliverable here; the repair is open, and the plausible directions (one entry per line, sorted; or dropping the routing and accepting line-position conflicts) each touch all four routed files and want their own design pass.
