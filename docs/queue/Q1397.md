# privileged-dind starts the runner before its Docker daemon is ready

A job on `privileged-dind` can start before dockerd listens, and then fails with `Cannot connect to the Docker daemon`.
The kubelet starts the runner once the native sidecar's process has started, and only a startup probe holds it for the daemon.
`kata-dind` has one, added after a sidecar crash loop let runners take jobs they could not serve ([the incident](../plan/archive/kata-on-gke.md#what-the-live-session-found-2026-07-16)); `privileged-dind` has none (`grep -c startupProbe` on the two templates reads 1 and 0).

Seen on 2026-11-24 on one `kindest/node:v1.35.5` container, a static pod with the template's entrypoint and no startup probe: the runner's container started in the same second as the sidecar, and in a second pod of the same kind, at 19:29:24, dockerd reported `API listen` at 19:29:25.
Nothing ran a job, so a failure was not reproduced, and a runner also takes time to register, which may hide the gap.

- Add the `tcpSocket` startup probe `kata-dind` carries, on the same port.
- Read whether a crash-looping daemon still lets the runner take a job without it, which is the shape the incident saw.
