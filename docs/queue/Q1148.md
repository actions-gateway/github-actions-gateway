# Share pull_request and push path lists with a YAML anchor

Five workflows scope both legs with identical `paths:` lists written twice: `dockerfile-lint.yml`, `endpoint-parity.yml`, `metric-tiers.yml`, `reason-tiers.yml` and `rung-order.yml`.
Q574 put each pair in `TWICE_WRITTEN` (`scripts/ci/check-path-filters.sh`), so drift now fails the gate, but the duplicate itself remains.
Anchoring the first list (`paths: &paths`) and aliasing it in the second (`paths: *paths`) would remove the pair rather than gate it, the way `autoscaler-drift.yml`'s `drift_shared` anchor already does inside a `filters:` block.

**Documented, not measured.** GitHub's changelog of 2025-09-18 says "GitHub Actions now supports YAML anchors", enabled for all repositories, and states no limitation on where one may appear (https://github.blog/changelog/2025-09-18-actions-yaml-anchors-and-non-public-workflow-templates/, read 2026-09-29).
No workflow in this repo uses one in its triggers, so nothing has exercised it on `on.<event>.paths` specifically.
The measurement that settles it is one real run: anchor one workflow's two lists, then confirm both a PR touching a listed path and a push to `main` still trigger it, and that a PR touching nothing listed does not.

What the change would owe beyond that run:

- `devtools/ci/pathfilters` already resolves aliases, so `pr-paths` and `push-paths` would both read the full list and assertion 4 would keep passing on the anchored pair.
  The pair's `TWICE_WRITTEN` entry then guards a list that cannot drift, so it goes; assertion 5 would still ask for it, because both trigger lists are non-empty, so assertion 5 needs to recognise a pair whose two sides are one node.
- `actionlint` (in the `actionlint` job and `make check`) must accept the anchor; that is also unmeasured.
- The doc section in `target:` says those pairs stay duplicated until this row measures it, and that sentence changes with the answer either way.
