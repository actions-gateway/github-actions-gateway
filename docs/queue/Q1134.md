# A backport tag claims `--latest`, demoting the newer minor

`publish.yml`'s last release step runs `gh release edit "${TAG}" --repo "${REPO}" --draft=false "${extra[@]}"`, and `extra` picks up `--latest` whenever the tag is not a prerelease.
That test reads the tag alone: it makes no comparison against the versions already released.
So a stable backport cut after a newer minor (`v1.5.1` published once `v1.6.0` exists) claims `latest` on the repository's releases page and demotes `v1.6.0`, which is the ref a reader arriving at `/releases/latest` gets.

Measured 2026-09-21 by driving the extracted body with a `gh` stub: `TAG=v1.5.1 PRERELEASE=false` produces `gh release edit v1.5.1 … --draft=false --latest`, recorded as the `publish-backport-claims-latest` case in [`workflow-publish-steps-test.sh`](../../scripts/ci/workflow-publish-steps-test.sh).
That case asserts what the step does today; it is not an assertion that the behaviour is right.

**Two other gates in the same tag push already make the opposite call**, which is what makes this worth asking rather than simply fixing.
`pages.yml`'s `mike` step moves the `stable` alias and the default root redirect only to the highest released version, so the docs site is not demoted by a backport.
`publish.yml`'s own announce-bar gate exempts a backport for the same reason, and [release.md](../operations/release.md) states the rule in prose for both.
Three mechanisms in one pipeline, and the one that sets the GitHub `latest` pointer is the odd one out.

**It is an open question rather than a defect because the documented behaviour is the current one.** release.md says a stable `≥1.0.0` tag means latest, and the step's comment explains `--latest` as restoring what `gh release create` would have picked had the release not been created as a draft, which is accurate about `gh`, and is a claim about a mechanism rather than about what the release should advertise.
Settle which the project wants before writing code:

- **Leave it.** `latest` then means most-recently-published, which is defensible and is what the prose says.
- **Guard it**, mirroring `pages.yml`: pass `--latest` only when this tag is the highest stable release, resolved from `gh release list` or `git tag`.
  That needs a read the step does not make today, and it needs deciding what happens when the read fails; claiming nothing is the safe answer and leaves `latest` on whatever held it.

Whichever way it goes, the `publish-backport-claims-latest` case and the paragraph in [testing.md](../development/testing.md#publishyml-has-its-own-suite) that names the asymmetry are updated with it.

## Notes

**Ask:** which of the two `latest` should mean here.
The measurement is taken and the alternatives are costed above; what is left is the maintainer's call about what the releases page should advertise, and no amount of reading the repo settles it, because the repo currently says both things in different places.
