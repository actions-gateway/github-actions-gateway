# An idle scale-set worker that started nothing has no reap backstop

**A `Running` scale-set worker whose runner never starts a job is reaped only if a surplus stamp reaches it, and an AGC restart can build one that no stamp will.** Its only other deadline is `maxWorkerLifetime`, 12 hours by default, held on a node its `safe-to-evict: "false"` keeps from scaling down.

**The measured case is closed.** On 2026-11-18 during the `v2.0.1-rc.1` gate (run 44236535751), the e2e job (run 44247655794, job 134610459870) got two workers.
The dogfood cluster's audit log for `gag-dogfood-e2e` shows why:

- 05:56:12Z: the AGC created a worker for scale-set job `aee1ea10-…`, one second after the job queued.
  Its events put its runner container's start at 06:01:13Z: a node scale-up from zero (about 1m20s), its block volume failing to provision with `no topology key found for node` until the CSI driver registered on the new node (scheduled 05:58:29Z), two `no runtime for "kata-qemu"` sandbox failures (about 52s), and image pulls (`docker:28-dind` 27s, the 722 MB runner image 1m10s).
  A cold node takes about as long as GitHub's withdrawal window, so this recurs on cold starts.
- 06:01:12Z: it stamped that worker `job-completed-at` and `surplus-for-job: aee1ea10-…`, which only a `JobCompleted` naming no runner writes.
  GitHub had withdrawn the assignment five minutes after making it.
- 06:01:13Z: it created a worker for scale-set job `ff8923a0-…`, carrying the same run ID and job name: the same workflow job re-issued under a new job ID.
- 06:01:17Z: the first worker's runner took the job (GitHub's job record names `gag-ci-e2e-aee1ea10-…`).
  At 06:02:03Z the AGC recorded that start, `started-job-id: ff8923a0-…`, lifting the stamp.
- The surplus that start moved found the second worker still `Pending` (bound 06:03:32Z), and was dropped, because `reclaimSurplusWorker` then took only `Running` workers.
  The second worker registered as runner 29119, listened from 06:05:24Z, and was deleted by hand at 09:01:48Z.

The reclaim now takes a `Pending` worker when no idle `Running` one is left.

**What is left.** A moved surplus is still dropped when no idle worker exists to take it, and two orderings leave the re-issue's own worker idle with no stamp:

- The re-issue's `JobStarted` arrives in the same batch as its `JobAssigned`, or before it.
  Starts are handled first, so the move runs before the re-issue's worker exists.
  Skipping that worker is not the fix: where another job's worker is still `Pending`, the move stamps it, and the re-issue's worker is the runner left for that job.
- After an AGC restart.
  The listener's `provisioned` guard is in memory, and a replayed queue delivers a job's `JobAssigned` ahead of its `JobStarted`, so a re-issue whose surplus worker was already reaped is provisioned again, and its start names a runner whose worker carries no stamp.

Both paths are derived from the code and not reproduced.

A deadline measured from the pod would close it and any path like it: reap a `Running` worker whose runner has started nothing some minutes after its runner came up.
It must not reap a runner whose start the AGC has not recorded yet, which is the state an AGC outage leaves, so it needs an authority beyond the pod's annotations, such as GitHub reporting the runner record not `busy`.

**Done when** a `Running` worker whose runner never starts a job is reaped on a deadline measured from the pod, with a test that goes red with the mechanism deleted and one showing a runner busy at GitHub is left alone.
