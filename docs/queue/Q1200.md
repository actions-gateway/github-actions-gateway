# GMC patches owned Secrets with no patch verb on secrets

The Gateway Manager Controller (GMC) writes every Secret it owns through `applyManagedChild`, which calls `controllerutil.CreateOrPatch`, and `CreateOrPatch` changes an existing object with a `patch` request.
The GMC's manager ClusterRole grants `create` and `update` on Secrets and no `patch`, so a change to an owned Secret's data or labels would be refused, read from source and not observed: the one Secret marker in `cmd/gmc` is `actionsgateway_controller.go`'s `resources=secrets,verbs=create;update`, and `charts/actions-gateway/files/manager-role-rules.yaml` lists only those two verbs for `secrets`.

## Measured 2026-10-23

- The callers are both reconcilers' `applyOwnedSecret` (v1 `actionsgateway_controller.go`, v2 `actionsgateway_v2_controller.go`) and the EgressProxy reconciler's owned-Secret writes, all through `applyManagedChild` in [`apply_helpers.go`](../../cmd/gmc/internal/controller/apply_helpers.go).
- `CreateOrPatch` skips the request when the mutate function leaves the object unchanged, so the refusal fires only when the desired Secret differs from the live one, for example when a metrics or proxy TLS bundle is reissued.
- Unverified: whether any owned Secret's data changes after creation in practice.
  The envtest suite runs the reconcilers as the admin user, so no test would see the refusal; `TestGMC_TenantSecretAccess_ScopesReadsToTenantNamespaces` runs as the GMC ServiceAccount but never changes an owned Secret.

## Fix

Measure first: run a reconcile as the GMC ServiceAccount that changes an owned Secret, and read the response.
If it is refused, add `patch` to the Secret marker; the `gmc-tenant-resource-guard` policy already confines Secret `UPDATE`, which is the admission operation a patch is, to tenant namespaces.
