# claude-usage: PR fetch misses a PR merged after a higher-numbered one

`pr_series` asks only for merged PRs numbered above the highest one already stored, so a PR opened early and merged after a later-numbered PR was recorded falls below that mark and is never fetched.
Measured 2026-11-10: after the page-widening fix, `pr_metrics.csv` held 2,203 rows against 2,208 merged on GitHub, missing #1547, #1562, #1563, #1566 and #1570; deleting the CSV and refetching all of them filled the five and changed none of the other 2,203.
The cycle-time percentiles are the column this skews, and in the worst direction: a PR that waited longest to merge is the one most likely to be skipped, so the recorded tail reads shorter than it was.
The fix is to dedupe on the stored set of numbers rather than a high-water mark, and to keep widening the page until it reaches a merge date older than some lookback (the open-PR age the queue tolerates) instead of stopping at the first stored number.
A full refetch every run is the blunt alternative: about 66 GraphQL points for 2,200 PRs against a 5,000/hour budget shared with every other tool on the account, derived from the 3-points-per-100 measurement in the README rather than measured at this size.
