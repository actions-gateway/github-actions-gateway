# Exercise every v2beta1 kind on the dogfood cluster (GA soak criterion 2)

[v2-ga.md](../plan/v2-ga.md) Phase 1 criterion 2 requires all five `v2beta1` kinds to have carried real traffic on the dogfood cluster, and today four of them have.

**Measured 2026-09-07** over `deploy/` and `scripts/dogfood/`, against the five kinds [v2-api.md](../plan/v2-api.md) names (`ActionsGateway`, `RunnerSet`, `RunnerTemplate`, `ClusterRunnerTemplate`, `EgressProxy`): the dogfood overlays apply `ActionsGateway` and `RunnerSet` (`deploy/dogfood-e2e`) plus three `ClusterRunnerTemplate`s (`deploy/templates`), and `scripts/dogfood/setup.sh` applies a namespaced `RunnerTemplate` (as `v2alpha1`, so it also passes through the conversion webhook on the way to storage).
The same script says in its own comments that it creates no `EgressProxy`, so workers egress directly; the only `EgressProxy` objects the repo exercises are in envtest and in `cmd/gmc/test/e2e`, whose venue is a kind cluster in CI rather than the GKE dogfood cluster.
A first reading of this row named `PriorityClassAllowlist` as the uncovered kind; it is not one of the five, and it ships in the main chart rather than the v2 CRD chart.
Whether the release candidate's e2e leg counts as dogfood traffic for those kinds is the first thing to settle, because [release.md](../operations/release.md#validate-the-release-candidate-on-dogfood)'s validation dispatches that matrix against the candidate's runners rather than applying the kinds to the dogfood cluster itself.

The deliverable is evidence, not a build: each kind applied and reconciled to a terminal condition on the dogfood cluster during a release-candidate window, recorded against the criterion in the plan's Phase 1 table, plus whichever overlay or window step makes the next candidate repeat it without being asked.
Rides in [release-1.8.md](../plan/release-1.8.md) rather than gating it, since a soak reading closes when the evidence exists and cannot be scheduled against a tag.
