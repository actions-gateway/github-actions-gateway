# A disruption before its worker's start re-runs the wrong job's run

Until GitHub's `JobStarted` is handled, a scale-set worker's pod names the job it was created for, and 2 of 16 and 4 of 19 workers on dogfood ran that job (2026-11-24).
The out-of-memory class waits for the start since Q1389; the disruption arms do not.

Read from source, not run: an eviction, preemption, node shutdown or drain of a worker in its first seconds reserves a slot of the created-for job's run and re-runs that run's failed jobs, and where another worker has started that job it withholds with no Event.
The job the runner held is then not re-run.
No limit is raised, so it costs less than the out-of-memory case did.

A kill the out-of-memory class does not wait for, because its runner had no memory limit or no sizing profile built its pod, is claimed with no job ID.
That claim covers the created-for job for an hour: a restarted AGC's orphan scan counts it as recovered, and its own failure is recorded with cause `oom`, though nothing was recovered.

Not the same wait: those arms re-run from 5 seconds by default (`evictionRetryDelay`) and within a 15-minute window, so a wait delays the recovery it is for, and a drained pod is usually gone before a start could be stamped on it.
One candidate is to key the recovery on the runner's name instead, and let a start that arrives for a pod already claimed correct the parked re-run; the first step is measuring how long after a kill a start arrives.
