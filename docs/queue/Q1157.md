# Gate exits 0 after a pass whose teardown left nodes up

A gate that passes and whose teardown then ends `Teardown INCOMPLETE` exits 0, so the one status a caller or a watching session reads says nothing about the nodes still billing.
`teardown()` runs from the `EXIT` trap and returns 0, and a trap that returns keeps the script's original status.
The reviewer of PR 2026 measured that on bash 5.3.15.
This session did not re-measure it.

`scripts/dogfood/release-sentinel.sh` makes the gap worse: its `passed` message says `the gate's own task exits when the cluster is back to 0 nodes at rest`, which is false whenever a stop script refused.
`docs/operations/release.md` § Confirming the cluster is actually at rest now names the case and sends the operator to `ops.sh at-rest`, so the docs no longer depend on the exit code.
The status itself is still wrong.

**The fix:** have the trap end with `exit 1` when the gate's own status was 0 and either stop script failed.
There is precedent in the same file: after a pass whose verdict could not be recorded, the gate already `exit 1`s (`scripts/dogfood/validate-release.sh:1732:		exit 1`).
Correct the sentinel's `passed` wording in the same change.
Keep the progress event `teardown done` rather than `fail`: `scripts/dogfood/lib/progress.sh` lets the first `fail` turn a passed gate into `failed`, and the verdict itself did pass and is recorded.
Assert both directions in `scripts/dogfood/validate-release-test.sh`.
The test has to read the status of a process whose EXIT trap fired, so drive a child `bash` rather than calling `teardown` in a subshell, where the trap never runs.

Filed from the review of PR 2026 (Q1155), which kept the lease on this path and left the exit status out of scope.
