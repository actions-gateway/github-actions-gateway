# No workflow or job can opt out of the automatic re-run

The only switch on automatic re-runs is `maxEvictionRetries` on the `RunnerSet`, so a job that must not be repeated cannot say so.
A workflow author whose job is not safe to run twice, such as a deploy or a release, shares a set with jobs that are, and the set's operator is usually someone else.
Cancelling the run stands the recovery down, which needs a person watching.

Read from source and the operator docs on 2026-11-27: no label, annotation, job property or repository setting is read by any recovery arm.
No request for one is on record, so this is filed from an audit and not from demand.

**The choice** is the channel, and each has a cost:

- A `RunnerSet` field listing repositories or workflows to leave alone keeps the decision with the operator, who does not know which jobs are unsafe.
- A second `RunnerSet` with `maxEvictionRetries: 0`, selected by a `runs-on` label, needs no new field and works today; it is undocumented as the answer, and Q1427 and Q1428 make 0 noisier and weaker than it reads.
- A signal from the job itself, such as a label in `runs-on`, puts the decision with the author; what of a job's definition reaches the AGC in the assignment message is not measured.

Documenting the second as the supported route is the cheap first step, once Q1427 and Q1428 land.

**Ask:** whether an opt-out below the `RunnerSet` is wanted at all, and if so which party decides it, the operator or the workflow's author.
