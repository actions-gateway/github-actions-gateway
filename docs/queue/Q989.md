# `cover-check` tolerance flips the verdict on a fixed coverage number

`effective_tolerance` is `max(COVERAGE_TOLERANCE, COVERAGE_TOLERANCE_STMT * 100 / NSTMT)`, so the pass bound moves with the module's statement count.
Measured 2026-08-25 on one unchanged tree, three runs of the same `make cover-check`: `./cmd/proxy` reported 78.7% every time, with tolerance `0.5000pp` once and `0.8621pp` twice, giving `FAIL`, `ok`, `ok`.
At the defaults (`0.5`, `3`) those imply `NSTMT` of 1044 and 348, a 3x swing in the denominator while the measured percentage did not move at all.
The failing reading was the one inside `make check`, where cover-check runs in the parallel fan-out.
It bites only because `./cmd/proxy` already sits below its recorded floor (78.7% < 79.3%) and passes on tolerance alone, which the script itself flags and which `make cover-update` would clear; `./cmd/probe` is in the same state.
So the floor drift is what makes the denominator swing observable, and either one alone is quiet.
Distinct from Q823, which is coverage *timing* under load rather than the statement count.
