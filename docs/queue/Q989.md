# `cover-check` tolerance flips the verdict on a fixed coverage number

**Event:** `cover-check` prints two different tolerances for one module across runs of an unchanged tree, or reports a `FAIL` whose percentage has not moved. → top of Queue, escalated.

Mitigation shipped: `profile_statements` counts each distinct block once, so the statement denominator is a property of the tree rather than of the test cache.

The cause was not the tolerance rule but the number fed to it.
A merged profile carries one row per (block, reporting test binary), so a package linked by three instrumented binaries is written three times and one served from the cache is written once.
`go tool cover -func` merges those rows, so the percentage is invariant to that multiplicity; `report_module` summed the raw rows, so `effective_tolerance` was not.

Measured 2026-09-04 over one unchanged tree at `origin/main`, a colder run against a fully cached one: 18,409 rows over 11,031 distinct blocks with multiplicities of 1, 2 and 3, against 11,031 rows all at 1.
`./cmd/proxy` read 456 rows over 228 blocks, 772 statements by row and 386 by block, `80.8%` either way, giving 0.5000pp of tolerance against 0.7772pp.
Four of the ten workspace modules changed tolerance between the two runs (`api`, `cmd/proxy`, `githubapp`, `scaleset`); counting per block makes all ten agree.

The row's own 2026-08-25 numbers (348 and 1,044 statements, 78.7% against a 79.3% floor) are a smaller `cmd/proxy` than today's.
The `FAIL` was **not** reproduced, and needs a second condition this tree no longer meets: the module must also sit below its floor and pass on tolerance alone.
`./cmd/proxy` is now at its floor exactly after a re-record, and the module currently below its floor is `./cmd/probe` (81.6% < 81.8%), which at 2,253 statements is past the 600-statement crossover and takes the fixed 0.5pp under either denominator.
So the swing that produces the flip is fixed and the flip itself was never observed here; a recurrence is expected to look like the Event above rather than like a repeat of the row's original reading.

`make cover-update` would clear the `./cmd/probe` shortfall and with it the observability of this defect, which is why the baseline was deliberately left alone.

Distinct from Q823, which is coverage *timing* under load rather than the statement count.
Distinct also from [Q992](Q992.md), which is `cover-check` replaying a cached test result: that one cannot produce a spurious FAIL, and this row owns the tolerance measurement.
