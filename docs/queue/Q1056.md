# Nothing drives publish.yml's acting `run:` bodies before a release

Q1006 shipped a driver for the workflow `run:` bodies that act, and scoped `publish.yml` out of it deliberately.
This is the residue.

`publish.yml` triggers only on a `v*` tag push and a dispatch, so no pull request executes any of its bodies.
Measured 2026-09-04 by parsing each workflow's `on:` block: it is one of eleven workflows with no `pull_request` trigger, and the only one of those whose bodies both act on the world outside the run and are undriven.
Its acting steps run `cosign sign`, `cosign sign-blob`, `helm push`, `gh release create`, `gh release upload` and `gh release edit`: publishing, signing and releasing, each first executed during the release it is publishing.

**What is already covered, so this row is not the whole gap.** [`check-publish-digest.sh`](../../scripts/ci/check-publish-digest.sh) holds the retried build's wiring statically, and `cosign-pin-check` and `semver-floor-sources-check` cover two more properties.
Those read the YAML.
None of them enters a step's shell, so nothing exercises what the bodies *decide*: which digest a `gh release edit --draft=false` promotes, whether a chart push that failed to parse its digest still signs something, what the `--latest` branch does on a backport tag.

**Why Q1006 excluded it, and what would change that.** The two steps Q1006 drives need one stub each (`gh`; `mike` plus `git`).
`publish.yml`'s need `cosign`, `syft`, `docker`, `helm` and `gh`, several of them recording multi-line output later steps parse, which is a driver several times the size of the one that ships in Q1006 rather than an afternoon's extension of it.
Sized M for that reason, not because the mechanism is unknown: [`workflow-step-body.sh`](../../scripts/ci/workflow-step-body.sh) and the case shape in [`workflow-acting-steps-test.sh`](../../scripts/ci/workflow-acting-steps-test.sh) both generalize, and the suite's `acting_registry()` already carries `publish.yml` with this row's id as its deferral reason.

**The extractor already reaches all six, so this is a driver to write rather than steps to convert first.** It refuses a body that interpolates a `${{ }}` expression into its script text, because the runner substitutes that before bash sees it, so a driven body would not be the body CI runs.
Measured 2026-09-04: `workflow-step-body.sh` returns rc 0 for `chart`, `chart_crds_v2`, and the four release steps (`Compose and create the GitHub Release …`, `Render, sign, and attach the v2 CRD manifest …`, `Build, sign, and attach the gag-migrate CLI binaries …`, `Publish the release now every asset is attached`).
All six take their inputs through `env:`, so the whole cost of this row is the stubs and the cases.
