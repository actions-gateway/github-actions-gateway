# Signalling the perl lock launcher orphans its child and frees the lock

`serialize_heavy_build` re-execs the calling script under perl, which takes an advisory `flock` and then runs the real work as a `system` child.
The lock fd lives in perl; the work lives in the bash child.
Signal perl alone and the kernel drops the lock while the child keeps running, reparented to init and still inside the critical section, so the next contender acquires and enters beside it.
That is the exact state the lock exists to prevent, reached through it rather than around it.

**Measured 2026-09-09**, on a verbatim reduction of the same pattern in `deploy/monitoring/preview/render.sh` (Q1072, which copied the mechanism from here).
A's child (pid 19380) entered its 20s section at `t=1789026381` and was still alive after `kill <launcher>`; B acquired and entered at `t=1789026386`.
Two concurrent entries under one lock.

**Every reachable path is safe today, which is what makes this debt rather than a defect in flight.** Group signals kill the child, verified on both `SIGINT` (Ctrl-C) and `SIGTERM` (`kill -TERM -- -PID`, which is how [`record-launch.sh`](../../scripts/agent/record-launch.sh) stops a recorded run when `pgid == pid`), and `timeout` takes the child too.
The one path that orphans today is a hand-typed `kill <pid>` against the launcher pid read off `ps`, which is a plausible thing for a session to do to a wedged gate.

`record-launch.sh` is safe by construction rather than by luck, and it carries a fallback worth knowing about.
`launch()` sets `set -m` so the run is its own process group, and the stop command is chosen on a measured `pgid == RUN_PID` rather than assumed; when that holds it group-kills.
The `else` arm records a single-pid `kill -TERM ${RUN_PID}`, which is exactly the orphaning shape, and it is reached only if job control did not give the run its own group.
So a fix here should keep that arm safe too, rather than relying on the group arm always being the one taken.

**The repair is unmeasured and the row does not prescribe one.** The shapes worth weighing: have perl trap `INT`/`TERM` and relay to the child before exiting; or `setpgid` the child and signal the group; or hold the lock in the child instead of the parent, which changes what "released on death" means.
Whichever is picked, assert the inverse as well: the child must still die on the paths that already work, or the fix trades a rare orphan for a routine one.

**Do not fix this in `render.sh` alone.** Both copies share the mechanism, and diverging them leaves the harness and the heavy-build semaphore reasoning differently about the same failure.
The change belongs in the shared helper, with `render.sh` following.
