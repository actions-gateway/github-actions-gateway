# Rule 8's prose forbids the fix-time retirement its ledger records

`check-queue-rules.py` states rule 8 as an invariant: a shipped mitigation parks a `flake` item in flake watch, and *only a groom* retires it to the ledger.
Practice departs from that deliberately, and the departure is sound.

Measured 2026-08-27, both cases on `main`:

Q982 was retired at fix time: [#1747](https://github.com/actions-gateway/github-actions-gateway/pull/1747) deleted the row and added its ledger line in the same commit.
Q968 was parked: [#1754](https://github.com/actions-gateway/github-actions-gateway/pull/1754) shipped the fix and left the row standing.

Q982 carried `flake` when it was deleted, so this is the governed case rather than an unlabelled row slipping past.
Its ledger entry states the reasoning outright: retired at fix time rather than after a soak, because a flake-watch trigger turns on recurrence observed on `main`, which could neither happen nor be falsified for a path `main` never ran.
A row whose trigger cannot fire has nothing to wait for, so parking it buys a soak against an event that is already impossible.

The gate permits both outcomes and cannot tell them apart.
`rule8` checks only that a deleted `flake` id appears in the ledger, which is a reachability test, not a timing one, and it has no way to know whether a groom made the call.
So the prose asserts an invariant the gate does not enforce and practice does not follow, which leaves a session reading it with no rule for the case it is actually in.

The fix is to make the prose describe both cases and name the discriminator, not to tighten the gate.
Tightening it would fail [#1747](https://github.com/actions-gateway/github-actions-gateway/pull/1747), which was right.
The discriminator the ledger already uses: park the row when the trigger can still fire, retire it at fix time when the fix makes the trigger unreachable, and say which in the ledger entry.

Two sites carry the stale claim.
`maintaining-backlog.md`'s flake-lifecycle section is the canonical one.
`check-queue-rules.py`'s own rule-8 text and its failure message repeat it, and the failure message is what a session sees first.
`CLAUDE.md` states it too, in one clause, and is loaded into every session.
