# RunnerSet admission reads the cluster twice over for two guards

`RunnerSetCustomValidator` now runs two cross-object guards that each build their own cluster-wide inventory on the uncached API reader: `scalesetscope.Of` lists v2 ActionsGateways and RunnerSets for the Q791 scale-set name guard, and `agentidentity.Of` lists v1 ActionsGateways, v2 ActionsGateways, RunnerGroups and RunnerSets for the Q1011 agent-identity guard.
Two of those four kinds are read twice, so one RunnerSet create costs six uncached cluster-wide `List` calls where four would do.

Uncached is deliberate on both sides, and not the thing to change: a just-created sibling may not be in the informer cache yet, and admitting a colliding claim through a stale cache is the race both guards exist to prevent.
What is duplicated is the *read*, not the caching decision.

The cost is bounded by how often a RunnerSet is written, which is human-paced, so this is not urgent.
It scales with the number of RunnerSets and gateways in the cluster rather than with write rate, so a large multi-tenant install pays it on every tenant's apply.

Neither package should absorb the other: they answer different questions over overlapping inputs, and `scalesetscope` has a second consumer in the reconciler (Q849) that `agentidentity` does not.
A shared read the two inventories are both derived from, resolved once per admission request, is the shape.
