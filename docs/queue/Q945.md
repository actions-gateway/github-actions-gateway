# Nothing records that make's database format differs by make version

A target-specific variable prints as a comment under the GNU make 3.81 macOS ships, and in rule position, `target: VAR := value`, under the 4.x CI runs.
A gate parsing `make -p` therefore reads `TOOL_PKG`, `:=` and a package path as prerequisites on CI alone, so `make check` is correctly green locally over a database that cannot contain the defect.
Measured on [#1671](https://github.com/actions-gateway/github-actions-gateway/pull/1671), run 32275796483: 24 failures in CI against a suite green on the dev box.
`scripts/ci/check-tools.sh` registers make with no version floor and no version probe, and `docs/development/testing.md` names 3.81 only to explain why `make -j` is unused.
[#1673](https://github.com/actions-gateway/github-actions-gateway/pull/1673) has since built the floor mechanism and the rationale list a new floor joins, so this is now a registry row to fill rather than machinery to design.
It already records a different local-vs-CI make divergence, a sub-make writing `Entering directory` onto stdout, so this is the second of a class rather than a one-off.
Record the divergence and set the floor; take the `--database PATH --print-rules` seam in `scripts/ci/check-tool-pins.sh` as the pattern that makes such a gate testable where no one machine runs both makes.
