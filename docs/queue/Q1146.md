# Dogfood gag-ci-e2e workers never receive their job on either lane

**Event:** the next dogfood window runs `gag-ci-e2e` on a worker image built from actions/runner 2.337.0.
If jobs reach a worker, delete this row; if they still sit at `queued`, the runner-version cause below is refuted and this row returns to `ready` with that result recorded.

On 2026-09-29 no job dispatched to `gag-ci-e2e` reached a worker, on the dind overlay or the Kata one, with `agc:v1.8.0-rc.2` deployed.
That same image passed the Kata e2e matrix 3/3 on 2026-09-14 ([release-1.8.md](../plan/release-1.8.md)), so something moved in the fifteen days between, and until it is found no dogfood window can validate anything, the next release candidate included.

**What was seen**, two dispatched runs of `e2e-test.yml` with `-f runner='"gag-ci-e2e"'`: [36598938858](https://github.com/actions-gateway/github-actions-gateway/actions/runs/36598938858) on the dind overlay, [36601766565](https://github.com/actions-gateway/github-actions-gateway/actions/runs/36601766565) on Kata.
Both sat at `e2e / e2e: queued` until cancelled, about 24 and 30 minutes after dispatch.
On the cluster, each worker pod reached `2/2 Running`, the runner logged `√ Connected to GitHub` and `Listening for Jobs`, and nothing followed; the AGC reaped it as `orphaned_running` about five minutes later (`reaper: deregistered worker runner record`, then `reaped worker pod`), and a new pod came up under a new job ID.
Six such pods across the two windows, one per re-offer, three distinct job IDs on the dind run alone.
Each reaped pod first logged a `FailedMount` for its `job-payload` volume, `secret "job-ss-<jobID>-<hash>" not found`, though the secret for the live job ID was present when listed.
Cancelling the run stopped the reaping: the Kata run's last worker was still `2/2 Running` 95 minutes after its cancel, so `e2e-stop.sh` refused to finish (`None of the 1 in-flight pod(s) turned over during the wait`) and held the AGC and three nodes up until that pod was deleted by hand.
The dind sidecar is not involved: `dockerd` 28.5.2 reported `Daemon has completed initialization` in every pod, and the runner never asks it for anything before receiving a job.

**Candidate cause, unverified: the runner is past GitHub's 30-day update window.** Every worker image here ships actions/runner 2.335.1.
GitHub's [runner update policy](https://docs.github.com/en/actions/hosting-your-own-runners/managing-self-hosted-runners/autoscaling-with-self-hosted-runners), read 2026-09-29, says a runner must be updated "within 30 days of a new version being made available" or it is not queued jobs, and nothing in it says the runner is refused a connection.
An `orphaned_running` reap means GitHub sent a JobCompleted for the job while its worker listened, which is what a job GitHub will not queue to that runner would look like from the AGC.

Read literally, the policy is **contradicted** by this repo's own runs, not supported by them.
[v2.336.0](https://github.com/actions/runner/releases/tag/v2.336.0) was published 2026-07-20 (`gh release list --repo actions/runner`), so 2.335.1 was due by 2026-08-19, and `gag-ci-e2e` still passed on 2026-08-26 (run [33018548757](https://github.com/actions-gateway/github-actions-gateway/actions/runs/33018548757)) and on 2026-09-14.
The candidate survives only if GitHub counts the window from the *newest* release, [v2.337.0](https://github.com/actions/runner/releases/tag/v2.337.0), published 2026-08-26, which closes it on 2026-09-25, between the 09-14 pass and the 09-29 failure.
That reading is untested: no dogfood run fell between 08-19 and 08-26 to tell the two apart.

**A second change landed on the same day.** GitHub's minimum-runner-version enforcement went fully live on 2026-09-25 ([v1.6.0 release notes](../releases/v1.6.0.md)), with a registration floor of 2.329.0 that 2.335.1 clears, and the workers did register and connect.
Nothing measured separates the two, and the event above tests only the first.

Neither the `job-payload` race nor GitHub's side of the ScaleSet protocol has been ruled out; they are the next suspects if the event refutes the runner-version candidate.

The pin went stale because `.github/dependabot.yml` watched `cmd/*/Dockerfile` directories that #870 deleted on 2026-07-26 when every image moved into the root `Dockerfile`, so no base-image bump has been proposed since.
The PR that parked this row bumps the product pin and the dogfood runner's `FROM` to 2.337.0 and points Dependabot at the root.

**Running the event** needs two images the parking PR did not publish: `scripts/dogfood/runner-build.sh` pushes `dogfood-runner:2.337.0`, and `scripts/dogfood/e2e-runner/Dockerfile` then builds on it, pushed as a new `dogfood-e2e-runner` tag and re-pinned in both `deploy/dogfood-e2e/overlays/*/kustomization.yaml` and `deploy/dogfood-migrate/resources.yaml`.
That Dockerfile's header names `scripts/dogfood-e2e-runner-build.sh` as its build script, and no such script exists in the tree or its history, so the build is a hand-run `docker buildx build --platform linux/amd64 --push`.
