# A drain's recovery is lost when no reconcile starts inside its window

`RecoverEvictedScaleSetWorkers` lists from the informer cache at the top of a RunnerSet reconcile, so a gracefully deleted worker is only ever judged if a reconcile *begins* in the seconds between the kubelet publishing the terminal phase and removing the object.
When none does, the pod is never seen, the claim patch is never attempted, and the job is silently never re-run: the same outcome [Q809](../development/flake-watch-retired.md)'s `NotFound` arm surfaces, with none of its evidence.

**Measured** on the three [Q549](Q549.md) sightings, from the AGC log each run captured:

| Run | Delete requested | Pod gone | Reconciles completed | AGC lines naming the pod |
|---|---|---|---|---|
| [32933225396](https://github.com/actions-gateway/github-actions-gateway/actions/runs/32933225396) | 05:24:24.95 | 05:24:28.37 | 05:24:21, then 05:24:29 | 0 |
| [33185281929](https://github.com/actions-gateway/github-actions-gateway/actions/runs/33185281929) | 15:33:34.62 | 15:33:41.33 | 15:33:34, then 15:33:39 | 0 |
| [32934571793](https://github.com/actions-gateway/github-actions-gateway/actions/runs/32934571793) | 05:41:27.58 | before 05:41:28.51 | 05:41:27, 05:41:28, 05:41:29 | 2: claimed, then re-ran |

The third row is the control: the same spec on the same day, whose reconcile loop happened to turn over inside the window, recovered the run.
In the first, an 8-second gap between reconcile completions swallows the whole 3.4-second window.
**The second row evidences the outcome, not this mechanism**: three reconciles completed inside its interval, so something other than an empty gap produced its zero, and this row does not claim to know what.

**Why the gap opens is unverified.** The RunnerSet reconciler runs at the controller-runtime default `MaxConcurrentReconciles: 1`, and controller-runtime never reconciles one key concurrently anyway, so any slow reconcile of that set delays the scan behind it.
In these runs that is the scale-set listener bootstrap, which does a DNS lookup and an HTTP POST inside `Reconcile`.
That is a hypothesis read off the timestamps, not a measurement: nothing in the log times a reconcile.

The exposure is not the e2e venue's.
A node drain is exactly when many workers terminate at once and the reconcile loop is busiest, and the design already records that this arm cannot be made restart-safe ([04-operational-flows.md § Detecting a disruption is not the same as claiming it](../design/04-operational-flows.md#detecting-a-disruption-is-not-the-same-as-claiming-it)).
Q844's orphan recovery does not cover it: that path reads the in-flight set the listener persisted, and a worker whose disruption the scan simply missed is still in it only until the listener's own next poll.

Q549 ships the *observability* half: the scan now logs the pods it judged and declined, so a missed window and a regressed discriminator stop being the same silence, and its spec re-stages rather than failing when no verdict was reached.
Neither closes this.
The fix is to stop making the observation depend on winning a race with the reconcile queue: observe the disruption from the worker-pod watch, where the event already carries the pod, rather than from a cached List a reconcile later.
Measure a reconcile's duration first, so the change is aimed at what actually opens the gap.
