# check-path-filters-test read a fixture filter as empty, 1 run in 4

**Event:** `check-path-filters-test.sh` reports a pair as listing no paths, or `could not read` a side, on a fixture that plainly holds them, on `main` or any branch that does not touch the parser or its fixtures. → top of Queue, escalated.

Observed 2026-09-29 09:25 PDT on the Q574 branch, local run of `scripts/ci/check-path-filters-test.sh`.
The `lanes-fail-on-subset` case read `lanes.yml` filter `calico-short` as empty and reported it as a stale entry, although the fixture gives it two patterns and the next case over the same pair passed in the same run.
Three reruns with no code change passed, and so did a later run after the mitigation below; `uptime` read `load averages: 63.59 68.53 56.40` on the 18-core host partway through the reruns, not during the failure.

**Mechanism unverified.** The empty read came back with no stderr, so the parser either exited silently or was killed without a message.
One real hazard sat next to it: every helper in the suite runs inside a command substitution, where `ensure_pathfilters`' built flag never reaches the parent shell, so each call re-linked `.build/pathfilters` and rewrote it in place (same inode, new mtime, measured the same day).
On macOS the kernel caches an executable's code signature per vnode, and an in-place rewrite can get a later exec killed with no output, which would match.
Thirty rebuild-then-exec cycles in a row did not reproduce it, so that remains a hypothesis rather than the cause.

Mitigation, shipped with Q574: the suite builds the parser once before its first case, so no call rewrites the binary.
Separately, `assert_twice_written_agree` now reports a failed read as `could not read` rather than as an empty list, so a recurrence names itself instead of posing as a stale registry entry — the test harness calls assertions under `|| true`, where errexit is off and a failed parse would otherwise read as empty.

Not [Q991](Q991.md)'s mechanism as it stands: that row is suites whose `tmp/` fixture path carries no uniquifier, and this suite's fixture carries `.$$`.
The adjacent hazard is real, though: `.build/pathfilters` is one fixed path every run in a worktree shares, and before the mitigation each run rewrote it.
The failing run was the only one in the worktree at the time, so a second run rewriting the binary under it does not explain this sighting; it is recorded because a recurrence under concurrent runs would read the same way.

Sweep of the idiom: the only other builder of this binary, `scripts/ci/check-gate-needs.sh`, builds it only when `[[ -x "$PATHFILTERS_BIN" ]]` is false, so it never rewrites an existing one and does not share the hazard.
