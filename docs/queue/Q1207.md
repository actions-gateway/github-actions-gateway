# Re-run jobs whose node an admin tainted out-of-service

A running worker on a `NotReady` node that an admin taints `node.kubernetes.io/out-of-service` (Kubernetes non-graceful node shutdown) ends `Failed` with no recovery on either tier, so its job stays failed.
On-prem nodes lost to network failure, kernel panic, power loss or hardware failure reach this shape routinely; Q1179 covers only a graceful kubelet shutdown and a deleted Node object.
Read from source, kubernetes v1.35.2 and `v1.37.0-beta.0-530-g7c2b6c32644` (identical in both): the taint manager stamps `DisruptionTarget=True/DeletionByTaintManager` and deletes gracefully (`pkg/controller/tainteviction/taint_eviction.go:139:		Reason:             "DeletionByTaintManager",`); the kubelet is gone, so pod GC's `gcTerminating` then patches phase `Failed` with no condition of its own and force-deletes (`pkg/controller/podgc/gc_controller.go:343:	return gcc.markFailedAndDeletePodWithCondition(ctx, pod, nil)`).
The container status stays `Running`, because no kubelet wrote a termination record.
`LostToNodeShutdown` accepts only `TerminationByKubelet`/`DeletionByPodGC`, and the deletion arm needs a termination record, so neither fires.
The taint is the admin's confirmation that the node is dead, so re-running carries none of the partition risk of the AGC force-deleting a `NotReady` node's pods on its own, which stays out of scope.
The likely fix is to accept `DeletionByTaintManager` in `LostToNodeShutdown` when the pod is `Failed` and a container is still `Running`, which a live kubelet finishing the same delete never leaves.
A never-started worker in this shape is Q1198's on the classic tier; on the scale-set tier `abandonedAwaitingRecovery` reads as already taking it (source, not run).
