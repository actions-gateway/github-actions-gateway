# A set recreated under one name reads its predecessor's guard records

Q1167 found this and Q1107 carried it until Q1107 narrowed to the cut.

An owner deleted between the `v2.0.0` CRD apply and its `v2.0.0` controller reconciling it leaves its children behind, and [upgrade.md](../operations/upgrade.md#action-required-after-v200-delete-what-an-owner-deleted-during-the-upgrade-left-behind) has the query that finds them.
A `RunnerSet` recreated under the same name then reads what its predecessor left, because `scaleSetGuardStore.Load` and `readRerunLedger` read by name with no owner UID check, so its predecessor's in-flight jobs could read as lost workers.
That is read from the code, not measured.

**The question** is whether either read should check the owner UID.
**Measure:** recreate a set over a guard ConfigMap its predecessor left behind, and read whether a job of the predecessor's is treated as lost.
Worker pods can reach this state outside the upgrade window too: on 2026-11-06, after an upgrade on kind, the workers a `v1.10.0` AGC had created still named their `RunnerSet` at `actions-gateway.com/v2alpha1`, so whether a later owner deletion collects them is unmeasured as well.
