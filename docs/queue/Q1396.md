# privileged-dind's memory limit does not bound a job's containers

On the one node image read, the `privileged-dind` sidecar's 4Gi memory limit does not cap a job's containers, so a job that outgrows it is not killed at 4Gi and the node runs short instead.
Node memory pressure then falls on whatever else is there, which can be another tenant's worker (evicted, or killed by the kernel), and a `ResourceQuota` on the tenant's namespace does not count that memory.

Measured on 2026-11-24 on one node image only, `kindest/node:v1.35.5` (containerd 2.3.1, kubelet 1.35.5): dockerd put the job's containers in `/sys/fs/cgroup/docker`, at the node's cgroup root (a kind node is itself a container, so a GKE host's root is a different one), and a container that allocated 150 MB was charged there while the sidecar's own usage moved by 5 MB. containerd gives a privileged container no private cgroup namespace (`container_create.go`, v2.1.4 source; v2.3.1 is the same there), so dockerd sees the host's cgroup root.
Nothing above the limit was run, so the node pressure is inferred from where the memory is charged.
No GKE or dogfood node was read.

**This is not a new escape.** [Security § 5.3](../design/05-security.md#the-three-profiles) rates the `privileged` profile's escape risk "High — admission imposes no restrictions" and says of a node without a sandbox runtime that "a privileged worker's escape lands on the node"; the operator guide tells a `privileged-dind` deployment to [assume the node is lost](../operations/runner-template-library.md#running-privileged-dind-assume-the-node-is-lost) and to use one pool per tenant.
The difference is that an ordinary job reaches this by accident, with no escape, and one pool per tenant still shares the node among that tenant's own workers.

**Claims this makes wrong, where it holds:**

- The template says "a nested cluster's containers and images live inside this sidecar" and sizes the limit from it; `deploy/dogfood-e2e/README.md` and the [archived rightsizing plan](../plan/archive/dogfood-runner-rightsizing.md#e2e-worker-sizing--measured-then-derived-dind-2026-07-07) say the same of a nested cluster.
- [Template library § Sizing](../operations/runner-template-library.md#sizing) calls the requests and limits measured on "a nested Kubernetes cluster inside the sidecar".
- The [security table](../design/05-security.md)'s resource-exhaustion row says "Rogue workflows cannot exceed the tenant quota".
- Q248 read the sidecar at 2343Mi on dogfood (`kubectl top pod --containers`) and attributed it to the nested cluster.
  The two are not reconciled: on the node image read here a nested container is charged elsewhere, and the dogfood nodes were not read.
- [Resource quota sizing](../operations/resourcequota-sizing.md) counts the sidecar's `limits`, which is right as a quota figure and not a bound on the job's containers.

No page read says outright that the limit caps a job's containers; each says the containers live inside the sidecar, which implies it.

- Read `/proc/<pid>/cgroup` of a job's container on a dogfood node (`E2E_VARIANT=dind`), and the sidecar's metrics while one allocates.
- Where it holds, decide between a `--cgroup-parent` under the sidecar's own cgroup, as `kata-dind`'s entrypoint does by evacuating its root (its step 4), and saying in the template that the limit covers the daemon only.
  The first needs its own probe: [Q1395](Q1395.md) records what a nested kill then does to the sidecar's status.
- Correct the claims listed above to whatever this finds.
