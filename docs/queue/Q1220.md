# Decide what GAG refuses to run for a fork pull request

GAG cannot tell a fork pull request's job from any other today, so it can neither refuse one nor route it to a tighter runner shape.
This is the first of three gaps [the multi-tenant goal](../plan/secure-multi-tenant-oss-ci.md#open-decisions-the-map-surfaced) surfaced, and the untrusted-PR claim waits on it.

**What a fork job can hold is the repository's decision, not GAG's.** Per GitHub's documentation, unmeasured here, a `pull_request` run from a fork gets no repository secrets and a read-only `GITHUB_TOKEN`, while `pull_request_target` runs the base repository's workflow with its secrets.
A workflow that checks out the fork's head under `pull_request_target` hands those secrets to fork code, and no runner-side control undoes that.
The goal doc already accepts this as residual risk; what it has not decided is whether GAG should refuse the shape when it sees it.

**What GAG could see is unmodelled.** The scale-set fixture carries `eventName` and `jobWorkflowRef` (`scaleset/types_test.go:54:"eventName": "push",`), mirroring upstream's `JobMessageBase`, and `JobMessage` in `scaleset/types.go` models neither.
That fixture is hand-written, so whether a live `JobAssigned` carries them is unchecked.
`eventName` would also separate `pull_request` from `pull_request_target` without saying whether the head is a fork.

**Measure:** capture a live `JobAssigned` for a fork `pull_request` run and a `pull_request_target` run against a test repository, and record which fields distinguish the two cases, and whether any names the head repository.
**Ask:** whether refusing a job by event is GAG's job at all, given that a workflow already chooses its runner by label and GitHub's fork-approval setting already gates first-time contributors; and if it is, whether refusal happens at acquisition or as a scheduling error the workflow run shows.
