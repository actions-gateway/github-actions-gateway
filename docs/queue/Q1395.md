# A sidecar reads OOMKilled for a nested container's kill it survived

The shipped `privileged-dind` template does not reach this as measured, because dockerd puts a job's containers outside the sidecar's cgroup ([Q1396](Q1396.md)); `kata-dind` is the shipped template that has the layout (its entrypoint keeps nested containers under the sidecar's cgroup), run here on runc and read from source for Kata.
There, a job that runs a container past its own `docker run -m` limit leaves the sidecar's status reading `OOMKilled` for a container that was never killed, and detection names that as a platform fault.
A container runtime sets the reason while the container still runs, whenever anything in its cgroup subtree is killed for memory, and keeps it for a later exit of any kind.

Measured on 2026-11-24, on a static pod of containerd 2.3.1 and kubelet 1.35.5 (the `kindest/node:v1.35.5` image, no control plane, so the API server's copy of a status was not read), with dockerd's containers in the sidecar's own cgroup:

| What happened | Sidecar status | `faults()` |
|---|---|---|
| A nested container is killed at a 32 MB limit; dockerd runs on; the job ends and the sidecar stops | `OOMKilled`, exit 0 | `container dind OOMKilled` |
| The same, then dockerd is killed by SIGKILL from the node | `OOMKilled`, exit 137, restarted | `container dind OOMKilled` |
| The sidecar's own 256 MB limit is exceeded | `OOMKilled`, exit 137 | `container dind OOMKilled` |
| A nested kill where the nested cgroup is not under the sidecar's (`privileged-dind` as shipped) | `Completed`, exit 0 | none |

`faults()` run over the captured statuses, by a throwaway test that fed them to `snapshotOf`, reports each.
With the limit the amendment applies (`faultsBy`, the completion's time), the first row reports nothing, because the sidecar stops after the job completes.

**How wide a false `PlatformFaultOnFailedJob` is.** It needs that layout, a nested memory kill during a job that then completes `failed`, and one of:

- **The completion handled after the sidecar stopped.** The time-limited check covers only a completion handled before that; a later one reports the finished worker's snapshot with no limit.
  The sidecar stopped 2 s after its runner in the reading, so a few seconds' delay in handling is enough, with no outage.
  In the [2026-11-22 readings](../plan/q555-automatic-recovery-design.md#readings-from-the-dogfood-turn-up-2026-11-22) (M4, on the `ci` set) all four completions of a red step were handled while the pod still ran, one of them just after its runner had terminated, so the margin is real and thin, and no rate is measured.
  A runner that died inverts the order, but its death raises its own fault, so that Event is true and only lists the sidecar beside the cause.
  The status's `finishedAt` has whole seconds, so a sidecar that stops in the second the completion is handled also counts as before it.
  The code path is read, not run; the M4 timings are measured.
- **A sidecar crash during the job.** The sidecar did crash, so the Event is false only in saying it crashed for memory.
  None was found on record ([what Q1316 waits for](Q1316.md)).

The record's `context` carries the misleading `OOMKilled` whenever the amendment or the completion reads the finished worker, so anyone reading it meets this without an Event.

The consequence is bounded: `faults()` and `faultsBy` feed only the `scale-set job failed with a platform fault` log line and the Event, and no retry, budget or flaky count reads them.

On `kata-dind` this is read from source and not run.
In Kata 3.32.0, the version `scripts/dogfood/lib/kata.sh` pins, the agent watches `oom_kill` in the container's `memory.events` (`rustjail/src/cgroups/notifier.rs`), which counts the subtree (kernel `cgroup-v2` documentation), reports the container once, and its shim publishes containerd's `TaskOOM` (`containerd-shim-v2/wait.go`), which CRI turns into `OOMKilled` as it does for runc.
Its entrypoint traps `TERM` and waits, so a normal stop should exit 143 rather than 0 (POSIX `wait`, not run).
A rootless or sysbox builder that nests cgroups is another shape that could.

- The exit code separates the first row (0, or 143 under `kata-dind`) from a real kill (137), and nothing separates the second from one.
  A candidate is to name a sidecar's `OOMKilled` as a fault only with exit 137, and to say in [troubleshooting](../operations/troubleshooting.md#flaky-jobs-and-platform-faults-on-failed-jobs) that a nested kill can cause one.
- That page says `OOMKilled` means the job needs more memory than the worker template gives it, which is wrong for a nested kill, where the job's own `-m` limit was too small.
- The runner container's `OOMKilled` is the out-of-memory class's fact, and a runner that nests cgroups has the same question.
  Read whether one can before touching it.
