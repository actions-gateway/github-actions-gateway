# A seeded GMC that cannot fetch /meta never owns its IP-range ConfigMap

**Event:** `e2e / e2e` fails in the step "Chart uninstall/reinstall check" with `FAIL: actions-gateway-gmc-ip-ranges has no Deployment owner`, or the GMC logs `not adopting the persisted GitHub IP ranges`. → top of Queue, escalated.
Q1119's event (an `UPSTREAM-DIAL-FAILED` banner) does not cover this: that is the suite failing on an empty proxy policy, and this is the step after a green suite failing on the seed's missing owner.

The e2e suite seeds the GMC's `actions-gateway-gmc-ip-ranges` ConfigMap from the job's token (Q1119), and the ConfigMap carries no owner reference.
`IPRangeStore.Save` was the only code that added the owner, and `Save` runs only after a successful `/meta` fetch.
A GMC whose unauthenticated fetch is rate-limited therefore seeded itself, served the seed, and never adopted the ConfigMap, so the check that `helm uninstall` removes it read an ownerless copy.
The GMC now adopts the persisted ConfigMap at startup (`IPRangeStore.AdoptOwner`, called from `wiring.go` after the seed), so the owner no longer waits on a fetch.

## Measured 2026-11-23

Two merge-group `e2e / e2e` jobs evicted [#2381](https://github.com/actions-gateway/github-actions-gateway/pull/2381), a docs change plus one Go comment:

- run 45077525616, job 137378031838, 2026-11-22T22:39:40Z
- run 45085639460, job 137403539638, 2026-11-23T00:09:10Z

Both failed in the "Chart uninstall/reinstall check" step with `FAIL: actions-gateway-gmc-ip-ranges has no Deployment owner`.
In both GMC logs `seeded GitHub IP ranges from the persisted copy` (`cidrs=8467`) is followed by `GitHub meta returned 403: rate limited`.
The same step passed in jobs 137382677538, 137378092061, 137359004712 and 137330204232, so a run whose own fetch succeeded was unaffected.

The cause is read from source at `origin/main` 8a215b698, not reproduced: nothing here spends the runner address's quota on demand.
The unit tests drive `AdoptOwner` and `Save` directly, and deleting the owner write from either turns its test red; no run has shown the seeded GMC adopting under a spent quota.

## What the check now covers

With a seed, the owner can only come from adoption, so the check reads that path and the cleanup by garbage collection after uninstall.
It no longer reads `Save`'s owner write in a seeded run, because adoption has already set it: that write is pinned by `TestIPRangeStore_SaveWritesOwner`, and by the check itself in a run with no seed (a local `make e2e`).
