# Raise the Kubernetes floor to a version CI tests

Both charts declare `kubeVersion: ">=1.30.0-0"`, `migration-from-arc.md` states 1.31 for v2, and `troubleshooting.md` says an AGC on 1.30 cannot sync its `RunnerSet` informer, while `ENVTEST_K8S_VERSION` and the e2e node image are both 1.35.
So the charts promise versions nothing here tests.
`scripts/e2e/validate-cluster.sh:234` passes 1.30 too, and `install.md`'s preflight row and `charts/actions-gateway/README.md:45` state it.

**Why it gates `v2.0.0`:** the charts accept versions the docs rule out and CI does not test, and at `v2.0.0` every tenant is on the API the docs rule 1.30 out for.
1.30 itself has not been run, so that failure is the docs' reading of the field selector's feature state unless this row runs it.

Karl's reason for a higher floor, on 2026-11-04: "1.33 is end of life now".
That date is his statement and is not checked against upstream's schedule here, and the dogfood cluster's version is not read either, so read both before choosing the number.

The status-write refusal that raised the question is not a reason for this row.
On 1.31.0 and 1.32.0 ratcheting misses the status subresource, which the `spec.tracing.endpoint` rule handles itself with `optionalOldSelf`.
Another rule tightened without that clause would meet the same refusal on those versions, and no gate here would see it.

Done when the charts, the preflight, `migration-from-arc.md` and the rest of `docs/operations/` state one floor that CI covers, and `upgrade.md` tells an operator below it what they get.
