# Gate build-runner's own Docker binaries in a blocking trivy leg

The release vulnerability policy ([release.md](../operations/release.md#the-vulnerability-policy)) blocks on fixable HIGH/CRITICAL findings in every component this project chooses, and `build-runner`'s Docker CLI, buildx and compose are chosen here: they are COPY'd from the digest-pinned `docker:<N>-cli` stage of the root `Dockerfile`.
Its trivy leg is report-only because the image is `FROM worker` and inherits the upstream runner base's findings, so findings in the three binaries this project chooses are reported but block nothing, and `check-vuln-policy.sh` cannot see them either.

Measured 2026-11-17 in scheduled run 44106603383: `docker-compose` carried 1 fixable HIGH (`golang.org/x/net` CVE-2026-78661) and `docker-buildx` 3, all in the `build-runner` leg and so all in `cache-runner`.
The `worker` leg reports a `docker-buildx` too, the base's own at the same path, which is why the split has to be by layer rather than by path.

Done when the binaries COPY'd from `docker-cli` are scanned in a leg that blocks (for example a trivy `rootfs` scan of that stage's `/usr/local/bin/docker` and `cli-plugins/`), with a test that it goes red on a known-bad pin.
Separate from Q70, which flips the whole `worker` leg once the upstream base scans clean; this one blocks on the binaries the project pins, whatever the base carries.
