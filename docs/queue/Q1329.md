# Measure what a JIT runner credential permits from inside its own job

A worker's job can read its runner's just-in-time (JIT) config, and what the job can do with it while its own job runs has never been run against GitHub.
The config holds the runner's ID, its OAuth client ID and its RSA private key, mounted from the per-job Secret and passed as the argument to `run.sh --jitconfig` (`cmd/worker/main.go`, `runScaleSet`).

**Read from the code, not measured.** The pod holds no registration token and no App token, so the credential cannot register a second runner.
It belongs to one ephemeral runner in one `RunnerSet`'s scale set, so anything it reaches stays inside that set.
The wrapper's comment on `runScaleSet` asserts it "grants nothing the job it configures does not already run with", and nothing measured backs that.

**Measure,** with the credential-gated scale-set probe against a test repository (testing.md § Credential-gated probe scenarios): while a job runs on a JIT runner, take that runner's credential from inside the job, mint an OAuth token with it, and try `CreateSession` and a message poll for the same runner.
Record whether the broker refuses the second session, and whether a second queued job for the same scale set can be acquired through it.

**Why it matters:** the decision this came out of, Q1221, settled in the plan doc's credential list and deleted with that change, rests on the credential reaching nothing beyond its own job.
If the probe finds it can take another job, a job's code can run inside a second job of the same set, which is a defect for every class rather than a narrowing for an untrusted one, and it goes into the [05-security.md](../design/05-security.md) threat table.
