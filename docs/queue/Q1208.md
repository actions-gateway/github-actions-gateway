# Keep a departing namespace's attribution port open until its jobs end

When a namespace stops being attributed by a pool (its last gateway sets `proxyFailureAttribution: Disabled`, the pool turns `failureAttribution` off, or a grant is withdrawn), the GMC drops that namespace's port from the pool's ingress policy and withdraws its projection on the same reconcile.
New jobs move back to the unattributed port at once, but a worker already running still dials the port it started with, and its new connections are refused for the rest of the job.
The withdrawn-grant case already cuts a consumer off on every port, so the new exposure is the two opt-out cases, where the namespace is still entitled to the pool.

The defect is read from the code (`reconcileAttributionProjections` and `applyAttributionToNetworkPolicy` in `cmd/gmc/internal/controller/egressproxy_attribution.go`), not measured on a cluster.
`docs/operations/tenant-onboarding.md` tells an operator to opt out between runs until this lands.

The pool's roll removes the listener too, since the port map is in its environment, so the fix has to keep both the departed namespace's port in the map and its ingress rule until no worker that could hold the port is left: for example until `maxWorkerLifetime` has passed since the withdrawal, recorded on the pool's Deployment the way the port map is.
While a departed namespace's port is held open it must not be reallocated, or a joiner's failures land in the leaver's partition: the rollout gate that closes that window today (see the [Q1184 plan](../plan/q1184-proxy-failure-attribution.md#phase-2-the-api-and-the-pool)) assumes the leaver is refused on the port at once.
