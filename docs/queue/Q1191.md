# Registry identity types beyond GKE and EKS are unmeasured

**Demand:** an operator asks for the runner-version read to log in with the gateway's own identity to a registry no current type covers: another cloud's, a neocloud's, or an on-premises one.

`ActionsGateway.spec.registryIdentities` is a list of discriminated unions with one type, `GKEWorkloadIdentity`; ECR is [Q1066](Q1066.md).
Other providers have a workload-identity analog, and they are not added because none has been measured as a path to the provider's **container registry**.
The shape exists for this: each joins as a `type` value plus a pointer member under a per-member CEL iff rule, on the `GitHubCredentials` pattern, and the list lets a cloud's method and an on-premises one coexist on one gateway, without reshaping the spec.

What a 2026-10-13 documentation search found, which covers pod access to storage, secrets and IAM rather than image pulls:

- **Alibaba ACK, RRSA** (RAM Roles for Service Accounts): a projected OIDC token exchanged at Alibaba STS for a RAM role, namespaces opted in through `ack-pod-identity-webhook`.
- **Oracle OKE Workload Identity**: IAM policy scoped to cluster, namespace and ServiceAccount, on enhanced clusters only.
  The search found nothing on pulling from Oracle's registry with it.
- **IBM Cloud trusted profiles**: a Kubernetes ServiceAccount registered as a compute resource, whose token is exchanged for an IAM token.
- **CoreWeave CKS**: each cluster is an OIDC issuer that other clouds can trust, so a pod federates outward (CoreWeave documents Google Cloud Storage); CoreWeave also federates inbound to its own object storage.
- **DigitalOcean DOKS**: no pod-level workload identity found; its documented OIDC federation covers Droplets and GitHub Actions.
- **Nebius, Lambda, Crusoe**: one search returned nothing, which is not evidence of absence.

On-premises registries take the same federated shape, from the same search: Red Hat Quay exchanges an OIDC token for a robot token at `/oauth2/federation/robot/token`, JFrog Artifactory maps OIDC claims to a scoped token, and a Harbor-based registry (container-registry.com's federated identity provider) takes the JWT as the Basic password.
The search found no Kubernetes ServiceAccount example for Artifactory, and nothing from the Harbor project's own docs.

Azure's AKS Workload Identity (a projected token exchanged at Entra ID, then at the registry for an ACR token) is the same shape, from memory and unverified.

Two shapes cover all of these, and they decide the egress each type needs:

- **A projected ServiceAccount token exchanged at the provider's token service, or presented to the registry, over 443**, which the AGC's default policy already admits: Alibaba, Oracle, IBM, Azure, AWS IRSA, Quay, Artifactory, Harbor.
  The parameters differ (a role, a client ID, a profile, an audience, the registry hosts), which is what a member carries; an operator-named host has to be in the member, since the token must reach no other host.
- **Federation to another cloud's registry**, where a neocloud with no registry of its own presents its cluster's OIDC token (or a SPIFFE JWT-SVID) to, for example, Google's Workload Identity Federation.
  That type's member names the source and the target exchange, which is why SPIFFE fits the union and fit no enum value.

Closing it is per provider and starts with the measurement GKE got: on a real cluster of that provider, confirm the registry accepts the identity for a manifest read, record the login it expects and the egress it needs, then add the type.
Each type is a dependency question (an SDK or a hand-written exchange) and an identity grant, and needs the operator half of [doc-update-matrix.md](../development/doc-update-matrix.md) in the same PR.
