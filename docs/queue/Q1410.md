# Consider moving the OOM reporter to its own repository

**The OOM reporter answers a question any Kubernetes cluster has, which memory limit ran out when a container was OOM-killed, and nothing in it needs the gateway.** Measured 2026-11-25 on `4cbe33286`: `cmd/oomreporter` is its own Go module, and none of its Go files imports another module of this repository.
The only tie runs the other way: the AGC reads the pod condition the reporter writes, by the `oom.actions-gateway.com/` prefix and the reason words in `cmd/agc/internal/provisioner/oom_reason.go`, which name `cmd/oomreporter/internal/controller/words.go` as their source.

**Why consider it.** A cluster without the gateway would install the reporter on its own, and a repository and chart named for the gateway hide it from them.
It is also likely to change far less often than the gateway, yet every gateway release now builds, scans, signs and publishes its image (`publish.yml`'s matrix and notes loop name `oomreporter` beside the seven gateway images), so it is re-released whenever the gateway is, changed or not.

**What a move costs.** The condition becomes an interface between two repositories, versioned and documented as one, where a change to it is today one PR that both sides' tests read.
The reporter needs its own release pipeline (image build, Trivy scan, signing, SBOM, digests in the notes), its own chart (Q1403's PR 3 adds `charts/oom-reporter` here), its own docs, and its own CI, including the kind e2e lane Q1403's PR 5 adds.
Q1403 gates 2.1 on the reporter, so the 2.1 release would then depend on another repository's release.

**Ask:** keep the reporter here, move it once [Q1403](Q1403.md)'s PRs have landed, or move it later with the condition held stable meanwhile.
The call is the maintainer's, since it creates a repository outside this one.
Whichever is picked, the reporter's own docs should say it runs without the gateway.
