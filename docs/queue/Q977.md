# Rate-limited refusal can transiently report `reason=ceiling`

`Admit` reserves before the scale-up rung refuses (Q717), so inside the reserve-to-release window a concurrent delivery reads an inflated count and is told `ceiling` while the set is really ramp-limited.
It cannot over-admit: `admit` refuses at `reserved >= limit`, so the churn inflates the count only within the ceiling.
It spends no token, costs no throughput, and self-corrects within one call stack.
It concentrates on a small `maxWorkers` with many listeners — a direction, not a threshold: incidence is scheduling-dependent and the same configuration measured anywhere from 0/20 to 20/20 reps across runs on one machine, so any figure here would invite the next reader to re-measure, get the other end of the range, and delete the row as stale.
Deterministic, and the reason not to "fix" it with a `tokens()` peek ahead of the ceiling rung: with both rungs binding the peek reports `[scaleup x5]` where the shipped order reports `[ceiling x5]`, so it trades this rare transient for a persistent mislabel on every delivery while a small set sits at its ceiling with an empty bucket.
Found in review of #1702.
