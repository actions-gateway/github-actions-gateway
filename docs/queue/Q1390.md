# Sizing envtest reads status directly and the pod build reads a cache

`TestV2_RunnerSet_ThroughputCPULimitInjectionIsReported` can get a worker pod built without the sizing profile it waited for, and fail three assertions that follow from it: no `sizing-profile` annotation, a 500m CPU limit (the provisioner's `defaultWorkerCPU`, since the test's template sets no resources) where the injected one is 2, and `SizingProfileOverridden` never True.
Seen once, on 2026-11-23 in a local full `make -C cmd/agc test-integration` at load average 100 on 18 cores; the same test alone passed every repeat straight after at load 60 to 70, and CI has not been searched for it.

The likely mechanism is read from source and not reproduced.
The test waits with `waitForSizingProfileState` on `k8sClient`, which reads the apiserver, then enqueues a job; `runnerSetTarget.Resolve` (`runnerset_target.go`) sizes the pod from `rs.Status.SizingRecommendation` on the manager's cached client.
Under load the cache can still hold the `RunnerSet` from before the status write when the job arrives, and `applySizingProfile` then returns the template untouched.
That would be a test that waits on one reader and asserts on another, not a product defect: a job arriving in that window gets the static template, which the profile's own rule allows.

Settle the mechanism first: hold the manager's `RunnerSet` informer back and see the same three assertions fail.
The fix is then to wait through the reader the pod build uses, and the other profile tests in the file share the wait.
