# Sizing envtest reads status directly and the pod build reads a cache

**Event:** a test in `v2_runnerset_sizing_profile_test.go` fails on a worker pod built from the template's static resources (a missing `sizing-profile` annotation, the template's CPU or memory where a derived value is expected, or `SizingProfileOverridden` never True) after its `waitForSizingProfileState` returned. → top of Queue, escalated.

`TestV2_RunnerSet_ThroughputCPULimitInjectionIsReported` failed once, on 2026-11-23 in a local full `make -C cmd/agc test-integration` at load average 100 on 18 cores, on three assertions: no `sizing-profile` annotation, a 500m CPU limit (the provisioner's `defaultWorkerCPU`) where the injected one is 2, and `SizingProfileOverridden` never True.
CI has not been searched for it.

The tests waited for `status.sizingProfileState` on `k8sClient`, which reads the apiserver, while `runnerSetTarget.Resolve` sizes the pod from `rs.Status.SizingRecommendation` on the manager's cached client.
The same status write sets both fields, so a cache still holding the `RunnerSet` from before it builds the job's pod from the template.
That is a test waiting on one reader and asserting on another, not a product defect: a job arriving in that window gets the static template, which the profile's own rule allows.
`waitForSizingProfileState` now takes the reader, and every call in the file passes the reconciler's cached client.

## Measured 2026-11-26

A temporary cache `Transform` on the manager's `RunnerSet` informer, delaying each new version of a sized set in a `v2-rs-sizing*` namespace by 3s before the cache stored it, reproduced the three assertions on the unfixed tests.
It also failed the Binpack and Throughput tests in the same file on the template's CPU and memory, which the 2026-11-23 run did not show.
The NodeShare test passed under it, since that profile reads only the spec, which the cache holds from the set's creation.
With the wait on the cached client the four tests passed under the same delay in 2 of 2 runs, the hold firing 13 times in each; the unfixed tests failed in 2 of 2.
The control is not committed, and no run has shown the fixed tests under real load.

The pod build's one other status read on the job path, `WorkerCapacityDeclined` in `capacityGateCondition`, is already waited on through the cached client (`waitForCapacityDeclined`).
