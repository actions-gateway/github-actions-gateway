# Choose drain-then-delete or the documented residual for a renamed set

When a set's first label is renamed, or a `RunnerSet` is deleted, the old scale set stays registered at GitHub, and the next tenant admitted onto that name adopts it by exact name, with the jobs still queued on it and, unless the adopting set declares `runnerGroup`, the first tenant's runner group.
[05-security.md](../design/05-security.md#cross-tenant-job-acquisition-via-a-shared-scale-set-name) states it as an open residual, and [security-operations.md](../operations/security-operations.md#retire-a-scale-set-when-its-runner-set-is-renamed-or-deleted) gives the operator step that closes it by hand: drain, then delete the old scale set with the probe's cleanup mode.

**Measured 2026-11-22, Investigation J on github.com** ([readings](../plan/q1344-scaleset-delete.md#the-readings-2026-11-22)): GitHub accepts the delete with a job queued and a runner record live, and removes the record, but the job stays queued, and a scale set re-created under the same name received it on both arms (runs `45054082229` and `45056284852`).
So a delete alone does not protect the queued jobs; only draining does.
A delete after the drain still stops the successor inheriting the runner group and retires the runner records a rename leaves behind.

**The open question is which of two fixes, and it is a security call** ([both laid out](../plan/q1344-scaleset-delete.md#what-the-readings-leave-to-decide)):

- **Drain, then delete, in the AGC.** The old name's listener serves until no job is queued, then deletes the scale set.
  Admission has to keep the old name claimed until the delete lands, because `scalesetscope.Of` builds the inventory from stored `RunnerSet`s and releases a renamed name at once (`cmd/gmc/internal/scalesetscope/scalesetscope.go:187:func Of(`); the listener needs a drain signal and has to outlive a deleted spec.
- **Keep the residual and close the group half by declaration.** The operator step stays, now with the measured reason, and every set binds a runner group through `runnerGroup` or `defaultRunnerGroup` (Q712, shipped).
  No code.

**Ask:** which of the two Karl wants, put to Karl when this row is picked up and before any code.
No choice has been made, and the answer turns on whether the AGC itself has to protect the queued jobs or an operator step is enough.
The AGC route costs a name that admission keeps claimed with no stored `RunnerSet` behind it, for as long as jobs stay queued, and a listener that outlives its spec.
The operator route costs no code, and when the step is skipped the queued jobs go to whoever claims the name.
Under either, a job queued after the delete goes to whoever claims the label next.

**Not the fix: moving an unpinned adoption into the default group.** `resolveRunnerGroup` deliberately leaves an existing scale set where it is, because an operator may have moved it into a narrower group at GitHub, and dragging it into the default group by omission widens that boundary.

**Done when** the choice is made and either the AGC drains and deletes on rename and on `RunnerSet` delete, holding the name at admission until it has, with 05-security.md and the operator step reduced to match, or 05-security.md records the residual as final and the onboarding docs require a runner group for every set.
