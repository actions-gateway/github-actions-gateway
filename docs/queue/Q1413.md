# A container's end trailed its kill by 7.65 s, past the 5 s pairing bound

The controller counts a kill for a container only when the kill is within 5 seconds before to 6 after the container's end; the design calls that bound "a guess, for reading 3 to set".
Outside it the answer is `Unknown`, even for a container whose own cgroup the agent read and named.

**Measured 2026-11-26 on a local kind cluster** (`kindest/node:v1.35.5`, Docker Desktop, host load 45 ten minutes after a reboot), in the oom-reporter lane's `above` case: the agent recorded the kill at 01:22:34.349Z with the hog's container ID read from its cgroup (`"read":true`, `"containers":["a10c37a1…"]`, `groupKills` 1, no counter below the pods risen), and the hog's status gave `OOMKilled` ending at 01:22:42Z.
The kill came 7.65 s before the end, so the controller wrote `Unknown` where the rise alone decides `AbovePods`.
The hog had taken 2 GiB; the same run's container, pod and pods cases passed, and the hog's container took 71 s from `Pulled` to `Started`, so the host was starved throughout.
The agent also logged `fsnotify: queue or buffer overflow` 0.4 s before the kill and `cannot write the report … context deadline exceeded` 2 s after the end; the report did land, with that kill in it.

This is one reading of the bound, and the first past it.
A node out of memory is a node under load, so the case it misses is the one the reporter is for: a wider bound for a container named by its own cgroup, which no other container's kill can claim, may be what reading 3 should set, against the bound's purpose for a container whose cgroup went unread.
Until then the lane's `above` case can fail on a starved host, and the retry for a non-`OOMKilled` end (Q1412) does not cover it.
The duplicate search flags Q1412, which is about a container the runtime does not call `OOMKilled`, not about when the end is recorded.
