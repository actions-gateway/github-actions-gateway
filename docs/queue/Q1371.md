# Per-namespace exemption from RunnerTemplate pod-shape rules

A platform admin can approve one tenant to run privileged worker shapes, but cannot approve one tenant to write them.
Running is per namespace: the `privileged` security profile plus the platform-only `actions-gateway.com/privileged-profile: allowed` label.
Writing is per cluster: the GMC webhook holds every namespaced `RunnerTemplate` to PSS `baseline` and the `restricted` volume types, and the only way off is `allowUncheckedRunnerTemplatePodShape`, which lifts both rules for every tenant at once.
So a trusted tenant that needs its own privileged shape either files a request for the platform to publish a `ClusterRunnerTemplate`, or the platform turns the switch on for everyone and writes its own admission policy to refuse the tenants it did not approve, which the chart comment on that value describes.

The change is an exemption the webhook reads from the template's namespace.
`RunnerTemplateCustomValidator.validate` skips `validateVolumeTypes` and `validateBaselinePodShape` when the namespace carries a platform-only label, and keeps the rules it applies on every profile today: reserved pod fields, the PriorityClass allowlist, no projected API credential, and no scheduler bypass.
The validator does not read the namespace today; the GMC ClusterRole already grants `get/list/watch` on namespaces, and `namespace-psa-guard.yaml` already stops the GMC itself from writing any non-PSA label, so the label stays out of reach of a compromised GMC.

**Open design questions, each to settle in the PR:**

- **Which label.** Reusing `privileged-profile: allowed` needs no new concept, and makes "may run privileged" imply "may write privileged".
  A separate authoring label keeps the two grants apart, so a platform can let a tenant run the shapes it reviewed without letting it write new ones.
  The second matches how the existing grants are split, so it is the default to argue against.
- **Whether the exemption should also lift the volume-type rule.** That rule stops a tenant naming an NFS or iSCSI server the node mounts from, which is a different risk from pod privilege, so it may want its own label or none.
- **What happens when the label is removed.** The webhook re-checks pod shape only when `podTemplate` changes, so a template admitted under the exemption keeps running after the label goes, the same gap the chart comment names for the cluster switch.
  Either the AGC refuses to resolve such a template, or the docs say removal does not revoke.

Done when the exemption is opt-in and off by default, both directions are pinned in envtest (an exempt namespace admits a privileged shape, an unlabelled one still rejects it, and a tenant cannot set the label itself), and [tenant-onboarding.md](../operations/tenant-onboarding.md#starting-from-a-shipped-template), the troubleshooting runbook and `05-security.md` say who can grant it and what it hands the tenant.
