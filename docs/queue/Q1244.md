# Persist and defer retry-class re-runs until the run concludes

Q1183 built the out-of-memory retry class on the disruption arms' path, which re-runs inside the arms' 15-minute window (`defaultEvictionRerunWindow`, `cmd/agc/internal/provisioner/eviction.go`).
That window covers GitHub concluding a runner it lost, about 10 minutes, and not a sibling job that runs longer: `rerun-failed-jobs` answers `403 This workflow is already running` until the whole run concludes, so such a run ends `run_never_concluded` and its raised memory floor is never used by GAG's re-run.
The disruption arms have the same limit today; the class makes it more likely, because a job that outgrows its memory is often one of a long matrix.
[The design's deferred wait](../plan/q555-automatic-recovery-design.md#how-it-waits) is the fix: pending re-runs in the failure ledger's `pending` map keyed by run and job, recording the attempt the job failed in, polled for the run's conclusion on a widening cadence and expired after 24 hours, then released into `handleScaleSetEviction`.
Unmeasured: how often a dogfood run's siblings outlast the window; the `run_never_concluded` count on `actions_gateway_eviction_rerun_failures_total` is the reading once Q1180 keeps those metrics.
The open design question is how a sweeper finds the sets that hold pending entries after a restart, since the abandoned arm's in-memory waiting set holds a `Target` and a ConfigMap does not.
