# Four scripts hand-copy one exponential jittered retry loop

The same retry schedule is written out four times: base delay doubled after each sleep, capped, plus up to half again in jitter.

- `scripts/fetch/download-verified.sh` wraps `curl` for pinned binaries.
- `scripts/fetch/pull-image-with-retry.sh` wraps `docker pull`.
- `scripts/fetch/prepull-manifest-images.sh` wraps the manifest `curl` (added in Q1133).
- `scripts/dogfood/validate-release.sh` has a `gh_retry` function that wraps `gh`.

Measured 2026-10-09: `grep -rln 'RANDOM % (' scripts/` returns exactly those four files.
Each copy carries its own env-var names and defaults, and nothing keeps the schedule's three properties (doubling, jitter, cap) in step across them.
Three have a test asserting the schedule (`download-verified-test.sh`, `pull-image-with-retry-test.sh`, `prepull-manifest-images-test.sh`), so the same assertions are triplicated as well; whether `gh_retry` is pinned is not checked here.

None can call another as it stands: each loop is inlined around its own command rather than exposed as a function that takes one.
`scripts/fetch/retry.sh` is generic but uses linear backoff with no jitter or cap, so it is not the shared form either.

A `scripts/lib/` function that takes the command and the schedule, with one test pinning the schedule, is the likely remedy; it is unmeasured.
How the variables a caller already sets would map onto it is part of the design, since dropping them would change behaviour for anyone tuning them today.
Raised by the independent review of Q1133's PR as a note that does not block it.
