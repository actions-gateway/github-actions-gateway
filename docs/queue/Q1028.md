# A workflow-level CI read cannot tell a skipped job from a passing one

`CLAUDE.md` and [testing.md](../development/testing.md#path-gated-workflows-verify-the-heavy-gates-actually-ran) both say to confirm a path-gated gate actually ran by filtering runs to the head SHA, and `session-worker` supplies `gh run list --commit "$head"` as the command.
That command reports **workflow-run** conclusions, and it cannot answer the question it is cited for.

**Measured 2026-08-28 on [#1787](https://github.com/actions-gateway/github-actions-gateway/pull/1787), head `fad48c715`.** `gh run list --commit` reported `success` for `.github/workflows/unit-test.yml`, `.github/workflows/integration-test.yml`, `.github/workflows/e2e-test.yml`, `e2e (calico)` and `security-scan`.
`gh api repos/:owner/:repo/commits/fad48c715/check-runs?per_page=100` reported, on the same head:

```
skipped  unit-test, integration-test, coverage, e2e, e2e-calico
success  unit-test-gate, integration-test-gate, e2e-gate, e2e-calico-gate,
         security-scan-gate, shellcheck
```

Every heavy job had skipped correctly (the branch changed no Go, so `changes.outputs.code` was false; both e2e lanes are merge-group-only per Q675) and only the `-gate` jobs reported.
There was no `security-scan` job run on that head at all.
A session read the workflow-level green, wrote "unit-test, integration-test, security-scan and both e2e lanes ran and passed, confirmed by `gh run list --commit` rather than by branch" into the PR body, and stated it to the maintainer twice.
An independent review session caught it; no gate could have, since none opens a PR body.

**Why the existing rule does not cover this.** The rule warns that a *skipped* gate reports no check and looks like a pass, so a reader goes looking for a missing entry.
Here nothing is missing: the gate job exists precisely to report green when the heavy job is correctly absent, so at workflow level "ran and passed" and "correctly skipped" are indistinguishable **by construction**, and no amount of care at that level recovers the difference.
`--commit` fixes *which commit*, which is why it reads as the fix; it says nothing about *which job*, which is what the claim needed.
A correct instrument aimed at a narrower question than the claim built on it, which is the shape [verify-claims](../development/testing.md#the-status-you-report-is-a-claim-too) already names and this instance evades.

**What to write.** Replace the `gh run list --commit` recipe in testing.md and `CLAUDE.md` with the job-level read, and say why the workflow-level one cannot substitute:

```bash
gh api "repos/:owner/:repo/commits/${head}/check-runs?per_page=100" \
  --jq '.check_runs[] | "\(.conclusion // .status)\t\(.name)"'
```

Then say what positive evidence looks like when the heavy jobs legitimately skip: name the job that did exercise the change and read its log.
On #1787 that was `shellcheck`, which carries `make scripts-test` (unit-test.yml:375) and whose log held 90 and 48 passing assertion lines from the two new suites.

The same rule belongs in the `session-worker` skill, whose §5 supplies the defective command and whose *What is GitHub-specific* table describes it as listing "CI results **for a revision**" — true, and not the same as results for a job.
That half is a `claude-skills` PR rather than repo work.

**Related.** Three near-misses of one shape landed across two sessions the same day: a probe aimed at state that could not have produced a positive, returning empty, where empty is indistinguishable from a finding.
The other two were a manifest probe taken after an abort path left the fixture empty, and a `check_before` whose two needles could not move relative to each other.
Worth one sentence generalising them wherever this lands: a negative result is evidence only once the instrument has been shown able to go positive.
