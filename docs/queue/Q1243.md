# Mergeability watch reports no merge-queue eviction

`pr-mergeability-watch.py` emits `head_change`, `conflict`, `closed` and `timeout`, and nothing when the merge queue evicts a PR.
An enqueued PR is the case it is armed for, since catching the merge is how a dispatcher learns the PR landed, so an eviction leaves the PR open and CLEAN with nobody told.

Measured on the 2026-10-27 dispatch run: #2190 was enqueued at 17:29Z on 2026-10-30, removed at 17:56Z with reason `failed_checks`, and found 72 minutes later only because a manual snapshot listed the queue without it.
Its watch stayed silent throughout.
A second eviction of the same PR at 19:16Z was also caught by hand.

The eviction is readable from the PR's timeline (`RemovedFromMergeQueueEvent`, with `reason`), so a `dequeued` event can name the reason and the failing run's candidate branch.

**Also in scope: the timeout.** The 21600 s default fits a PR whose CI is running.
A PR handed to the maintainer waits on a human: on the same run, eight such watches timed out over two days and were re-armed by hand about ten times.
`--timeout` already exists, so the fix may be documentation in `parallel-dispatch.md` rather than a new default.

Done: a `dequeued` event with the eviction reason, a test in `pr-mergeability-watch-test.sh` that fails without it, and the timeout guidance settled.
