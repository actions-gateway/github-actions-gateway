# Tighten the e2e NodeShare envelope against a measured allocatable

The e2e tenant's `NodeShare` envelope is pinned at `1500m` with one worker per node, a lower bound chosen to sit under both variants' static runner request because nobody had measured the node's allocatable CPU.
Raising it needs one live reading, less the dind sidecar and Kata's 250m, and nothing is unschedulable meanwhile.

**Revived 2026-10-09: the trigger fired on every release candidate since it was written.** It read "a dogfood turn-up stands an e2e node up", and the e2e matrix that `validate-release.sh` runs on each candidate scales the `e2e` pool up from zero to carry it, twice for `v1.9.0` alone.
Nobody took the reading because the trigger needs someone watching a gate that runs unattended, so the fix is to make the gate take it.

Have the gate's e2e leg record the e2e node's `status.allocatable` in its evidence, then set the envelope from that reading.
The recipe in `deploy/dogfood-e2e/base/resources.yaml:83:  #   kubectl get node -l cloud.google.com/gke-nodepool=gag-e2e-pool \` is stale on two counts, so do not copy it: `scripts/dogfood/e2e-setup.sh:77:	gcloud container node-pools create e2e \` names the pool `e2e`, not `gag-e2e-pool`, and creates it as `n2-standard-8`, not the `c2-standard-8` the comment above the recipe states.
`EXPECTED_NODESHARE_CPU` in `scripts/dogfood/validate-release.sh:164:EXPECTED_NODESHARE_CPU="1500m"` mirrors the envelope on purpose and moves with it.

Ranked beside [Q1048](Q1048.md), the other reading nothing takes in a dogfood window, because the repair is the same for both: the gate takes the reading itself, so the next candidate answers it whether or not anyone is watching.
