# The release gate check reads a gh error body as required contexts

`required_contexts` in `scripts/release/check-gates-green.sh` reads the branch rulesets with `gh api … --jq … 2>/dev/null || true`, and treats empty output as "fall back to the fixed workflow list".
An API error does not give empty output: `gh` prints the error body to stdout, so the body is read as ruleset IDs and then as context names.

Measured 2026-11-26 on gh 2.103.3: `gh api 'repos/actions-gateway/github-actions-gateway/rulesets/999999999' --jq '.rules[]?.type'` exits 1, writes `gh: Not Found (HTTP 404)` to stderr, and writes `{"message":"Not Found",…,"status":"404"}` to stdout, `--jq` notwithstanding.

Reported during the 2026-11-22 dispatch run by a worker session: `make check` failed twice while the shared REST quota was 0, in `check-gates-green-test.sh`'s "every required context resolves to a workflow" case, and passed after the quota reset.
That case calls `required_contexts` and expects every line to name a workflow, so the error body's words come back unmapped.
The quota-0 run itself was not reproduced; the 404 above is the same `gh` path with a different status.

The release pre-flight takes the same branch, so at quota 0 it prints each fragment of the error body as an `UNMAPPED` required check rather than its "the ruleset could not be read" fallback note.
It still exits red, so nothing ships on it, but it names the wrong cause.

The fix is to keep stdout only when `gh` succeeds (`ids="$(gh api … 2>/dev/null)" || ids=""`, and the same for each ruleset read), with a test case that stubs `gh` to exit 1 with a body on stdout and asserts the fallback.
