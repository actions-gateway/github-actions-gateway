# Keep the AGC and egress proxy above every allowlisted worker priority

A worker whose priority class outranks an AGC or egress proxy may be able to evict that pod from a node the worker wants, which the control-plane separation does not cover.
The separation is a required pod anti-affinity that the GMC, AGC and egress proxy pods carry against workers, and the default scheduler enforces it from both sides.
Once a namespaced `RunnerTemplate` can no longer set `nodeName` or another `schedulerName` (Q1347), preemption is the remaining scheduler path past that term.

What the code shows, read 2026-11-12 at `7b7dce5da`: an AGC pod gets a priority class only when `ActionsGateway.spec.scheduling.priorityClassName` sets one (`cmd/gmc/internal/controller/actionsgateway_v2_builder.go:703:	if s.PriorityClassName != "" {`), and an egress proxy only when `EgressProxy.spec.scheduling.priorityClassName` does (`egressProxyPriorityClassName`).
Both run at priority 0 by default.
A worker can carry any class on the platform allowlist (`--allowed-priority-classes`, empty by default), from `podTemplate.spec.priorityClassName` or a `priorityTiers` tier.
The GMC defaults to `system-cluster-critical` (`charts/actions-gateway/values.yaml`), so no worker can preempt it.

**The mechanism is unverified.** It rests on the PR #2319 reviewer's reading of kube-scheduler: a node blocked by an existing pod's required anti-affinity is reported `Unschedulable` rather than `UnschedulableAndUnresolvable`, so preemption may evict that pod to make room.
If it holds, the result is disruption, not co-residence: the controller is evicted before the worker binds, so the worker never runs beside it.
Preemption picks victims on a node regardless of namespace, so the controller it evicts can be another tenant's, not only the worker's own.
It needs the platform to have allowlisted a worker class above 0; with the allowlist empty, every worker runs at 0, and a pod cannot preempt one of equal priority.

**Gates `v2.0.0`** (decided 2026-11-16), because both enforcement steps below are stricter than today, and after the tag a stricter rule waits for `v3`.
The design already says the control-plane pods sit above workers (the `allowedInfraPriorityClasses` comment in `charts/actions-gateway/values.yaml`), but the GMC checks only that the two allowlists share no class name, never their values.

**Approach.**

1. **Measure first:** on kind, allowlist a class above 0, fill a single node with an AGC pod at priority 0, then create a worker pod carrying that class, and record whether the scheduler evicts the AGC.
   The answer goes into the row's closing PR whichever way it comes out; the steps below hold either way, because node-pressure eviction by the kubelet also ranks by priority.
2. **The GMC refuses a misordered allowlist:** it refuses to start, and refuses to apply a `PriorityClassAllowlist` update, when an allowed worker class has a value at or above the lowest control-plane class.
3. **Controllers get a default class:** an AGC or egress proxy whose spec names no priority class gets the platform's default control-plane class instead of 0.
   Applying it whatever the worker allowlist holds keeps an allowlist edit from rolling every controller in the cluster.
4. **The chart ships that default class with `preemptionPolicy: Never`,** so the controllers never evict another workload in a shared cluster, while no lower-priority worker can evict them.

Step 2 can stop an install whose classes are misordered from upgrading, and step 3 rolls every AGC and proxy whose spec names no class, so `upgrade.md` names both.

**Done when** the measurement is recorded, the GMC enforces the order with a test that drives each refusal, the default class reaches an AGC and a proxy that name none, and `security-operations.md § Keep GAG's control plane off worker nodes` states the guarantee.
