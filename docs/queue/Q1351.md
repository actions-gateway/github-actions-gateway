# A worker's priority class may preempt an AGC or proxy off its node

A worker whose priority class outranks an AGC or egress proxy may be able to evict that pod from a node the worker wants, which the control-plane separation does not cover.
The separation is a required pod anti-affinity that the GMC, AGC and egress proxy pods carry against workers, and the default scheduler enforces it from both sides.
Once a namespaced `RunnerTemplate` can no longer set `nodeName` or another `schedulerName` (Q1347), preemption is the remaining scheduler path past that term.

What the code shows, read 2026-11-12 at `7b7dce5da`: an AGC pod gets a priority class only when `ActionsGateway.spec.scheduling.priorityClassName` sets one (`cmd/gmc/internal/controller/actionsgateway_v2_builder.go:703:	if s.PriorityClassName != "" {`), and an egress proxy only when `EgressProxy.spec.scheduling.priorityClassName` does (`egressProxyPriorityClassName`).
Both run at priority 0 by default.
A worker can carry any class on the platform allowlist (`--allowed-priority-classes`, empty by default), from `podTemplate.spec.priorityClassName` or a `priorityTiers` tier.
The GMC defaults to `system-cluster-critical` (`charts/actions-gateway/values.yaml`), so no worker can preempt it.

**The mechanism is unverified.** It rests on the PR #2319 reviewer's reading of kube-scheduler: a node blocked by an existing pod's required anti-affinity is reported `Unschedulable` rather than `UnschedulableAndUnresolvable`, so preemption may evict that pod to make room.
Nobody has run it.
If it holds, the result is disruption, not co-residence: the controller is evicted before the worker binds, so the worker never runs beside it.
It still takes a tenant's own gateway or egress path down, and it needs the platform to have allowlisted a class above 0.

**Measure:** on kind, allowlist a class above 0, fill a single node with an AGC pod at priority 0, then create a worker pod carrying that class, and record whether the scheduler evicts the AGC.
