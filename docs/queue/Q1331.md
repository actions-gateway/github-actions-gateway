# Measure whether a workflow-restricted runner group refuses a fork job

The operator guidance for fork pull requests leans on a GitHub runner group restricted to selected workflows, and nobody has checked that a fork job fails to match one.
A `pull_request` run takes its workflow from the fork's head, so a restriction to `.github/workflows/ci.yml@refs/heads/main` refuses a fork only if GitHub matches the ref the job ran from rather than the file path alone.

GitHub's REST docs for runner groups (read 2026-11-09) describe `restricted_to_workflows` and `selected_workflows` but give no entry format and say nothing about pull requests.
The docs also place custom runner groups on Team plans and above, and `actions-gateway` reads `plan.name: free` (`gh api orgs/actions-gateway`, 2026-11-09), so this needs an organization on a paid plan.
The `gh` token here lacks `admin:org`, so the org's current groups were not read.

**Measure:** in a Team-plan organization, a runner group allowing public repositories and restricted to one workflow at `refs/heads/main`, a scale set registered into it, and a fork pull request whose workflow names that set's label.
Record whether the job is assigned, and what the run page shows if it is not.
**Settles:** the hedge in [security-operations.md](../operations/security-operations.md#fork-pull-requests-choose-their-own-runner-label), either dropped or rewritten to say the restriction does not stop forks, in which case [Q1330](Q1330.md) is the only control on every plan.
