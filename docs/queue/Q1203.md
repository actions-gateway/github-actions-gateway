# GMC IP-range retry drains the unauthenticated GitHub quota it waits on

A GMC that cannot fetch GitHub's IP ranges at startup keeps every proxy pool it manages from reaching GitHub.
Its own retries can then keep that fetch failing indefinitely.

`HTTPGitHubIPRangeFetcher` calls `https://api.github.com/meta` unauthenticated.
GitHub allows 60 such calls an hour per source IP.
On any non-200 response, `reconcileInitial` retries with exponential backoff capped at `defaultMaxBackoff = 30s`.
That is about 120 calls an hour from the leader alone, and it never reads `X-RateLimit-Reset` or `Retry-After`.
So once the IP's quota is spent, the GMC's own retries spend each new hour's 60 calls within about 30 minutes of the reset, and the fetch stays at 403.

The cache starts empty, and `buildProxyNetworkPolicy` adds the GitHub `443` egress rule only when the cache has CIDRs.
Until a fetch succeeds, the proxy's NetworkPolicy permits DNS and nothing else.
Every CONNECT then dials into a dropped SYN, and the proxy answers `502 upstream unavailable` after its 10 s dial timeout.
The AGC's GitHub App token POST rides that tunnel, so the tenant never gets a token and never acquires a job.

**Measured 2026-10-24** on the local kind e2e cluster, during Q1177's live runs.
Three consecutive `E2E_GitHub_EvictedWorkerLatencyAndRerun` runs left the job `queued` for 10 minutes.
In the third, during the queued wait:

- The GMC logged `failed to fetch GitHub IP ranges` with `GitHub meta returned 403` every 30 s.
- `curl -sSI https://api.github.com/meta` from the host read `x-ratelimit-remaining: 0` and `x-ratelimit-used: 60`.
- Its `x-ratelimit-reset` was 28 minutes away.
  The suite's own preflight had already read `x-ratelimit-remaining=0` at 02:55Z, over four hours earlier.
- The tenant's `actions-gateway-proxy` NetworkPolicy had a single egress rule, DNS.
- The proxy logged `upstream dial failed` with `dial tcp 172.182.252.137:443: i/o timeout` on every attempt.
- In the same second, that address answered HTTP 403 in under 100 ms from the host, from the proxy's own node (`docker exec`), and from a pod in `default` on that node.
  The drop is the policy, not the network.

The kind cluster's GMC stayed up between runs (`E2E_SKIP_TEARDOWN=true`), and its 30 s retry alone outruns the 60-an-hour budget, which fits the quota staying at zero for hours.
That it was the only consumer is unverified: nothing else on the host was checked.

**Where it bites in production.** Several GMCs behind one NAT can exhaust the quota together, and so can anything else sharing the egress IP.
After that, a GMC restart leaves every proxy pool with no GitHub egress, and it stays that way while the retry loop keeps the quota spent.
The existing `EgressRulesStale` condition covers a cache that went stale, not one that never filled.

**Q1119 may be this.** Its 2026-09-16 v1 capture shows the same `dial tcp 172.182.252.137:443: i/o timeout` from the proxy.
The runner-host preflight in that same run read `BLOCKED (HTTP 403; x-ratelimit-remaining=0)`.
Whether those CI runs' GMC was failing its `/meta` fetch is unverified; the GMC log is the place to read it on the next occurrence.

Fix shape, unmeasured:

- On a 403 or 429 carrying `X-RateLimit-Remaining: 0`, wait until `X-RateLimit-Reset` (or `Retry-After`) before retrying, rather than every 30 s.
- Persist the last good CIDR set, for example in a ConfigMap the GMC owns, and seed the cache from it at startup, so a restart during a rate-limited window keeps working egress.
- Surface the never-filled case on the gateway's conditions.
  Whether `Ready` reads `True` in this state is unmeasured.
