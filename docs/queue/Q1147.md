# go-work-tidy.sh exits 0 having tidied nothing if workspace_modules fails

`go-work-tidy.sh` reads the go.work members with `done < <(workspace_modules)`, and a process substitution's exit status is lost under `set -euo pipefail`.
So if `go work edit -json` or `jq` fails inside the helper, the loop tidies nothing and the script carries on to exit 0.
`tidy-check` then diffs an untouched tree and reports it tidy, so the gate goes vacuously green.
Measured 2026-09-29 on bash 5 with the repo prologue: a helper that runs `go work edit -json -nosuchflag | jq ...` printed the usage error, the loop ran 0 times, and the script reached its end with `rc=0`.
`nonworkspace_modules` has the same `< <(...)` shape at the end of the script.
Q1067 (PR #1996) replaced a go.work parse that had the same shape, so this is not a regression.
Q1067 was about the dead ordering step and its GNU `realpath` call; this row is about a lost exit status.
A reviewer of that PR raised it as a note.
`go-work-tidy-test.sh` catches it only on the test's own run, where its count assertion needs every module tidied.
A production run has no such check.

Fix: capture each list first (`mods=$(workspace_modules)`), then fail if the workspace list comes back empty.
Measured the same day, the capture form stops the script: the same failing helper exited `rc=2` before the next line ran.
