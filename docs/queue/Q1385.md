# check-runner-window.sh reports a missing feed as an empty one

**A bare `scripts/release/check-runner-window.sh --pinned 2.338.1` exits 2 with `could not read the releases feed: it was empty`, because it was given no feed.** With no `RELEASES_JSON` argument the script reads stdin, so a run with nothing piped in reads zero bytes.
Measured 2026-11-22 at the head of #2386 (found by rev-ci, reproduced by Claude here): `--pinned 2.338.1 </dev/null` exits 2 with that message, and the same command given a saved copy of `gh api repos/actions/runner/releases` as a file exits 1 and prints `3 days remain of the 30-day window` (exit 1 is the stale verdict, not a failure). The script makes no `gh api` call of its own, so the first reading of this row, a fetch that returned no body, was wrong.

**Why it matters.** The message blames the feed, so the caller looks for a broken fetch when the fix is to pass one.
The orchestrator who hit it on 2026-11-22 read it as a failure of the check, and the one instrument that says a pinned runner is about to leave GitHub's 30-day window (a closing window is silent on the cluster) went unread until someone re-ran it with input.

**Done when** the script says what is missing when stdin is empty or a terminal (that no `RELEASES_JSON` was given, and the `gh api repos/actions/runner/releases` invocation that makes one), with a case in `scripts/release/check-runner-window-test.sh` for a zero-byte stdin that asserts the new wording and exit 2.
Whether the script should fetch the feed itself when given none is the design question to settle first; the usage header says it takes a feed, so the minimal fix is the message.
