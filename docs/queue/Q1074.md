# render.sh reports success on an all-empty dashboard render

`render()` checks that Grafana's `/render` call returned HTTP 200 and prints the file size.
Neither reading can tell a populated dashboard from one where every panel says "No data", so the harness exits 0 and writes four PNGs a session then commits.

Measured 2026-09-07 while working Q1061.
An `exporter.py` edit tripped the Q704 counter floor (`ValueError: counter rate 0.004 is below 0.01/s`), so the process died at startup: `__main__` calls `render()` unconditionally before `HTTPServer(...).serve_forever()` and outside any `try`, and `counter_total` raises on `rate < MIN_COUNTER_RATE` alone, with no dependence on `elapsed`.
Confirmed by running the edited file directly, which exited 1 on that line without binding :9100.
That startup crash is the Q704 design working as its docstring says it should.
Prometheus scraped nothing for the whole 660s window, every panel on all four dashboards rendered "No data", and `render.sh` exited 0 and wrote the PNGs.

**Why `kubectl rollout status` still passed is not established, and the row does not need it.** The container carries no `readinessProbe` and no `livenessProbe`, so a pod counts Ready the moment the container is Running, which a process that starts and exits satisfies for a moment.
That fits `render.sh` logging `successfully rolled out`, and it is a hypothesis: a peer session re-applied the shared cluster from its own worktree before the pod state was inspected, so the ReplicaSet sequence this run actually produced was not observed and cannot be recovered.
What is verified is the pair that makes the gap real either way: `rollout status` on a probe-less Deployment is the only liveness gate the harness has, and nothing afterwards checks that a single series exists.
The security PNG was 223,577 bytes against the committed one's 281,994, so size is not a signal either: a dark-theme dashboard of empty panels compresses to the same order as a full one, and `trim_bottom` crops to the last non-background row, which the panel chrome supplies regardless.

What caught it was opening the PNG.
Nothing else in the loop would have: `make dashboard-render-check` compares *whether* the PNG changed against the JSON diff, never what it shows, so a committed empty render satisfies it exactly as a good one does.

**The check belongs before the render, not after it.** A sentinel query against Prometheus once the accumulation window closes fails in seconds with a cause (`actions_gateway_build_info` has no `namespace` label and no rate, so it is present or the scrape is broken), where a post-hoc pixel heuristic on the PNG would be both slower and vaguer.
Worth also failing on a `/metrics` fetch that does not return 200 before the wait starts, which would have caught this instance 11 minutes earlier.

**A sentinel proves the data exists, not that the render is readable**, and the second failure mode is the one nothing here can reach.
A panel populated *wrongly* passes every check in the loop: the Q969 session's own render of this same harness came back with two stacked panels auto-scaling their y-axis to a ~50 floor, truncating the bottom band of a stack whose entire claim is that the total equals a declared ceiling, and with refusal bands at roughly 1% of the acquired series, rendering the panel as one solid blob.
Both are legible only to a human or a vision pass opening the image.
So the sentinel is the cheap floor rather than the answer, and a session that adds one has not been relieved of looking at the PNG.
