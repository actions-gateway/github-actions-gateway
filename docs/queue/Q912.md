# endpoint-parity startup: the inherited-pipe mechanism is not this one

**Event:** recurs on main after the fix. → top of Queue, escalated.

The trigger fired 2026-08-24 under `make check` on an unrelated branch.
Both instances went red in one run: `endpoint-parity-check` at the top level of the fan-out, and `check-endpoint-parity-test` inside `scripts-test`.
The top-level one reported `fakegithub was still running after 30s and never accepted on http://127.0.0.1:56220`.

Two findings, neither resting on what the fake did or did not write.
The recurrence is **after** the pipe-to-file change this row originally credited: `cmd.Stdout = logFile` landed 2026-08-18 in #1627 and the row was filed from that PR's retro, so the child's fds have been a private `*os.File` throughout, and an inherited-pipe write is not this occurrence's mechanism.
And the top-level gate is not under `scripts-test`, so the 85-suite nested fan-out this row blamed was not in play for it either.
What is left is contention past the 30s bound: 45 gates and 90 suites concurrent on one host.
A second worker hit the same failure independently in the same window on a different port (55916 against 56220), with concurrent envtest also running on that host, which is a confound worth recording because it makes starvation more plausible and is unrecoverable once a session ends.

Parked with the diagnosis fixed and the cause still open.
`readyTimeout` was deliberately not raised, because a bound is not a fix, so a recurrence is expected to look the same on the socket and different in the report.
What the timeout branch now carries: when the poll first observed the child's log non-empty, and a best-effort `ps` reading of the child's scheduling state and accumulated CPU time.
Neither settles whether the child was starved, and the row would over-claim if it said so.
Read `state=` first: R is runnable and waiting for CPU, S is blocked on something else, and one sample of it is evidence rather than proof.
The CPU time is a floor: procps-ng 4.0.4 on `ubuntu-latest` prints whole seconds, so a child that burned 200ms and one that burned none both read `00:00:00` (measured 2026-08-27 against `ubuntu:24.04`; macOS `ps` prints hundredths), and the sub-second reading a starvation verdict would need is not available from `ps` there.
A finer Linux figure means `/proc/<pid>/stat` fields 14 and 15, which does not port to darwin; that is the trade to weigh if the next occurrence is still ambiguous.
`childLog`'s `(the fake wrote nothing, so it had not reached its first log line)` was the over-claim that made the first occurrence unanswerable, and it now states the observation alone.
The suite instance yielded only `expected rc=0, got rc=2` because `expect_rc` discarded the checker's output; it now prints it on a status mismatch.

A second sighting 2026-08-27, under local `make check` on a PR branch, so the trigger does not fire and the row stays here.
The soak counts from this date rather than from the fix.
The suite instance went red on port 50347 (`check-endpoint-parity-test`, the "failure names the endpoint and the call site" case); the same suite passed standalone straight afterwards and the whole gate passed on a re-run, and the branch changed neither the checker nor anything it builds.
The reading the timeout branch was built for: `ps` reported the child as `S 0:00.00`, and the poll never observed the log non-empty.
`S` is blocked on something other than CPU, where starvation past the 30s bound predicts `R`, so this sample points away from the cause the row was left with.
The `0:00.00` discriminates nothing on its own, since a child that never got going and one waiting for CPU both burn none, and macOS printing hundredths only bounds it under 10ms.
One sample, on a host running the rest of the fan-out at the time, so it narrows the cause without settling it.

A third sighting 2026-09-03, again under local `make check` on a PR branch, so the trigger still does not fire.
Both instances went red in one run, as on 2026-08-24: the top-level gate on port 56339 and the suite's "shipped tree passes with no arguments" case on port 56585.
Both read `S 0:00.00` with an empty log and the poll never observing it non-empty.
That is three `ps` samples now across the two sightings that carry one, all `S` and none `R`, so the reading keeps pointing away from CPU starvation without any of them settling it.
The branch touched only `mk/gate-lists.mk`, `scripts/ci/gate-list*.sh` and prose, none of which the checker or the fake is built from, and `make endpoint-parity-check` alone passed straight afterwards.
A full `make check` over the same tree twenty minutes earlier was green, taking 298s across the 50-gate fan-out against 164s for the red run.
`uptime` read `load averages: 51.29 57.82 46.32` on an 18-core host, taken after the failure rather than during it, so it bounds the contention loosely and dates nothing.
The suite instance printed the checker's output this time, so the `expect_rc` change is doing its job and the two instances are now comparable.
A second session in the same parallel batch reported the same failure within the same two-hour window, at a load average it read as 72, and also cleared it by re-running the single gate; that reading is theirs rather than one taken here, and their PR ([#1826](https://github.com/actions-gateway/github-actions-gateway/pull/1826)) touches neither this row nor anything the fake is built from.
Two concurrent sightings under a batch that is itself loading the host is the strongest contention evidence the row has, and it still does not separate contention from whatever `S` says the child was blocked on.
