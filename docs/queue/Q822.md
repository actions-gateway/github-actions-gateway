# Three unrelated suites fail under concurrent load and pass on rerun

Measured 2026-08-12 under 8 workers: `provisioner` eviction-window and `controller` 2m timeout failed in one window, all green on rerun.
A third suite failed with them and has since been deleted with the piped-gate hook.

**The fan-out half is settled and the row's scope was wrong.** `run-parallel.sh` launches every spec with `&` into a pid list and then waits, with no cap anywhere in it, and `SCRIPTS_TESTS` holds 97.
So `make scripts-test` starts all 97 at once by construction: a property of the runner, not a sampling result.
No suite in the fan-out takes `serialize_heavy_build`, so a session in its fast gates gets no machine-wide bound while a sibling's heavy phase holds one of two lock slots.
[What that does and does not establish](../development/testing.md#the-fast-gates-fan-out-past-the-heavy-build-semaphore).

Two corrections before this is implemented as written.
The `controller` 2m timeout is covered by the raise to 5m Q823 shipped, which is itself in flake watch pending recurrence, so only `provisioner` still sits under this row.
And nothing here reproduces a suite failing *because of* the fan-out: a property of the runner and a failure traced to it are separate claims, and only the first is in hand.

Capping is a machine-wide throughput decision of the same kind as [Q966](Q966.md) and wants the same hands.
The same runner backs `check` itself at 45 gates, with `scripts-test` nested inside as one of them, plus `docs-gates` at 19 and `queue-gates` at 10, so a cap nests and would cost the largest caller most.

## A sighting at ordinary load, 2026-09-04

`git-merge-script-index-test` failed once under local `make check`, case *a one-sided row edit is kept alongside the other side's add*, and passed standalone straight afterwards.
Load average at failure was **32.21** on 18 cores, which is an ordinary working figure on this machine rather than a contention peak.
A PR branch, so no trigger fires.

**The load is the finding, not the failure.** This row's premise is that suites fail *under concurrent load*, and 32 is what this box sits at with a few sessions running.
So the sighting is evidence against the premise as stated: either the threshold is far lower than the row assumes, or load average is the wrong axis.
[Q1031](Q1031.md) reaches the same conclusion from the other end, with a sighting that failed at roughly 15 to 19 and then passed at 20.39 on the same tree.
Two rows now carry a reading where the passing run was the more loaded one.

**The fan-out counts in this row have all moved**, and they size its closing argument about what a cap would cost.
Measured 2026-09-04 from `mk/gate-lists.mk`: `SCRIPTS_TESTS` is **117**, not 97; `CHECK_FAST_GATES` is **51**, not 45; `DOCS_GATES` is **23**, not 19; `QUEUE_GATES` is **11**, not 10.
The fan-out is about a fifth wider than the row describes, so the nesting cost it weighs is understated rather than wrong.

**The second disjunct is the live one, and [Q1031](Q1031.md) now carries the reading that settles it.** Three failure/re-run pairs there record the load on both sides, and the passing run comes out above, below and level with the failing one.
What separates them is the fan-out itself — a standalone re-run is one suite, the failing run is that suite inside the 117-wide and 51-wide bursts this row measured — so the axis to sweep is concurrent process count, not load average.
That does not change what this row asks for; it means a cap would be evaluated against fan-out width, and that no threshold on load average can stand in for one.
