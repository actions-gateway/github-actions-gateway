# A consumer's unwritable projected Secret stalls a provider's EgressProxy

A granted, opted-in consumer namespace can pre-create a Secret at `proxyAttributionName(<provider-ns>, <proxy>)` that the apiserver will not update, such as an immutable one holding different data.
`applyProjectedSecret` then returns `Invalid`, `reconcileAttribution` fails, and the provider pool's NetworkPolicy, Deployment, Service and every later step never apply.
One consumer can stall a pool every other consumer shares.

**Measured** in the PR #2292 review, at `7b78afc`: a fake client with an interceptor returning `Invalid` on that Secret's Update fails the reconcile with `reconcile failure attribution: project attribution: project client certificate into "team-a": Secret ... is invalid`.
The apiserver half is measured too: envtest on Kubernetes 1.35 returns `Invalid` for a data change to an immutable Secret (`TestV2_EgressProxy_Attribution_ForeignUnblankableSecretDoesNotStallThePool`).
PR #2292 closed the same class on the withdrawal path only (Q1324), where a Secret the GMC cannot blank is now left as it is.

The share ConfigMaps do not have this shape.
`reconcileProxyShares` is the last step of `reconcileResources`, after every child is applied, and it collects a per-namespace failure and carries on to the next consumer (read from source at `b5edaef1b`, not probed).
An unwritable share ConfigMap therefore marks the pool Degraded without stopping its children or other consumers' shares.

**Done when** a consumer-side attribution Secret the GMC cannot write fails only that consumer's projection, surfaced on the pool (an Event or condition naming the namespace), while the pool's own children and every other consumer's projection still reconcile.
A unit case beside `TestEgressProxyReconcile_ForeignProjectionsDoNotStallThePool` pins it.
