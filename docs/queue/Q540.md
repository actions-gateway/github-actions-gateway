# Ship Dragonfly's node client as a supported node-layer recipe

The composed stack is validated on dogfood ([plan §6](../plan/q540-node-layer-p2p.md#6-dogfood-validation)): Dragonfly's node client pulls pod images through a loopback-bound proxy and moves them between Kata nodes, coexists with `kata-deploy`, shares the Q539 scheduler, and leaves a Kata worker's reachable set unchanged.
What remains is shipping it, since the validation ran from a hand-installed chart that was removed afterwards.

- **Manifests.** A node-layer overlay beside `deploy/dragonfly/`: chart 1.8.5's client by digest, `proxy.server.ip: 127.0.0.1`, dfinit with its containerd restart on (GKE's containerd reads `certs.d` only after one), and the additive policy admitting the node subnet to the scheduler.
- **GKE's Docker Hub mirror.** dfinit's rewrite drops the `mirror.gcr.io` endpoint GKE configures for docker.io; decide whether to keep docker.io out of dfinit's registries or accept Docker Hub as the source.
- **Operator docs.** The recipe in `docs/operations/p2p-image-distribution.md`, including that the restart is required on GKE.
- **Release gate.** Whether the Dragonfly leg installs the node layer too, which would also give the composed stack a full e2e run; none ran during validation.

Not tested in validation: UDP 4006, and more than one fresh-node startup order between dfinit and `kata-deploy`.
