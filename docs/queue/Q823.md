# `scalesetlistener` runs closest to the coverage budget, now 5m

**Event:** a package trips the coverage gate's `-timeout` on `main` after the raise to 5m.

Fixed 2026-08-24 by raising the budget 2m to 5m, on a measurement that reframed the row twice.

The swing is not duration, it is scheduling: `go test -timeout` is per-binary wall clock, so a binary that is not scheduled spends the budget doing nothing.
`api/apinames` reported 37.983s and 0.645s across two `cover-check` runs at an identical 98.6% coverage, and that package has no sleep, poll or `TestMain` to block on.
Six timed runs of the named package held CPU inside 1.43x while wall spanned 9.99x.

The row also named one package where 58 were measured: `agc/internal/scalesetlistener` peaked at 81.57s against the same budget, and at a 1.29x swing it sits closer to the wall more often than `controller` does at 3.26x.
Twelve packages were at or above a quarter of the budget.
One budget covers all of them, which is why this stayed one row.

The at-rest baseline this row asked for, taken 2026-08-24 at load 21 to 36 on 18 cores with every binary uncached: `scalesetlistener` 67.834s, `proxy` 45.991s, `controller` 14.467s, 58 packages measured.
So the worst package held only 1.8x headroom under the old 2m even on a quiet machine, which justifies the raise on its own, with no starvation argument needed.
The named package was never the one at risk.
