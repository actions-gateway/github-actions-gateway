# A release note's commit count goes stale on every merge

A release body's "Everything since vX.Y.Z" line asserts a commit count and a `feat`/`fix`/`perf` subject count, and [`check-release-notes.sh`](../../scripts/release/check-release-notes.sh) is deliberately narrow enough not to read them.

Measured across the 1.7.0 cycle, that line was wrong at three separate points: drafted as `61 commits, 27` when `3540b89f1` was the tip, corrected to `65 and 29` at the rc.3 target, and corrected again to `68 and 29` at the tag.
Each correction was right when it was made.

Q1037 closed the five operator-visible surfaces by giving metric names, CLI flags and chart values enumerators in `api-surface-since.sh`, each refusing rather than reporting a silent empty.
This sixth claim was named in that row and deliberately left out, because it is the same defect class with a different fix shape and folding it in would have made neither clean.

**Why an enumerator does not close it.** The other five go stale when the *product* changes.
This one goes stale when **anything** merges, including the pull request carrying the correction, so enumerating it once at draft time cannot be a fix.
Whatever lands here has to run at tag time: either the renderer substitutes the count as it builds the body, or a check refuses a note whose count disagrees with `git rev-list` at the tag being published.

The renderer arm is the more likely one, since it removes the hand-written number rather than policing it, but it changes what an author writes in `docs/releases/vX.Y.Z.md` and that is a convention decision rather than a mechanical one.

## Done when

A published release body cannot carry a commit count that `git rev-list` contradicts at its own tag.

Filed out of Q1037, which measured the three wrong values above.
