# Dashboard preview harness has no lock on its shared kind cluster

`render.sh` keys on a single fixed cluster name (`CLUSTER=gag-obs`) and a single Helm release (`RELEASE=kps`), and nothing stops two sessions entering it at once.
Measured 2026-09-07: two sessions started a render six minutes apart, the second reused the first's cluster and died on `Error: UPGRADE FAILED: another operation (install/upgrade/rollback) is in progress`, having already spent the cluster-create step.

The collision is worse than the wasted run, and the session that fails is not the session that is harmed.
Both runs apply `../grafana-dashboard-*.json` from their **own** worktree into the shared Grafana, and neither notices the other.
Applying is not the race the operator sees, though: the whole 660s accumulation window sits between the apply and the render, so **the harm lands entirely on whichever session applied first**.
It renders the *other* branch's JSON, and gets a PNG that looks plausible and is a different branch's work — the same silent drift `dashboard-render-check` exists to catch (Q868), arriving through the harness rather than around it.
The session that applied last is unaffected and has no way to tell it just corrupted a peer's run.

Measured again the same evening, on the second collision: two sessions were mid-`shot` together, and the cluster's `cm/ag-grafana-dashboard-security` held the title from the branch that had *not* changed it, with zero occurrences of the metric the changing branch had added.
The session about to shoot that dashboard was the one that had applied first.
It killed its run on the strength of that read; nothing in the harness would have told it.

Every dashboard-touching PR must render, so this fires whenever two are in flight, which parallel dispatch makes routine.
Both sessions here hand-rolled the same `pgrep`-for-`render.sh` wait, and the second collision happened *because* of it: the poll fired in the four-minute gap between one render exiting and the same session starting its next.
A wait built on observing the peer's process cannot see an intent to re-enter, which is the argument for a real lock over better etiquette.

Two candidate fixes, and the row does not pick one: a per-session cluster name (`CLUSTER` already defaults through the environment, so deriving it from the session or worktree is small, but each cluster is a full kube-prometheus-stack install and the box runs oversubscribed); or a lock around the shared one, which keeps the single install and makes the second session wait instead of fail.

**Notes:** the harness is a preview tool, so a failure never reaches CI.
It costs a session its render and, in the interleaved case, ships a wrong screenshot past a green gate.
A lock does not subsume Q1074 (unlinked: that row lands on another branch): a locked run can still render an empty exporter, and a series sentinel can still be overwritten by a peer's apply.
