# Scale-set envtest harness reads the guard ConfigMap through the cache

`startRunnerSetReconcilerWithScaleSetClients` sets `p.APIReader` and `EventReader` from `mgr.GetAPIReader()`, each with a comment saying it wires them "exactly as main.go wires it", and leaves `RunnerSetReconciler.APIReader` nil.
`scaleSetGuardStore` falls back to the cached client when that field is unset ([scaleset_guards.go](../../cmd/agc/internal/controller/scaleset_guards.go)), so every envtest read of a scale-set guard ConfigMap goes through the informer cache while production (main.go, which sets `APIReader: mgr.GetAPIReader()` on the reconciler) reads it live.

**Why it matters more since Q1064.** The orphan scan now spends its one per-process claim on the first reading of the in-flight set, empty or not.
Before that, a stale-empty read cost nothing: the claim stayed unspent and the next reconcile retried.
Now a first reading served stale-empty would burn the scan for the life of the process, which is the failure mode `liveScaleSetWorkerPodNames` already argues about its own List: "a cold cache would read as every worker in the set having been disrupted".
Production is unaffected, because the read there is uncached; the exposure is the harness telling us less than it claims to.

**Not currently believed to bite**, and that belief is unmeasured: the Q844 specs build a fresh manager per AGC generation, so the new cache's initial LIST should already carry the seeded ConfigMap, and a cached `Get` for a kind with no informer blocks until that sync.
Read off the harness and controller-runtime's `getInformerForKind` rather than driven.

**The work.** Wire `APIReader: mgr.GetAPIReader()` on the reconciler in that harness and run the AGC envtest suite.
It is not a one-line change to wave through: the field also routes the v1alpha1 `RunnerGroup` adoption probe and `resolveRunnerSetRefs` off the cache, so the suite is the measurement rather than a formality.
If some suite genuinely needs the cached reader, wire the guard store's reader on its own instead and say why in the comment that currently claims main.go parity.
