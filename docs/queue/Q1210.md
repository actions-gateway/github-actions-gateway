# AGC records an Event naming the host when it attributes a policy denial

`ActionsGateway.spec.proxyFailureAttribution`'s description, in `v2`, `v2beta1` and `v2alpha1`, says a policy denial the AGC attributes "is reported as an Event in this namespace naming the blocked host", and nothing emits one: `cmd/agc/internal/proxyattribution` only counts records (no recorder call there, read 2026-10-26 at `4762ad58f`).
Q1184 closed at phase 4 without it, and Q555, Q1181 and Q1183 do not schedule it.
The release candidate's API pre-flight found the gap; the maintainer chose on 2026-10-26 to build the Event for 1.10 rather than soften the description, because rc.1 publishes the CRD manifest and its descriptions as final.

The design already wants it: [05-security.md § Proxy failure attribution](../design/05-security.md#proxy-failure-attribution) says a denial "is worth an Event naming the blocked host", and accepts as a residual that the Event surfaces the host in the job's own namespace.
The [Q555 proxy table](../plan/q555-flaky-job-retry.md#the-egress-proxy-as-a-failure-sensor) has the Event name the host and the allowlist change that fixes it.

Done is a Warning Event per attributed denial, deduplicated so a job hammering one blocked host cannot flood the namespace, with dial failures and discarded records producing none.
The new reason is new API surface, so it gets [api-review.md § Step 2](../development/api-review.md#step-2--ask-these-of-each-addition), a tier-ledger row and a runbook entry.
The descriptions on both `proxyFailureAttribution` and `EgressProxy.spec.failureAttribution`, the operator docs, the security design and the v1.10.0 notes then say what ships.
