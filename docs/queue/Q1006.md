# Nothing executes a workflow `run:` body before it reaches main

`make check` runs targets over the tree, and no target enters a workflow step's shell, so a `run:` body is first executed by the runner on the event that triggers it.
The 11 workflows with no `pull_request` trigger first run their bodies after merge, or at a `v*` tag in `publish.yml`'s case, so the first reader of a defect there is a bot acting on it or a release.
Measured 2026-08-27 by parsing each workflow's `on:` block: a grep of the whole file answers 10, because `release-freeze-watch.yml` names `pull_request` only in a comment explaining why it does not use one.
Neither actionlint nor shellcheck's integration executes it, so a defect in what the script *decides* is invisible to both.

Measured 2026-08-27 on this repo's own release-freeze-watch.yml, which reached review with `if [ "${rc}" -eq 2 ]` where the delegate's crash codes are 2 and above.
Exit codes 7, 126 and 137 each fell through to the report step and opened a `release-freeze` issue retiring a candidate nothing had measured, and the issue could not name the candidate because the report's sed finds no rc string in a crash log.
Green actionlint, green shellcheck, green `make check`, and a full review; the defect was found by hand-driving the step.

The mechanism is cheap and needs no new dependency: read the step's `run:` body out of the YAML through the block-scalar dedent, put stubs for the delegate and `gh` on PATH, drive it under `bash -e -o pipefail` (the shell Actions uses for a `run:` step), and assert on what the stubs were asked to do.
A driver posing rc 0/1/2/7/126/137 against the two steps above took 69 lines, plus a 37-line extractor.
The positive control is the load-bearing half: a case that must still open an issue, so a change silencing every code fails instead of passing.

Separate from [Q856](Q856.md) and [Q943](Q943.md), which both ask whether a gate job is *wired*: reconciled with its `needs`, or registered as required.
Those two catch a correct script that nothing requires; this one catches a required gate whose script decides the wrong thing.

Scope is a judgement call and belongs in the item: covering every `run:` body in 29 workflows is not proportionate.
The steps worth it are the ones that act rather than report, meaning those that open an issue, push, publish, or tag, which is a much smaller set than the workflow count suggests.
