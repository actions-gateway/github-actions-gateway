# RC validation runs the storage sweep and reads storedVersions on dogfood

[release-1.10.md](../plan/release-1.10.md#what-the-candidate-must-show) requires the 1.10 candidate to show every `actions-gateway.com` CustomResourceDefinition (CRD) reading `storedVersions: ["v2"]` after the upgrade, on the dogfood cluster.
Nothing in the validation gate produces that reading.
`scripts/dogfood/validate-release.sh` applies the candidate's signed v2 CRD manifest server-side and asserts the five kinds register, and runs nothing after it that rewrites stored objects: on 2026-10-09 its only mention of `gag-migrate` was a comment, at `scripts/dogfood/validate-release.sh:1508:# v1 is gag-migrate, a migration, not a conversion`.

The sweep exists: Q1086 shipped it as `gag-migrate storage-version`, in the signed `gag-migrate` binaries each release publishes, and proved the prune on envtest.
What is missing is the leg that runs it against the candidate on a cluster that has run 1.x: fetch and verify the candidate's `gag-migrate` binary the way the gate already fetches the CRD manifest, run `storage-version --apply --assume-yes` against the pinned dogfood context, and assert all six CRDs read `["v2"]` with the [check upgrade.md documents](../operations/upgrade.md#before-upgrading-to-v200-every-actions-gatewaycom-crd-stores-only-v2).

Six, not five: `PriorityClassAllowlist` ships in the main chart's `crds/` directory, which Helm skips on upgrade, so the leg also has to apply that CRD before the sweep.
Unverified whether dogfood's setup re-applies it today; if it does not, the sweep refuses with `priorityclassallowlists.actions-gateway.com: storage version is "v2beta1"`, which is the precondition working.

Run the alias check first, since the sweep refuses while any `EgressProxy` still names `CiliumFQDN` or `CalicoFQDN`; dogfood's own tenants were not read for one when this row was filed.
