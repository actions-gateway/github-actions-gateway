# Spot preemption of a running worker may reach no re-run arm

Dogfood's Cloud Logging and audit logs for 2026-09-13 to 2026-10-05 hold 16 `compute.instances.preempted` events on the `workers` Spot pool, every preempted node having hosted a worker pod, against a single "worker pod disrupted; scheduling auto-retry" AGC line (a `deletion` on an already-cancelled run).
Not established: that any worker was still running a job when its node went, so the gap is a lead, not a finding.
The hypothesis is unverified and comes from recall of kubelet behaviour: GKE graceful node shutdown fails the pod with a `Terminated`-style reason and a `DisruptionTarget` of `TerminationByKubelet`, which none of the arms keys on (`eviction` needs `reason: Evicted`, `preemption` needs `PreemptionByScheduler`, `deletion` needs a `deletionTimestamp`), leaving only `vanished` if the pod object is then removed.
This is unrelated to Q501 (relaying a cancel), which the near-duplicate search proposed.
**Measure:** stop a GCE instance under a worker running a long job on dogfood, then read the pod's final status and whether the AGC re-ran the run.
If no arm fires, the fix is a node-shutdown arm, which is also a classified retry for Q555.
