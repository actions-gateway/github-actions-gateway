# Version the attribution bundle Secret instead of updating it in place

An `EgressProxy`'s attribution server bundle (`<ep>-attribution-tls`) is rewritten in place when its namespace set changes, so a pod template from before the change mounts the new contents.
The rollout itself is tracked: the template carries `actions-gateway.com/attribution-ca-sha256`, a new CA rolls the Deployment, and consumer projections wait for `deploymentRolledOut`.
The proxy loads the bundle once at startup (`mtlsConfig` in `cmd/proxy/proxy.go`), so a running pod keeps the cert it started with.

**Read from source 2026-10-26, neither case reproduced.** Two cases still see the new bundle under an old template:

- **Rollback.** `kubectl rollout undo` restores a template whose CA hash names the old bundle, but the Secret it mounts holds the new one, so the pods start with a CA that their hash annotation does not describe and the old port map.
- **A restart mid-rollout.** An old-ReplicaSet pod whose container restarts during the rollout reloads from the same Secret name, so it serves the new bundle with the old `PROXY_ATTRIBUTION_PORTS`.

A content-addressed name (the CA hash as a suffix, with the template referencing that name) makes each template carry the bundle it was built with, which closes both.

**The cost is cleanup, and it decides the shape.** The GMC holds no `delete` on Secrets (`ensureAttributionCerts` blanks a bundle rather than deleting it for that reason), so superseded versions accumulate unless something garbage-collects them.
An owner reference to the `EgressProxy` frees them only when the pool goes; one to the ReplicaSet would follow `revisionHistoryLimit`, but the ReplicaSet does not exist until after the template naming the Secret is applied.
Granting `delete` is a privilege change and goes through `docs/design/05-security.md`; whether a DELETE response returns the stored Secret, as PATCH does, is unmeasured and has to be before that is weighed.

**Measure:** whether a DELETE of a Secret by a ServiceAccount holding only `delete` returns its data, the same raw-request probe that settled PATCH for Q1214; then the version-versus-accept choice is the maintainer's.

**Done when** either the bundle is versioned with a cleanup path that needs no new cluster-wide Secret verb, with an envtest that rolls a namespace in, undoes the rollout, and asserts the restored pods mount the bundle their hash names; or the in-place design is kept and its two gaps are written into `docs/design/` as accepted, with this row deleted.
The metrics TLS bundle is mounted the same way and is the same question.
