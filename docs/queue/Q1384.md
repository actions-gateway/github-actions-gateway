# Derive share and attribution projection names injectively

**Two pools whose namespace and name join to one string, (`a-b`, `c`) and (`a`, `b-c`), still derive one projection name, so the second pool's consumer in a shared namespace gets no projection at all.** Q1323 made that collision fail closed: the GMC leaves the first pool's projection in place and records `ProjectionNameCollision`, and every reader checks the `proxy-namespace` and `proxy-name` keys, so no reference is wired to the wrong pool.
What it did not take is the November audit's primary fix ([finding](../plan/security-audit-2026-11.md#share-and-attribution-projection-names-collide-for-ns-a-b-proxy-c-and-ns-a-proxy-b-c)): make the derived name injective, so the two pools never contend for one object and both references work.

The derivations are `proxyShareConfigMapName` and `proxyAttributionName` in `cmd/gmc/internal/controller/`, and the AGC derives the same names from prefixes in `cmd/agc/internal/controller/runnerset_target.go` and `cmd/agc/internal/proxyattribution/poller.go`.
The audit suggests a short hash of `namespace + "/" + name`, since `/` cannot appear in either field.

The cost is the rename, which is why it was left out of Q1323.
Every existing projection changes name, the GMC has to delete the old-named object in each namespace it keeps, and a GMC writing new names beside an AGC still reading old ones would leave every cross-namespace reference unresolved until the AGC rolls, so the AGC has to read both names for a release before the GMC stops writing the old one.
Read from source, not measured.

**Done when** (`a-b`, `c`) and (`a`, `b-c`) derive distinct names at every site, pinned by a table case in `egressproxy_sharing_test.go`, an upgrade from the old names keeps every cross-namespace reference resolved throughout, and `docs/operations/security-operations.md` names the new form.
