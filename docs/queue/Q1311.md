# v3 API candidates: v2 field shapes only a new version can change

**Decision:** we decide to open a `v3` API version, for these or for any other reason.

Each item below is a `v2` field whose shape we would choose differently today, and none can change inside `v2`: `v2` has been served since 1.9 and stored since 1.10, `v2.0.0` serves nothing else, and a rename or removal there would drop what clusters have stored, with no conversion to carry it ([api-review.md § the cost curve](../development/api-review.md#the-cost-curve)).
None of them is a defect worth a version on its own, which is why this waits for a `v3` opened for something else rather than starting one.
Collected 2026-11-09 from a read of `api/v2` against [api-review.md](../development/api-review.md#design-rules), at `3d07ebd6d`.

**`auditLogging: Off`, on both `ActionsGateway` and `EgressProxy`.** YAML 1.1 reads a bare `Off` as `false`, so an operator who writes it unquoted is rejected for a value they never typed ([why](../development/api-review.md#an-enum-value-yaml-reads-as-a-boolean-rejects-a-value-the-operator-never-typed)).
The same two objects already spell the do-nothing state `Disabled` for `proxyFailureAttribution` and `failureAttribution`, so `v3` would rename the value to match them.
`capacityGate.mode` and `agcAutoscaling.mode` keep `Off`: api-review.md records a reason for each.

**`logLevel: info|debug`, on both kinds.** Every other enum the project defines uses PascalCase values, as Kubernetes convention does, and these two are lowercase.
`tracing.sampler`'s lowercase values stay, because they are OpenTelemetry's own names passed through.
Cosmetic, so take it only if a `v3` is already happening.

**Two `spec.tracing` fields answer one question: whether to use TLS.** Read from the vendored `otlptracegrpc` v1.47.0, not run: `envconfig.go` makes an `http://` or `unix://` endpoint plaintext and every other endpoint TLS, including a scheme-less `collector:4317`, and then applies `OTEL_EXPORTER_OTLP_TRACES_INSECURE` after it, so `insecure: true` turns an `https://` endpoint plaintext.
`caBundleRef`'s admission rule also requires an `https://` prefix, so it refuses a scheme-less endpoint the exporter would verify with that bundle.
`v3` would let one field decide, most simply by dropping `insecure` and reading the scheme.
Loosening the `caBundleRef` rule alone is additive and can land in any minor.

**`priorityTiers` ordering is stated and never checked.** The godoc says tiers "must be in strictly ascending threshold order", and no CEL rule, admission policy or controller check enforces it; an out-of-order tier is unreachable without anything saying so ([api-review.md § list semantics](../development/api-review.md#choose-the-list-semantics-deliberately)).
Adding the rule tightens validation, which breaks a stored out-of-order set on its next write unless the rule passes an unchanged value, as `tracing.endpoint`'s does (Q1283).
With that clause it could land at any major tag rather than waiting for `v3`.

**`RunnerTemplate` and `ClusterRunnerTemplate` declare a status nothing writes.** `api/unconsumed-fields.txt` lists `conditions` and `observedGeneration` as declared for the uniform `v2` status contract (§H.7) and never populated.
`v3` either gives the templates a writer or drops the status.

**Considered and left off.** These reasons do not depend on the version, so a `v3` does not reopen them:
- `EgressProxy`'s flat HPA knobs beside `managedAutoscaling`, closed by Q486 on direction and neighbour consistency ([release-1.3.md § E](../plan/archive/release-1.3.md)).
- `sizing.profile` carrying two axes, closed by Q481 because both missing cells are reachable additively.
- The three `*bool` fields, which api-review.md names as genuinely two-valued.
- The `networkPolicy` name on an `EgressPeer`, already shipped twice with the same meaning.
