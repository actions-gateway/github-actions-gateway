# Scale-set recovery ties a job to the worker minted for it, not a runner

Eviction recovery on the scale-set tier re-runs whatever `actions-gateway.com/run-id` and `actions-gateway.com/repository` say on the evicted pod (Q417), and those are stamped at provision time from the `JobAssigned` the pod was created for.
GitHub gives a scale-set job to whichever of the set's runners asks first, so the pod can be running a different job, possibly from a different run, when it is evicted.
Recovery then re-runs the wrong run's failed jobs and leaves the run that lost its job to fail.

Start-up orphan recovery (Q844) has the same keying from the other side.
`RecoverOrphanedScaleSetWorkers` (`cmd/agc/internal/provisioner/orphaned_scaleset.go`) judges an in-flight job's worker lost when the pod named `scaleSetPodName(set, jobID)` is not listed.
That pod can be gone because its runner finished some other job, while the in-flight job runs on a live worker, which re-runs a run that is still running.
The reverse also holds: the job's real worker can be gone while its namesake is alive, and nothing is recovered.
Found by the reviewer of the Q1151 fix, from source; not observed on a cluster.

**Measured, 2026-09-30 on `gag-dogfood`** (the Q1151 evidence): the pod created for job `7d6b7dca-…` ran `integration-test (agc)` of run [36751338479](https://github.com/actions-gateway/github-actions-gateway/actions/runs/36751338479), per the Actions jobs API's `runner_name`.
Its completion stamp landed at 17:34:27Z, the moment `shellcheck` of run [36751334381](https://github.com/actions-gateway/github-actions-gateway/actions/runs/36751334381) completed, so job `7d6b7dca-…` was most likely `shellcheck` and the pod carried the other run's ID.
That pairing is inferred from timing; nothing recorded the job ID of `shellcheck`.
No eviction was traced through recovery.
The three spot preemptions in the same burst were not checked for which run recovery re-ran, and the mechanism is unverified end to end.

**Where the fix likely goes.** `JobStarted` carries `workflowRunId`, `ownerName` and `repositoryName` (`scaleset/types.go`, `JobMessage`), and since Q1151 the listener already patches the started runner's pod with `actions-gateway.com/started-job-id`.
Stamping the started job's run identity there, and having recovery prefer it, would name the run the runner was actually serving.
Orphan recovery would need the same record the other way round: which live worker, if any, carries `started-job-id` for the in-flight job.
The `observability-metrics.md` sentence calling `run-id` and `repository` "the only record of which workflow run a worker was serving" is wrong for the same reason and changes with the fix.

**Reach.** Any scale-set tenant whose worker is evicted while running a job it was not created for: a spot preemption or a node drain re-runs an unrelated run, and the run that lost the job is not recovered.
Orphan recovery reaches the same tenants after any AGC restart with jobs in flight.
