# Two of the five release-note surfaces have no enumerator

[release.md § Writing the curated notes](../operations/release.md#writing-the-curated-notes) names five surfaces an operator can see and requires each be diffed mechanically between the two tags: CRD fields, metric names, Event reasons, condition reasons, and configuration (chart values, env tunables, CLI flags).
Three of them have a scanner behind them — `api-surface-since.sh` covers CRD fields, condition types and reasons, and Event reasons via `devtools/docs/reasontiers`.
Metric names and configuration have prose instructions and nothing else, so each release re-derives them by hand.

That section's own argument is the case for closing this: the Event reasons and the metrics "had no enumeration at all until they were diffed, and the notes had already been through several reviews".
The Event reasons got `reasontiers` out of that finding.
The metrics were named in the same sentence and did not.

Measured 2026-08-29 drafting the 1.7.0 notes: a hand-rolled CLI-flag query matched the wrong declaration shape and returned zero on both sides of the window.
Two zeros and an empty diff are indistinguishable from a real "nothing changed", and the reading survives to the notes as a claim; a corrected query then found 33 flags on each side.
The metric diff came back genuinely empty for this window, which is only trustworthy because the same query over `v1.5.0..v1.6.0` surfaces two additions, a control the runbook does not ask for and a hand pass will not always run.

Both surfaces are enumerable the way the CRD one is: metric names from the `actions_gateway_*` literals the exporters register, configuration from the flag declarations plus `charts/*/values.yaml` plus the env tunables.
The natural home is a new section in `api-surface-since.sh`, so one command answers the whole checklist and an unenumerable surface reports `COULD NOT ENUMERATE` and blocks the claim, as the Event-reason scanner already does, rather than reporting a silent empty.

**A sixth claim has no enumerator either, and it fails differently.** The notes' "Everything since v1.6.0" line asserts a commit count and a `feat`/`fix`/`perf` subject count, and `check-release-notes.sh` is deliberately narrow enough not to read them.
Measured across the 1.7.0 cycle, that line was wrong at three separate points: drafted as `61 commits, 27` when `3540b89f1` was the tip, corrected to `65 and 29` at the rc.3 target, and corrected again to `68 and 29` at the tag.
Each correction was right when it was made.

The other five surfaces go stale when the *product* changes; this one goes stale when **anything** merges, including the pull request carrying the correction, so enumerating it once is not a fix.
Whatever lands here has to run at tag time rather than at draft time: either the renderer substitutes the count as it builds the body, or a check refuses a note whose count disagrees with `git rev-list` at the tag being published.
Treat it as the same defect class and a different fix shape.
