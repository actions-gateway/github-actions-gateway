# DirectEgress anti-vacuity control fails on calico, negative disqualified

**Top of queue per the [flakes-first rule](../development/maintaining-backlog.md#flake-fixes-go-first).**

`E2E_V2_DirectEgress_MetadataServerBlocked` failed on `main` in [e2e-calico merge_group run 33080749313](https://github.com/actions-gateway/github-actions-gateway/actions/runs/33080749313), 2026-08-27 14:19 UTC, at `cmd/gmc/test/e2e/direct_egress_test.go:276`.
It is the only `e2e-calico` failure on `main` besides [Q549](Q549.md)'s since 2026-08-18.

**The security assertion did not fail — its control did.** Line 276 is the anti-vacuity probe: a workload-labelled pod must reach the same link-local address on `:53`, so that the blocked `:80` below it means something.
The probe returned a non-zero `CURL_RC` and the spec refused the negative, exactly as designed: `workload pod could not reach link-local on :53 — the NodeLocal DNSCache allowance (Q136) is not in effect`.
So this is not a NetworkPolicy enforcement regression, and reading it as one is the mistake the ledger's [refuted calico row](../development/flake-watch-retired.md) already records once.

The failing wait is `runEgressProbe`'s 2-minute poll for the probe pod to terminate (`cmd/gmc/test/e2e/provisioning_test.go:627`), which the log shows still in the first poll of `metadata-linklocal-dns` at 30 s.
Whether the allowance is genuinely absent under calico's DPv2-adjacent enforcement, or the probe pod merely had not run yet under a 6-way parallel suite, is **unmeasured** — settle that before touching either the allowance or the wait, because the two remedies exclude each other.
[Q402](Q402.md) holds the related upstream finding, that Google documents DPv2 as exempt from the extra NodeLocal DNSCache rule while Q229 measured the opposite.
