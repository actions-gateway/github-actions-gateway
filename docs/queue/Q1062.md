# Gauge whether the Q986 attribution pair is on for a gateway

The security dashboard (Q725) keys its egress row on the pool, because nothing scrapable says which consumer opened a tunnel: the proxy metrics carry the pool namespace stamped by the scrape target, and tenant-and-job attribution lives only in the two audit log streams the Q986 join reads.
The row's own constraint, that a consumer-keyed panel show nothing rather than the pool's traffic when the pair is off, is met today by not having a consumer-keyed panel at all.

What a dashboard could key on is whether the pair is on for a given gateway.
The GMC already reads both halves, `EgressProxy.spec.auditLogging` and `ActionsGateway.spec.auditLogging`, when it renders the two deployments, and already exports one condition gauge per gateway (`actions_gateway_egress_unattributed` and its siblings).
A gauge of the same shape, so a dashboard can key a panel on the consumer: `1` when the gateway's AGC has `WorkerAddresses` and the `EgressProxy` it references has `ConnectionsWithSource`, is the evidence the audit persona is missing: which tenants' egress is attributable by job right now, and since when.
A dashboard panel keyed on it reads the pool's traffic under a consumer's name only where the join exists to back the reading, and stays empty otherwise, which is the row's constraint stated as a series.

Out of Q725's scope because it is a GMC metric with its own reconciler and test work, not a dashboard change, and because the half-on case needs a decision: a gateway on a shared pool whose provider turned on `ConnectionsWithSource` for another consumer's sake reads as attributable under this gauge, and whether that is right depends on whether the consumer's own `WorkerAddresses` is what the gauge should require.
