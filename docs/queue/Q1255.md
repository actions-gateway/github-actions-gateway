# Make increase()-based alerts see a lazily created counter's first count

Several alerts in `deploy/monitoring/prometheusrule.yaml` fire on `increase(<counter>[window]) > 0`, among them `ActionsGatewayEvictionRetriesExhausted`, and the counters behind them are created the first time the AGC increments a label set (`WithLabelValues` at the write site, `cmd/agc/internal/provisioner/eviction.go` for that one).
Prometheus computes `increase()` from samples inside the window, so a series whose first scraped sample is already 1 has no earlier sample to rise from, and its first event may read as no increase at all: a set's first exhausted budget would not page.
The retry-class misclassification alert Q1245 adds has the same shape with a five-re-run floor, where five failed re-runs spread over two series could read as about three and hold the alert silent at a 100% failure rate.
This is the independent reviewer's reading of the Q1245 review, unmeasured: no `promtool` is installed here, so no rule test has shown the missed count, and the affected list above is from reading the rule file, not from a run.
Measure first, with a `promtool test rules` case that scrapes a counter appearing at 1, then fix whichever alerts it confirms: initialise each label set at 0 when the AGC learns of it, or rewrite the expression to count a series' appearance.
