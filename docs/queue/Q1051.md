# `fixedCapacity` reports a constant, not the free slots it stands for

`fixedCapacity(n)` returns `n` forever.
A real `CapacityFunc` reports *free* slots, so a saturated set advertises zero; the fake set advertises its original figure no matter how many of its slots are occupied.

That divergence is load-bearing rather than cosmetic, because production code relies on the property it breaks.
`refreshDemand` returns early whenever advertised capacity is above zero ([listener.go](../../cmd/agc/internal/scalesetlistener/listener.go)), and its Q960 rationale is sound: a set with a free slot is delivered a message whenever GitHub has anything to assign, and every delivery carries statistics, so its gauge cannot go stale.
Under `fixedCapacity` that premise is false.
A test can fill its only slot, keep advertising one free, receive no further message, and never refresh, so any wait on a `lastStats`-derived value hangs on a gauge frozen at whatever the last delivery happened to carry.
**`refreshDemand` is correct**; the fake is what diverges.

This was [Q1005](Q1005.md) mode B, and the fix there was to open capacity only after the enqueue loop.
That idiom already existed: `TestListener_StatusReportsServerCountAheadOfProvisioning` enqueues, calls `capVal.set(n)`, and only then waits on `l.Status().AssignedJobs`, which reads `lastStats.TotalAssignedJobs`.
It is a statistics-derived wait that would have been exposed had it opened capacity first, and it is immune because it does not.
So the safe pattern is in the file; `fixedCapacity` is the shortcut past it.

**No second live instance.** Measured as this change lands: `fixedCapacity` appears in no non-test file, and in 16 test files here across 49 sites (50 before this change, since the test fixed here stops using it).
Counting files is too coarse for the trap, which needs one *test* to combine a constant non-zero capacity, a slot it fills, and a wait on a statistics-derived value.
Exactly one test does: [`TestListener_RetiresGuardsOfJobsWhoseMessagesAreGone`](../../cmd/agc/internal/scalesetlistener/guards_q597_test.go), pairing `fixedCapacity(5)` with `setCompleteErr(true)`.
Its waits are all listener-internal (`prov.count()`, `m.completedCount()`, `GuardedJobIDs`, `PendingMessageCount`) rather than statistics-derived, so it cannot reach the trap.
This is a latent trap with a known-good idiom beside it, not a bug with victims.

Options, in preference order: make the helper subtract in-flight work so it models free slots; or rename it to say it is a constant, so the next reader does not read it as capacity; or leave it and rely on the idiom.
The first changes behaviour under every existing caller, so it needs the suite re-run rather than a mechanical edit.
