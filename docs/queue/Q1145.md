# check-release-ladder-test revived-missing flakes under make check

**Event:** `check-release-ladder-test` is reported KILLED by `make scripts-test`, or exits 1 with a shell error from a `write_*` fixture builder, or any of its cases fails again with an empty path in the checker's message.

Sighted once, 2026-09-29, in `make check` on the Q737 branch, whose diff touches neither the checker nor its test:

```text
[check-release-ladder-test] FAIL: revived-missing — a revived item whose row is gone fails: expected rc 1, got 2
[check-release-ladder-test]        release-ladder:  does not exist, so this gate would verify nothing
```

The double space is an empty `--page`: `write_page rm` printed nothing that run, and every other case passed.

**What the mitigation changes.** Every fixture builder ran inside `expect`'s argument list, where bash drops a command substitution's status, so a builder that failed or died became an empty path the suite reported as the checker's rc 2.
They now run in assignments, so errexit ends the suite with the builder's own status: 143 for a SIGTERM, which `run-parallel.sh` reports as KILLED with the signal, and 1 plus bash's own error for a failed write.
A recurrence therefore names its cause instead of reading as a wrong verdict.

**What is measured, 2026-10-09 on `02fb0338b`.**

- A SIGTERM'd `write_page rm` in the old suite reproduces the sighted output exactly, with no shell error line; in the new suite the same injection exits 143.
- Deleting the fixture directory before that case also yields the empty path in the old suite, but bash prints `No such file or directory` first.
  The Q737 log's lines between the `reparked` result and the FAIL carry no such line (read from that session's transcript; the log file itself is gone), so deletion is not what happened.
- 120 copies of the suite run 40 at a time, at load average 75, all passed: load alone does not reproduce it.

**Not measured:** what killed the builder, if that is what happened.
The Q737 session ran one `make check` and stopped nothing; its only concurrent work in that worktree was a dogfood `e2e-start` against GKE.
No sibling in `make scripts-test` kills a stale pid: the two `kill -KILL "$PPID"` sites (`release-sentinel-test.sh`, `progress-watch-test.sh`) fire while that parent is blocked in the stub `sleep`. Nor is it [Q991](Q991.md)'s mechanism, suites sharing a fixed fixture path: this suite's path carries `$$`.
