# metrics-server image cache has been dead since the 2026-06-19 tar rename

`metrics-server-images-${METRICSSERVER_VERSION}` restores an entry the pre-pull script cannot use, so every e2e run in both lanes re-fetches the manifest and re-pulls the image.
Bumping the key generation retires it, the same one-token change that Q1125 made for cert-manager.

## Measured 2026-09-24

[#316](https://github.com/actions-gateway/github-actions-gateway/pull/316) wrote the tar as `metrics-server.tar` on 2026-06-19.
[#319](https://github.com/actions-gateway/github-actions-gateway/pull/319) renamed it to `images.tar` hours later, for all three pre-pulled manifests at once, and bumped no cache key.
`METRICSSERVER_VERSION` has not moved since, so the key has not either and the stale entry still hits.

Run [35139093856](https://github.com/actions-gateway/github-actions-gateway/actions/runs/35139093856) shows the full sequence in both lanes:

```
Cache hit for: metrics-server-images-v0.8.1
Cache restored from key: metrics-server-images-v0.8.1
metrics-server images: registry.k8s.io/metrics-server/metrics-server:v0.8.1
v0.8.1: Pulling from metrics-server/metrics-server
```

The restore succeeds at the `actions/cache` layer and the script's hit predicate (`images.tar` and `images.txt` both present) then fails, so it takes the miss branch.

## Scope, and what is not known

cert-manager had the identical defect and Q1125 fixed it as a side effect of needing a new generation anyway.
This row is the same fix on a different key, with nothing else attached: one cold run, then warm.

**Calico is not affected, and the reason rules out any repair but this one.** `gh api repos/actions-gateway/github-actions-gateway/actions/caches`, measured 2026-09-24: `calico-images-v3.31.5` was created 2026-08-28T01:42:48Z, ten weeks after the rename, while `cert-manager-images-v1.20.2` dates from 2026-06-19T16:58:12Z and `metrics-server-images-v0.8.1` from 2026-06-20T06:30:55Z.
No calico key ever moved, so the only way a fresh entry lands under the same string is the old one being gone first: calico's skewed entry was evicted and the current script rewrote it.

That path is closed for these two.
An entry is repaired only by eviction followed by a rewrite, GitHub evicts on non-access, and both dead entries were last accessed at 21:00Z on the day of measurement by every e2e run in both lanes.
They are stuck precisely because they hit.
Calico's lane is per-PR on NetworkPolicy and proxy paths, so it can go quiet long enough to be evicted, and did.
The key bump is therefore the only repair available, not one option among several.

Eviction on inactivity is GitHub's documented policy rather than something measured here, and which eviction took calico's June entry, inactivity or LRU against the repository cache-size limit (264 entries at measurement), is not established and does not change the conclusion.

Raised in independent review of the cert-manager PR, which found the dead entry while checking that its own generation bump was necessary.
