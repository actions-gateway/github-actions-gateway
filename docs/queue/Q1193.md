# Validate a DinD + Dragonfly profile once, job pulls through the mirrors

DinD is the fallback for workloads Kata cannot run yet, GPUs above all: AMD GPUs do not work under Kata today, so a GPU fleet can land on DinD with Dragonfly for its large images.
That pairing runs in production elsewhere with ARC, so it is a profile users will ask about, worth validating once rather than adding to the release gate ([Q1194](Q1194.md)'s validated-once tier).

It has two halves, in different states:

- **The worker pod's own image.** Q540's node client runs per node and does not depend on the runtime, and on dogfood the DinD and Kata tenants share the e2e node pool, so it should already serve the DinD worker image.
  That combination has never run.
- **Images the job pulls inside DinD.** The DinD overlay has no mirror wiring, so its inner `dockerd` pulls from the upstreams directly and never touches Dragonfly.

Decided 2026-10-23: route the inner `dockerd` through the in-cluster mirrors, which already fetch through Dragonfly under `E2E_MIRROR_BACKEND=dragonfly`, by giving the DinD overlay the Kata overlay's `daemon.json` mirror wiring.
Rejected: pointing `dockerd` at the node's `dfdaemon` directly, the usual ARC shape, because it means binding the node proxy to the node address, and that proxy forwards to any host, so every pod on the node would gain an open egress proxy.

Done when the DinD overlay carries the wiring with `make registry-mirror-wiring-check` covering it, one dogfood run with `E2E_VARIANT=dind E2E_MIRROR_BACKEND=dragonfly E2E_DRAGONFLY_NODES=1` is green, and the Dragonfly readings show the mirrors serving the DinD job's pulls and the node client serving its pod image, recorded where Q1194's page can cite them.
`e2e-start.sh` does not reject DinD with the Dragonfly back end today, but nothing has run that combination.
