# GMC child writes strip labels other controllers set

Every child the GMC applies loses any label it did not write itself, on the next reconcile.
`applyManagedChild` and `applyManagedSecret` (the Secret path, added by #2151) both call `obj.SetLabels(desired.Labels)`, which replaces the live label map, so a label another controller or an operator added is dropped.

**Read from source 2026-10-26, not exercised against a cluster.** Both helpers read the object first (controller-runtime v0.25.2 `CreateOrPatch` and `CreateOrUpdate` each open with `c.Get`).
Annotations, finalizers and other owner references survive, because the mutate function never touches them.
Labels do not: under `CreateOrPatch` the merge patch from the read copy turns each dropped key into `null`, and under `CreateOrUpdate` the update carries the replaced map.
So the behaviour predates Q1214's switch to `CreateOrUpdate` for Secrets and is identical on both paths.
The foreign label is itself the difference between the read copy and the mutated one, so the helpers' no-op check never skips it: any reconcile of the owner strips it.
Whether anything in a real cluster labels a GMC child today is unmeasured.

**Done when** both helpers merge the desired labels over the live ones, so a key the GMC owns is set and every other key is left alone, with a unit test that seeds a foreign label on the live object, reconciles, and asserts the foreign label survives.
Removing a label the GMC used to set is the case a plain merge cannot express; decide whether any child has ever dropped one before choosing merge over a tracked owned-key set.
