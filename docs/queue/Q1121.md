# No instrument answers whether the merge queue will conflict

`git merge-tree` is the command a session reaches for, and in this repo it answers a different question than the one being asked.

## The trap, and why it reads as reassurance

Four paths are routed to merge drivers by `.gitattributes`, measured 2026-09-16: `scripts/README.md`, `mk/gate-lists.mk`, `docs/plan/README.md` and `docs/roadmap.md`.
`git merge-tree --write-tree` consults `.gitattributes`, so in a clone that has run `make merge-driver` it returns the **driver's** resolution.
GitHub builds the merge queue's candidate itself and runs no merge drivers, so the queue performs the raw three-way and can reject a branch the local probe called clean.

The failure is silent and its output is the encouraging one, which is what makes it survive a careful read: nothing errors, nothing warns, and the answer is `exit 0`.

## The measurement

**Taken 2026-09-16.** The trap is already written down, at [testing.md § the status you report is a claim too](../development/testing.md#the-status-you-report-is-a-claim-too), in the Q828 entry, which records a `merge-tree` probe exiting 0 for a branch the queue then rejected and notes that the driver announced itself in the output being quoted as clean.

**Two sessions reached for `merge-tree` anyway that afternoon**, both with that doc in their own checkout.
One ran it and reported `exit 0` as evidence a pull request would merge, then withdrew it on being challenged; that half is in this repository's own transcripts.
The second session reported that it avoided the command only by reasoning about drivers being per-clone beforehand, and read the Q828 entry after finding the conflict rather than before — its own account, not something the tree records.

Two independent sessions in one afternoon, both competent, both with the rule available, is the shape that says a prose rung is not holding it.

The conflict under measurement was one row of `scripts/README.md`: an open pull request rewriting the `dependabot-rebase-stale.sh` row while the dispatch-run branch appended two rows directly beneath it.
`git merge-tree --write-tree` exited 0; `git merge-file` on the three blobs exited 1 with two conflict markers, against a control with an unchanged side that exited 0 and produced none.

## Why an instrument and not a gate

Nothing lands in the tree, so a gate has no artifact to inspect and could never fail on what it targets — worse than no gate, because it would read as covered.
What went wrong is an agent reaching for the wrong command, so the rung that fits is a thing to run rather than a mistake to remember not to make.

## Shape

A script under `scripts/ci/` answering *will the merge queue conflict?*, taking two refs and optionally a path list.
It shells `git merge-file` on the three blobs per overlapping path and never `merge-tree`, carries its own positive control so an always-conflicts or always-clean harness is visible, and says in its header why `merge-tree` is wrong, citing Q828.
Scope and name are open; the sketch is a starting point rather than a spec.

Then the doc line points at something to run, and `testing.md`'s Q828 entry gains a *use this instead* rather than only a warning.

## Done when

A session asking whether the queue will conflict has one documented command to run, and it cannot silently answer the driver's question instead.

## Notes

The control is not optional decoration: a raw three-way that exits 1 is equally consistent with a harness that always conflicts, so the instrument is unreadable without a case that must come back clean.

A wrong driver key name reads identically to a driver that is not installed: measured 2026-09-16, `git config --get merge.<name>.driver` exits 1 with empty output for a misspelling and for a driver nobody configured alike.
Read `.gitattributes` for the name and enumerate with `git config --get-regexp '^merge\..*\.driver'` rather than testing a name someone handed you.

Found by the dispatch run of 2026-09-16, which hit it twice in one afternoon.
