# Classic drain of a Pending worker reports failed with no force-cancel

The design table's never-started row claims both tiers recover a drained `Pending` worker that publishes a transient `Failed` with its deletion mark, and on the classic tier nothing does, by source reading on 2026-10-27.
`InformerPodWaiter.onPodEvent` resolves the waiter on that `Failed` before the delete arrives, `terminalPhase` leaves `DeletedBeforeStart` unset (only `onPodDelete` and the poll's `NotFound` set it), and `externallyDeletedBeforeTerminal` rejects a pod with no exit record, so `provision()` reports `TaskResultFailed` with no cause, no force-cancel and no re-run.
`TestInformerPodWaiter_NeverRanDeletionIsNotExternal` pins only that this shape is not read as external; nothing asserts what the classic tier does with it next.
The scale-set tier takes the same shape through `abandonedAwaitingRecovery`.
The same question reaches the AGC's own reap of a bound `Pending` worker on the classic tier: if a real kubelet publishes the transient `Failed` there too, the Q683 force-cancel that the `onPodDelete` path gives a vanished pod is skipped, and the AGC-own exclusion the scale-set predicate carries does not transfer, because on the classic tier the provision goroutine is the only handler.
Measure first whether a reaped bound `Pending` pod publishes that `Failed` (kind iteration), then set `DeletedBeforeStart` on the terminal path for a `Failed` pod with a deletion mark and no container start record.
Q1198 made the same move for a node shutdown.
