# A gateway's defaultProxyRef to another namespace wedges its AGC

An `ActionsGateway` whose `defaultProxyRef` names an `EgressProxy` in another namespace gets an AGC that never starts, although the reconciler checks the provider's consent for exactly that reference (`actionsgateway_v2_controller.go`, the `proxyShareGranted` branch).

Measured on the Calico lane, run 40238996928 (2026-10-25): with the pool `v2-attr-pool/pool` granting `v2-attr-alpha`, and the pool itself rolled out and ready, `alpha-agc` sat in `ContainerCreating` for the full 240 s wait.
The run dumped no pod events, so the mechanism below is read from source, not observed.
`buildAGCDeploymentV2` takes the resolved remote `EgressProxy` and builds the AGC's `HTTPS_PROXY` with `v2ProxyServiceAddr(ag.Namespace, …)`, so it points at `pool-proxy` in the gateway's own namespace, and mounts the TLS Secret `pool-proxy-tls` from that namespace too.
That Secret exists only in the provider's namespace, and a pod whose Secret volume is missing stays in `ContainerCreating`.

The RunnerSet-level reference already does this right: the AGC resolves a remote `proxyRef` through the share ConfigMap the GMC projects into the consumer namespace (`proxy-host`, `proxy-port`, `ca.crt`; `resolveSharedProxy` in `cmd/agc/internal/controller/runnerset_target.go`).
The fix is likely the same for the gateway: build the AGC's proxy address from the projection's host, and mount its `ca.crt` instead of a Secret, failing closed with a condition until the projection exists.

No test shares a pool across namespaces at the gateway level, which is why nothing caught it.
The envtest sharing suites reference the pool from a RunnerSet, and the Q1184 attribution e2e does the same so it can run.
A fix should add the gateway-level case to `cmd/gmc/test/e2e/v2_proxy_attribution_test.go` or beside it.
