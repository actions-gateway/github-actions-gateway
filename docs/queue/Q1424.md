# A sizing profile's derived requests can pass a pod-level request

A template that sets pod-level `spec.resources` can get a pod the API server refuses from a sizing profile, on the request side.
Q1402 capped every limit the profiles and the out-of-memory class derive at the pod's limit, and held the class's Binpack request to the pod's request; the profiles' own requests are still written without reading either.
Read from `applySizingProfile` and `applyNodeShare` (`cmd/agc/internal/controller/runnerset_sizing_profile.go`), and not run:

- **Throughput** sets each container's memory limit no lower than its derived request, so a request above the pod's limit lifts the limit past it: `cmd/agc/internal/controller/runnerset_sizing_profile.go:101:if memLimit.Cmp(memReq) < 0 {`.
- **Binpack and Throughput** derive every container's request from history, and nothing compares their sum with a pod-level request the template sets, which the API server requires to be at or above it (`validatePodResourceConsistency`, Kubernetes v1.35.5, read for Q1402).
- **NodeShare** sets the runner's request to the declared envelope ÷ `workersPerNode` and lifts a lower template limit to it, so a share above the pod's limit refuses the same way.

Where the template sets only pod-level limits, the API server defaults the pod's request to the containers' sum (`defaultPodRequests`, `pkg/apis/core/v1/defaults.go`, v1.35.5, read), so the sum check passes by construction.
That defaulted request must still be at or below the pod's limit, so a derived sum above a pod-level limit is refused too: measured against envtest's Kubernetes 1.35 API server, `Pod "defaulted-above" is invalid: spec.resources.requests: Invalid value: "2816Mi": must be less than or equal to memory limit of 2560Mi` (`TestPodLevelResources_RefuseWhatTheRaiseIsHeldTo`, 2026-11-26).
A `LimitRange` maximum is expected to refuse a derived value the same way, from recall and not read; it is admission-time, so envtest would need the plugin enabled to show it.

The operator sees `WorkerPodCreateFailed` carrying the API server's message, with the profile `Active` in `status.sizingProfileState`.

What closes it is open: cap each request to what is left, which is order-dependent across containers, or fall back to the template's values, as the profiles already do while any container lacks samples, and say so in status.
The second is an API change to `sizingProfileState`'s values ([api-review.md](../development/api-review.md)).

The duplicate search flags Q1402, which closed the limit side and the class's request, and Q1388, which is a raised request no node can hold rather than one the pod's own resources refuse.
