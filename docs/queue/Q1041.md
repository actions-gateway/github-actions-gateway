# A pages deploy can succeed while the site never serves the version

Every stable tag from `v1.6.0` to `v1.10.0` has published nothing to the site while every check the run could make of its own tree was correct.
The deploy step succeeds, `verify-pages-live` exhausts its 300s budget, and a hand-run `workflow_dispatch` of the same content publishes.

| tag | `main` deploy | tag deploy | gap | site served it |
|---|---|---|---|---|
| `v1.5.0` | 2026-08-15T19:17:12Z | 19:19:12Z | 2m00s | unmeasured, the live check did not exist yet |
| `v1.6.0` | 2026-08-26T23:22:15Z | 23:24:13Z | 1m58s | no; 1.5.0 for ~25 min ([website.md](../development/website.md#what-the-publish-job-verifies-and-why-it-takes-two-checks)) |
| `v1.7.0` | 2026-08-30T04:21:18Z | 04:22:28Z | 1m10s | no; `versions.json` ≤ 1.6.0 40 min later |
| `v1.8.0` | 2026-09-14T10:27:39Z | 10:29:10Z | 1m31s | no; `/1.8.0/` 404 at origin 14 min later |
| `v1.9.0` | unmeasured | 2026-10-06 (run 37395739033) | unmeasured | no; the run failed `verify-pages-live` |
| `v1.10.0` | 2026-10-27T01:58:00Z | 02:31:18Z | 33m18s | no; `versions.json` still listed 1.9.0 as `stable` at 02:36 |

**A short gap is common to `v1.5.0` through `v1.8.0`, and `v1.10.0` shows it is not the cause.** A stable tag sits on `main`'s tip, so the merge push and the tag push are the same commit and both trigger `pages`.
The `pages-deploy` concurrency group serialises them on `gh-pages`, and for those four the tag's deploy landed one to two minutes behind `main`'s.
`v1.10.0`'s landed 33 minutes behind it, on a site `main` had finished deploying long before, and still never served.

`v1.8.0` is the clearest reading because the winner is identifiable.
The live `/1.7.0/` page carried `last-modified: 10:28:39`, which is the `main` run's artifact, assembled at 10:28:28, before `mike` wrote 1.8.0 at 10:30:15.
`x-proxy-cache: MISS` and `age: 0` on the 404 rule out an edge cache.
The tag run's own checks were all correct: `mike` pushed 1.8.0 with the `stable` alias, and `verify-pages-artifact.sh` confirmed the upload carried both.

**A same-commit collision is not the mechanism, and the recovery is what refutes it.** Both runs create a Pages deployment whose id is `pages_build_version`, which `actions/deploy-pages` defaults to `github.sha`, so both get the same string.
That is a real observation and it does not explain the failure: the `v1.8.0` republish (run 34834527848) deployed **the same** `09a57c0cc…` build version 13 minutes later and served fine.
So a deployment at that id is not permanently deduped.
The republish was alone, but so was `v1.10.0`'s tag deploy, which failed; its republish (run 40439517751) deployed the same `6465a4562…` build version 7 minutes later and served.
So neither the gap nor solitude separates a deploy that serves from one that does not, and the republish is the one action that has recovered every time.

**This bears on the two candidate fixes, which had no evidence when they were written:**

- Retry the publish once from inside the job when `verify-pages-live` exhausts its budget, then re-verify.
  Now the better-supported one: it reproduces the recovery, which is a solo deploy at the same build version after the first has settled.
- Give the budget an adaptive tail rather than a fixed 300s.
  Weaker than it looked.
  `v1.7.0` was still unserved at 40 minutes and `v1.8.0` at 14, so the publish is not slow-but-working and a longer budget waits for something that is not coming.

A third shape worth pricing: give the tag deploy its own `pages_build_version` so the two are distinguishable, which is cheap and tests the collision reading directly.
Skipping the `main` deploy when a stable tag points at the same commit is worse, because `dev` would then miss the merge.

**Until this is fixed the republish is the release path rather than an exception**, which [release.md](../operations/release.md#the-site-deploy-fails-on-a-stable-tag-and-the-republish-is-a-step) states as a step.

Distinct from [Q1034](Q1034.md), which is `verify-pages-live-test`'s own clock flakiness rather than the publish path.
