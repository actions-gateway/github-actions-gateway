# A pages deploy can succeed while the site never serves the version

`verify-pages-live` failed on the `v1.7.0` tag after its 300s budget, and the artifact was not the problem.
`mike` had written `1.7.0` into `gh-pages` twice from `837f3d230`, and `https://actions-gateway.com/versions.json` still listed only up to `1.6.0` forty minutes later, so this was not propagation lag inside a budget that was merely too short.
The deploy step succeeded and the serving layer did not take it.

**The gate did its job and there is nothing to fix in it.** The gap is what happens next: recovery is a hand-run `workflow_dispatch` with `version`, `alias` and `set_default` retyped from the error text, so a release stalls until a human reads the failure.
Re-dispatched unchanged as run 33293076832, the same content published and `verify-published-docs VERSION=v1.7.0` passed, which is what says the deploy was never the defect.

Two candidate fixes, and the row does not pick between them:

- Retry the publish once from inside the job when `verify-pages-live` exhausts its budget, then re-verify.
  Cheapest, and it matches what the manual recovery does.
- Give the budget an adaptive tail rather than a fixed 300s, so a slow-but-working publish is not reported as a failure at all.
  Riskier: it trades a false red for a longer window in which a genuinely dead publish reads as pending.

**One observed occurrence, and the population is small.** The `pages.yml` run history reachable at 40 runs spans 2026-08-29 10:44Z to 2026-08-30 04:47Z, which is this release cycle and no earlier one, so whether `v1.6.0` hit this is unmeasured.
The three prerelease tag deploys in that window succeeded, but they add no version entry to `versions.json`, so they are not a control for what a stable tag does.
Confirm against a wider window before treating one retry as a proven fix.

Distinct from [Q1034](Q1034.md), which is `verify-pages-live-test`'s own clock flakiness rather than the publish path.
