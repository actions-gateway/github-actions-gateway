# Move existing comment rationale to docs; drop dead backlog IDs

[code-comments.md](../development/code-comments.md) limits a comment to what a later reader of the file needs, and the existing source contradicts it at every turn.
`make comment-provenance-check` holds the lines a branch adds, so the contradiction stops growing; what is already there stays until a change is about it.

`scripts/ci/check-comment-provenance.sh --all --report` lists every comment line the gate would fail if it were added today.
Measured 2026-11-27 at `a79628a59`, over 78,957 comment lines in 1,321 files: 4,913 carry a backlog ID outside `TODO(QNNN):`, 111 a pull request number, 103 a date with no measurement beside it, and 96 the phrase "used to".
Not one comment in the tree uses the `TODO(QNNN):` form.

Two pieces, separable.

**Burning down what exists.** The dead backlog IDs are the mechanical half: an ID cited outside a `TODO` can be dropped where the sentence stands without it.
The long blocks are not mechanical, because most hold real design rationale that has no other copy.
Each needs its content moved to `docs/design/` before the comment shrinks, starting with the longest: `Admit` in `cmd/agc/internal/provisioner/admission.go` (98 lines) and the script headers over 70 lines under `scripts/`.
A sweep per package, in its own PR, keeps each reviewable; the gate then holds every line the sweep rewrites.
One comment to fix on the way: the header of `scripts/docs/check-no-plan-refs-in-code.sh` still recommends citing a Q-ID in a comment.

**A length cap, which the gate does not have.** The page's limits are per kind of comment (two lines for an implementation comment, the contract for a doc comment, ten lines for a file header), so a cap has to know the kind, and outside Go nothing in the syntax says it.
Measured over the 300 commits ending at `a79628a59`, which added 3,648 whole-line comment blocks: of the 116 shell blocks of four lines or more, 32 open a file and 25 sit above a function, and the other 59 sit above a statement, where a comment documenting the case below and one narrating it look the same.
Workflow and manifest YAML is the same, 45 of 65.
A kind-blind ceiling does not rescue it: the page sets no number for a doc comment, and the blocks of 18 lines or more in that window are mostly file headers and package comments.
The ten-line header limit is checkable by position, and 23 of the 34 shell headers added in that window exceed it, so gating it fires on two new scripts in three; whether those headers or the number is wrong is a decision to take with the burn-down's first header rewrites in hand.
A cap is also weaker than it looks under diff scoping, since one line added to a 40-line block is a one-line addition.
What can be built is Go alone: `go/ast` separates a doc comment from one inside a function body, so a two-line cap on added in-body comments is decidable there, as a `devtools/` tool behind the same gate.

Narration wording is gated on "used to" only.
Read over the whole tree, that phrase narrates a change in 79 of the 96 lines the gate matches.
The other candidates describe runtime state too often to gate: "no longer" narrates in 3 of 17 added lines sampled ("the pod no longer exists" is the usual sense), "previously" in 4 of 28, "is now" in about 15 of 24.
Those stay with review.
