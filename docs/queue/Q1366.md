# Take the Dragonfly gate readings concurrently, not one probe at a time

**After the Dragonfly e2e job the gate takes its readings in series, 4m25s on `v2.0.1-rc.1` and 5m03s on `v2.0.0-rc.3`, and two of the probes spend 74 seconds each waiting out a timeout that is the expected answer.** Measured from gate run 44236535751: the mirror battery probe pod took 68s, `worker to seed proxy` 74s, the `CONNECT` probe 5s, `node P2P` 1s, and `worker to node client` 74s.

The probes read different pods and targets, so running them together bounds the step by the slowest one.
**Saving:** about 2.5 minutes per gate (estimate).
**Cost:** falls by the same Actions minutes and system-pool time.
**Risk:** the readings, not the verdict, since none of them gates: concurrent probe pods need distinct names, each keeps its own control, and the readings must still be written to the soak-readings file in a stable order.
The readings must also stay ahead of `e2e-stop.sh`, which scales the seed peer to zero.

**Done when** `dragonfly_readings` runs its independent probes concurrently, each reading's record is unchanged, and the gate's tests cover a probe that fails while another passes.
