# Ship a CI-validated rootless BuildKit template for daemonless builds

The template library has no shape for a job that builds container images without a Docker daemon, so the only shipped way to run `docker build` is one of the two DinD entries.
For a job that only builds images, rootless BuildKit avoids the daemon, the PSA `privileged` namespace both DinD entries need, and Kata's nested-virtualization requirement, which makes it the shape to recommend before either DinD entry wherever it works.
The [template README](../../deploy/templates/README.md#what-may-ship-here) already says so and excludes it for the one reason this row exists to remove: nothing in CI runs it.

**The admissible profile is the unknown, and it decides the shape.** Q1332 measured that PSS `baseline` refuses `seccompProfile: Unconfined` and an unconfined AppArmor profile, which is what upstream rootless BuildKit asks for on many kernels.
So the first step is to run `moby/buildkit:*-rootless` on GAG's e2e nodes under `RuntimeDefault` seccomp, and the result picks the template:

- it builds under `RuntimeDefault`: a `baseline`-admissible entry, which a tenant may also author as a namespaced `RunnerTemplate`;
- it needs a `Localhost` seccomp profile: the template plus a node-installed profile GAG does not install, listed as a cluster prerequisite as the Kata entry lists its own;
- it needs `Unconfined`: a platform-owned `ClusterRunnerTemplate` on the `privileged` profile, which loses most of the reason to ship it over `kata-dind`.

That measurement is also what Q1332 lacks to correct the image-build guide's recommendation, so closing this answers the open half of Q1332.

**Like Q1369, the library gate sets the size.** `scripts/ci/check-template-library.sh` fails an entry no dogfood overlay consumes, so the deliverable includes a dogfood RunnerSet whose job builds and pushes an image through the template on every release candidate, to the in-cluster registry mirror or a throwaway repository.
This row is separate from Q1369: that one adds Kata isolation to a no-daemon job, this one adds image builds to a no-daemon job, and they share only the gate.

**Kaniko is out of scope.** `GoogleContainerTools/kaniko` is archived (`archived: true`, last push 2025-06-03, read 2026-11-18 from the GitHub API), and [in-runner-image-builds.md](../operations/in-runner-image-builds.md) still presents it as Approach 2 without saying so.
Correcting that page belongs with Q1332's edit of the same page.
