# Nothing asserts a path filter covers the inputs its gated jobs read

Every assertion runs pattern → repo: the registry is complete, workspace filters cover `go.work`, patterns pin live paths, duplicated lists agree, globstars expand.
None runs the reverse, so an input a gated job reads and no pattern matches is invisible — the gate then goes green by skipping, which the file's own header calls the most expensive false negative.
Four instances so far, all found by hand: Q881 (a tree, `docs/plan/*.md` against a filter naming two files in it), [Q947](Q947.md) (two scripts a job runs), [Q1004](Q1004.md) (a directory `manifest-validate` lints that its own filter never names), and `mk/gate-lists.mk` below.
The tree case needs a hand-kept script → tree map, so the design decision is how to keep that map from going stale the way the lists it guards do.

**The fourth is the sharpest, because the uncovered input is not something its gates happen to read: it is their whole subject.** [`mk/gate-lists.mk`](../../mk/gate-lists.mk) is named by exactly one path filter in the workflow tree, `manifest-validate.yml`'s `dashboards`.
Neither job whose subject it is names it: `gate-lists` runs `make gate-lists-check` behind doc-links.yml's `docs` filter, and the shellcheck job runs `make scripts-test`, and so `gate-list-test.sh`, behind unit-test.yml's `scripts` filter.
The registry file's own header says every gate- or suite-adding PR appends one entry to it, so the canonical edit to that file is the one that reaches neither gate that reads it.

Measured 2026-09-03 with this repo's own extractor, over every workflow:

```bash
(cd devtools && GOWORK=off go build -o ../.build/pathfilters ./ci/pathfilters)
for w in .github/workflows/*.yml; do
    ./.build/pathfilters filters "$w" | grep -H --label="$w" 'mk/' || true
done
```

That returns `.github/workflows/manifest-validate.yml:dashboards	mk/gate-lists.mk` and nothing else.
That sweep is the control as well as the finding, which is the half worth keeping: the extractor does report the file where a filter names it, so the empty `docs` and `scripts` results are real negatives rather than a query that never matched.
`Makefile`, which both filters do name, does not cover it, because a filter matches changed paths textually and the `include mk/gate-lists.mk` at `Makefile:88` is not a path.

Three independent misses rather than one, so the merge queue does not catch it either. doc-links.yml gates the job on `docs == 'true' || github.event_name == 'push'`: a PR misses on the filter, the queue's candidate misses because a `merge_group` event is not a push and the filter still decides, and the `push:` list for main omits `mk/**` as well.

Found while confirming the heavy gates on [#1829](https://github.com/actions-gateway/github-actions-gateway/pull/1829), itself a `DOCS_GATES` change (Q1040), which reached both jobs only incidentally by also touching `scripts/**`.
