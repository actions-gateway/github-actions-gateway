# Refuse fork pull request jobs by default on every RunnerSet

A fork pull request can rewrite `runs-on` to reach a trusted `RunnerSet`, because a `pull_request` run executes the pull request's merge commit, whose workflow file carries the fork's edits.
GitHub's runner groups cannot stop it: they scope by repository, and the selected-workflows restriction (Enterprise Cloud and Server only) pins ordinary workflows to a branch while a `pull_request` run's ref is `refs/pull/N/merge`, so per GitHub's docs it refuses every pull request rather than only forks.
GitHub's approval setting keys on the contributor rather than the fork: even "all external contributors" exempts organization and repository members, and costs a maintainer's click per run where it applies, so this refusal is the only control that separates a fork's job from the repository's own.
Decided in Q1220 (2026-11-10): **every `RunnerSet` refuses fork jobs unless it explicitly accepts them**, and a set meant for untrusted pull requests (the Kata posture) is the one that accepts.
An opt-in is rejected: with no GitHub-side backstop, it leaves every adopter who never sets the field exposed.
The default is a breaking change for any adopter running fork CI today, so it ships with an upgrade note naming the field that restores acceptance, and is cheapest inside a release that is already breaking.
The decision and the GitHub-side controls it sits beside are in [the goal doc](../plan/secure-multi-tenant-oss-ci.md#open-decisions-the-map-surfaced).

**The job message cannot mark a fork, so the refusal reads the run.** Upstream `JobMessageBase` (actions/scaleset `716908e`, read 2026-11-09) carries `eventName` and `jobWorkflowRef` but no head-repository field, and the live `JobAssigned` captured 2026-07-26 has none ([scaleset-eviction-recovery.md](../plan/scaleset-eviction-recovery.md)).
The AGC already calls `GET /repos/{owner}/{repo}/actions/runs/{run_id}` for eviction recovery (`cmd/agc/internal/provisioner/eviction.go:690:// runConclusion calls GET /repos/{owner}/{repo}/actions/runs/{run_id}`), and decodes the head repository's name into `runState.headRepo` (`cmd/agc/internal/provisioner/eviction.go:750:headBranch: run.HeadBranch, headSHA: run.HeadSHA, headRepo: run.HeadRepository.FullName,`) and the event into `runState.event`.

**The refusal compares names, never the `head_repository.fork` flag.** A job is foreign when `headRepo` differs from the run's own `owner/repo`.
The flag answers whether the head repository is a fork of anything, which is a different question, measured 2026-11-10:

| Run | `head_repository.full_name` | `fork` | Foreign by name |
| --- | --- | --- | --- |
| `actions/runner`, 100 `pull_request` runs | 44 a contributor's fork (e.g. `jenseng/runner`), 56 `actions/runner` | `true` on the 44, `false` on the 56 | agrees on all 100 |
| `karlkfi/gag-q215-fork` (itself a fork), a pull request from a branch of that same repository (run `42869194507`) | `karlkfi/gag-q215-fork` | `true` | no |

So the flag refuses every pull request on a repository that is itself a fork, and the comparison does not.
The probe pull request (`karlkfi/gag-q215-fork#1`) and its branch were closed and deleted after the read.

**Open in this row, each to settle before the field is written** ([api-review.md](../development/api-review.md)):

- Where the refusal happens: not acquiring leaves the job queued with nothing on the run page, while acquiring and failing it shows the contributor why.
  Whether the AGC can fail an acquired job visibly without running a runner is unmeasured; `force-cancel` (`cmd/agc/internal/provisioner/abandoned.go:120:// forceCancelRun calls POST`) is the existing call nearest to it.
- What happens when the run lookup fails or the identity is absent (`RunIdentity` returns `ok=false`): a refusing set fails closed, which is the secure default, but costs a refused pull request job on every refusing set per GitHub API outage.
- **The refusal must also check the event, or it refuses the base repository's own `pull_request_target` workflows.** A `pull_request_target` run triggered by a fork pull request reports the fork as its head repository: 22 of `cli/cli`'s last 100 such runs did (e.g.
  `shounakjoshi88-a11y/cli`, read 2026-11-10).
  Its workflow comes from the base, so a fork cannot retarget `runs-on` there; refusing it would refuse the maintainers' code, such as a triage workflow.
  `runState.event` already carries the event to scope the refusal.
- **The scope is every event that runs the merge commit, not `pull_request` alone.** GitHub's events reference (`github/docs` `f309096`) gives `pull_request_review` and `pull_request_review_comment` the same `GITHUB_REF`, `refs/pull/N/merge`, so a fork can add either trigger beside a trusted label.
  What those runs report as `head_repository` is unmeasured: 11 public repositories with `pull_request_review` runs had no fork-headed run in their last 100, and `pull_request_review_comment` was not checked (reviewer's read, 2026-11-10).
- **An empty `headRepo` reads as foreign, deliberately.** A deleted fork leaves the run's head repository empty, and a refusing set refuses that job rather than guessing.
- **Compare the names case-insensitively.** GitHub resolves repository names case-insensitively (`gh api repos/ACTIONS/Runner` answers `actions/runner`, read 2026-11-10), and the run's own `owner/repo` comes from the job message while `headRepo` comes from REST; whether the two can differ in case is unmeasured.
- One extra REST call per pull request job on every refusing set, against the installation's rate limit.
  Only the three merge-commit events need it: `eventName` is on the job message itself (seen live on a `JobAssigned`, 2026-07-26), so a `push` or `schedule` job is decided without a lookup.
  The field is best-effort and `omitempty` (`scaleset/types.go:221:EventName      string`), so an absent `eventName` takes the lookup; skipping it would admit that job unchecked.

The security audit's lead on a fork naming a dogfood scale-set label ([its audit lead](../plan/security-audit-2026-11.md#no-source-visible-control-stops-a-fork-pull-request-from-naming-a-dogfood-scale-set-label-in-runs-on)) is the first consumer.
