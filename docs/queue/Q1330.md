# Add an opt-in RunnerSet refusal for fork pull request jobs

A fork pull request can rewrite `runs-on` to reach a trusted `RunnerSet`, because a `pull_request` run executes the pull request's merge commit, whose workflow file carries the fork's edits.
GitHub's runner groups cannot stop it: they scope by repository, and the selected-workflows restriction (Enterprise Cloud and Server only) pins ordinary workflows to a branch while a `pull_request` run's ref is `refs/pull/N/merge`, so per GitHub's docs it refuses every pull request rather than only forks.
GitHub's approval setting keys on the contributor rather than the fork: even "all external contributors" exempts organization and repository members, and costs a maintainer's click per run where it applies, so a `RunnerSet` that must not run fork code needs a refusal of its own.
Decided in Q1220 (2026-11-09): opt-in per `RunnerSet`, default unchanged, so no adopter's existing fork CI breaks.
The decision and the GitHub-side controls it sits beside are in [the goal doc](../plan/secure-multi-tenant-oss-ci.md#open-decisions-the-map-surfaced).

**The job message cannot mark a fork, so the refusal reads the run.** Upstream `JobMessageBase` (actions/scaleset `716908e`, read 2026-11-09) carries `eventName` and `jobWorkflowRef` but no head-repository field, and the live `JobAssigned` captured 2026-07-26 has none ([scaleset-eviction-recovery.md](../plan/scaleset-eviction-recovery.md)).
The AGC already calls `GET /repos/{owner}/{repo}/actions/runs/{run_id}` for eviction recovery (`cmd/agc/internal/provisioner/eviction.go:690:// runConclusion calls GET /repos/{owner}/{repo}/actions/runs/{run_id}`), and that object carries `head_repository.fork`.
The same call already decodes `head_repository.full_name` into `runState.headRepo` (`cmd/agc/internal/provisioner/eviction.go:750:headBranch: run.HeadBranch, headSHA: run.HeadSHA, headRepo: run.HeadRepository.FullName,`), so comparing it with the run's own `owner/repo` is an alternative that needs no new field decoded.
Q1052 read the field over REST and saw only `fork: false`; a real fork run's value is unmeasured.

**Open in this row, each to settle before the field is written** ([api-review.md](../development/api-review.md)):

- Where the refusal happens: not acquiring leaves the job queued with nothing on the run page, while acquiring and failing it shows the contributor why.
  Whether the AGC can fail an acquired job visibly without running a runner is unmeasured; `force-cancel` (`cmd/agc/internal/provisioner/abandoned.go:120:// forceCancelRun calls POST`) is the existing call nearest to it.
- What happens when the run lookup fails or the identity is absent (`RunIdentity` returns `ok=false`): an opted-in set fails closed, which is the secure default, but costs a refused job per GitHub API outage.
- What `head_repository` reads for a `pull_request_target` run from a fork.
  Its workflow comes from the base, so a fork cannot retarget `runs-on` there, and refusing it would refuse the base repository's own code.
- One extra REST call per job on opted-in sets, against the installation's rate limit.

The security audit's lead on a fork naming a dogfood scale-set label ([Q1326](Q1326.md)) is the first consumer.
