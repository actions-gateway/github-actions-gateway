# Dogfood scripts write shared kubeconfig state on every run

`gke_get_credentials_and_verify` ([scripts/lib/common.sh](../../scripts/lib/common.sh)) runs `gcloud container clusters get-credentials` unconditionally, then asserts the resulting context is the expected one.
The assertion is the valuable half and it needs no fetch: when the current context already equals `gke_<project>_<zone>_<cluster>`, the fetch rewrites the identical entry.

prod-guard denies that write, and correctly — the kubeconfig is shared by every session on this machine, so a session that switches it silently moves any parallel session relying on ambient context.
Its message names the fix: prefer per-command pinning over switching shared state.

Every dogfood script calls this function, so every dogfood session pays the prompt.
Measured 2026-08-28: the Q408 Phase 4 session ran five of them (`e2e-start.sh` twice, `e2e-mirror-validate.sh`, `e2e-mirror-hits.sh`, `e2e-stop.sh`, `stop.sh`) and carried a `PROD_GUARD_OVERRIDE` on each.

**The decision to override rather than fix was taken deliberately** in that session, to spend the booked cluster window on the validation rather than on a shared library function.
This row is the record of what that deferred, not a re-opening of it.

**The change, if it is taken:** verify first, fetch only on a mismatch.
Idempotent, removes a shared-state write from every dogfood script, and leaves the guard in force for the case that matters, which is switching to a *different* cluster.
The risk to weigh is a kubeconfig entry that is present but stale (a rebuilt cluster reusing the name), where skipping the fetch turns a working refresh into a confusing failure on the next call; a cheap mitigation is to fetch when the entry is older than some age, or to keep the fetch behind an opt-out rather than removing it.

An override is the wrong long-term shape here for the reason overrides usually are: used routinely it stops being a decision and becomes a prefix nobody reads.
