# A disruption re-run takes the run's genuine failures with it

A job that failed on its own is re-run automatically when another job of its run is disrupted.
Every disruption arm (eviction, preemption, node shutdown, deletion, vanished, abandoned) calls `rerun-failed-jobs`, which re-runs every failed job of the run; only the out-of-memory class re-runs the killed job alone (Q1319).
The design says what that costs, in its account of Q1319: the call re-runs a sibling's genuine failure and hides it if it passes.
A job that is not safe to repeat, such as a deploy that failed partway, is re-run without anyone asking.

Read from source and the design on 2026-11-27; how often a disrupted run also holds a genuine failure is not measured.
`actions_gateway_scaleset_job_reruns_total{trigger="gag_collateral"}` counts these re-runs, and its share of `trigger="gag"` on dogfood is that measurement.
The operator runbook's boundary list says a genuine job failure never fires, which holds only for a run with no disrupted job.

**A fix:** give the disruption arms the scope decision the out-of-memory release already makes (`planJobRerun`), re-running the disrupted job by its runner's name where another job of the attempt failed on its own.
That decision needs the run concluded and its jobs list read, which the out-of-memory class gets by parking the re-run; the disruption arms call inside a 15-minute window instead, so this is a change of shape and not a flag.
[Q1394](Q1394.md) is the dogfood reading of the single-job call on a killed job, and should land first.
Q1398 is a different defect on the same arms: there the re-run names the wrong run, and here it names the right run and too many of its jobs.
Until then, correct the runbook line to say what happens beside a disrupted job.
