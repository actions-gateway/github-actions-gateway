# Pin the dashboard preview harness's kubectl to its kind cluster

`deploy/monitoring/preview/render.sh` selects its cluster with `kubectl config use-context "kind-$CLUSTER"`, in `ensure_cluster` for a full run and directly in `main()` for `shot`, and every later `helm` and `kubectl` call reads the ambient context from the shared `~/.kube/config`.
Any other session on the machine can switch that context between the switch and the call, and the harness then acts on whatever cluster the other session chose.

**Measured 2026-10-12** rendering Q1070: the run reused `gag-obs`, applied the workload and dashboards, and slept the 660 s `WAIT`; the port-forward after it failed `port-forward to kps-grafana did not become ready`, and `kubectl config current-context` then read `gke_actions-gateway-dogfood_us-east1-b_gag-dogfood`.
The port-forward is read-only and found no `kps-grafana` there, so nothing changed on the dogfood cluster.
A re-run with a private kubeconfig (`kind export kubeconfig --name gag-obs --kubeconfig tmp/<name>`, then `KUBECONFIG=tmp/<name> ./render.sh shot`) is unaffected by the switch.

The read-only failure is the mild half.
The `helm upgrade --install` and the `kubectl apply` / `create configmap` / `rollout restart` calls in `install_stack` and `apply_artifacts` are unpinned the same way, and the window is only shorter for them, not closed.
They run inside a script, so prod-guard, which inspects the agent's own Bash command, never sees them: a switch landing in that window would install `kube-prometheus-stack` and the synthetic workload onto the dogfood cluster, which is hard-classified prod.
The cluster lock Q1072 added serializes `render.sh` runs against each other, not against other sessions' `kubectl config use-context`.

Fix shape, unmeasured: pass `--context "kind-$CLUSTER"` to every `kubectl` call and `--kube-context "kind-$CLUSTER"` to `helm`, or export a private `KUBECONFIG` from `kind export kubeconfig` at start-up and drop the `use-context` calls, so the harness never writes or reads the shared current-context.
The second also stops the harness from moving another session's ambient context to `kind-gag-obs`, which is the same hazard pointed the other way.
