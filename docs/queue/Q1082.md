# Decide whether `v2beta1` retires at `v2.0.0` or survives to `v3.0.0`

[Q452](Q452.md) decided that GA `v2` defines the deprecated `CiliumFQDN`/`CalicoFQDN` aliases, on the premise that `v2.0.0` keeps serving `v2beta1`.
The premise is asserted in three docs, two of them published operator pages, and contradicted by the graduation ladder's own step 3 in [v2-api.md](../plan/v2-api.md) and [v2-ga.md](../plan/v2-ga.md), which both say the hop drops the superseded served version.
For the `v2beta1` → `v2` hop that superseded version is `v2beta1`.

Both cannot be true, and Q452's answer flips on which does: if `v2beta1` retires at `v2.0.0`, the aliases go with it and `v2` never defines them.
[#1867](https://github.com/actions-gateway/github-actions-gateway/pull/1867) is drafted pending this.

The comparison is written up in [v2beta1-retirement.md](../plan/v2beta1-retirement.md): both paths need the same Rule #4b overlap release and the same storage migration, so they differ only in what `v2` carries and whether the published `v3.0.0` floor is walked back.
Measured 2026-09-07: `v2beta1` shipped in `v1.1.0` (2026-07-12); upstream would allow removal 9 months after a deprecation notice, and requires no major version for it; the project's own major-tag rule is what creates the `v3.0.0` floor.

**Deciding sooner widens the options** — a notice in 1.8 starts a clock and commits to nothing, while each release it slips pushes the earliest clean-GA date out.
The deliverable is the decision recorded in the plan, and the losing path's cost beside it.
Sibling: [Q1083](Q1083.md) on the notice period this project owes, which is independent of the choice.
