# Every stable tag's Pages deploy is accepted and never served

**No stable tag since `v1.6.0` has published its own docs site.** Each time, the tag's Pages run deployed successfully, the live site kept serving the deployment from before it, and the docs went live only after someone dispatched the workflow again.
The [`v1.6.0` postmortem](../postmortems/2026-08-26-the-tag-published-no-docs.md) treated this as a one-off and added `verify-pages-live.sh` (Q1000).
That check has failed at every stable tag since.

**Measured 2026-11-17** with `gh run list --workflow pages --branch <tag>` and each run's failed-step log:

| Tag | Tag's run | Failed step | Repaired by |
|---|---|---|---|
| `v1.7.0` | 33292335581 | `verify-pages-live`: did not serve 1.7.0 after 286 s | dispatch on `main`, 2026-08-30 04:42 |
| `v1.8.0` | 34833404022 | same, 1.8.0 | dispatch on `main`, 2026-09-14 10:42 |
| `v1.9.0` | 37395739033 | same, 1.9.0 | dispatch on `main`, 2026-10-06 01:03 |
| `v1.10.0` | 40438829107 | same, 1.10.0 | dispatch on `main`, 2026-10-27 02:37 |
| `v2.0.0` | 44106140533 | same, 2.0.0 | dispatch on `main`, run 44110604524, 2026-11-17 15:06 |
| `v2.0.1` | 44362798205 | same, 2.0.1 | dispatch on `main` with `docs_ref=v2.0.1`, run 44366938350, 2026-11-18 |

The "Repaired by" column is read from the next successful dispatch after each tag.
That each dispatch was a republish is inferred from its timing, not read from its inputs.
At `v2.0.0`, `gh-pages` commit `cb96d404e` listed `2.0.0` as `stable`, and every step through `Deploy to GitHub Pages` passed.
Twenty minutes later, a cache-busting request still returned `last-modified: Tue, 17 Nov 2026 14:38:16 GMT`, which is the `dev` deploy from before the tag.

**What is ruled out so far.** A tag ref is not enough to cause it: dispatch 41391767190 ran on ref `v1.10.0` on 2026-11-02 and was served.
At `v1.6.0` the uploaded artifact was correct ([postmortem](../postmortems/2026-08-26-the-tag-published-no-docs.md#why-the-artifact-was-correct-and-the-site-did-not-serve-it)).
At `v2.0.0`, run 44106140533's artifact check passed before upload.
The mechanism is unmeasured.
One thing every failing run shares is that a `dev` deploy of the same tree ran minutes before it: the tag points at `main`'s tip, which just merged and deployed.
That is a lead, not a finding.

**Done when** a stable tag's own run serves its version with no manual dispatch, and the postmortem names the cause.
If the cause can't be found, have the publish job redeploy once when `verify-pages-live.sh` fails, before failing the run.
Every repair so far was a full dispatch, minutes later, that rebuilt the artifact.
So an immediate retry of the same artifact is the weaker option, and it should only ship once a test shows it works.
Release runbook step 5 currently reads as if the tag's deploy works, so update it in the same change.
