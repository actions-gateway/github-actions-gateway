# GMC deletes its Secret-reader RoleBinding from ex-tenant namespaces

A namespace that stops being a tenant keeps the `gmc-tenant-secret-reader` RoleBinding the GMC created there, so the GMC keeps `get`/`list`/`watch` on Secrets in a namespace it no longer manages.
`v2.0.0` makes this the upgrade path, not only an operator's choice: Q1258 stops the GMC honouring the 1.x `actions-gateway.github.com/tenant=true` marker, so every namespace carrying only that marker becomes an ex-tenant at upgrade with its binding in place.
Q1258 documents the manual `kubectl delete rolebinding` in `upgrade.md`'s `v2.0.0` pre-upgrade check; this row makes the GMC remove the binding itself, and it gates `v2.0.0` so the release never ships with the leftover grant.

What the code does today, read from source at `1e2d75a` and not measured on a cluster:

- **How the GMC identifies its binding.** `buildTenantSecretReaderRoleBinding` in `cmd/gmc/internal/controller/tenant_secret_access.go` names it `gmc-tenant-secret-reader`, labels it `app.kubernetes.io/component=gmc-tenant-secret-reader` and `app.kubernetes.io/managed-by=actions-gateway-gmc`, points `roleRef` at the ClusterRole `gmc-tenant-secret-reader`, and makes the GMC ServiceAccount its only subject.
  `applyManagedChild` is called with a nil owner, so the binding carries no ownerReference and nothing garbage-collects it.
- **RBAC allows the delete; admission denies it.** The manager ClusterRole grants `delete` on `rolebindings` cluster-wide (`cmd/gmc/config/rbac/role.yaml`), and `gmc-tenant-resource-guard` denies the GMC every `DELETE` of a RoleBinding in a namespace without `actions-gateway.com/tenant=managed`.
  That denial is Q1188's deliberate choice ([its plan](../plan/archive/q1188-scoped-secret-reads.md): "the guard denies the GMC's delete there, because the namespace is no longer a tenant").
- **The reconciler reaches the namespace but never deletes.** `tenantMarkerPredicate` passes a namespace event only when the old or new labels carry the marker, so a namespace that was only ever legacy-marked never enters through the Namespace watch.
  But the controller also watches every RoleBinding named `gmc-tenant-secret-reader` and enqueues its namespace, so the upgraded GMC's initial list of a leftover binding does reconcile that namespace.
  `Reconcile` then sees a non-tenant namespace and only calls `Watches.Stop`.

**The design is the policy exception, and it is a security change.** The cleanup needs a delete-only exception in `gmc-tenant-resource-guard`, in `cmd/gmc/config/admission-policy/` and its chart twin: let the GMC delete a RoleBinding outside a tenant namespace only when it is the GMC's own reader binding.
Scoped to the bar below, the exception can only remove the GMC's own access.
The PR states its exact match conditions, and the reconciler has to act on the non-tenant namespace the binding watch already enqueues.
The maintainer merges it as security.
Karl accepted loosening the policy for this (2026-11-03), but not any particular design.

**The bar the reviewer of Q1258 set for the exception**, each condition with an envtest negative that is verified by deleting that condition from the policy and watching its test fail:

- it applies only to `DELETE`, and reads `oldObject`;
- `oldObject.metadata.name` and `oldObject.roleRef.name` are both `gmc-tenant-secret-reader`, and `oldObject.roleRef.kind` is `ClusterRole`;
- the subjects are exactly the GMC ServiceAccount, written with the same identity the policy's `matchConditions` uses so the config copy and the chart twin cannot drift apart;
- it does not extend to Roles or ClusterRoleBindings.

**It changes Q1188's manual-unmark path too.** An operator removing the marker from a namespace today has to delete the binding by hand, as `upgrade.md`'s Q1188 note says.
With the exception, the GMC removes it on its next reconcile of that namespace, so that note and the Q1258 pre-upgrade step both change in the same PR.

**Done when** the GMC deletes its reader binding from a namespace without the tenant marker, envtest shows the guard admitting that delete and still denying the GMC any other RoleBinding delete outside a tenant namespace, and the operator docs no longer ask for the manual delete.
