# Re-run only the classified job once job names are shown to match (M6)

Every automatic re-run today uses `rerun-failed-jobs`, so a class firing on one job also re-runs every other failed job of the run, including genuine failures the boundary says must never be re-run.
Detection's `gag_collateral` count measures that cost; job-granular re-run removes it, and it waits on the design's M6.

M6 is two readings, from a test workflow with a matrix, a reusable workflow and a `needs:` chain:

- Whether `jobDisplayName` matches the jobs API's `name` exactly for matrix jobs and reusable-workflow jobs, and what happens when two jobs share a `name:`, which GitHub allows (from recall).
  The match is how a classified job finds its job ID for a single-job re-run.
- What a single-job re-run does to the jobs it depends on and the jobs that depend on it, and whether the upstream jobs' outputs and artifacts survive (outputs from recall, artifacts unknown).

[Q1236](Q1236.md) is the neighbour and a different question: its M2 asks whether a re-run carries a new job ID and the same display name, which detection's pairing keys on, while this row matches the display name to the API's, which a single-job re-run needs.
Run both in one session where convenient.

If both hold, a class re-runs its own job and the disruption arms stay run-granular unless the readings argue otherwise; if the name match is ambiguous, the class falls back to `rerun-failed-jobs` and says so.
The design's [granularity section](../plan/q555-automatic-recovery-design.md#run--or-job-granular-re-run-open-question-2) and the API shape's `retry.scope` (`FailedJobs` or `Job`) are where it lands.
Gated on 2.1 ([release-2.1.md](../plan/release-2.1.md)): more classes means more collateral re-runs, so this is what makes adding them cheap.
