# Roadmap merge driver duplicates a bullet when both sides edit its q: IDs

When two branches each change the `<!-- q: -->` IDs on the same `docs/roadmap.md` bullet, the merge driver keeps both versions: the merged page lists the bullet twice, the rebase reports `resolved docs/roadmap.md by backlog ID` and raises no conflict.
Whether `make roadmap-check` catches the duplicate was not checked.
Seen on two rebases on 2026-10-27, not reproduced in isolation: Q1181's branch dropped `Q1181` from the flaky-job bullet's `q:Q555,Q1183,Q1181,Q1178` while main (Q1178's merge) had dropped `Q1178`, and Q555's branch did the same against main.
Each rebase produced the bullet twice, once per side's ID set, and both duplicates were removed by hand.
The mechanism is read from source, not exercised: `keyedrecords.Merge` keys a bullet by `mdroadmap.MarkerKey`, its whole joined ID list, so when both sides change the list the base key is gone from both and each side's new key reads as an added record.
The page-wide duplicate check `duplicateBindings` (`devtools/git/mergedriver/roadmap.go`) keys on the same joined list through `mdroadmap.DupeKey`, so two bullets sharing some IDs but not all pass it.
The fix probably keys the duplicate check on each ID rather than the joined list, falling back to git's own merge on any ID bound twice; a `git-merge-roadmap-test.sh` case with both sides editing one bullet's IDs is the reproduction to write first.
Until then, two concurrent PRs that close different items behind one bullet will merge cleanly into a page with that bullet twice, and the second PR's author reads only the driver's "review the bullet set" note.
