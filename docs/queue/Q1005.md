# `PublishesAvailableJobsFromDelivery` flakes in two unrelated ways

**Event:** `TestListener_PublishesAvailableJobsFromDelivery` fails on `main` again, in any tier.
Record which of the two modes below, by line and message: they share a test name and nothing else.

The row was filed against mode A and cited a CI run as proof it reached CI.
That citation is wrong, and reading it is what found mode B: [run 32936563082](https://github.com/actions-gateway/github-actions-gateway/actions/runs/32936563082) failed at line 52 with `Condition never satisfied`, not at line 61 with `expected: 1  actual: 0`.
Mode A has been seen locally only; mode B is the one that reds `main`.

**Mode A, the assertion outran its wait.** `handleMessage` publishes the availableJobs gauge from `setLastStats` the moment statistics arrive and provisions the job the same message assigned afterwards, so the wait on the gauge cleared while the provisioner call was still owed.
Sighted once, `make test-integration` run 2 of 4 on one unchanged tree, 2026-08-27, `expected: 1  actual: 0`.
Fixed by waiting on `prov.count()` and then holding it across a 500 ms window.
The hold rather than the wait is what carries the property: a bound that merely accepts a provision is also cleared by a listener that provisions the rest of the batch a moment later.

**Mode B, the wait could never be satisfied at all.** A poll landing mid-enqueue assigned the first job and published the statistics riding on that message, counting only what GitHub held at that instant.
Nothing republished: the slot was then full so no further message arrived, and `refreshDemand` returns early whenever advertised capacity is above zero, which `fixedCapacity(1)` always is.
The gauge held the stale value for the rest of the run, so `n == queued-1` was not slow to come true; it never came true and the 5 s wait always elapsed.
Fixed by advertising zero capacity while enqueueing and opening the slot afterwards, so the delivered message's statistics count the whole queue.

Measured on the fixes, three runs each.
Mode A: a 300 ms sleep between `setLastStats` and the assignment loop fails the pre-fix test 3/3 with the local sighting's own text and passes the fixed one; an over-provision landing 200 ms late fails the fixed test 3/3 at the hold, and passes both the pre-fix test and the fixed one with the hold deleted.
Mode B: a 150 ms sleep inside the enqueue loop fails the mode-A-only test 3/3 with CI's own `Condition never satisfied` at the gauge wait, and passes once the slot is held closed.
Instrumenting the failing wait gave `n=0 writes=2 prov=1`, the `writes > 1` half satisfied and `n == queued-1` stuck at zero, which is what distinguishes a permanently unsatisfiable condition from a slow one and rules out raising the timeout.

Idiom sweep over the 141 waits in `cmd/agc/internal/scalesetlistener` as `origin/main` holds it, per [sweep the idiom](../development/maintaining-backlog.md#flake-fixes-go-first): one instance of mode A, the one fixed.
The gauge is the only test-visible signal established to precede what a following assertion names: `metricsIncProvisioned` fires after `Provision` returns and `metricsIncAbandoned` before `metricsSetDeferred`, so the waits keyed on those cover their assertions.
The one other wait on the gauge, [`TestListener_RefreshesDemandGaugeWhileWithholding`](../../cmd/agc/internal/scalesetlistener/demand_q960_test.go), is followed by `assert.Zero(prov.count())`: reading a negative early makes it pass, so it cannot flake in mode A's way.
It advertises zero capacity throughout, so `refreshDemand` keeps its gauge current and mode B cannot reach it either.
