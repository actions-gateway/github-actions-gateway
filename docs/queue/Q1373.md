# GMC may run a Deployment as any ServiceAccount in a tenant namespace

**A GMC compromised while a namespace is marked can create a Deployment there that runs as any ServiceAccount in it, a tenant's own included, and the pod keeps that ServiceAccount's tokens after the unmark.** Found while closing Q1343, which stops the GMC minting a ServiceAccount token Secret; this is the route that rule does not reach, so it is a separate fix rather than part of that one.

Read from source at `f69b814`, not measured.
`gmc-tenant-resource-guard` confines the GMC's Deployment writes to marked tenant namespaces and checks nothing in the pod template, so `spec.template.spec.serviceAccountName` may name any ServiceAccount there.
Kubernetes checks no permission on the ServiceAccount a pod names, and a pod gets a projected token for it unless automount is off.
After the unmark the guard refuses the GMC deleting that Deployment, so its pods keep refreshing the token for as long as they run.

The GMC provisions two ServiceAccounts per gateway, the AGC's (bound to `agc-tenant-role`) and the worker's, and the AGC Deployment names the first (`cmd/gmc/internal/controller/shared_agc_deployment.go:265:ServiceAccountName: names.serviceAccount,`).
Which ServiceAccount the egress proxy Deployment runs as has not been checked.
Once that set is known, a guard rule refusing a GMC Deployment write whose pod template names any ServiceAccount outside it should cost nothing in normal operation.

**Done when** the guard refuses a GMC Deployment write naming a ServiceAccount outside the set the GMC provisions, with an envtest case in `cmd/gmc/internal/controller/integration/tenant_resource_guard_test.go` that goes red with the rule removed, and `docs/design/05-security.md` §5.1 says so.
