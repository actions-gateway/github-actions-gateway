# Measure flaky-job detection on dogfood: result spelling, re-run job IDs

Q555 built flaky-job detection without the dogfood turn-up its row put first, because the GKE dogfood cluster is prod-classified and the building session was not scoped to it; the design's M1, M2 and M4 are still unmeasured, and each is an assumption the code now rests on.
- **M1, the `result` vocabulary.** Read `actions_gateway_scaleset_jobs_completed_total` by `result` for a red step, a cancelled run and a timed-out job; only a disruption's `failed` has been seen live.
  Detection records any result but `succeeded` as a failure, and `canceled` only when a recovery claim names the job, so a timed-out job's spelling decides whether it is recorded.
- **M2, pairing's key.** Re-run a failed job and read both completions at debug level: detection assumes the re-run carries a new `jobId` and the same `jobDisplayName`, and treats a repeat of the same `jobId` as a replay.
  A workflow with two jobs sharing a `name:` would share one record.
- **M4, where context is read.** Compare the worker pod's terminal transition and its deletion to the completion's arrival.
  Detection snapshots the pod at its terminal transition and falls back to reading it, so a pod gone before both leaves the record with no context.
  If the completion usually arrives first, the snapshot is never taken in time: the fallback reads a still-`Running` pod, so a runner that exits non-zero never reads as a fault, and the snapshots no completion takes fill the 1,024-entry map (independent review of Q555, 2026-10-27).
  Also unmeasured: whether the runner container exits non-zero when its job fails, which would make every red test a `PlatformFaultOnFailedJob` Warning (the snapshot's fault reading assumes it exits 0), and whether `JobCompleted` carries `eventName` and `jobWorkflowRef` (decoded from it, never seen on it).
  The reading needs `actions_gateway_*` series stored, which Q1180 adds.
