# Stranded scale-set job named only on the abandoned path, not re-checked

Q1195 gave abandoned-run recovery a walk that names the job a lost scale-set runner left without one (`scaleSetWorkerSet.strandedJob`, reading the listener's in-flight record) and cancels and re-runs that job's run.
Two shapes still leave the stranded job unrecovered, read from source on 2026-10-27 and not observed on a cluster.
The disruption path skips a never-started evicted, preempted or drained worker whose own job another runner started (`recoverDisruptedScaleSetWorker`'s `assignedJobAccountedFor` check, Q1169), with no walk, so the set is one runner short and the job left without one waits out GitHub's ~15-minute unstarted-job timeout, as Q1195 described for the reaper.
And the walk declines while any worker is `Running` with no start recorded, because that runner may already hold the job; nothing re-checks once the start lands, so a stranded job found in that window is never recovered.
One fix closes both: run the walk on the disruption path too, and re-check a declined walk on a later reconcile, keyed by the lost worker so it fires at most once.
Recovering the stranded job on the disruption path would force-cancel a run whose job never started, where that path otherwise re-runs, so the cause label and budget slot need deciding there.
