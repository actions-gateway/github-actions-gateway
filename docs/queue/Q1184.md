# Attribute egress proxy failures to the job that hit them

Two retry uses need to know which job's pod a proxy failure came from: an upstream dial failure as a retry class, and a policy denial as a futile retry whose Event names the blocked host.
Per-job identity is unbounded for metrics and per-job egress is sensitive, so this is a bespoke endpoint, not a label on Q1178's metrics: each proxy replica keeps recent failures by source in memory for minutes, and the tenant's single AGC pulls them with a cursor over the proxy's existing mTLS port, then joins them to jobs.
Separate from Q1178, which counts outcomes by destination for operators and holds no per-job data.
Today the proxy logs a denial or dial failure with the host but not the client, and per-job records exist only behind the opt-in `ConnectionsWithSource` audit mode (Q986).
**Ask:** whether failure-only, in-memory attribution is acceptable against `05-security.md`, since it is new use of per-job egress data even though nothing is retained.
Costs: attribution needs the pod's lifetime as well as its IP, and the AGC needs a client certificate the proxy's metrics port accepts, which is unverified.
