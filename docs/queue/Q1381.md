# A displaced merge-group run is re-run: GitHub never cancels it

The futility checks assume a merge-group run that loses its place in the queue is cancelled by GitHub and so withheld as `run_cancelled`; measured on 2026-11-22 against this repo's queue of 2026-10-30, GitHub leaves it running.
When #2190 failed at the head of the queue and was removed (`failed_checks`, 17:56:25 UTC), the groups behind it, `gh-readonly-queue/main/pr-2179-e90ed166…` and `pr-2180-1558b6ca…`, were rebuilt as new groups at 17:56:30, and the old groups' runs kept going: six concluded `success` after the removal, the last at 18:05:13 (run 41099950920, `doc-links`).
Their eight `cancelled` runs were each cancelled by a job of their own that exceeded its `timeout-minutes`, every one before 17:56:25, read from the jobs' check-run annotations, so none of the 30 runs was cancelled by the displacement ([the readings](../plan/q555-automatic-recovery-design.md#readings-from-githubs-api-2026-11-22)).
Both old group refs now return 404.

So a disruption in a displaced group's run passes every check that is built: `superseded` covers only `push` and `pull_request`, and nothing else reads the event, so the AGC re-runs a run whose result no queue entry is waiting for, and spends a slot of `maxEvictionRetries` on it.
What that re-run does once its `gh-readonly-queue` ref is deleted was not measured.

A candidate check is that the run's `head_branch` ref still exists, one `GET …/git/ref/heads/<head_branch>` for `merge_group` runs only, which a 404 answers; whether a displaced group's ref is deleted before its runs conclude, so that the check can see it in time, is the open part.
Separate from [Q1230](Q1230.md), which is about preemption victims that never started.
