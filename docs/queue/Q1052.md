# A PR whose workflows await approval blocks silently and forever

A queued `action_required` run is indistinguishable from a PR nobody has pushed to, and it holds every PR that needs the fix.

**Measured 2026-09-03 02:00 PDT** on [#1825](https://github.com/actions-gateway/github-actions-gateway/pull/1825), a dependabot bump of `google.golang.org/grpc` from 1.83.0 to 1.83.1.
Every workflow run on its head reads `completed / action_required` with a duration of **0s**, queued `2026-09-02T08:16:17Z`, over 24 hours earlier.
Nothing failed, because nothing started.

```bash
gh pr view 1825 --json statusCheckRollup --jq '.statusCheckRollup|length'   # 0
gh run list --commit "$(gh pr view 1825 --json headRefOid --jq .headRefOid)"
# completed  action_required  ...  0s  2026-09-02T08:16:17Z   (every row)
```

**Why it is not visible.** `statusCheckRollup` is empty, so every instrument that reads a PR's checks reports *no checks* rather than *checks withheld*, which is the same answer it gives for a branch pushed seconds ago.
`mergeStateStatus` reads `BLOCKED`, which is also what a PR with a failing required check reads.
So the state has no signature of its own at either level, and the PR ages out of view.

**What it cost here.** `main` has no classic branch protection, but the active `default-protect` ruleset requires nine contexts including `security-scan-gate`, so this is a hard block in three directions at once:

- #1825 cannot merge, because its own required checks have never run.
- A HIGH severity `CVE-2026-84304` stayed live on `main`'s dependencies, at `cmd/agc/go.mod:77` and `cmd/gmc/go.mod:92`.
- Two unrelated PRs from a dispatch batch, #1828 and #1832, were hard-blocked on `trivy (agc, 1)`, `trivy (gmc, 1)` and `security-scan-gate`, each otherwise green at 52 pass and 0 pending, with the CVE as their only red.

Two sessions independently diagnosed the CVE, and both initially searched the open PRs for `trivy` and `CVE`, the symptom's vocabulary, which a dependency bump's title carries neither of.
Only searching the package the scanner named reached #1825.

**Not every dependabot PR is affected**, which is what makes it a defect rather than a setting: #1824, same author, has 65 checks and reads `CLEAN`.
Whatever selects #1821, #1823 and #1825 for approval and lets #1824 through is the thing to identify first.

**Done when** an open PR whose runs are all `action_required` cannot age silently.
The mechanism is deliberately not chosen here.
A repository-settings change may remove the approval requirement for this actor entirely, in which case there is nothing to detect and the row closes on that.
Otherwise a scheduled check or a `make doctor` probe can name such PRs, and the reach is the argument for the first option: the failure is invisible to the PR's own surface, so anything that reads only that PR will keep reporting nothing.

Found by the dispatch run of 2026-09-03, which lost two of its eight PRs to it.
