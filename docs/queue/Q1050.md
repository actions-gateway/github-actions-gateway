# 17 of 19 go-throttle shell cases re-run the Go table test's matrix

**Measured 2026-09-03** by extracting each suite's case commands and normalising whitespace: of the 19 command literals in `claude-go-throttle-hook-test.sh` that carry a `go build`/`go test`, **17 are also cases in `TestDecide`** (`devtools/agent/gothrottle/decide_test.go`, 39 cases).
The two that are not are near-variants: a differently worded commit message, and `(cd cmd/agc && go test ./...)`.
So the shell suite re-runs the decision matrix the table test already owns, through a real fork per case, and the table test's own comment says it is the one that carries the matrix.

**The question is what the duplicate cases buy, not whether they duplicate.** Each shell case additionally exercises the entry point resolving the binary and the throttle script, the on-demand build, the JSON envelope Claude Code reads, and `GOTHROTTLE_DEBUG` end to end.
Whether that needs 17 cases or 3 is the open question, and it is a judgement about how much end-to-end signal a seam is worth rather than a defect.

**Not a flake row, and it is no longer one.** Each duplicated case costs a probe fork, and a starved fork used to redden the suite; [Q1031](Q1031.md) closed that by re-asking a probe that never answered, so cutting the case count no longer buys reliability.
What it would buy is run time and one less place to edit when the decision matrix moves.

**The run-time half is bounded small, groomed 2026-09-17.** [Q1117](Q1117.md) measured the capped `scripts-test` fan-out on CI and named its three longest suites, `check-registry-mirror-render-test`, `check-roadmap-test` and `gate-list-test`; `claude-go-throttle-hook-test` is in neither run's top three, so it falls in the remaining 129 suites at a median of 4s and 3s.
That bounds rather than measures it, since nobody has timed this suite by name, but the job cannot finish faster than its 125s and 97s floors, so no cut here reaches the wall time.
What survives as the case for cutting is edit-locality alone, against two end-to-end escapes (Q624, Q696) that bought those cases.

Weigh it against the reason those cases exist: the suite asserts both directions because both fail silently (Q624, closed), and its wrapper and heredoc cases were each added after a real escape (Q696, Q624).
Deleting an end-to-end assertion because a unit test covers the same input is the move that looks clean and loses the integration signal, so this needs the argument made rather than a count applied.

**Ask:** whether 17 duplicated end-to-end cases or 3 is the right price for this seam.
The run-time arm is bounded above and the reliability arm closed with [Q1031](Q1031.md), so what is left is how much end-to-end signal a duplicated case is worth against the cost of one more place to edit, with two real escapes (Q624, Q696) arguing the other way.
Both answers are defensible on the same 17, so nothing here is a measurement waiting to be taken.
