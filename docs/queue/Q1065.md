# Decide whether a scoped AGC egress policy should admit the registry read

The registry read behind `RunnerVersionTooOld` (Q988) reaches the worker image's registry from the AGC pod over 443, so it works wherever the AGC's egress policy admits that destination.
By default it does: `buildAGCNetworkPolicy` admits 443 with no `to:` restriction, the breadth [05-security.md](../design/05-security.md#github-app-key-exfiltration-via-agc-apiserver-egress) records as the deliberate default.
An install that narrows it with `apiServerCIDRs` (Q145) closes the registry too, and `githubEgressFQDNs` lists no registry host, so an FQDN-mode allowlist would not reopen `ghcr.io` even for the default image.
In both cases the read fails and the tag verdict stands, which is the designed fallback and not a defect.

The open question is posture: whether a scoped AGC policy should carry a registry allowance at all, and if so what shape — the default image's `ghcr.io` alone, the hosts of every `workerImage` the gateway's sets name, or an operator-listed set on the `ActionsGateway`.
Each widens what a compromised AGC can reach, which is the trade the scoping exists to make, so this is a decision to record before any rule is written.
