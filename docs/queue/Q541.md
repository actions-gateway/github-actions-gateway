# EgressProxy watch-isolation test passes with its watch deleted, at times

`TestV2_EgressProxy_CiliumFQDNCarriesReferrerGHESHost` claims the referrer watch edge is the only thing that can re-enqueue the proxy once the pool is Ready.
Deleting both referrer `Watches` from `SetupWithManager` usually reddens it, but not always: across two sessions on 2026-09-21, 10 mutant runs at head f9e26b8 gave 9 FAIL and 1 PASS, so the assertion can pass with the mechanism it names removed.
The single green was taken with the mutation verified present in the tree and the package confirmed to compile that source, so it is a real observation rather than a mutation that failed to land.
Both hosts sat at load 14–80 on 18 cores; treat the split as evidence of non-determinism, never as a rate.

Unverified hypothesis, stated as such: residual self-triggered reconciles from the Ready status write may straddle the gateway creation, letting a reconcile pick the referrer up with no referrer watch.
A fix likely has to quiesce the reconcile chain before the gateway lands, rather than lengthen a timeout.

Nobody has reproduced the green on demand, so a hardening fix cannot currently be shown to be load-bearing — whoever takes this needs a reliable red first, or the fix repeats the defect it closes.
The helper godoc this row originally named was corrected separately (PR #1974); what remains is the racy isolation itself.
