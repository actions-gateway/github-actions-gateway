# Retry cannot span a release-CDN incident on the cert-manager manifest

`scripts/fetch/prepull-manifest-images.sh:70:curl -fsSL --retry 5 --retry-all-errors --retry-delay 2 -o` is the only fetch of the pinned cert-manager release manifest left on the e2e critical path, and its retry window is about 13 seconds.
A cache miss that lands inside a github.com release-CDN incident kills the lane before the cluster exists, and has.

## Measured 2026-09-10

Run [34539304371](https://github.com/actions-gateway/github-actions-gateway/actions/runs/34539304371), `e2e (calico)` on `push main`, died in the `Pre-pull cert-manager images` step:

```
curl: (22) The requested URL returned error: 500   (x6, 22:52:03.5 -> 22:52:16.2)
##[error]Process completed with exit code 22.
```

Six responses of 500 on `https://github.com/cert-manager/cert-manager/releases/download/v1.20.2/cert-manager.yaml`, one attempt plus five retries all inside 12.7s, then exit 22.
Calico's pre-pull in the same run logged `==> loading calico images from cache`, so the cert-manager miss was the only manifest fetch that ran, and it was the one that failed.

## The same asset failed twice in six days, on two different lines

2026-09-10 is a 500 on the retried fetch above; 2026-09-14 (run [34856925669](https://github.com/actions-gateway/github-actions-gateway/actions/runs/34856925669)) is a 504 on the unretried `kubectl apply -f <url>` in `make apply-cert-manager`.
Same release asset, same CDN, two calico-lane runs killed.

[Q1125](Q1125.md) removed the unretried one, by caching the manifest beside the images and applying from the cached copy.
That is the right fix for what it names, and it concentrates this exposure rather than removing it: the cold-path fetch above is now the only one left, and a warm run has none.

## Retry bought nothing on the occurrence it was there for

`--retry 5 --retry-all-errors --retry-delay 2` is six attempts across roughly 13 seconds.
That spans a single bad response and not a CDN incident, which is the failure the two measurements above actually show.
Widening it is one of three candidates and not obviously the right one; none is settled:

- **A longer, backed-off retry window.** Cheapest, and it still assumes the incident is short.
- **Vendor the pinned manifest into the repo.** Removes the fetch outright and puts manifest bytes under `updatecli`'s version bump rather than under a URL, so the bump becomes a diff someone reads.
- **Seed it from an artifact or the local registry**, the way first-party images already reach the nodes.

## The `ErrImagePull` sibling is not one

[Q1125](Q1125.md) listed an `ErrImagePull` in `E2E_V2_TwoGatewaysCoexist`'s `BeforeAll` (merge group, 2026-09-16 19:11Z) as a possible member of this class, unestablished.
It is not: run [35139093856](https://github.com/actions-gateway/github-actions-gateway/actions/runs/35139093856) died on `conversion webhook for actions-gateway.com/v2alpha1, Kind=RunnerSet failed: Post "https://webhook-service.gmc-system.svc:443...`, which is in-cluster and fetches nothing.
The `ErrImagePull` in that log is `registry.invalid/preempt-probe-runner:none`, a deliberately unresolvable image in an unrelated preemption-probe fixture, and expected output.
Nothing further is owed on it.
