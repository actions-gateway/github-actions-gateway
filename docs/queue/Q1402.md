# An out-of-memory raise past a pod-level limit builds a refused pod

A template may set a pod-level memory limit (`spec.podTemplate.spec.resources`, which the CRD carries), and the out-of-memory class raises the runner's limit without reading it.
A raise past it builds a pod the API server refuses: each container's limit must be at or below the pod's (`validatePodResourceConsistency`, Kubernetes v1.35.5, read).
The raise is recorded for 7 days and the re-run spends a slot of the run's budget, for a job that cannot then be provisioned.
Read from source and not run: no non-test code in `cmd/agc` reads a pod-level `spec.resources` (`git grep`, 2026-11-24).

What the operator sees is a `WorkerPodCreateFailed` Event carrying the API server's message (`createPodWithQuotaRetry`, `cmd/agc/internal/provisioner/capacity.go`), which does not say that the raise is the reason.
What the listener does next with the job it was offered has not been read.

- The class could cap the raise at the pod's limit, and withhold as `own_limit` where that is no raise.
- The sizing profile is expected to have the same gap: a limit it derives can pass a pod-level limit with no kill at all.
- Under `Binpack` the request rises too, and the containers' requests together must be at or below a pod-level request (the same function).
- A `LimitRange` maximum is expected to refuse the raise the same way (from recall, not read).

[Q1388](Q1388.md) has the same shape, a raise nothing can hold, with no refusal: the pod is created and stays `Pending`.
The duplicate search flags Q1389, which was a raise for the wrong job, and Q1400, which was what the raise's Event says of the cause.
