# The runner-host preflight scores an HTTP answer for a dial failure

The Q352 attribution banner scored two identical spec failures in one run in opposite directions, and the one it got most confidently wrong is the one a reader acted on.

**Measured 2026-09-17** from the 2026-09-16 kindnet e2e job log (`gh run view --job 104998010114 --log`, run [35156765438](https://github.com/actions-gateway/github-actions-gateway/actions/runs/35156765438)).
Both `[real-github-egress]` proxy-CONNECT specs failed on `curl: (56) CONNECT tunnel failed, response 502`, minutes apart, on the same signature.
The failure-time `AfterEach` stamped:

```
=== RUNNER-HOST GITHUB PREFLIGHT: BLOCKED (HTTP 403 in 71ms; x-ratelimit-remaining=0; body: {"message":"API rate limit exceeded for 52.160.165.208. …
=== RUNNER-HOST GITHUB PREFLIGHT: REACHABLE (HTTP 200 in 164ms) ===
```

`BLOCKED` prints *this spec's failure is attributable to runner->GitHub egress: infrastructure, not a product regression (Q352).
Re-run the job.* `REACHABLE` prints *treat this failure as real and inspect the in-cluster path.* Same run, same signature, opposite instructions.

## The defect is the layer, not the scoring table

`ScoreGitHubEgress`'s 403 → `BLOCKED` rule is Q648's fix and it is correct for the question that probe asks: `/zen` needs no credentials, so a refusal is about the source address, and the in-cluster path NATs through it.
The defect is that every row of that table describes a response GitHub **sent**, which means the TCP connection and the TLS handshake both completed.
The failure being attributed is a `net.DialTimeout` that never got that far.
The proxy's own logs on that run recorded nine `dial tcp 172.182.252.137:443: i/o timeout` across both replicas, spanning the whole window in which the probe returned 403 and then 200.
A rate limit cannot produce a dial timeout, so `BLOCKED` was not an explanation of that failure; it was a true statement about a different layer, delivered as a verdict on this one.

The banner does not say so, which is what makes it expensive: it is the strongest-looking signal on the page, it names the spec that failed, and its guidance ends in an instruction.

## What to change

The probe's own reading is sound and worth keeping; what it needs is a scope sentence rather than a narrower table.
Two candidates, and they are not exclusive:

- **State the layer in the guidance.** A non-2xx verdict already proves the runner completed a TCP connection to GitHub, so `BLOCKED` on a 403/429 could say that outright instead of only *re-run*.
  It is evidence *against* a dial-level cause, which is the opposite of how it currently reads.
- **Add a layer-matched probe.** A bare `net.DialTimeout` to `api.github.com:443` from the test process answers the hop a CONNECT 502 failed at, and costs no credentials and no HTTP request.
  Where the TCP dial succeeds from the runner and the proxy's dial times out in the same window, the divergence is in-cluster; where both fail, it is the segment.

[Q1119](Q1119.md) shipped the proxy-side half of this, an `EGRESSPROXY CONNECT ATTRIBUTION` banner that names the refusing hop from the proxy's own logs, and is parked on its next occurrence.
That banner's `UPSTREAM-DIAL-FAILED` guidance already carries one sentence saying an HTTP-layer verdict cannot explain a dial-level failure, so the two banners no longer contradict each other silently; this row is the other side of the same reading, in the mechanism that produced the wrong instruction.

`.github/workflows/e2e-reusable.yml` mirrors the scoring table in shell for the case where the suite process dies before its `AfterEach` runs ([testing.md § Runner→GitHub egress attribution](../development/testing.md#runnergithub-egress-attribution-q352) says so, and `github_egress.go`'s godoc says to change both together).
Whatever lands here lands there too.
