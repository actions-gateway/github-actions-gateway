# Warn before the pinned runner ages out of GitHub's 30-day window

GitHub stops queueing jobs to a self-hosted runner not updated "within 30 days of a new version being made available" ([runner update policy](https://docs.github.com/en/actions/hosting-your-own-runners/managing-self-hosted-runners/autoscaling-with-self-hosted-runners), read 2026-09-29), and says nothing about refusing its connection, so a stale pin would show up as every job lapsing rather than as an error.
It has already happened once: the dogfood e2e tenant received no job on 2026-09-29 on a 2.335.1 worker and ran one the same day on 2.337.0, the worker image being the only difference between the two dind windows.
Its runs show the window is not counted from the first newer release; counting from the newest is consistent with them, and the exact start is still unmeasured.

Nothing in the repo reads that window.
`MinRunnerVersion` and the `RunnerVersionTooOld` condition check GitHub's registration floor only, and `names.go` already says why a compiled-in constant cannot track a rolling floor.
Dependabot's docker ecosystem proposes the bump, but a proposal is not a merge, and its weekly PR can sit unmerged past the deadline without anything reddening.

**Done when** a scheduled check compares `names.RunnerVersion` against the actions/runner releases newer than it, counting from the first one's `publishedAt` (the documented reading, and the stricter one), and goes red with days-remaining well before day 30 (say day 21), so the product default and the dogfood images are bumped while jobs still run.
It reads GitHub's release API rather than the tree, so it belongs in a scheduled workflow, not in `make check`.
The tenant-side analogue, a `workerImage` older than the window, is a separate question for `RunnerVersionTooOld` and not in scope here.
