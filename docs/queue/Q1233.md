# A terminating-worker re-offer mints a runner registration each time

A scale-set job held under `reason="worker_terminating"` mints a JIT config on every re-offer before the provisioner finds the previous worker pod still terminating, so each re-offer registers a runner at GitHub and the next one's name conflict deregisters it (the Q334 reclaim).
The ceiling path avoids the same cost with `CheckCapacity`, a pre-check the listener runs before the mint (Q576); the terminating path has none.

Bounded by the re-offer ladder (30s doubling to 5 minutes), so at most about 12 registrations an hour per held job once the backoff caps.
That figure is derived from the ladder, not measured.
It matters only for a pod held terminating for a long time, which usually means a lost node.

**A likely fix**: a pre-check beside `CheckCapacity` that reads the job's pod by its deterministic name and defers without minting when it carries a `deletionTimestamp`.

Not Q1195, which the near-duplicate search names: that row is a reaped `Pending` worker leaving an unnamed job with no runner, a lost job; this one loses no job and only spends registrations.

**Reach.** Scale-set tenants with a worker stuck terminating while its job is replayed: GitHub API calls and offline runner records, not lost jobs.
