# Make the `restricted` worker security profile the default

**The default worker profile is `baseline`, so a tenant gets in-container root through `sudo` and the container runtime's default capabilities unless its namespace opts in to `restricted`.** `baseline` sets pod-level `runAsNonRoot`, `runAsUser: 1001` and seccomp `RuntimeDefault`, and deliberately leaves out `allowPrivilegeEscalation: false` and `capabilities.drop: [ALL]` (`docs/design/05-security.md:1143:Deliberately **not** `, `docs/operations/admission-policies.md:65:deliberately does not`).
A namespace labelled `actions-gateway.com/security-profile=restricted` gets both.
Default-deny egress holds under either profile; what `restricted` adds is resistance to a kernel escape, with no root to escalate to and no capabilities to start from.

**Why `baseline` is the default today, and how much of it is measured.** The reason given on 2026-11-19 is migration: jobs written for Actions Runner Controller (ARC) or GitHub-hosted runners expect `sudo`.
The docs give a related one, that "a large fraction of real CI jobs rely on it", and nobody has measured that fraction.

**Why the full flip is a 3.0 candidate.** 2.0 spent its breaking-change window on refusing fork pull requests by default, a default with a one-field opt-out (`spec.forkPullRequests: Accept`).
`restricted` with an opt-out back to `baseline` is the same shape.
It is breaking by [api-review.md § Is this change breaking?](../development/api-review.md#is-this-change-breaking): a namespace with no label changes behaviour on upgrade.

**The opt-out is one label only at namespace creation.** `namespace-security-profile-guard` ranks `restricted` above `baseline` and refuses a lowering update without the `actions-gateway.com/allow-profile-downgrade=allowed` annotation; a create is exempt (`charts/actions-gateway/templates/namespace-security-profile-guard.yaml:57:oldObject == null`).
So a tenant opting out after the flip needs the label plus a platform-set annotation, not the one label the fork-refusal comparison suggests.
The absent-label default also lives in three places that would all move together: that guard's CEL (`absent → 'baseline'`), `ActionsGatewayV2Reconciler.namespaceSecurityProfile`, and `NamespacePSAReconciler`.

**Two options might land before 3.0**, and grooming picks between them and waiting:

- **(a) Default newly created tenants to `restricted`, leaving existing ones alone.** By the api-review table this is still a changed default with "two populations, silently", so it is likely breaking under GAG's own policy; settle that before scoping it.
  It also needs a way to tell a new tenant from an existing one, which reading a label at reconcile time does not give.
- **(b) Report tenants still on `baseline`**: a status condition, a metric, or an admission warning, so an operator can see the population a flip would change.
  Not breaking, and it produces the inventory the flip needs anyway.

**Measure:** what fraction of dogfood and sample jobs actually run `sudo` or need a capability `restricted` drops.
That number decides whether the flip is a migration note or a migration, and whether (a) is worth its breaking-change cost.

**Done when** the measurement is recorded, one of (a), (b) or wait is chosen with the reason written here, and the chosen shape is built or this row is deferred on a 3.0 scoping trigger.
