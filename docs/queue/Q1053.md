# Docs say a GITHUB_TOKEN push creates no runs; it creates withheld ones

Eight places in the tree assert that GitHub never re-triggers workflows from a `GITHUB_TOKEN` push, and prescribe close + reopen.
Both halves are refuted by measurement.

**Measured 2026-09-04 06:25 PDT**, with the full derivation in Q1052, which **owns the measurement**.

- **Runs are created.** All 16 workflow runs on [#1821](https://github.com/actions-gateway/github-actions-gateway/pull/1821)'s head `1851d3637e1ce1b0ad5489eea17b1430f35ab548` exist and read `action_required` (for example run 33508119136, `event: pull_request`).
  They are withheld pending approval, not suppressed.
- **Close + reopen is not what has been used.** Across the ten historical cases, nine have exactly one unit-test run and **zero** `reopened` timeline events; every one shows `run_attempt: 2` on the same run id with `run_started_at` well after `created_at`.
  They were released in place, by the "Approve and run" path, which a close + reopen could not produce, since reopening fires a fresh `pull_request` event and a new run at attempt 1.

The distinction is not pedantic.
The documented mechanism predicts an empty check list is benign and expected, which is exactly why a withheld PR ages unnoticed (Q1052).
It also sends a maintainer to a remedy that re-queues runs which will again await approval, instead of to the approval that actually releases them.
