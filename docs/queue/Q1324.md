# Validate four egress proxy sharing leads from the security audit

**Leads, not confirmed vulnerabilities.** Source supports each path and something outside the repository decides the outcome, so none has a severity.
[Each lead, with evidence, blockers and a validation plan](../plan/security-audit-2026-11.md#egress-proxy-sharing-leads):

- Provider-writable proxy TLS Secret is projected unvalidated into consumer namespaces and installed as an unconstrained trust root by consumer AGCs and workers (needs validation).
- A tenant can stall another tenant's EgressProxy reconcile with a labelled ConfigMap and an unblankable Secret in its own namespace (needs validation).
- Bring-your-own-autoscaled EgressProxy lets the live Deployment replica count drive an unbounded repeated-addition loop on the GMC's single EgressProxy worker (needs validation).
- Transport-only proxy tunnels to its own loopback listeners, so a worker can replace its source address and arrival port with the proxy's (needs validation).

Start with the first: a provider's proxy TLS certificate is projected unvalidated into consumer namespaces and installed as a trust root for the consumer's controller and workers.
Five separate hunting passes reported it, and it decides how far a tenant that shares its proxy is trusted by the tenants that consume it.

**Measure:** each lead's local test in the plan doc is an envtest or unit case that needs no cluster; what the test leaves open is one owner-observed fact per lead, named beside it.

**Done when** each lead is either confirmed and fixed, refuted with the measurement recorded, or written into `05-security.md` as an accepted residual with its bound.
The plan doc gives each one a bounded local test and the fact an owner has to observe.
