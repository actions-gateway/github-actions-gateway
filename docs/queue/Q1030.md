# Nothing reconciles the mirror's ingress peer with the worker's label

Two halves of the registry mirror's network posture have to name one label, and nothing compares them.
The worker-side [`e2e-mirror-egress`](../../deploy/registry-mirror/base/networkpolicy.yaml) selects `actions-gateway/component: workload`, and the shared topology's ingress peer ([`components/shared-tenants/`](../../deploy/registry-mirror/components/shared-tenants/kustomization.yaml)) ANDs that same label into its `from` element (Q1026).
Change one and the other keeps its own copy.

The drift is fail-closed and expensive rather than dangerous: workers lose the path entirely, which surfaces as a booked Kata window in which nothing pulls, and `manifest-validate` renders no kustomize overlay so nothing before that window sees it ([Q1024](Q1024.md) is the row for that gap).

The reconciliation is cheap and has a home.
[`check-registry-mirror-catalog-deny.py`](../../scripts/manifest/check-registry-mirror-catalog-deny.py) already reads both files and already reconciles the *port* across the base, the Services, the base policy and the component's restated copy; the label is the same shape of fact and the same two files.
Whether it belongs in that gate or a sibling is the open question — that gate's stated concern is the catalog deny, and a label reconciliation is a second concern under one name.

**Measured 2026-08-29:** the component's ingress peer and the base's egress `podSelector` both read `actions-gateway/component: workload`, so the tree is in step and a gate added now would pass.
That is what makes it worth adding rather than urgent, and it is also why "it passes" proves nothing on its own: assert a seeded mismatch fails.
