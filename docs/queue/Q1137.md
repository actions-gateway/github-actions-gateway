# Preflight `BLOCKED` asserts in-cluster egress is refused too, unmeasured

Both `BLOCKED` arms of `GitHubEgressGuidance` tell the operator that the in-cluster path "NATs through the same address, so it is refused too", and conclude the spec's failure is attributable to runner egress.
The NAT half is a property of the cluster and is not in question.
The inference drawn from it is: that a refusal of the *runner host* predicts a refusal of *in-cluster* traffic to GitHub.

**The mechanism is unverified, and this row asserts no defect.** The probe fetches `https://api.github.com/zen` unauthenticated, and the refusal that drove Q1126's own evidence was `API rate limit exceeded for 52.160.165.208`, GitHub's unauthenticated per-IP bucket.
In-cluster traffic from a runner is authenticated with a GitHub App or runner token.
If GitHub buckets authenticated requests separately from the unauthenticated per-IP pool, a 403 on the probe says nothing about whether the in-cluster path is refused, and the banner would be sending an operator to re-run a job whose failure is real.
If it does not, the sentence is correct as written and this row closes with a citation.

Nobody has measured GitHub's bucketing here, on either side.
That is the whole task: establish whether an unauthenticated per-IP 429/403 predicts refusal for an authenticated request from the same source address, then either cite it in the godoc or narrow the sentence to what the probe actually establishes.

## Scope

The clause predates the layer split and was carried through it unchanged, so it is not a regression.
The layer split settled *which layer* a `BLOCKED` verdict speaks at; this row asks whether the verdict's claim about the in-cluster path holds at all.

Raised in independent review of the preflight-layer PR, which deliberately left it alone rather than edit an operator instruction on an unmeasured hunch.
Any change here moves a string two unit tests pin, so it lands with its own test update.

**Measure:** drive the in-cluster path while runner egress is refused and record whether it is refused too.
The claim is about a NAT the row has never observed, so no precedent in the repo can settle it and no preference should -- the answer decides whether the banner keeps an operator instruction or drops it.
A kind lane with the egress policy applied is the cheapest venue; say in the row which lane was used, because the two CNI lanes NAT differently and an answer from one is not an answer for both.
