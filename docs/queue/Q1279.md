# Load-test the scale-set tier for concurrency and goroutine leaks

The only measurement of the shipped acquisition tier is `TestScaleSetPerListenerMemory` (`make scaleset-mem-profile`): 200 parked scale-set sessions in one AGC, memory only.
It runs no jobs through them, so it says nothing about throughput with many jobs in flight or about goroutines leaking across session re-creates and job completions.

The classic tier had that evidence: the in-process harness Q13 built ([`cmd/agc/test/load/` at `v1.10.0`](https://github.com/actions-gateway/github-actions-gateway/tree/v1.10.0/cmd/agc/test/load), `load-test-quick`) held ~1,000 concurrent sessions with zero goroutine leak.
It drove the classic multiplexer, which Q264 removed with the harness, so none of it describes the scale-set path.
Q1274 ported the e2e suite to the scale-set tier, which checks that jobs run correctly one or a few at a time; it applies no sustained load and asserts nothing about goroutine counts, so it does not cover this.
[README.md](../../README.md) and [appendix-a](../design/appendix-a-capacity-slos.md) say so since Q264, and point here.

**The work:** drive many RunnerSets' listeners against `scalesettest` with jobs assigned and completed at a sustained rate, and assert the AGC's goroutine count returns to its baseline once they drain, and after forced session expiry.
`scalesettest`'s per-session server goroutines run in the same process, so count against a baseline taken with the server up, or the figure measures the fake.

**Done when** a make target runs it, its leak assertion fails with a listener goroutine deliberately leaked, and the README and appendix-a cite its result in place of the "not yet load-tested" caveat.
