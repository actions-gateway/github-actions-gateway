# A runner killed for the node's memory is read as its own-limit kill

The out-of-memory class, shipped in `v2.0.0` (Q1183) and unchanged for this by 2.1, acts on a runner the kernel killed because its **node** ran out of memory as if the runner had reached its own limit.
Read from source and not run: no node-level kill of a runner has been made or found on record.

`oomKilledAwaitingRecovery` (`cmd/agc/internal/provisioner/oom_class.go`) takes any `PodFailed` worker whose runner terminated `OOMKilled`, and `recoverOOMKilled` compares nothing with the limit.
The reason is expected for a node kill too: containerd sets it from the cgroup's `oom_kill`, which counts "any kind of OOM killer" (kernel `cgroup-v2` documentation), and that counter rose for a kill made by a limit above the pod on one local kernel ([the counters](../plan/q555-automatic-recovery-design.md#what-is-left-open-q1316)).

What an operator would see, by the runner's shape, beside the `PlatformFaultOnFailedJob` Event that a killed runner's completion raises about ten minutes later ([M4](../plan/q555-automatic-recovery-design.md#readings-from-the-dogfood-turn-up-2026-11-22), whose runner had a limit; read from `flaky_jobs.go` for one without):

- **`Binpack` or `Throughput`, with its limits derived:** where the run still has a slot, a Normal `MemoryLimitRaisedForRetry` Event says the runner was killed at its memory limit, the job's limit is raised for its next attempts (under `Binpack` its request too), and the run is re-run on a slot of its budget.
  The re-run may well pass, on a fresh node.
  A second kill of the job is withheld as `same_class_again`, and the class's breaker counts the run, so a node short of memory can pause the class for the set.
- **`Static` or `NodeShare` with a limit, or `Binpack` or `Throughput` still `AwaitingSamples` when the pod was built:** the re-run is withheld as `own_limit`, and the Event tells the operator to raise the runner's limit or pick another profile, neither of which is the cause.
  A derived limit already at its ceiling is withheld the same way, with `spec.sizing.maxRequests` named instead.
  A fresh pod on another node would have been a fair retry.
- **No memory limit:** no re-run and no Event from the class, and an Info log line that says the runner had no limit of its own.

The exposure is widest for a BestEffort worker, whose containers set no requests or limits and are scored 1000, and it is otherwise a Burstable worker's, where the kubelet scores a container by its request: `Throughput`, `Static` or `NodeShare` without equal limits, and `Binpack` beside a container that keeps its pod Burstable, as `privileged-dind`'s sidecar does, or the wrapper's init container where image volumes are off.
Inside such a pod a Docker-in-Docker sidecar never scores above the runner ([why](../plan/q555-automatic-recovery-design.md#what-is-left-open-q1316)).
A Guaranteed pod, which `Binpack` is meant to give, is scored -997 whatever it requests and is among the last to go (`pkg/kubelet/qos/policy.go`, v1.35.5, read).

- What separates the two is open, and is the [node-level out-of-memory kill](../plan/q555-flaky-job-retry.md#candidate-classes) candidate's question: a kill below the container's own limit, with a `SystemOOM` Node Event or the pod's `oom` counter at 0.
  The Event names a process and not a pod, and is raised for a node-wide kill and not for one at `kubepods`' limit: the kubelet records it where the kernel's line names no memory cgroup (kubelet 1.35.5 `oom_watcher_linux.go` and its cAdvisor `oomparser.go`, kernel 6.12 `memcontrol.c`, read).
  The AGC reads neither Node Events nor cgroups today; the usage sampler's peak beside the limit is the one fact it has, and a spike between samples defeats it.
- Reproduce it first, since every step above is read: [Q1316](Q1316.md)'s dogfood reproduction fills a node and expects exactly this kill.
- Failing a discriminator, the Event and the withheld reason's text can stop asserting a cause the class did not check.
