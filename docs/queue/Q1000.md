# A green pages run published no docs for the tag

Cutting `v1.6.0` on 2026-08-26, the tag's `pages.yml` run finished with every step green, including `Deploy to GitHub Pages`, and the site did not have the release: `https://actions-gateway.com/1.6.0/` returned 404 and `/stable/` still served 1.5.0, for roughly 25 minutes until a manual `workflow_dispatch` republished it.
`make verify-published-docs VERSION=v1.6.0` is what found it.
Postmortem: [2026-08-26-the-tag-published-no-docs.md](../postmortems/2026-08-26-the-tag-published-no-docs.md).

**The mechanism is not established, and this row should not code to one.** What is measured: `mike` pushed `898d30bb6..36c3acfc5` to `gh-pages` at 23:25:05.550 with `1.6.0` carrying the `stable` alias, the next step in the same job assembled the artifact with `git archive gh-pages` at 23:25:05.557, and the artifact that deployed did not contain 1.6.0.
The two pages runs in the window did not overlap (the `main` run finished 23:23:14, the tag run started 23:24:12), so serialisation is ruled out.
Two hypotheses survive: `git archive gh-pages` resolving a ref that is not the one `mike` just wrote, or unusually long CDN propagation that the republish merely coincided with.
Distinguish them before changing anything -- the second would make an artifact assertion useless and point at a wait-and-verify step instead.

The preventative fix is the same either way and is worth having on its own: the job's `Verify the artifact serves a reachable root` step asserts `_site/index.html` and `_site/CNAME` exist, neither of which can fail when the version tree is stale.
Assert that `_site` contains the version being deployed, and that `_site/versions.json` lists it with the alias the run resolved.
A deploy that publishes the wrong tree should fail its own run rather than wait for a human to read the live site.
