# Build the dogfood runner images in CI

`dogfood-e2e-runner` and `dogfood-runner` are built by hand and pushed to GHCR, so a Dockerfile edit changes nothing until someone runs that push and bumps the overlay pins.
Q1284 needed exactly that: the pinned image's Helm refused the new Kubernetes floor, and the fix took a manual `2.338.1-2` push.

No workflow names either image (`git grep` over `.github/workflows`, 2026-11-06).
Both GHCR packages read `repository: null` where `gmc` reads this repo (`gh api orgs/actions-gateway/packages/container/<name>`), so a workflow's token probably needs the repo granted Actions access to each package first.
That access rule is recalled from GitHub's documentation and has not been tested here.

Done when a workflow builds and publishes both images from their Dockerfiles, without overwriting an existing tag, and `scripts/dogfood/e2e-runner/Dockerfile`'s header and `runner-build.sh` describe that instead of a manual push.
