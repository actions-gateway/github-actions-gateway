# A removed pull request's merge-group run is still re-run

A pull request removed from the merge queue and not queued again has no newer group, which is the only thing the `superseded` check can see of a merge group (Q1381).
So a job disrupted in such a group's run is re-run, for a result nothing reads, and spends a slot of `maxEvictionRetries`.

Measured with the shipped check over 373 merge-group runs whose commit never reached the default branch (three repositories, one workflow each, [the readings](../plan/q555-automatic-recovery-design.md#readings-for-the-merge-group-check-2026-11-23)): a newer group exists for 62 when the run concludes, 161 ten minutes later, 265 after an hour and 342 after a day.
A disruption that fails a required job is the case it misses most: of the 106 runs that concluded `failure`, 5 have a newer group then and 38 ten minutes later.
How often a disruption lands in such a run is not measured.

What would close it is the group's ref, which is deleted within two seconds of the removal.
Two things stand in the way:

- Reading a ref, a comparison, the activity list or a branch needs `Contents: read`, and [onboarding](../operations/tenant-onboarding.md#0a-create-the-app-web-ui) leaves Contents at No access, because the gateway never reads tenant code.
- A merged group's ref is deleted too, and its optional runs can go on (370 s after, on #2344), so a missing ref would also withhold a re-run for a merged commit, which somebody may want.

Reading whether the pull request is in the queue (GraphQL `mergeQueueEntry`) is the other candidate; onboarding leaves Pull requests at No access too, and which permission that read needs is not checked.
The question is whether the saving is worth a wider App permission, or an opt-in one; leaving it as it is costs one slot and one re-run per disrupted job.
