# Validate five worker pod and NetworkPolicy leads from security audit

**Leads, not confirmed vulnerabilities.** Source supports each path and something outside the repository decides the outcome, so none has a severity.
[Each lead, with evidence, blockers and a validation plan](../plan/security-audit-2026-11.md#worker-pod-and-networkpolicy-leads):

- Gateway teardown deletes the workload NetworkPolicy while worker pods running job code can still be alive (needs validation).
- Unmarking a tenant namespace revokes only the one canonical reader RoleBinding, so other GMC-written bindings keep granting Secret access there (needs validation).
- namespace-psa-guard admits the GMC ServiceAccount setting Pod Security enforce=privileged on a marked tenant namespace that lacks the platform eligibility label (needs validation).
- DNS egress rule confines which resolver a pod may contact, not which names it resolves; the design states the DNS exfiltration channel is closed (needs validation).
- GitHub CIDR allowlist admits /meta `actions` ranges that serve Azure blob storage, so direct-mode worker 443 egress may not be GitHub-only (needs validation).

The Azure-ranges lead is already open as [Q1253](Q1253.md), which holds a dogfood measurement this audit did not have; Q1253 owns it and it is listed here only so the audit's record is whole.
Of the other four, start with gateway teardown deleting the workload NetworkPolicy while job pods may still be running.

**Measure:** each lead's local test in the plan doc is an envtest or unit case that needs no cluster; the network leads also need a reading on an enforcing CNI.

**Done when** each lead is either confirmed and fixed, refuted with the measurement recorded, or written into `05-security.md` as an accepted residual with its bound.
The plan doc gives each one a bounded local test and the fact an owner has to observe.
