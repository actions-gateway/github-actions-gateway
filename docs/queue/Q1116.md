# Three scripts-test suites fail only on the dogfood runner

**Event:** the `scripts-test` job fails on a `gag-ci-scaleset` runner with any of `FAIL rule 9: an anchored last item still obliges the flip (rc=0 want=1)`, `FAIL a target that does not render is caught: want rc 1, got 0`, or `FAIL the recorded stop takes the run AND its children: want 'yes', got 'no'`.

**Measured 2026-09-16** from the only two `unit-test.yml` runs that have put this job on the lane, both `workflow_dispatch` on `main` with `target_gag=true`:

| Run | When | Commit | Job | Suites failing |
|---|---|---|---|---|
| [34802508013](https://github.com/actions-gateway/github-actions-gateway/actions/runs/34802508013) | 2026-09-14 03:24Z | f771594d11 | 364s | `check-registry-mirror-render-test`, `check-queue-rules-test` |
| [34827435782](https://github.com/actions-gateway/github-actions-gateway/actions/runs/34827435782) | 2026-09-14 09:20Z | 86fbb6061a | 314s | those two, plus `record-launch-test` |

Both concluded `failure` rather than a timeout `cancelled`, and every other step in each job succeeded.

**It reproduces, so it is not a flake, and the label drops accordingly.** Two runs six hours apart on different commits produced character-identical assertion text for the first two suites.
A flake passes on rerun without a code change; these did not.

**The lane is 2 for 2 and `ubuntu-latest` is 0 for 11.** Across the `unit-test.yml` runs carrying this job on 2026-09-15 and 2026-09-16, `scripts-test` was green every time on `ubuntu-latest` at 140-245s.
No green run exists on the scaleset lane, so runner and outcome are still perfectly confounded and the association cannot yet be called causal; what the second run removes is the possibility that one reading was chance.

**One signature spans all three suites**, which is why this row is no longer about rule 9.
Each assertion wants the active answer and gets the passive one: a checker told to exit 1 exits 0, twice, in two unrelated checkers; and a stop that must reach the run's children reports that it did not.
That last one is the most legible, because reaching a child process is a property of the process group rather than of any assertion's logic, and a worker pod's PID namespace is exactly the kind of thing that differs from a GitHub-hosted VM.
**Unverified:** no reading has been taken inside the pod, and the three are grouped on the shape of their failure rather than on a mechanism anyone has traced.

For `check-queue-rules` specifically the line beside the failure reads `check-queue-rules: ok (1 item(s), 2 at the merge base, rules 8, 9, 11, 13 and 14)`, a one-item view, so the thread there is whether the fixture's second item was absent when rule 9 was evaluated, which would make the rule vacuous rather than wrong.

Reaching the lane again needs a `workflow_dispatch` with `target_gag`, which is what a third reading costs.

Not [Q822](Q822.md): that row's trigger names `git-merge-script-index-test` and `git-merge-plan-index-test` and a `merge-*-index: the build failed with:` line, and these are different suites reaching different verdicts.
Not Q947, which is `status-lint`'s path filter omitting a checker's wrapper rather than any checker's own behaviour.
