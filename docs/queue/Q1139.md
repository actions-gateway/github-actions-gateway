# Let a pin-bearing page cite a measured kubectl version

`check-release-pins.sh` asserts that every release-version literal on the five pin-bearing pages names the current release, so a third-party version written plainly there reads as a stale pin and fails the gate.
The documented escape is to write the project's name immediately before the version, which works only for names in `release_thirdparty_projects_regexp` (`scripts/lib/common.sh`).
That list holds two entries, `ARC` and `actions-runner-controller`.

`kubectl` is not on it, and it is the third-party tool those pages name most.
Measured 2026-09-24: adding `Measured on kubectl v1.36.3` to the pre-upgrade alias check in `docs/operations/upgrade.md` failed the gate, which reported that line as pinning `v1.36.3` when the current release is `v1.8.0`.
The claim it was citing is real and locally reproducible without a cluster, `kubectl config view -o 'jsonpath={range .clusters[?(@.name=="a" || @.name=="b")]}{.name}{end}'` exiting 1 with `unrecognized character in action: U+007C '|'`, so the version is exactly the kind of measurement [documentation-standards.md § An upstream-behavior claim cites a measurement](../development/documentation-standards.md#an-upstream-behavior-claim-cites-a-measurement) asks for.
The in-flight work that hit this shipped the citation as `the kubectl 1.36 client` instead, which clears the gate because the regexp needs a third component, and loses the patch digit.

**The question is whether the hole is worth it, and it is the maintainer's.** That doc calls adding a name a deliberate act, "because each is a hole in a gate whose whole tractability rests on that small noise floor".
Against: one more name is one more shape a stale pin could hide behind.
For: a `kubectl vX.Y.Z` on these pages can never be a this-project pin, the pages will keep wanting to cite one, and the minor-only workaround is a precision loss the standard did not ask anyone to take.

**Done when** either `kubectl` is in `release_thirdparty_projects_regexp` with the gate's test asserting both directions, or the decision to leave it out is recorded in documentation-standards.md beside the existing two-name list, so the next session hitting it reads the answer instead of re-deriving the workaround.
