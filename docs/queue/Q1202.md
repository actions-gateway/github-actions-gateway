# Flake: lease-test's lost-lease renewer races the owner's sleep 2

**Top of queue per [flakes-first rule](../development/maintaining-backlog.md#flake-fixes-go-first).**

Observed 2026-10-23 at about 20:00 PDT in a local `make check` on the Q1193 branch, which touches nothing under `scripts/dogfood/lease*` or `scripts/dogfood/lib/`.
One case failed and the rest of the suite passed:

```
[lease-test] FAIL a renewer that lost its lease stops renewing: want '0', got '1'
```

Running `scripts/dogfood/lease-test.sh` alone straight afterwards, with no code change, exited 0 with 69 `ok` lines.
`uptime` read `load averages: 223.22 126.78 60.58` while that `make check` ran, on the 18-core host.

**Mechanism unverified; the shape points at a wall-clock budget.** The case at `scripts/dogfood/lease-test.sh:388:check "a renewer that lost its lease stops renewing" "0" "${quiet_alive}"` starts a renewer, hands the lease to another holder with `remote_lease 1 "ci-runner-7/4242"`, and checks `kill -0` on the renewer once the owner's `sleep 2` returns. So the renewer has to notice the loss and exit inside that window, and at load 223 it plausibly did not get scheduled in time. Not measured: the renewer's poll interval against the 2 s, and whether the renewer was still running or merely slow to exit. The fix is likely a bounded wait for the renewer to exit, the shape the next case already uses (`for _ in $(seq 30)` at line 401), rather than a single `kill -0` read.
