# Flake: lease-test's lost-lease renewer races the owner's sleep 2

**Event:** `lease-test` fails `a renewer that lost its lease stops renewing` on `main`, or locally on a tree that passes it alone.

Observed 2026-10-23 at about 20:00 PDT in a local `make check` on a branch that touches nothing under `scripts/dogfood/lease*` or `scripts/dogfood/lib/`, at load averages of 223 on the 18-core host:

```
[lease-test] FAIL a renewer that lost its lease stops renewing: want '0', got '1'
```

**Mechanism, measured 2026-10-27.** The case ran the renewer at `RELEASE_LEASE_RENEW_INTERVAL=0.2` against an owner that slept 2 s, and read `kill -0` once the owner returned.
The renewer notices the lost lease only on its next tick, so a host that delays it past the owner's sleep fails the read.
Stretching the interval to 2.5 s in a copy of that test reproduces the exact line above (`want '0', got '1'`, exit 1, every other case `ok`).

**The case holds the owner alive while it waits.** The owner sleeps 8 s, and the test polls up to 5 s (50 x 0.1 s) for the renewer to exit, then asserts the owner is still running.
A wait that starts after the owner exits passes through the renewer's owner-gone exit (`kill -0 "${owner}" || exit 0`) and never exercises the lost-lease one. Mutating `lib/lease.sh`'s `[[ "${on_lost}" == stop-owner ]] || exit 0` to `|| continue` makes the suite exit 1 with the flake's own line; unmutated, it exits 0.
A grep for `kill -0` in the test finds the renewer-exit case, already a bounded wait, and this one.

**Not this row:** `kill -0` succeeds on a zombie, which is how the same suite fails deterministically on GAG runners.
The row for the renewer-exit check carries that state check, and the same one belongs in this loop.
