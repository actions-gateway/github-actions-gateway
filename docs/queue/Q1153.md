# Idle scale-set worker left by a cancelled job waits out lifetime cap

When a scale-set job ends before any runner starts it, one of the set's workers has nothing left to run.
Since Q1151 the completion reclaims the worker created for that job only when its runner has not started another job.
If it has, the idle worker is a different one, created for a job that ran elsewhere, and nothing stamps it.
It then sits at `Listening for Jobs` holding a concurrency slot and a node until `spec.maxWorkerLifetime` (12 hours by default), which is the Q420 symptom with a lifetime cap behind it.

The case needs a cancellation that lands while the cancelled job's own runner has already taken another job, so it shows up under `cancel-in-progress` concurrency groups on a busy set.
Its rate is unmeasured.

**What a fix has to do.** Pick the surplus worker without reaping a busy one: some worker whose runner has not started a job (no `actions-gateway.com/started-job-id`), stamped only when the set has more such workers than assigned jobs still waiting to start.
A `JobStarted` already lifts a stamp set on an idle worker, so a wrong pick costs a stamp rather than a job, but the choice of which idle worker is still the open part.

**Reach.** Any scale-set tenant that cancels queued jobs; the cost is idle capacity held, not failed jobs.
