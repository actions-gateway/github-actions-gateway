# Rank-collision signal is gone from this repo's allocation path

Before the Q956 re-vendor, `queue.py lint` noted every pair of items sharing a rank: `shares rank X with Y; order falls back to id`.
Measured over the store at `25edfb0c4`, it was firing on 33 rows.
The re-vendor removed it, deliberately and correctly on upstream's argument, which is in `Item.sort_key`: a tie is the resolution rather than a defect, and a duplicate-rank check paired with the duplicate-id one implies otherwise.

Upstream did not drop the signal, it moved it to mint time — `queue.py rank` warns when the key it just minted is one the store already holds.
That relocation does not reach this repo.
`scripts/docs/alloc-queue-id.sh` names neither `queue.py` nor `rank`, so nothing on the path a session actually takes to allocate an ID ever asks the question, and the signal is gone here rather than moved.

Nothing is broken by that: ties are legal, order falls back to id, `queue-lint` is green, and no gate or doc depended on the note.
What is lost is the only reading that said how often it happens.
Two rows sharing a rank means whoever minted the second one did it by hand or off a stale read, which is the same class of mistake [queue-id-allocation.md](../development/queue-id-allocation.md) built the claim refs to catch for IDs — and 33 is not a rounding error.

The repair is to decide where the question belongs and put it somewhere the allocation path reaches: `alloc-queue-id.sh` calling `queue.py rank` so the mint-time warning fires, or a repo-local check that reports collisions without treating them as defects.
Prefer the first if it fits, since it is the shape upstream chose and needs no second implementation.

Found in review of [#1886](https://github.com/actions-gateway/github-actions-gateway/pull/1886), which is where the removal shipped.
