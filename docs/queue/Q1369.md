# Ship a CI-validated kata-plain template: Kata isolation without DinD

The template library has no entry that puts a job in a Kata micro-VM without also giving it a Docker daemon, so an operator who wants "Kata by default" has to make `kata-dind` the default for every job.
That is a poor default: as shipped, `kata-dind` sizes each worker's guest at 8 vCPU and 12Gi of limits (4 vCPU and 8Gi requested) plus a 100Gi block PVC, needs the worker namespace at PSA `privileged` for its capability adds, and opts out of the AGC's `applySecurityDefaults` gap-fill, which only `plain` composes with.

A `kata-plain` entry would be `plain` plus `runtimeClassName: kata`: a guest kernel around every job, with no daemon, no added capabilities and no block volume.
It is the entry an operator would mark with `actions-gateway.com/is-default-template` on a cluster whose nodes support Kata, keeping `kata-dind` for the jobs that need Docker.

**Unverified, and the first thing to measure:** the row assumes the shape admits under PSA `baseline` (and `restricted`) and that the gap-fill's `runAsNonRoot`, numeric `runAsUser` and seccomp stamps still let the runner start inside the guest.
`runtimeClassName` is not a PSS-checked field, which is why this looks free, but nothing here has run the stock runner image under Kata without the dind sidecar.

**The library gate decides most of the size.** `scripts/ci/check-template-library.sh` fails an entry no dogfood overlay consumes, and the [README](../../deploy/templates/README.md#what-may-ship-here) makes that the membership rule, so declaring `kata-plain` inert would ship an unvalidated claim.
The deliverable therefore includes a dogfood consumer: a RunnerSet on the e2e Kata node pool running a job that needs no Docker, so every release candidate exercises it.
Picking that job and its label is the open design question.

Also in scope: a row in the library's "Which entry" table and in [runner-template-library.md § Choosing an entry](../operations/runner-template-library.md#choosing-an-entry), and an `envtest` admission case beside `TestTemplateLibrary_Admitted`.

Out of scope: an AGC that falls back to another template when Kata cannot schedule.
That would let the environment silently pick a less isolated shape, which the secure-by-default rule forbids; the supported pattern is a separate, fork-refusing `privileged-dind` RunnerSet that jobs name explicitly in `runs-on`.
