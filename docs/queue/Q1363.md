# Start the Dragonfly gate leg on a fresh e2e node, not a warm one

**The Dragonfly leg's `node-p2p` reading needs the worker image pulled through the node client, and today it gets a fresh node only because the tenant swap before it is slow.** Land this before [Q1362](Q1362.md), which removes that slowness.

The leg installs Dragonfly's node client (Q540) so the kubelet pulls worker images through it, and `dragonfly_node_p2p_reading` records whether containerd sent any request by the peer-to-peer rule.
On both measured gates (`v2.0.1-rc.1` run 44236535751 and `v2.0.0-rc.3` run 44043297649) the swap into the leg held for 13 and 16 minutes, so the autoscaler had removed the DinD leg's node and the Dragonfly worker cold-started.
With the hold gone, the worker lands on the DinD node with the 722 MB runner image already cached, and the reading reports no request by rule, its `finding` shape, for a reason unrelated to Dragonfly.

**Done when** `dragonfly_leg` resizes the e2e node pool to zero (through `scripts/dogfood/lib/pool.sh`, not a bare `gcloud`) and waits for it before `e2e_leg` dispatches, and the gate's tests cover the order.
Today the resize is a no-op, because the pool is already at zero by then, so this changes nothing until Q1362 lands.
The cost is the resize itself, about a minute (estimate), on top of the cold start the leg already pays.

Not a duplicate of [Q1161](Q1161.md), which the allocator matched on the shared target: that row runs the legs on separate clusters.
