# Re-run a job killed at the limit all pods share, with no tenant cause

Blocked on [Q1406](Q1406.md), on v2.1.0 shipping, and on a dogfood reproduction of its own (reading 9 of Q1403's design): Q1316's victims are `privileged-dind`, which this class could never reach.

PR 8 of Q1403's design.
Being killed above the pod does not mean the tenant did not cause it, so `PodsLimit` would qualify only where no tenant pod on the node fails Pod Security `baseline`, the victim stayed within its memory request, and no other pod of the tenant passed its own.
`AbovePods` could never qualify.
The rule can also name `PodsLimit` for a kill above the pods, where another pod's allocation at the shared limit is waiting or spare, or that pod's directory went unread ([the shapes, and what each costs](../plan/q1403-oom-kill-reporter.md#where-it-names-the-wrong-limit)).
Today's actions are the same for both, and this class's would not be, so it has to answer that too.
What is known of each, and which of it is only reasoned, is in the design.
The duplicate search flags Q1394, a reading of one retry GitHub may refuse; it has nothing to do with which limit ran out.
