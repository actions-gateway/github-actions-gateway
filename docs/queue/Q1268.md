# Dashboard preview render times out on a slow exporter rollout

`apply_artifacts` in `deploy/monitoring/preview/render.sh` runs `rollout restart` on the synthetic exporter and then `rollout status --timeout=120s`, so on a loaded host `render.sh shot` dies `error: timed out waiting for the condition` before rendering anything.
Each retry restarts the exporter again and resets its counters, so retrying does not converge.

Measured 2026-11-02 by the Q1267 worker: three consecutive `render.sh shot` runs against `gag-obs` failed this way, at load averages between about 80 and 18 on the 18-core host, with ten kind nodes from other sessions sharing one 7.75 GiB Docker VM.
Each time the new exporter pod was Running within about 20 s, and the old one took more than two minutes to leave `Terminating`; a `rollout status --timeout=90s` taken afterwards reported success.
Why termination is that slow is unmeasured.
The exporter is a stdlib Python HTTP server, which may not handle SIGTERM and so would wait out its grace period, but nobody has checked.

Q1267 got its screenshot by running the script's render step by hand after the rollout settled, which is not something a contributor should have to know.

**Done when** `render.sh shot` renders on a host where the old exporter pod takes minutes to terminate: a rollout wait long enough for that, or an exporter that exits promptly on SIGTERM, or both.
Sibling of Q1187, the 30 s Grafana render timeout, which is the same wall-clock assumption at the next step; one PR could take both.
