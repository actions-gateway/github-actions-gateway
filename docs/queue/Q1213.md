# template-library-check passes an overlay whose patch matched nothing

A dogfood e2e overlay's JSON 6902 patch against a shipped `ClusterRunnerTemplate` selects its target by `group`/`version`/`kind`/`name`, and when the selector matches nothing kustomize skips the patch and still exits 0.
`make template-library-check` passes that tree, so the e2e lane would run the library template without its cluster specifics and nothing would say so.

**Measured 2026-10-26 while working Q1211**, kustomize from kubectl at `/opt/homebrew/bin/kubectl`: with `deploy/templates/privileged-dind/template.yaml` moved to `actions-gateway.com/v2` and `deploy/dogfood-e2e/overlays/dind/kustomization.yaml` still targeting `version: v2beta1`, `kubectl kustomize deploy/dogfood-e2e/overlays/dind` exited 0 and its render lost the overlay's `workerImage`, the `e2e` node-pool `nodeSelector`/`tolerations` and the `REGISTRY_MIRRORS` env.
`make template-library-check` reported `3 entries (2 exercised by a dogfood e2e overlay, 1 declared inert), 2 overlays, all patches JSON 6902` at exit 0.

**Why rule 7 misses it.** Rule 7 asserts the overlay's render is a superset of its *base's* load-bearing lines, which catches a patch that clobbers the base; a patch that never applies leaves the base intact, so the superset holds.

**Done when** the check fails on an overlay patch whose target selector matches no resource in the overlay's render, with a `check-template-library-test.sh` case that moves a template's `apiVersion` and leaves the overlay's target alone.
A plausible form is to assert, per patch, that the render differs from the render with that patch removed; that is unverified.
