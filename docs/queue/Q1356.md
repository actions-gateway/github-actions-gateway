# Check that every commit SHA a release note or plan doc cites resolves

**A commit hash in a release record can be invented, and nothing catches it.** On 2026-11-17, during the `v2.0.0` cut, the draft candidate-validation table in `docs/plan/v2-ga.md` named `v2.0.0-rc.1` as commit `00b4f4e`.
No such commit exists; the real one is `0c0048d5a`.
Review caught it before merge.
An abbreviated hash either resolves in `git cat-file -e <sha>^{commit}` or it does not, so this is a mechanical check that nothing runs.

**Scope it before writing it.** Three things decide the shape:

- **Which docs.** Release notes (`docs/releases/*.md`) should cite only commits reachable from a tag, so every SHA there must resolve.
  Plan docs also cite commits from PR branches that a squash merge later orphaned, and those resolve only while the branch's objects are fetched.
- **Which hex tokens are commits.** A backticked 7-to-40-character hex token is the candidate.
  Image digests are excluded because they carry a `sha256:` prefix.
- **History depth.** CI checks out shallow, so the gate needs a deeper fetch, or it has to say it skipped rather than pass.

This case was in a plan doc, so a check over release notes alone would have missed it.
The smallest version that would have caught it reads both, and fails only on a hash that resolves nowhere in the fetched history: an orphaned branch commit still resolves while it is fetched, and an invented one never does.
