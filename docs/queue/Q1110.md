# Tag and main pages deploys collide on one pages_build_version

A stable tag sits on `main`'s tip, so the merge push and the tag push are the **same commit** and both trigger `pages`.
`actions/deploy-pages` defaults `pages_build_version` to `github.sha`, so both runs create a Pages deployment under one id and only the first one serves.
The `pages-deploy` concurrency group serialises them on `gh-pages` and does nothing about this.

Measured on `v1.8.0`, 2026-09-14, at `09a57c0cc`:

| | main run 34833278906 | tag run 34833404022 |
|---|---|---|
| artifact assembled | 10:28:28 | 10:30:15 |
| `Created deployment for` | `09a57c0cc…` | `09a57c0cc…` |
| deploy step | success 10:28:40 | success 10:30:29 |
| what the site served | this one | never |

The tag run's own checks were all correct: `mike` pushed 1.8.0 with the `stable` alias to `gh-pages`, and `verify-pages-artifact.sh` confirmed the uploaded artifact carried both.
`verify-pages-live.sh` then failed after 286s, and the site still 404'd `/1.8.0/` at origin fourteen minutes later — `x-proxy-cache: MISS`, `age: 0`, so not an edge cache.
What identifies the winner is `last-modified: 10:28:39` on the live `/1.7.0/` page: the main run's artifact, assembled before `mike` wrote 1.8.0, is what the site was serving.
A `workflow_dispatch` republish fixed it.

`v1.6.0` failed the same way and is written up in [website.md](../development/website.md#what-the-publish-job-verifies-and-why-it-takes-two-checks) as a serving-side fault with no identified cause.
The deployment-id collision is a cause that fits both, and the `v1.6.0` run's logs should be read before this row is believed.

**Why it has been invisible is more interesting than how often it fires.** [Step 7](../operations/release.md#the-bump-on-main-does-not-reach-the-published-release) dispatches a republish on every release, to land the pin bump the tag's own tree cannot carry — and that republish repairs this on its way past.
`v1.8.0` bumped its pins *before* the tag, so no step 7 was owed and nothing masked the failure.
Whether earlier tags hit it is not established either way: their `pages` runs are past what `gh run list` returns, and a run that failed would have been repaired before anyone compared the site to it.

The fix to evaluate first is passing an explicit `pages_build_version` that distinguishes a tag deploy from a `main` deploy at the same commit.
Skipping the `main` deploy when a stable tag points at the same commit is the other shape, and it is worse: `dev` would then miss the merge.
