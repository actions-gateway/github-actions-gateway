# Republish 1.6.0-1.9.0 docs; their .github/ source links 404

The live `1.6.0`, `1.7.0`, `1.8.0` and `1.9.0` docs carry links into the source tree that `hooks/source_links.py` never rewrote, so they resolve against the site and 404.
Measured 2026-11-01 21:20 PST with `curl -fsS "https://actions-gateway.com/<v>/operations/release/?r=$RANDOM" | grep -oE 'href="[^"]*\.github/workflows/[^"]*"' | grep -vc github.com`: 4, 6, 6 and 7 relative `.github/workflows/` links on that one page, and `https://actions-gateway.com/1.9.0/.github/workflows/pages.yml` returns 404.

All four were last published by a `docs_ref` republish from `main` (runs 33024832599, 33293076832, 34834527848, 37397207266; each log reads `via mkdocs.versioned.yml`).
That overlay set `hooks:` to a single entry, and `INHERIT` replaces the list rather than merging it, so every hook but `release_version.py` was dropped.
The Q1041 change makes the overlay copy the whole list; its fix was measured by building `v1.10.0` through the overlay in a scratch repo, where 57 links read `blob/v1.10.0` and none stayed relative.
Nothing republishes the four versions already live, so they stay broken until someone dispatches them.

The fix is one dispatch per version once that change is on `main`, oldest first.
A version whose pins were bumped after its tag republishes from its `release-X.Y` branch, per [release.md step 7](../operations/release.md#the-bump-on-main-does-not-reach-the-published-release).
A version whose tag already carries the right pins (`1.8.0` was the first, per that step) can instead take `gh workflow run pages --ref vX.Y.Z` with no inputs, which builds the tag wholesale and leaves `stable` alone for a non-highest release; which of `1.9.0`'s two cases applies is unchecked.
Each dispatch publishes the live site, so this is the maintainer's to run or authorize.
Done when the curl above counts 0 for every version.
