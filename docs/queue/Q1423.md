# An Event note carrying another component's text has no length cap

An Event whose note runs past 1,024 bytes never reaches the operator: the API server refuses it (`NoteLengthLimit`, `core/validation/events.go`, v1.35.5, as read for Q1405 and not re-read here), and client-go's recorder sends the note as built (`grep` for `1024`, `NoteLength` and `truncat` over the vendored `k8s.io/client-go/tools/events` and `tools/record` finds nothing, 2026-11-26).
Q1405 removed the way a `%` grew a note about sixfold; length on its own is what remains.

**The AGC bounds its own notes one at a time, and only the ones it wrote.** `cmd/agc/internal/provisioner/flaky_jobs.go:757:if len(text) > maxEventNote {` shortens the failed-job record, and `TestOOMNotes_FitAnEvent` and `TestOOMReason_GivesWayToTheEventsLength` pin the out-of-memory notes at or under 1,024 bytes with a 255-byte job name.
Nothing bounds a note that carries text another component wrote: `WorkerPodCreateFailed` records the API server's error whole (`cmd/agc/internal/provisioner/capacity.go:37:fmt.Sprintf("the apiserver rejected worker pod %s: %v", pod.Name, err))`), and that error carries an admission webhook's or a policy's denial message as the webhook wrote it.
How long such an error gets has not been measured, so whether any real one is lost is not known.

What the operator would see is no `WorkerPodCreateFailed` Event for a pod the AGC could not create, with only the AGC's `apiserver rejected worker pod` log line left.

The fix is expected to be one cap at `maxEventNote`, cut at a rune boundary and marked, in `channelEventRecorder` for the notes the provisioner and the listener queue or in `recordEvent` for all of them; which, and whether the GMC's two `recordEvent` wrappers want it, is open.

The duplicate search flags Q1402, which is about a memory raise the API server refuses in the pod it builds, and not about the length of any Event.
