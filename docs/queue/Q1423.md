# An Event note past 1,024 bytes is refused and lost

An Event whose note runs past 1,024 bytes never reaches the operator: the API server refuses it (`NoteLengthLimit`, `core/validation/events.go`, v1.35.5, as read for Q1405 and not re-read here), and client-go's recorder sends the note as built, with no cap of its own (`grep` for `1024`, `NoteLength` and `truncat` over the vendored `k8s.io/client-go/tools/events` and `tools/record` finds nothing, 2026-11-26).
Q1405 removed the way a `%` grew a note about sixfold; length on its own is what remains.

**The out-of-memory notes are the closest to the limit.** Their fixed text, counted from the literals in `cmd/agc/internal/provisioner/oom_class.go` with every verb removed, is 525 bytes for the `own_limit` withhold on a set with no sizing profile, 495 for `breaker_open` and 476 for `same_class_again`, before the pod, node, run and job names and the sizes are added (2026-11-26).
A workflow author chooses the job name, and `same_class_again` quotes it, so a name of a few hundred bytes is expected to push that note past the limit.
How long a GitHub job name can be has not been read, and no note has been driven to the limit through a live API server.

What the operator sees then is the `MemoryLimitRaisedForRetry` or `EvictionRerunWithheld` Event missing, with only the AGC's log line left to say what happened.

The fix is expected to be a cap in one place, either in `channelEventRecorder` for the notes the provisioner and the listener queue or in `recordEvent` for all of them, that cuts a note at a rune boundary below 1,024 bytes and marks the cut.
Which of the two, and whether the GMC's two `recordEvent` wrappers want the same cap, is open.

The duplicate search flags Q1402, which is about a memory raise the API server refuses in the pod it builds, and not about the length of any Event.
