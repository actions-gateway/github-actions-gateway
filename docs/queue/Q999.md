# Cross-namespace proxy revoke has no event source, so its test races

`TestV2_RunnerSet_GrantedCrossNamespaceProxy_ResolvesAndRevokes` failed the revoke leg on PR 1726 (2026-08-26): after the projection is deleted, the 20-second `require.Eventually` at `v2_runnerset_sharing_test.go:90` never saw `Ready=False/ProxyShareNotGranted`.
A rerun of the same job on the identical head SHA `da096e442`, no code change, passed in 6m40s, and `main` at `811c670d5` passed the same suite, so the bump under test is not implicated.

The mechanism is read from source and **not yet confirmed end-to-end**: the projection is a ConfigMap (`newProjectedShare`), and `resolveRunnerSetRefs` reads it through the *uncached* reader on purpose, because the AGC Role grants `get` on ConfigMaps but not `list`/`watch` and a cached read would try to start an informer it has no permission to run (`runnerset_target.go:470`).
`SetupWithManager` registers no ConfigMap watch, and cannot.
So deleting the projection generates no reconcile event for the RunnerSet, and the assertion passes only when some unrelated trigger happens to land inside the 20-second window: a worker-pod event, a `wakeCh` push from the active listener, or a rate-limited requeue.
Confirm by deleting those triggers and requiring red before changing anything.

Worth more than a timeout bump: the test's own comment says the revocation leg is the one that matters, because a grant that cannot be taken back is not a grant.
If revocation is only observed incidentally, the operator-visible latency is unbounded in the quiet case, which is a security property rather than a test-timing one.
Decide whether the AGC should get `list`/`watch` on the labelled share ConfigMaps (`actions-gateway/proxy-share: "true"`) so revocation has a real event source, or whether a bounded requeue is the intended contract, then make the test assert whichever it is.
