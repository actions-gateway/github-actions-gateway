# Nothing rejects a CR name colliding across the v1/v2 derivations

Q979 stopped a colliding pool from deregistering the incumbent's GitHub record, but the collision itself is still accepted and still costs one tenant its whole agent pool until an operator renames a CR.
A `RunnerGroup` named `rs-<x>` derives the same agent Secret and the same GitHub runner name as a `RunnerSet` named `<x>`, because Q466's discriminator is an `rs-` prefix rather than an injection.
The AGC reports `agent identity is owned by another pool` on every reconcile of the loser and cannot self-heal.

Admission is the place to refuse it, and only one direction is cheap today: `RunnerSetCustomValidator` already does a cross-object uniqueness check (`validateScaleSetLabelUniqueness`), so a create of RunnerSet `<x>` can reject when RunnerGroup `rs-<x>` exists in the namespace.
The reverse direction has nowhere to land — `cmd/gmc/internal/webhook/v1alpha1/` carries only the ActionsGateway validator, so a RunnerGroup named `rs-<x>` created after the RunnerSet is unguarded until a v1alpha1 RunnerGroup validator exists.
Whether v1 gets a validator at all is the design question: v1 is the rollback target of a migration and adding admission to it can reject writes an operator relies on during rollback.

Note the guard is namespace-scoped for Secrets but the GitHub runner-name half is scoped to the org or repo, so two namespaces can still collide on the runner name alone; scoping the check is part of the work, not an afterthought.
