# v2beta1 deprecation notice, alias reject, and the pre-upgrade check

Q1082 decided that `v2beta1` is not served past `v2.0.0`, which puts three pieces of work on the critical path that were optional while the aliases had until `v3.0.0`.
**The deadline is 1.9**, the [Rule #4b overlap release](../plan/release-ladder.md#why-19-exists-the-storage-version-cannot-advance-in-the-same-release-that-introduces-v2), and it is now the only target.
1.9 is where `v2` starts being served, so it is the first release in which a conversion that cannot represent an alias can be asked for at all.
This row preferred 1.8, where the population would already be clean when `v2` appeared; `v1.8.0` tagged on 2026-09-14 without items 2 or 3, so what ships is the other case, where the guard and the hazard arrive in one release with no margin.
The consequence is an ordering rather than a risk to carry: items 2 and 3 land ahead of [Q413](Q413.md) inside 1.9, so the reject and the check are in the tree before `v2` is served.
Item 1 is complete: the docs half shipped with Q452, and the release-notes half is in [v1.8.0.md](../releases/v1.8.0.md) under Deprecations.
What remains is items 2 and 3, both 1.9.

1. ~~**The formal deprecation notice for `v2beta1`.**~~ Done.
   [v1alpha1-deprecation.md](../operations/v1alpha1-deprecation.md) records the decision and lists `v2beta1` in the removal table, which satisfies the roadmap's "announced at least one release ahead", and `v1.8.0`'s notes name the removal the way `release-1.3.md` announced the other three.
2. **Admission rejects a *new* `CiliumFQDN`/`CalicoFQDN` write**, where today it warns.
   Rejecting a new write while continuing to admit an unchanged object is the shape that stops the population growing without breaking anyone mid-upgrade; a flat reject would fail every re-apply of an object an operator has not migrated yet.
   The mechanism to check first is a CEL transition rule (`self == oldSelf`) on the `v2beta1` schema, which is how the existing immutability rules in this repo are written.
3. **A pre-upgrade check that finds unmigrated objects**, added to the [Pre-Upgrade Validation Checklist](../operations/upgrade.md#pre-upgrade-validation-checklist).

Item 3 is the load-bearing one, and the reason is mechanical rather than procedural.
`v2` cannot represent an object naming an alias, and the conversion contract cannot report one object as absent: `convertedObjects` must match the input list in size and order, `Result` is a single `metav1.Status` for the whole request, and on failure `convertedObjects` is empty.
`ConversionRequest.Objects` is a list, so one unmigrated `EgressProxy` fails the request that carries it and breaks `kubectl get egressproxies` at `v2` for the whole cluster.
Measured from the vendored [`apiextensions/v1` types](../../vendor/k8s.io/apiextensions-apiserver/pkg/apis/apiextensions/v1/types.go) on 2026-09-07; that a `LIST` batches into one `ConversionRequest` follows from the field being a list and was not driven against an apiserver, which is the first thing to confirm.

The migration is expected to be a no-op on every real cluster — no chart, overlay or e2e manifest sets an alias, and [Q245](../plan/q245-fqdn-intent-backend-split.md#migration--compatibility) recorded the only known consumers as tests and docs — so the check exists for the case that is unknowable rather than the case that is likely.
That expectation is also what makes item 2 cheap: there is very little population to reject against.

Deliberately **not** in scope: retiring the aliases from `v2`, which cannot arise because [Q452](../plan/v2-ga.md#decided-v2-omits-ciliumfqdncalicofqdn) omits them from the GA version.
