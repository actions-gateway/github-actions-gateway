# Bring-up races GKE konnectivity, so the first v2 apply fails

Measured 2026-08-28 on `gag-dogfood`, scaling from zero for the Q408 Phase 4 session: `e2e-start.sh` resized the pool, waited out the GMC rollout, and then failed its tenant apply with

```
conversion webhook for actions-gateway.com/v2beta1, Kind=ActionsGateway failed:
Post "https://webhook-service.gmc-system.svc:443/convert?timeout=30s":
No agent available
```

Re-running the same script unchanged succeeded four minutes later.

**This is a third variant, and the two documented ones both mis-diagnose it.** [troubleshooting.md](../operations/troubleshooting.md#applying-any-v2-object-fails-with-no-endpoints-available-for-service-webhook-service) covers `no endpoints available` (no Ready GMC pod, does not clear on retry) and `context deadline exceeded` (endpoints present, not yet serving, clears in seconds).
Here both of those readings were healthy at the moment of failure: `gmc-controller-manager` was `1/1 Running` and the `webhook-service` EndpointSlice named `10.36.1.2`.
What was missing was on the other side of the call.
GKE routes control-plane-to-pod traffic through the konnectivity tunnel, and `kubectl get pods -n kube-system -l k8s-app=konnectivity-agent` showed one agent `0/2 PodInitializing` and the other only 31 seconds into `Running`.
With no agent connected the API server cannot reach any in-cluster webhook, whatever the endpoints say, and it fails instantly rather than timing out.

So the diagnostic that separates the three is the konnectivity agent, and it appears in none of the entry's steps.

**Two deliverables, and the second is what stops it recurring.** Add the variant to the troubleshooting entry, with the agent listing as its distinguishing reading.
Then decide whether `wait_for_gmc` ([scripts/dogfood/lib/gmc.sh](../../scripts/dogfood/lib/gmc.sh)) should also wait for a Ready konnectivity agent: it already encodes "bring the GMC up before applying v2 objects", and this is the same ordering rule with a second precondition the script does not know about.
The cost of not fixing it is one failed apply and a re-run on every scale-from-zero, which is every dogfood session that starts at rest.

**Not a Q408 defect**, and deliberately not folded into that PR: the posture change is egress, this is bring-up sequencing, and they share only the session that found it.
