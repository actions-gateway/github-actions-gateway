# `record-launch.sh` sees a concurrent same-command run and says nothing

Measured 2026-08-29 (Q1035): two `make check` runs were live in one worktree at once, both redirected to the same `tmp/` log.
The second launch's `rm -f` truncated the file the first was still writing, and the interleaved result still read as one coherent gate run — a green `EXIT=0` beside a log describing a different tree.

`--list` already holds what a warning needs: every live record carries `pid`, `command`, and `worktree`, so a launch whose command and worktree both match a live record is detectable at launch time and is almost always a mistake.
Nothing consults it; the script writes its own record and exits.

The log path is the half it cannot see — that is the caller's redirect, so `record-launch.sh` is never told where output goes.
A warning naming the live run's pid and stop command is enough: the caller then knows to pick a different log or kill the other run.

The script's own header cites Q690, where two verification runs in one worktree recorded two contaminated results as genuine red, so the concern is established and only the trigger is missing.
Distinct from [Q739](Q739.md), which is that nothing makes the script fire at all, and from [Q841](Q841.md), which is editing under a running gate.
