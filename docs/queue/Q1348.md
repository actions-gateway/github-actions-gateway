# Gate a plan doc's restated open-lead count against its disposition table

**The 2026-11 audit plan restates its open-lead count and its list of open follow-up rows by hand, and nothing checks either against the table they summarise.** The count sits in the status line of `docs/plan/security-audit-2026-11.md` and again in its row in `docs/plan/README.md`.
Three concurrent PRs, Q1325, Q1327 and Q1328, each changed the disposition table, so every merge forced a rebase and a hand recount on the next.
The recount went wrong twice in one batch, and a reviewer or the orchestrator caught both:

- One status line said 20 open leads when the table held 16.
  It was checked by subtracting from the previous number, not by counting the rows.
- After Q1328, the list of open rows filed from the audit left out Q1342 and Q1344.
  The plan cites both as bare IDs, not `../queue/` links, so a scan that matched only links missed them.

The rendered page is published, so a wrong count reaches readers of `actions-gateway.com/dev/` until someone notices.

**Done when** `make docs-gates` fails when a plan doc's status line states an "N of which still are" count that differs from the number of `| needs validation |` cells in its own table.
Read `mk/gate-lists.mk` and the existing `plan-index-check` first, and extend that check if it fits rather than adding a gate.
Scope it to plan docs that carry such a table.
Today that is only the 2026-11 audit, so if a gate costs more than the next audit's recounts would, the alternative is to drop the restated number in favour of the table, and write that choice into `docs/development/documentation-standards.md`.
