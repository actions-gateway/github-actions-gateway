# Operator docs, migration guide, and the `v2.0.0` cut

Q1167 landed the coupled removals, after Q1086's storage migration in 1.10, and Q1291 took the last one-valued label off the metrics, so the surface the docs describe is the one `v2.0.0` ships.

Split out of Q413 on 2026-09-14, which held [v2-ga.md](../plan/v2-ga.md)'s Phases 2 and 4 in one `1.9-gate` row.
Phase 2 ships in 1.9 and Phase 4 in `v2.0.0`, so a single row could only carry one of the two labels and misreported what blocks 1.9 for whichever release it named.
Q413 keeps Phase 2; this is the rest.

[v2-api.md](../plan/v2-api.md)'s Definition of Done for v2 GA carries "Operator docs updated" as an open item, and it is the last one that is not the graduation itself.

**What this is not.** The `v2.0.0` release executes four coupled removals and a storage advance, and every one of them is already its own row or shipped: Q1086 rewrote stored objects and pruned `storedVersions` in 1.10, Q1167 dropped `v2alpha1`, `v2beta1` and the hub, Q273 removes `v1alpha1`, Q264 removes classic acquisition and the transitional `acquisitionProtocol` / `maxListeners` fields; the validating webhooks already name `v2` alone (Q1150, in 1.9), so no rule names a removed version.
This row is the documentation and the tag on top of them, which is why it is `S` where they are `L`.

**What it covers.** The operator-facing pages under `docs/operations/` that still describe a world where `v1alpha1`, `v2alpha1` and `v2beta1` are served, the migration guide for the `v1`→`v2` hop now that migrating off the `CiliumFQDN` / `CalicoFQDN` aliases stops being optional ([Q452](../plan/v2-ga.md#decided-v2-omits-ciliumfqdncalicofqdn)), and the release itself.

**The AGC and the CRDs cannot be upgraded in either order without a gap.** Q1263 moved the `RunnerSet` selectable field from `v2alpha1` to `v2`, and an AGC lists at one version: a list against the other release's CRDs fails with `field label not supported: spec.gatewayRef.name` in both directions (measured in envtest on Kubernetes 1.35, 2026-11-03, on the Q1263 tree, where `v2alpha1` was still served).
With `v2alpha1` no longer served, a `v1.10.0` AGC that restarts in the gap exits naming the missing CRD (read from the tag's `cmd/agc/main.go`, not run), and a `v1.10.0` GMC that starts on those CRDs crash-loops, with a running standby following within about 2.5 minutes of the leader going ([measured](../operations/upgrade.md#action-required-at-v200-apply-the-crds-with-the-upgrade-because-the-agcs-watch-depends-on-them)), so which order is least bad for the AGC is unmeasured.
[upgrade.md](../operations/upgrade.md#action-required-at-v200-apply-the-crds-with-the-upgrade-because-the-agcs-watch-depends-on-them) says to close the gap and that a rollback crosses it in reverse; this row measures the running AGC's behaviour in it, then states the upgrade and rollback order.

**Four things Q1167 found that the order has to carry.** The CRD apply is refused on a cert-manager install until each CRD's conversion webhook is patched away ([measured](../operations/upgrade.md#action-required-at-v200-remove-the-crds-conversion-webhook-before-applying-them)), and a rollback re-applies that webhook.
Re-applying it, with a `v1.10.0` GMC then serving `/convert`, is [measured](../operations/upgrade.md#gmc-rollback) with no tenant gateway running, so what remains unmeasured is a live AGC through it.
The `v2.0.0` `PriorityClassAllowlist` CRD goes after `helm upgrade`, because applied first it stops the upgrade: Helm cannot map the current release's manifest, which names the object at `v2beta1` ([measured](../operations/upgrade.md#action-required-at-v200-apply-the-crds-with-the-upgrade-because-the-agcs-watch-depends-on-them)), and `make chart-released-upgrade-check` walks that order.
The rollback puts that CRD back too ([measured](../operations/upgrade.md#gmc-rollback)).
An owner deleted between the CRD apply and its `v2.0.0` controller reconciling it leaves its children behind ([query](../operations/upgrade.md#action-required-after-v200-delete-what-an-owner-deleted-during-the-upgrade-left-behind)).
A set recreated under the same name then reads what its predecessor left, because `scaleSetGuardStore.Load` and `readRerunLedger` read by name with no owner UID check, so its predecessor's in-flight jobs could read as lost workers (read from the code, not measured; whether either should check the UID is open).

**`v1alpha1` text Q1273 left for this row, read 2026-11-06.** [tenant-onboarding.md](../operations/tenant-onboarding.md) line 13 calls the `v1alpha1` flow "still fully supported", and its Step 2 `runnerGroups` example and `kubectl get runnergroup` around line 638 depend on it.
[air-gapped-install.md](../operations/air-gapped-install.md) line 210 still shows `kind: RunnerGroup`, [troubleshooting.md](../operations/troubleshooting.md) lines 1258 and 1357 describe a v1 AGC and an orphaned `RunnerGroup`, and [migration-v1-to-v2.md](../operations/migration-v1-to-v2.md) still tabulates the agent Secret names `v2` no longer derives.

**Done when** the operator docs and the migration guide describe the `v2.0.0` surface with no served version that `v2.0.0` removes, and the tag is cut.
