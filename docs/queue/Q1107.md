# Operator docs, migration guide, and the `v2.0.0` cut

Blocked on the rows below: Q1167 landed the coupled removals, after Q1086's storage migration in 1.10, so the surface the docs describe is the one `v2.0.0` ships.
The tag also waits on [Q1273](Q1273.md), which retires the classic tier ledgers, runbook sections and AGC env vars Q264 left visible to operators.
It waits on [Q1281](Q1281.md) as well, because on a CNI that enforces NetworkPolicy the AGC's spans reach no collector until `spec.tracing` can name one, and a proxied tenant exports them in plaintext until it can name the collector's CA.

Split out of Q413 on 2026-09-14, which held [v2-ga.md](../plan/v2-ga.md)'s Phases 2 and 4 in one `1.9-gate` row.
Phase 2 ships in 1.9 and Phase 4 in `v2.0.0`, so a single row could only carry one of the two labels and misreported what blocks 1.9 for whichever release it named.
Q413 keeps Phase 2; this is the rest.

[v2-api.md](../plan/v2-api.md)'s Definition of Done for v2 GA carries "Operator docs updated" as an open item, and it is the last one that is not the graduation itself.

**What this is not.** The `v2.0.0` release executes four coupled removals and a storage advance, and every one of them is already its own row or shipped: Q1086 rewrote stored objects and pruned `storedVersions` in 1.10, Q1167 dropped `v2alpha1`, `v2beta1` and the hub, Q273 removes `v1alpha1`, Q264 removes classic acquisition and the transitional `acquisitionProtocol` / `maxListeners` fields; the validating webhooks already name `v2` alone (Q1150, in 1.9), so no rule names a removed version.
This row is the documentation and the tag on top of them, which is why it is `S` where they are `L`.

**What it covers.** The operator-facing pages under `docs/operations/` that still describe a world where `v1alpha1`, `v2alpha1` and `v2beta1` are served, the migration guide for the `v1`→`v2` hop now that migrating off the `CiliumFQDN` / `CalicoFQDN` aliases stops being optional ([Q452](../plan/v2-ga.md#decided-v2-omits-ciliumfqdncalicofqdn)), and the release itself.

**The AGC and the CRDs cannot be upgraded in either order without a gap.** Q1263 moved the `RunnerSet` selectable field from `v2alpha1` to `v2`, and an AGC lists at one version: a list against the other release's CRDs fails with `field label not supported: spec.gatewayRef.name` in both directions (measured in envtest on Kubernetes 1.35, 2026-11-03, on the Q1263 tree, where `v2alpha1` was still served).
With `v2alpha1` no longer served, a `v1.10.0` AGC that restarts in the gap exits naming the missing CRD (read from the tag's `cmd/agc/main.go`, not run), and the `v1.10.0` GMC meets the same version gone, so which order is least bad is unmeasured.
[upgrade.md](../operations/upgrade.md#action-required-at-v200-apply-the-crds-with-the-upgrade-because-the-agcs-watch-depends-on-them) says to close the gap and that a rollback crosses it in reverse; this row measures the running AGC's behaviour in it, then states the upgrade and rollback order.

**Three things Q1167 found that the order has to carry.** The CRD apply is refused on a cert-manager install until each CRD's conversion webhook is patched away ([measured](../operations/upgrade.md#action-required-at-v200-remove-the-crds-conversion-webhook-before-applying-them)), and a rollback re-applies that webhook, so it depends on the CA injector re-injecting and on a GMC that serves `/convert`; that direction is unmeasured.
The main chart's `v1.10.0` `PriorityClassAllowlist` policy names its `paramKind` at `v2beta1` with `parameterNotFoundAction: Deny`, so applying the `v2.0.0` `PriorityClassAllowlist` CRD before `helm upgrade` would deny the writes it matches until the policy moves to `v2`; the `v1.10.0` CRD also serves `v2`, so upgrading the chart first looks safe, and neither order is measured.
A set deleted between the CRD apply and its `v2.0.0` AGC starting leaves its ConfigMaps behind ([query](../operations/upgrade.md#action-required-after-v200-delete-what-a-set-deleted-during-the-upgrade-left-behind)).

**Why it is blocked rather than ready.** Writing it before the removals land means describing a surface that does not exist yet, and the removals are where the surface is actually decided.
The sequencing constraint is Phase 3's, not this row's: storage-migrate first, drop served versions second, then strip the dual-read arms.

**Done when** the operator docs and the migration guide describe the `v2.0.0` surface with no served version that `v2.0.0` removes, and the tag is cut.
