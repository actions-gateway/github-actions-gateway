# `ScaleSetWorkerEviction_DoesNotRecover` reruns via the orphan scan

`TestAGC_Drain_ScaleSetWorkerEviction_DoesNotRecover` asserts that a scale-set worker evicted before any terminal phase is not re-run, and it fails with a re-run under `cause=vanished`: the AGC logs `worker pod for an unconcluded job was gone when this AGC started` for a pod its own listener provisioned seconds earlier, in a process that never restarted.

**Measured 2026-09-07**, on one tree, at a host load average of 100 to 120 on 18 cores: 2 failures in 4 runs on the branch that found it and 1 pass in 1 run on the base it was cut from, none of which touched the orphan scan.
The failing runs finish in about 3 s because the `assert.Never` fires the moment the re-run lands.

**Mechanism.** `RecoverOrphanedScaleSetWorkers` takes its once-per-process verdict when it first sees a **non-empty** in-flight set, not on the set's first reconcile: the caller returns early on an empty `state.InFlight` before the provisioner's `orphanScans.claim`.
The listener adds the in-flight entry on a successful provision, so the reconcile the pod's Create event enqueues can read the ConfigMap before the entry lands and consume nothing.
The spec then evicts the pod the instant it appears, envtest removes it at once, and the next reconcile is the first to see a non-empty set: the entry's pod is gone, so the scan reads it as a worker lost while the AGC was absent.
That is the false positive the file's own comment says the once-per-process rule exists to prevent ("an entry this process created is covered by the live pod-watch recovery, so re-examining one can only produce a false positive"), reached because the claim is keyed on the reading rather than on the process.

Two shapes for the fix, and the row does not choose: claim the verdict on the set's first reconcile in the process whether or not the in-flight set is empty, which needs a measurement that the guard ConfigMap is readable by then (a cold cache would hand the first reconcile an empty set and miss real orphans), or have the listener mark entries it created in this process so the scan skips them.
Either way the spec's own race is worth keeping as the tripwire rather than widening its wait: the product defect is a live AGC re-running a job that never ran, and the fake accepts the `rerun-failed-jobs` a real GitHub would refuse.

Not bumped to the top of the queue: sighted locally under load, not yet on `main`; bump on a CI sighting per [flake fixes go first](../development/maintaining-backlog.md#flake-fixes-go-first).
