# Dogfood heartbeat relay reads nothing from a log with escape sequences

`collect_heartbeats` in [`scripts/dogfood/e2e-run-watch.sh`](../../scripts/dogfood/e2e-run-watch.sh) fetches job logs with `gh api .../actions/jobs/<id>/logs` and no `--allow-escape-sequences`, then discards stderr and the exit status.
When the log holds terminal escape sequences, gh refuses and writes nothing, so the operator sees no `[e2e t+…]` progress and no error.

Measured 2026-11-26 on gh 2.103.3, job `140270029259` (`e2e / e2e`, run `45926825833`, a GitHub-hosted merge-group run): without the flag, exit 1 and 0 bytes; with it, 371,613 bytes holding 19 heartbeat lines.

Unverified: that job had completed and was not a dogfood run, so neither an in-flight log nor a dogfood runner's log has been read.
Check both before fixing, and check whether the flag changes what `heartbeat_lines` matches.
`job_progress` in the same script records a passing run whose e2e log GitHub never served (Q855); whether this refusal explains that is unknown.

The rule for a reader fetching a log by hand is in [testing.md](../development/testing.md#a-refused-job-log-fetch).
The one near-duplicate the allocator offered, Q1128, was that doc rule and closed when this row was filed.
