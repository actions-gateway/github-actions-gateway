# Is 2 heavy slots at 16 jobs on 18 cores the right point?

Measured 2026-08-24: `local-throttle.sh` reports `jobs` = physical cores minus 2 and `slots` = 2, so two heavy phases put 32 threads on 18 cores before any sibling session exists.
`serialize_heavy_build` records why `slots` moved from 1 to 2, and that reasoning is about queue depth rather than about what the gates then measure.

`jobs` is derived from `hw.physicalcpu`; `slots` is the literal `DEFAULT_HEAVY_BUILD_SLOTS=2`, returned for anything at or above `MIN_CORES_FOR_MULTIPLE_SLOTS=4`.
So the one number bounding machine-wide concurrency scales with neither the core count nor the number of sessions: it is 2 on a four-core laptop and 2 here.
The script says so itself at `scripts/agent/local-throttle.sh:71`, "Capping parallelism (jobs) bounds ONE run's fan-out, but nothing stops three".
Measured 2026-08-24 during a 12-session batch, which this repo's own dispatch playbook recommends: 97.43 / 149.30 / 118.63 on 18 cores, against the ~1.8x the defaults make the designed floor.

What makes it worth re-deciding is that the gates' own budgets are wall clock, so they absorb the oversubscription directly rather than merely running slower: [`api/apinames` spent 37.983s on 0.645s of work](../development/testing.md#the-coverage-budget-is-wall-clock-so-it-measures-scheduling) under it.
[Q823](Q823.md) bought headroom by raising one budget; this asks whether the machine should be handing out 1.8x in the first place.

Needs the maintainer: it changes every gate run for every session on the box, and the trade is queue depth against measurement fidelity.
