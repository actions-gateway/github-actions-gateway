# Reproduce the out-of-memory retry class on a Binpack set (R12)

Q1317 asked for the out-of-memory class's reproduction on a `Binpack` set and took it on dogfood's `ci` set, which runs `Throughput`, so half of the class's R12 reproduction is unmeasured.
The kill itself does not depend on the profile, and that half is settled: on 2026-11-22 the runner died with the container, the pod failed, and the class fired from the pod watch and re-ran the job ([the reading](../plan/q555-automatic-recovery-design.md#readings-from-the-dogfood-turn-up-2026-11-22)).
What `Binpack` changes is the arithmetic and the request: its headroom is 1.4 rather than 1.5, and because requests equal limits under it, the raised floor raises the request too, so the re-run's pod asks the scheduler for more memory where `Throughput`'s asked for the same 5568Mi.

- Run [`q1317-oom-probe`](../../.github/workflows/q1317-oom-probe.yml) on a set with `spec.sizing.profile: Binpack` and `sizingProfileState: Active`, with `ALLOC_MIB` re-derived to sit between the set's derived limit and 1.4 times it, rounded up to 64Mi; its `runs-on` names the `ci` set, so either switch that set's profile for the run or point the job at another set.
- Read the `MemoryLimitRaisedForRetry` Event's two limits, and the re-run pod's runner request and limit, which should be equal and raised.
- Read whether the raised request still schedules: a request a node cannot hold leaves the re-run `Pending`, which the `Throughput` reading could not show.

Gated on 2.1 because Q1317 was, and this is the part of it the reading did not reach.
