# Storage-migrate stored objects to `v2` before the `v2.0.0` removals

**Revived 2026-10-09.** It waited on `v2` being served beside `v2beta1` in a shipped release; Q413 landed in #1999 and `v1.9.0` tagged 2026-10-05.
The migration cannot run before `v2` exists, and must complete before `v2beta1` is dropped.

[v2-ga.md](../plan/v2-ga.md#phase-3--the-storage-advance-and-the-coupled-removals) Phase 3 opens by marking `v2` the storage version and rewriting stored objects, and Phase 4 cuts the tag on top of that.
Both assume a migration mechanism this repo does not have: `StorageVersionMigration` and `storedVersions` appear nowhere outside `vendor/`, measured 2026-09-08 across the whole tree.
Until this row existed the gap was recorded in one sentence of a plan doc and tracked nowhere, which is what makes it `L` rather than the `M` the phase table implies.

Marking `+kubebuilder:storageversion` on `v2` changes only what the apiserver writes *next*.
Objects already stored as `v2beta1` stay that way, and `metadata.storedVersions` on each CustomResourceDefinition keeps listing `v2beta1` until every object is rewritten and the list is pruned.
The apiserver's own contract is that "versions may not be removed from `spec.versions` while they exist in this list" (the `storedVersions` godoc, `k8s.io/apiextensions-apiserver` v0.37.0 as vendored), so skipping this does not fail loudly at the tag: it fails when an operator applies the `v2.0.0` CRDs, on a cluster, mid-upgrade.

The deliverable is the migration itself plus the evidence it completed: rewrite every stored object of all five kinds, prune `storedVersions` to `["v2"]`, and record the reading.

**The mechanism is a read-write sweep, settled 2026-10-09.** The in-tree alternative is Kubernetes' own `StorageVersionMigration` API, which the vendored `k8s.io/api` marks beta from 1.35 and GA only from 1.37.
The charts accept Kubernetes 1.30 and up and the tested floor is 1.35 ([Q354](Q354.md)), so the in-tree API reaches only the newest clusters this release supports, and the separate `StorageVersionMigrator` controller would add a component with its own install story.
A sweep over each kind needs neither, and `storedVersions` is the assertion either way.

The pre-upgrade alias check Q1085 shipped in 1.9 is a precondition rather than a neighbour: an `EgressProxy` naming `CiliumFQDN` or `CalicoFQDN` cannot be rewritten as `v2` at all, because `v2` does not define those values ([Q452](../plan/v2-ga.md#decided-v2-omits-ciliumfqdncalicofqdn)).
Running this before that check has cleared is how one unmigrated object stalls the migration partway.

**Ask:** what turns on the maintainer is the release shape, because the contract above forces an intermediate state between "every object is stored as `v2`" and "`v2beta1` is no longer served", and an operator has to pass through it.
It can be a `1.10` minor, which advances storage and runs the sweep with every version still served, so `v2.0.0` is removals only; or a two-phase `v2.0.0` upgrade, one CRD apply that advances storage, the sweep, then a second apply that drops versions.
The first adds a release and leaves `v2.0.0` a single apply, with `v1.9.0` still a rollback target from `1.10` because it serves `v2`; the second adds none and makes the one breaking upgrade a three-step procedure.
[release-ladder.md](../plan/release-ladder.md#whether-a-110-rung-belongs-before-20) records the evidence; the choice decides whether the first tag cut after this row's storage flip is `1.10` or `v2.0.0`.
