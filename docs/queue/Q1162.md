# Make the CI release gate wait for the candidate's images to publish

`validate-candidate.yml` dispatches the gate the moment a candidate tag is pushed, and `publish.yml` starts from the same push, so nothing orders the gate's deploy after the images it deploys.
The gate pulls the tag's six images at deploy time; the chart comes from `git archive` of the tag, so only the images race.

Measured on `v1.9.0-rc.2` (2026-10-05, gate run 37268268065, publish run 37268258417): the last image job finished at 05:39:39 UTC and the gate began deploying at 05:41:57, a 2m18s margin.
The approval of the `dogfood-validation` environment took under a minute (run created 05:32:51, job set up 05:33:45); the margin is the gate's own seven-minute preamble of tool installs, lease, e2e-lane settle and node scale-up, so a slower publish run or a free e2e lane eats it.
A lost race fails the gate on `kubectl rollout status --timeout=3m` in `start.sh`, a gate failure that says nothing about the candidate and costs a cluster cycle.

The fix is a wait before the gate step: poll for the tag's `publish.yml` run to conclude, or for each image tag to resolve with `docker buildx imagetools inspect`, and fail on a red publish rather than deploying what it left behind.
Separate from Q880, which made `publish.yml` read the CI gate's verdict on the way out; this orders the gate after the publish on the way in.
