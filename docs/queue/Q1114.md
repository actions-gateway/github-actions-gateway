# check-uses-pinned cannot tell a vanished default pick from a bad path

**Event:** `uses-pinned-check` fails with `usespin: open <path>: no such file or directory` for a path nobody named on the command line.

The gate builds its own file list when given no arguments, filters it through `select_present_files`, then hands it to `usespin`, which opens each path.
A file removed in that gap fails the gate on a path the gate itself chose — measured 2026-09-16 at 1 in 20 runs against a probe being created and removed continuously in a directory the selection covers, so the real rate is far lower and the shape is the point rather than the number.

Every other writer of those directories can produce it, not only a test: a rebase, a branch switch, an editor saving over a workflow.

What makes it awkward is that the obvious tolerance is forbidden.
[check-uses-pinned-test.sh](../../scripts/ci/check-uses-pinned-test.sh) group 2 asserts that an unreadable file is exit 2 and never 0, which is the fail-closed property the gate exists for, so `usespin` may not simply skip what it cannot open.
The distinction the gate needs is one it already draws elsewhere: a path the caller **named** must fail closed, while one the gate **selected** and that has since disappeared is not evidence about any pin.
That is a flag on `usespin` set only for the default file set, or a re-selection and single retry in the script, plus a Go test for each side of the split.

Q1106 is the sibling; it closed the same race for `check-gate-needs.sh`, whose reader has no fail-closed constraint, and moved the probe that exposed this one out of the shared directory.
