# GMC ClusterRole reads every Secret cluster-wide, kube-system included

A compromised Gateway Manager Controller (GMC) can read the body of every Secret in the cluster, `kube-system` included, and nothing but the audit log would see it.
The ClusterRole `<prefix>-manager-role` ([`rbac.yaml`](../../charts/actions-gateway/templates/rbac.yaml)) is bound by a ClusterRoleBinding and grants `create, get, list, update, watch` on core `secrets`.
The `tenant-resource-guard` ValidatingAdmissionPolicy fences the writes to tenant namespaces, but admission never runs on `get`/`list`/`watch` (the policy's own header says so), and RBAC cannot scope a grant by namespace label.
Raised by the maintainer reviewing PR #2077 (Q1066).

## Measured 2026-10-13, at `57ee7abfa`

- **One marker declares the verbs**: `grep -rn --include=*.go 'kubebuilder:rbac.*secrets' cmd/gmc` returns one marker, `verbs=get;list;watch;create;update` near the head of [`actionsgateway_controller.go`](../../cmd/gmc/internal/controller/actionsgateway_controller.go), which `make chart-rbac` generates into [`manager-role-rules.yaml`](../../charts/actions-gateway/files/manager-role-rules.yaml).
- **`list` and `watch` are in use, so they cannot simply be dropped.** Both gateway reconcilers register `WatchesMetadata(&corev1.Secret{}, …)`: [`actionsgateway_controller.go`](../../cmd/gmc/internal/controller/actionsgateway_controller.go) `SetupWithManager` (v1) and [`actionsgateway_v2_controller.go`](../../cmd/gmc/internal/controller/actionsgateway_v2_controller.go) `SetupWithManager` (v2), found with `grep -rn --include=*.go -E 'corev1\.Secret(List)?\{' cmd/gmc`.
  That is a metadata-only informer, so no `.data` enters the cache, but an informer issues `list` and `watch` whatever it keeps, and RBAC cannot tell a metadata `list` from a full-body one.
  That the informer's requests reach the API server as `verb=list`/`verb=watch` on `secrets` is read from source, not observed in an audit log.
- **The informer is cluster-wide.** [`buildCacheOptions`](../../cmd/gmc/cmd/config.go) sets `ByObject` only for the allowlist `ConfigMap` and `PriorityClassAllowlist`, and nothing sets `DefaultNamespaces`; read by hand, no command.
- **Body reads already bypass the cache**, like the Actions Gateway Controller (AGC): [`wiring.go`](../../cmd/gmc/cmd/wiring.go) `newManager` sets `Client.Cache.DisableFor: []client.Object{&corev1.Secret{}}`, so `r.Get` on a Secret goes to the API server.
- **No GMC code `List`s Secrets directly**: `grep -rn --include=*.go -E '\.List\(' cmd/gmc` lists no `SecretList`.

## The operator doc contradicts the first measurement

[`security-operations.md`](../operations/security-operations.md) says the GMC's legitimate path is a cache-bypassing `Get` and lists "no Secret informer" among the structural mitigations.
Its EKS CloudWatch query alerts on any GMC `list`/`watch` of `secrets`, which the metadata informer issues at every start and every watch re-establishment, so the query as written fires on healthy traffic.
Correcting the doc is part of this row, whichever stage below lands.

## Stage one: take `list`/`watch` off the cluster-wide grant

The informer drives event-driven reconcile when a `gitHubAppRef` Secret is created or deleted.
Two shapes are open, and neither is measured.

- **Drop the Secret watch** and pick up credential changes on the requeue cadence, then drop `list`/`watch` from the marker.
  The cost is the latency between a Secret change and the reconcile that notices it.
- **Scope the informer to tenant namespaces.** A `cache.ByObject` `Label` selector only narrows what is cached, not what RBAC grants, so this needs per-namespace `list`/`watch`, which is stage two's problem.

**Measure:** the requeue interval a healthy gateway sits on, and what a rotated or newly created `gitHubAppRef` Secret costs in reconcile latency with the watch removed; if that is acceptable, stage one is the first shape.

## Stage two, open design question: scope `get` to tenant namespaces

Even with `list`/`watch` gone, `get` stays cluster-wide.
The natural shape is a per-namespace Role and RoleBinding created when a namespace is marked `actions-gateway.github.com/tenant=true`, with the cluster-wide grant removed.
The catch is RBAC escalation prevention: the GMC cannot create a Role granting `get secrets` it does not already hold in that namespace.
The ways round it are the `bind`/`escalate` verbs on `roles`/`rolebindings` (themselves a Tier-0 grant, so the trade needs weighing) or a platform-admin onboarding step that creates the binding when the namespace is labelled.
This needs a design pass in [`05-security.md` §5.1](../design/05-security.md#51-gmc-level-threats-cluster-scoped) before code.

**Ask:** whether the maintainer accepts granting the GMC `bind`/`escalate`, or wants tenant onboarding to carry a platform-admin step instead.
