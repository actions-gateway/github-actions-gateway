# Serve `v2` beside `v2beta1` (v2 GA graduation, Phase 2)

Add the `v2` version to all five kinds and serve it alongside `v2beta1`, with the storage version deliberately unmoved.
This is 1.9's entire content and blocks that tag.

**Scoped down to Phase 2 on 2026-09-14.** This row previously carried Phases 1, 2 and 4 together, which meant one `1.9-gate` row holding work that ships at `v2.0.0`, so neither release could read its own blockers off the label.
Phase 4 is now [Q1107](Q1107.md).
Phase 1 was the soak, and it has produced its evidence.

**The soak's measurable criteria are met.** Criterion 1 elapsed: `v1.3.0` shipped 2026-08-03 and two minors followed with no incompatible `v2beta1` shape change.
Criteria 2 and 3 were read in the `v1.8.0-rc.1` dogfood window on 2026-09-14 and both came back positive: all five `v2beta1` kinds reconciled on the dogfood cluster, and the standing tenant's `ActionsGateway` round-tripped both served versions with identical specs ([the readings](../plan/v2-ga.md#soak-readings)).

**Criterion 4 is why this is `ready` rather than still deferred, and the reasoning is worth keeping.** It asks for the [v2-api.md](../plan/v2-api.md) Definition of Done to audit clean, and two items in it are still ❌: the `v2beta1` → `v2` graduation, which is this row, and the operator docs, which are Q1107.
Both are outputs of the graduation rather than preconditions for it, so waiting on criterion 4 would be waiting on this row to finish before it may start.
What the soak was actually there to establish -- evidence that `v2beta1`'s shape is right before GA freezes it -- is established.

## What ships here

1. Add `v2` to each of the five kinds.
   **Do not carry `+kubebuilder:storageversion`**: that marker belongs to Phase 3 and `v2.0.0`, and withholding it is this row's job rather than a follow-up.
   Rule #4b will not let storage advance in the same release that introduces `v2`, and what the overlap buys is a rollback destination for the largest upgrade this project asks anyone to make ([why 1.9 exists](../plan/release-ladder.md#why-19-exists-the-storage-version-cannot-advance-in-the-same-release-that-introduces-v2)).
2. Extend the existing `Hub`/`Convertible` conversion webhook to round-trip the new served set.
   The hub moves to `v2`, which is free to happen here: `convertViaHub` routes spoke to hub to spoke and nothing ties the hub to the storage version.
   The GA enum is `CIDR;FQDN` -- `v2` never defines `CiliumFQDN` or `CalicoFQDN` ([Q452](../plan/v2-ga.md#decided-v2-omits-ciliumfqdncalicofqdn)).

**Two project-specific constraints to read before starting**, both carried over from the `v2alpha1` → `v2beta1` hop and named in the plan as the most likely way to break this one: shared version-neutral code lives in `api/apiconditions` with one-line re-exports per version, and `check-v2-api-sync.sh` gates every shared v2 file.
The hop is otherwise mechanically identical to the last one, which is the useful part.

**[Q1085](Q1085.md) is better landed first.** Its alias reject and pre-upgrade check are what stop a stored `EgressProxy` naming an alias from reaching a `v2` conversion, and 1.9 is the first release where such a conversion can be asked for at all.
Landing them in 1.8 means the population is already clean when `v2` appears; landing them in 1.9 means the guard and the hazard arrive together, which works and has no margin.

**Done when** `v2` is served on all five kinds with `v2beta1` still the storage version, verified by reading `storage: true` off each shipped CustomResourceDefinition rather than off the markers, and the conversion webhook round-trips the new served set.
