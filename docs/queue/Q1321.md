# GMC can write ConfigMaps and CNI policies outside tenant namespaces

**The security design claims a confinement the shipped admission policy does not deliver, and `v2.0.0` should not ship the claim as it stands.** `docs/design/05-security.md` says a compromised Gateway Manager Controller (GMC) is confined to marked tenant namespaces.
Its ClusterRole grants cluster-wide writes on ConfigMaps, on the CNI-native network policy kinds and on ServiceMonitors, and no rule in `gmc-tenant-resource-guard` or any other shipped policy names those kinds.
Confirmed by reading source on 2026-11-09 at medium severity, not observed on a cluster ([the finding](../plan/security-audit-2026-11.md#confinement-claim)).

Gated on `v2.0.0` because General Availability is when the security doc becomes a commitment, and the second audit's rule was that the claim and the code must agree.

Two fixes clear it, and they are not exclusive:

- Correct the claim: state the kinds a compromised GMC can still write cluster-wide, with the bound.
  This is the smallest change that makes the doc true.
- Extend the policy to the unmatched kinds, so the claim holds as written.
  It changes no tenant-facing API, so it does not need the major.

**Done when** the doc's confinement claim and the shipped policies agree, a test fails if a kind in the GMC ClusterRole's write rules is matched by no policy, and the envtest copies under `cmd/gmc/config/admission-policy` match the chart templates.

The `security` label is left off deliberately: with a gate label it would oblige a public roadmap bullet (`roadmapcheck` rule 7), and Q1312 set the precedent of gating a pre-release tightening as `debt`.
