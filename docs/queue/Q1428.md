# `maxEvictionRetries: 0` does not stop the abandoned force-cancel

With automatic re-runs turned off, a worker removed before it ran still has its run force-cancelled, and the run is then never re-run.
Read from source on 2026-11-27, not run: `forceCancelAbandonedRun` takes no budget, so the cancel is posted whatever `maxEvictionRetries` holds, and the budget is consulted only when the capacity-gated re-run is released, where 0 refuses it as exhausted.
No field turns the force-cancel off.
Withholding the App's `Actions: write` permission stops it, and each attempt then counts as `actions_gateway_abandoned_run_force_cancels_total{outcome="error"}`.

Without the cancel, GitHub ends the unstarted job at its own timeout of about 15 minutes, so at 0 the cancel changes when the run ends and not whether a human re-runs it.
What it can change is the run's other jobs, which is what [Q1246](Q1246.md) measures and Q1426 guards against; this row is the off switch alone.

**The choice:** either 0 means the gateway makes no write to a run, which skips the force-cancel and leaves the job to GitHub's timeout, or the force-cancel stays as a faster ending and the field's description says that 0 does not cover it.
**Measure:** Q1246's reading of a force-cancel on a multi-job run settles which: if it ends jobs the timeout would spare, 0 has to skip it.
