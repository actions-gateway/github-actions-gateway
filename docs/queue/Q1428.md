# `maxEvictionRetries: 0` does not stop the abandoned force-cancel

With automatic re-runs turned off, a worker removed before it ran still has its run force-cancelled, and the run is then never re-run.
Read from source on 2026-11-27, not run: `forceCancelAbandonedRun` takes no budget, so the cancel is posted whatever `maxEvictionRetries` holds, and the budget is consulted only when the capacity-gated re-run is released, where 0 refuses it as exhausted.
No field turns the force-cancel off.
Withholding the App's `Actions: write` permission stops it, and each attempt then counts as `actions_gateway_abandoned_run_force_cancels_total{outcome="error"}`.

Without the cancel the job stays queued: on a scale set GitHub did not cancel it, or its run, in 41 minutes.
What it changes is the run's other jobs: measured on dogfood on 2026-11-27, the force-cancel ends every unfinished job of the run, and a never-started job left alone ended none in 41 minutes and was not cancelled by GitHub either ([the readings](../plan/q645-abandoned-completion.md#q1246--the-multi-job-measurement-2026-11-27), Q1246).
Q1426 is the guard for a run with a job running; this row is the off switch alone.

**A fix:** at 0, skip the force-cancel and leave the job queued, since at 0 it ends healthy jobs and nothing re-runs them.
The field's description and the runbook's section on a worker reaped while `Pending` say what 0 covers.
