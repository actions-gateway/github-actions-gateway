# EgressProxy applies its Deployment before its NetworkPolicy

`EgressProxyReconciler.reconcileResources` applies the proxy Deployment, Service, HPA and PDB, and only then the proxy NetworkPolicy, returning on the first error (`cmd/gmc/internal/controller/egressproxy_controller.go`, the `reconcileResources` body).
So on a first provision, an error in any step between the Deployment and the policy leaves proxy pods running with no policy selecting them, open to ingress from any namespace and to unrestricted egress, until a reconcile gets past the failing step.
The v2 gateway does the opposite and applies its workload and AGC NetworkPolicies before the AGC Deployment, so this gap is the proxy's alone; v1 has the proxy's order too, with only the Service in between.

**Unmeasured.** This is a source read of `origin/main` at 7b292627a, by the Q273 A0 reviewer and re-read by the orchestrator; no run has caught a proxy pod without its policy.
Also unread: whether some other policy in a tenant namespace selects proxy pods in that window.
The default-deny the chart ships selects the GMC manager pod (`charts/actions-gateway/templates/networkpolicy.yaml`), not tenant pods.
The proxy forwards CONNECT only to allowlisted hosts, so the egress half is bounded at the application layer; the ingress half is not.

**Done when** the proxy NetworkPolicy (and the FQDN policy, if its inputs are ready) is applied before the Deployment, with an envtest case that fails a step between them and asserts the policy exists, and the order is checked against the cert and attribution steps the Deployment depends on.
The policy-first order is untested; it may need attribution's ports before the Deployment exists.
