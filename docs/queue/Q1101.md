# A v2 ActionsGateway gets no AGC ServiceMonitor

`applyOrPruneServiceMonitors` builds the two per-tenant `ServiceMonitor`s that let Prometheus scrape a tenant's AGC and proxy over mTLS.
Measured 2026-09-12: its only caller is ``cmd/gmc/internal/controller/actionsgateway_controller.go:289:if err := r.applyOrPruneServiceMonitors(ctx, ag); err != nil {``, the **v1** reconciler.
The v2 reconciler has no call to it and no ServiceMonitor path of its own, so a v2 `ActionsGateway` gets the AGC metrics `Service` (`buildAGCServiceV2`) and nothing that scrapes it.
`buildMetricsServiceMonitor` takes a `*gmcv1alpha1.ActionsGateway`, so it cannot be called from the v2 path as it stands.

A v2 `EgressProxy` is unaffected: `egressproxy_metrics.go` reconciles its own monitor.
So the gap is the AGC half only, and a v2 fleet's proxy metrics arriving normally is what makes it quiet.

**Whether this is a defect or a decision is the first question, and it is not answerable from the code**. v2 moved metrics to a per-gateway mTLS identity (`<gateway>-agc-metrics-{tls,client}`), so one plausible reading is that a per-gateway monitor was deferred to whatever replaces the v1 pair.
The other is that it was missed, which is what the v1 code path being intact and uncalled suggests.
Settle it against [appendix-h](../design/appendix-h-v2-api-decomposition.md) and the M3b history before writing either a monitor or a design note.
