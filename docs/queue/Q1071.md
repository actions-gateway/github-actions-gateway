# promql-check never reads the security doc's shipped alert group

`check-promql.sh` passes the checker four kinds of input: `deploy/monitoring/prometheusrule.yaml`, `docs/operations/observability-alerting.md`, `docs/operations/runbook.md`, and the four dashboard JSONs.
`docs/operations/security-operations.md` is not among them, so the nine-rule `actions-gateway-security` group that doc tells an operator to drop into a `PrometheusRule` has never been parsed by anything.

That is what let Q1061's two inert expressions ship, and Q1061 named the wrong cause: it said the gate parses the doc's expressions and a well-formed query selecting nothing is what the gate cannot see.
The first half is false: the gate never opens the file.
Measured 2026-09-07 by extracting the doc's fenced `groups:` block into a synthetic `PrometheusRule` and running `scripts/manifest/check-promql.sh` on it: all nine expressions parsed, and a deliberate `{{` in one produced `expr does not parse`, so the checker would have had an opinion had it been pointed at the file.

**Adding the file needs an expression-only mode, which is why this is not one line.** The doc's group is a reference operators copy, not a shipped rule, so the same probe returned eight `has no runbook_url annotation` findings and one missing runbook heading, all of it policy the checker applies to `prometheusrule.yaml` and that does not hold here.
`run()` currently takes one doc path and spends it on `checkMirror`/`checkRunbook` against the shipped rule; this needs a second doc path that gets `docBlocks` + `checkExprs` and nothing else, plus a printed rule count so a walk that stopped reaching the block reads as a gap rather than a pass, which is the argument the dashboard target count already makes.

Neighbour to [Q996](Q996.md), which is the other direction: there the gate reads the right file and compares too little (`for:` and every label unguarded).
One fix does not close the other, and the two together are what "guards less than it reads as" means for this tool.
