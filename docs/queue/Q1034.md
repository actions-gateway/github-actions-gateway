# `verify-pages-live-test` retry cases rest on a clock it does not control

**Event:** any of `verify-pages-live-test.sh`'s three retry assertions fails on `main`: *a site that goes correct on a later attempt passes*, *the check polls rather than sampling once*, or *each attempt carries its own cache-busting query*.

Three cases failed under host load and passed on rerun, and the mechanism was `SECONDS` rather than anything about the subject.

**Measured 2026-08-29 03:24 PDT** in `make check` on a branch touching no file under `scripts/pages/`, host at load average 28.35 over 18 cores.
The three that failed are the retry cases.
Their reported reason is one line:

```
did not serve 1.6.0 after 606s (60s budget, 1 attempt(s))
```

Re-run alone eight minutes later on the same tree: all assertions pass.

**Why the budget was the wrong instrument here.** [`verify-pages-live.sh`](../../scripts/pages/verify-pages-live.sh) stops starting attempts when `((SECONDS + INTERVAL >= TIMEOUT))`, so the loop's attempt count is a function of wall clock.
That is correct for the real subject, where the budget bounds how long a release waits on Pages.
Under a stubbed `curl` the same expression measures the host instead: one simulated attempt took 606 s against a 60 s budget, so the loop made a single attempt and every assertion about *retrying* had nothing to observe.
The three failures are one cause, and none of them is about the code under test.

## The asserted cause was measured before it was fixed

Confirmed 2026-09-03 by driving `verify-pages-live.sh` directly with the propagation case's own arguments behind a stub `curl` sleeping 59 s per request, which is the smallest delay that consumes a 60 s budget in one attempt.
The reported line reproduces in shape: `did not serve 1.6.0 after 59s (60s budget, 1 attempt(s))`, 1 request, 1 distinct query string, exit 1.
The same stub at 0 s gives 3 attempts, 4 requests, 3 distinct, exit 0.
So the row's stated mechanism is measured rather than inferred, and the three assertions collapse together because they read one loop.

## Mitigation

The second of the row's two candidates.
Injecting the clock was the first, and it leaves the same failure available on a slower machine; the cases are about *how many* attempts, not how long, so the clock is not the subject and a test-settable deadline is the wrong repair.

- The propagation case runs against a budget no run can reach (`--timeout 86400`), rather than a raised one.
- Its assertions are exact and read the loop's **own** attempt counter off the success line, not a count of stub requests: one attempt makes one or two requests depending on how far through `check` it gets, and the old floor of `>= 3` conflated the two.
- The cache-busting assertion is tied to that attempt count, so it cannot pass vacuously.
  Over a single attempt one query string is trivially all-distinct, which is how it stayed green through the sighting.
- A budget no run can reach turns non-convergence into a hang, so the stub caps the case at 8 **requests**.
  Counted in requests rather than seconds, so the guard cannot itself become a second clock.
  Past the cap it answers synthetically rather than serving the fixture's correct tree, which may be the very thing that stopped converging; a run that reaches the cap then fails the exact-attempt assertion instead of polling for a day.

Verified 2026-09-03 under the same 59 s stub, both configurations against one stub and only the arguments differing: the old arguments fail after one attempt at 59 s, the shipped ones succeed at attempt 3 with 4 requests and 3 distinct query strings, having spent 238 s of wall clock, four times the budget that used to bind.
Both inversions go red by name.
Deleting the retry (`if true` in place of the budget check) reds all three, and a constant cache-bust token reds only the distinctness assertion while the attempt count still reads 3, so the two are independent.
