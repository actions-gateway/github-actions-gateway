# Scope a release-time e2e leg on a throwaway GKE cluster

The gmc e2e suite's assertions have only ever run on kind clusters.
The release-candidate gate (`scripts/dogfood/validate-release.sh`, `docs/operations/release.md`) does deploy the candidate onto the GKE dogfood cluster and route real CI through it, but the e2e matrix it dispatches still runs inside a kind cluster in a DinD or Kata runner pod.
So NetworkPolicy enforcement under a provider's dataplane, HPA against a provider's own metrics-server, the admission webhook through a managed control plane, and teardown are all unchecked anywhere but kind.
The aim is a leg run before a stable tag, not on every PR, and GKE first, with other providers (EKS, AKS) only once the suite is provider-clean.

**It must run on a throwaway cluster, never dogfood.** Setup installs cert-manager and metrics-server cluster-wide and force-applies the CRDs, and teardown runs `make undeploy`.
GKE ships its own metrics-server, and an upstream one beside it shared the `k8s-app=metrics-server` label when the suite ran on dogfood by accident on 2026-10-24.

**Porting is work, not a flag.** A file-level grep over `cmd/gmc/test/e2e/*.go` on 2026-11-01 found kind-specific assumptions in about a dozen files: three call `docker` or `kind` directly, image refs default to the `127.0.0.1:5000` local registry, setup patches metrics-server with `--kubelet-insecure-tls`, and six reference the control-plane node role, which GKE hides.
Those are counts of matching files, not a reading of each site; some will be one-line fixes and some may need a spec to skip off kind.

**Measure:** on a throwaway GKE cluster in the dogfood project, before choosing a shape.
**The scoping pass should answer:**

- each kind-ism and its fix, or the specs that should skip on a managed cluster;
- how the suite is told a non-kind context is intended.
  The context guard proposed in PR 2212 accepts only `kind-$KIND_CLUSTER`, so this needs an explicit opt-in naming the expected context, never a relaxed check;
- where images come from (an Artifact Registry push instead of the local registry) and how the cluster gets its credentials;
- cluster create time and run cost, measured, to decide whether this is a release-candidate leg beside `kata`, `dind` and `dragonfly` or a manual pre-tag step.
