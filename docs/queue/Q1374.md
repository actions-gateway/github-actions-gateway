# Detection drops timed-out jobs: JobCompleted reports them canceled

A job killed by its `timeout-minutes` completes `canceled` on the scale-set message queue, the same spelling as a user's cancel, and flaky-job detection records a `canceled` completion only when a disruption recovery claimed the job, so it records no timed-out job.
Measured on dogfood on 2026-11-22: jobs `b31558d4…` and `486169c1…` of run 45052015868 (`timed-out`, `timeout-minutes: 1`) both completed `canceled`, and the jobs API concluded them `cancelled`; a user's cancel of job `3762586f…` in run 45053166409 completed `canceled` too ([the readings](../plan/q555-automatic-recovery-design.md#readings-from-the-dogfood-turn-up-2026-11-22)).

So a job that hangs and times out, then passes on a re-run, is never counted flaky, and the manual re-run rate misses it: a common flake shape, since a hung test is what a job timeout catches.
Recording every `canceled` would count deliberate cancels instead.
The completion alone cannot separate the two, so the question is which fact can: the jobs API's annotation (`The job has exceeded the maximum execution time`) costs a read per cancelled job, which R6 rules out on the hot path, or the run's conclusion read on the next attempt's completion, which costs a read only when a later attempt exists.
Decide which, or record the gap in the operator docs as a stated blind spot.
This is the defect Q1236's measurement found, not a repeat of it: that row asked which spelling a timeout completes with, and this one is what detection does with the answer.
