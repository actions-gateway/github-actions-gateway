# Untrusted-PR egress posture for Kata workers

Phase 1 validated 2026-08-24: four green self-hosted Kata runs name no non-GitHub non-registry host, graded against a Phase 0 control that fires on both.
Phase 2 is done as of 2026-08-28: the mirror manifests, over five upstreams rather than four once the grading added `gcr.io`, are validated on the dogfood cluster at 25 of 25 checks by `scripts/dogfood/e2e-mirror-validate.sh`.
Every instance serves a real upstream manifest, refuses uploads with 405, and exposes no debug listener, so the mirrors are measured serving rather than merely applied.
Phase 3 is done as of 2026-08-28: dockerd via a mounted `daemon.json`, the non-Hub docker refs rewritten at the one chokepoint every `docker pull` shares, buildkit given a generated `buildkitd.toml`, and helm's OCI ref pointed at the ghcr mirror.
Validated on the dogfood cluster by a green Kata run (75 of 75 specs) whose five instances served 161 content requests, against a zero baseline measured on the same cluster twenty minutes earlier, so the reading is a change rather than a number.
The repositories attribute each client separately: the OCI chart can only be helm's, `distroless/static` only buildkit's, cert-manager and metrics-server only the rewritten refs, `kindest/node` only dockerd's own mirror.
Phase 4 is done as of 2026-08-28: `e2e-open-egress` is deleted from the Kata overlay, and the tenant's live rules carry zero allow-all, so a worker reaches cluster DNS on 53, GitHub on 443 and the mirrors on 5000 and nothing else.
Validated on the dogfood cluster by a green Kata run (75 of 75 specs) whose in-job negatives passed all eight checks on a `runtimeClassName: kata` worker: a mirrored upstream by its own hostname, the plain internet and the metadata server on port 80 all silent, each against a control that answered, so the silence is the policy rather than a dead network.
Phase 2's battery re-ran at 25 of 25 under that policy, and the five mirrors served 178 content requests.
The negatives run as a step of every run of the lane rather than once, because a policy that stops selecting the worker is invisible in a green suite.
Two findings the session turned up, neither an egress defect: deleting the manifest does not delete the object, since `kubectl apply -k` does not prune and `e2e-stop.sh` leaves policies standing, so `e2e-start.sh` now deletes it on the Kata lane; and the bring-up races GKE konnectivity, filed as [Q1016](Q1016.md).
Next is Phase 5: flip the `kata-dind-workloads.md` caveat to a how-to, link the manifests from `security-operations.md`, mark G.14 shipped, move the roadmap entry out of "exploring", and delete this row.
