# Run a patch line's own source through e2e before its candidate is tagged

A patch line's source goes through e2e nowhere today.
`e2e-test.yml` triggers on `pull_request` too, but its `e2e` job's `if` admits only `merge_group`, `push` (to `main`) and `workflow_dispatch` (`.github/workflows/e2e-test.yml:125:if: (needs.changes.outputs.e2e == 'true' && github.event_name == 'merge_group')`), and only `main` has a merge queue (the `default-protect` ruleset, `~DEFAULT_BRANCH`, read 2026-09-29).
So the fix is that job condition or a dispatch, not a new trigger.
The release gate dispatches the workflow at `main` on purpose (decided in Q1027, 2026-09-29), so on a patch the suite, the chart checks and the released-chart upgrade check all test `main`'s build, not the patch.
[release.md § Patch releases and backports](../operations/release.md#patch-releases-and-backports) records the split and why the gate keeps `main`.

**Why not just dispatch the gate at the candidate tag.** The e2e leg does two jobs.
The candidate-side half (runners carrying the matrix, NodeShare sizing, the admission ladder, the Q1048 mirror-client census, and the in-job mirror probes) wants `main`'s newest instruments, and `v1.4.0`–`v1.6.0` carry none of the three mirror steps (`Configure buildkit registry mirrors`, `Prove the worker's egress is mirror-only`, Q1020's timing), read off each tag's `e2e-reusable.yml` on 2026-09-29.
The source-side half is what a patch needs from its own tree.
One ref cannot serve both.

**What the run needs, none of it tried end to end since no patch has ever been cut here:**

- Dispatch `e2e-test.yml` at the release branch or the candidate tag, routed off the dogfood tenant.
  Every stable tag from `v1.4.0` carries the `runner` dispatch input; what an empty `runner` resolves to depends on `vars.GAG_E2E_RUNNER`, which was not read.
- Keep the released-chart upgrade check on the patch's own line.
  `scripts/e2e/chart-released-upgrade-check.sh` discovers the highest stable `vX.Y.Z` on the remote, so for `v1.7.1` it would install `v1.8.0` and "upgrade" to 1.7.1's chart.
  The script already honours `RELEASED_TAG`; the workflow has no dispatch input to pass it, and an older tag's copy of the workflow would not gain one without a cherry-pick.
- Decide where it sits: a step the maintainer runs before tagging `-rc.1` (release.md's patch recipe), or a leg of `validate-release.sh` that runs only when the candidate is a patch.
