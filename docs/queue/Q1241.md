# A hosted runner reporting late timed out the 2-minute gate jobs

**Event:** a `*-gate` job concludes `cancelled` with the annotation `The job has exceeded the maximum execution time of 10m0s`.
On a sighting, take the readings below for it and return the row to the top of the Queue.

**The sighting, 2026-10-30.** Run 41099353135 is `integration-test.yml` on the merge_group branch for PR #2190 (Q1239).
`integration-test-gate` (job 124217088825) started at 17:41:43Z on a GitHub-hosted runner, labelled `ubuntu-latest`, image `ubuntu-26.04` 20261025.179.1.
Its log runs from `17:41:44.195Z Current runner version: '2.338.2'` to `17:41:44.427Z Cleaning up orphan processes` and holds nothing after that; the jobs API records all four steps, `Complete job` included, as `success` with `completed_at` 17:41:44Z.
The job concluded `cancelled` at 17:45:05Z, 201 s after its last step completed, and #2190 left the queue at 17:56:25Z.
The dispatcher re-enqueued it at the same head and it passed.

**The cause is the gate's own 2-minute timeout firing on a runner that reported completion late.** Measured 2026-11-01:

- The check run's annotations, read with `gh api repos/actions-gateway/github-actions-gateway/check-runs/124217088825/annotations`, carry a `failure` annotation reading `The job has exceeded the maximum execution time of 2m0s`.
  That rules out the workflow's `concurrency` group, whose `cancel-in-progress` is `true` only for `pull_request` events, and a cancel from outside the run.
- Across every run created since 2026-10-11 of six workflows (`integration-test`, `unit-test`, `e2e-test`, `security-scan`, `doc-links`, `manifest-validate`; about 1,800 runs, read from the Actions jobs API per run), seven gate jobs sat silent after their last step, and all seven started between 17:38Z and 17:55Z on 2026-10-30.
  Three were cancelled by the cap: `security-scan-gate` (126 s from last step to cancel), `integration-test-gate` (201 s) and `manifest-validate-gate` (311 s).
  Four reported late inside the cap and succeeded: `unit-test-gate` (84 s and 112 s) and `e2e-gate` (107 s and 111 s).
  Across the whole sweep every workflow's median gate wall time is 3 s, and the per-workflow p99 runs from 5 s to 40 s.
- GitHub opened a major incident, *Incident with Actions, Pages, and Webhooks*, at 17:50:54Z, reporting delays to Actions workflows; it was resolved at 19:23:40Z.
  Read from `https://www.githubstatus.com/api/v2/incidents.json`.

Whether the three cancelled runners would ever have reported is not measured.

**The mitigation:** the eleven `*-gate` jobs that carried `timeout-minutes: 2` now carry 10, which covers the four late reports (112 s at most) and the 126-311 s the three cancelled tails ran before their cancels landed.
The 2-minute value came in with #606 (Q297), which gives no reason for it.
A cap still reports a hung gate as a failure, so no real failure is hidden; the cost is that a gate that truly hangs holds its merge-queue slot 8 minutes longer.
A retry or rerun wrapper was ruled out because it would hide the cancel the gate exists to report.

**Sibling, not a duplicate:** [Q1105](Q1105.md) is a timeout eviction on `unit-test.yml` too, but there the job's own steps ran past the cap.
Here the steps ran in under a second and the time went to the runner reporting completion.

**On a sighting, record:** the run and job ids, the runner image and version, the gap between the last step's `completed_at` and the cancel, and whether a GitHub incident covers it.
A tail longer than 10 minutes is the case for an upstream report to GitHub rather than a longer cap.
