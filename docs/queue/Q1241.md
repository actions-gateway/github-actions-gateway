# integration-test-gate is cancelled after its steps pass, evicting a PR

**Event:** a gate job (`integration-test-gate` or a sibling `*-gate`) concludes `cancelled` with every step green, or a PR leaves the merge queue with reason `failed_checks` while every gated job succeeded.

**What was measured, 2026-10-30.** Run 41099353135 is `integration-test.yml` on the merge_group branch for PR #2190 (Q1239).
`integration-test (agc)` and `integration-test (gmc)` both succeeded (17:38:28Z and 17:39:25Z).
`integration-test-gate` (job 124217088825) started at 17:41:43Z on a GitHub-hosted `ubuntu-26.04` runner, image 20261025.179.1.
Both of its steps ran green and the log ends `needed job results: success success`, then `Complete job: Cleaning up orphan processes`.
The job concluded `cancelled` at 17:45:05Z, about 3m20s after it started.
The run concluded `cancelled` at 17:56:24Z and #2190 left the queue at 17:56:25Z.
Every other merge_group workflow for that candidate succeeded, and the dispatcher re-enqueued the PR at the same head, so the rerun supplies the passes-on-rerun half of the evidence.

**The mechanism is unverified.** The log carries no cancellation reason, so the cause is not established.
Two things are read from `integration-test.yml`, not from the run: the gate declares `timeout-minutes: 2`, and the concurrency group's `cancel-in-progress` is `true` only for `pull_request`, so a merge_group job is not cancelled by a newer run.
The job's 3m22s exceeds the 2-minute cap, so a timeout is a candidate: both steps finished within a second of 17:41:44Z, which would leave the job idle after `Complete job` until the cap fired.
That reading is untested, and a runner-side loss after the last step looks the same in the log.

**Sibling, not a duplicate:** [Q1105](Q1105.md) is the same eviction shape on `unit-test.yml`, where a job's *timeout* cancelled it with every step green and the fix was a longer cap and a split job.
If the 2-minute cap is what fired here, this is that defect on another gate, and the row may fold into Q1105's trigger; Q1105 is parked as mitigated, so it does not cover this occurrence as written.
[Q1196](Q1196.md) is that workflow's wall-time measurement and is unrelated.

**First step on recurrence:** read the job's check-run annotations and the run's `jobs` API record for a cancellation reason, and compare the cancel time with `started_at` plus 2 minutes.
Record each recurrence's run id, runner image and gap between the last step and the cancel, so a second reading can say whether the gap is constant.
If one recurs, decide between a gate-side retry and an upstream report to GitHub; a repeat on the same image points at the image.

**Ranked at the top per** [flakes-first](../development/maintaining-backlog.md#flake-fixes-go-first), though the rule's outside-service exception (file, don't bump) may apply if the cause proves to be the hosted runner: the first recurrence decides.
