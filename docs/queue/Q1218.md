# Move the release signer to cosign v3 without breaking v2/Flux verifiers

The weekly updatecli cosign bump now crosses a major version, v2.5.2 to v3.1.4 (PR #2139, opened 2026-10-26), and is held unmerged until this row is done.
That binary signs every image, attestation, chart and blob [`publish.yml`](../../.github/workflows/publish.yml) releases, and operators verify those signatures with their own tools: their own cosign ([install.md](../operations/install.md), [migration-v1-to-v2.md](../operations/migration-v1-to-v2.md)) and Flux's cosign provider ([gitops.md](../operations/gitops.md)).

No pre-merge check reaches the risk.
The publish job runs only on a `v*` tag, so no PR executes a signing step, and the release-candidate gate verifies with the same pinned cosign that signed, so it would pass a release a cosign v2 or Flux verifier rejects.
Whether v3's default signature and bundle output stays readable by those verifiers is unmeasured.

Done means: sign a test artifact with v3 the way `publish.yml` does (image `sign --recursive`, `attest --type spdxjson`, `sign-blob` bundle), verify each with cosign v2.5.x and with the Flux version `gitops.md` names, and either merge the bump with the operator docs stating the verifier floor, or pin the v2-compatible signing flags in `publish.yml` before merging.
Validate the result with a release candidate before the next stable tag.
