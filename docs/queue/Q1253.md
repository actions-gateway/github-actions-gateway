# Worker egress admits any Azure storage account, not only GitHub's

Every worker egress mode admits Azure blob storage, and nothing in [05-security.md](../design/05-security.md) records what that lets an untrusted-PR worker reach.

What is measured, on 2026-11-01 from a Kata worker in the dogfood cluster's `gag-dogfood-e2e` tenant (direct mode, no additive egress): `productionresultssa0` and `productionresultssa19.blob.core.windows.net` answered HTTP 400 while `example.com` timed out, in [run 41371432425](https://github.com/actions-gateway/github-actions-gateway/actions/runs/41371432425).
Their addresses sit in `20.209.226.0/23` and `20.209.112.0/23`, two of the 8,419 ranges the GMC's workload policy admits on 443, taken from the `actions` key of GitHub's `/meta` (`cmd/gmc/internal/controller/ipranges.go`).
The hostname backends name `*.blob.core.windows.net` outright ([network-architecture.md](../design/network-architecture.md)), and that wildcard matches any account by construction.

What is not measured: whether a storage account nobody at GitHub owns resolves into the admitted ranges in direct mode.
If it does, a compromised worker can upload to an account its attacker controls, which is the exfiltration the GitHub-only posture is described as preventing.
Blob storage cannot simply be dropped, because the runner uploads to GitHub's own accounts.

Done is a measurement and a recorded answer: create a throwaway storage account in a region GitHub's ranges cover, probe it from a Kata worker in direct mode and through an EgressProxy, then either add the residual to 05-security.md's threat table with its bound, or narrow the admitted set (for example to GitHub's account names where a hostname backend is in use) and say what that costs.
Found by Q215's Kata run, whose step 3 assumed blob storage was unreachable ([the Kata run](../plan/q215-worker-cache.md#the-kata-run-2026-11-01)).
