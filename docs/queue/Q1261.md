# Cut v1.10.1 with the runner bump if v2.0.0 is not tagged by 2026-11-18

**Event:** 2026-11-18 arrives and `v2.0.0` has not tagged.
If it has tagged, delete this row.

`v1.10.0`'s default worker image runs `actions/runner` 2.338.1.
`scripts/release/check-runner-window.sh --pinned 2.338.1` measured on 2026-11-01 that 2.338.2, published 2026-10-26T14:45Z, leaves it 24 days of GitHub's 30-day update window, so around 2026-11-25 GitHub stops queueing jobs to those runners while each keeps logging `Listening for Jobs`.
Nothing on the cluster names the cause.

The window after `v1.10.0` is held for `v2.0.0` rather than shipped as `v1.11.0` ([why](../plan/release-ladder.md#why-there-is-no-111-rung)), so no minor will move the default before that date unless 2.0 does.
The fix is a patch: create `release-1.10` from the `v1.10.0` tag, cherry-pick only #2170 (`fix(worker): bump actions/runner to 2.338.2`), and cut `v1.10.1` through the candidate flow ([Patch releases and backports](../operations/release.md#patch-releases-and-backports)).
The 2026-11-18 trigger leaves a week for the candidate, its dogfood gate, and operators to roll it out.

Re-run the window check first: a runner release after 2.338.2 does not restart 2.338.1's clock, but it does mean `v1.10.1` should take the newest stable runner rather than 2.338.2.
