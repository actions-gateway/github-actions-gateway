# Cut v1.10.1 with the runner bump and a wrapper fix, whatever v2.0.0 does

**`v1.10.1` has to reach operators before about 2026-11-25, and `v2.0.0` cannot do that for a cluster below its Kubernetes floor.** Q1284 (#2268) raised that floor to 1.35, so an operator below it has to upgrade the cluster before taking `v2.0.0`, and `v1.10.1` is the path past the deadline that needs no cluster upgrade.
Starting the candidate by 2026-11-18 leaves a week for it, its dogfood gate, and operators to roll it out.

**The runner bump.** `v1.10.0`'s default worker image runs `actions/runner` 2.338.1.
`scripts/release/check-runner-window.sh --pinned 2.338.1` measured on 2026-11-06, with the feed from `gh api repos/actions/runner/releases` as its input, that 2.338.2, published 2026-10-26T14:45Z, leaves it 19 days of GitHub's 30-day update window.
After that GitHub stops queueing jobs to those runners while each keeps logging `Listening for Jobs`, and nothing on the cluster names the cause.
The bump is #2170 (`fix(worker): bump actions/runner to 2.338.2`).
Re-run the window check first: a runner release after 2.338.2 does not restart 2.338.1's clock, but `v1.10.1` should then take the newest stable runner.

**The wrapper fix.** `useImageVolume` in `v1.10.0`'s `cmd/agc/main.go` picks an image volume on any server from 1.33, on the stated ground that the feature is on by default there.
The measurement in #2268, on kind with the `v1.10.0` charts: on Kubernetes 1.34.11 the AGC logged `imageVolume: true`, a Pod with its worker's volume, mount and command stored neither the volume nor the mount and failed with exit 128, and the initContainer form reached the wrapper; on 1.35.5 the same Pod kept its volume and reached the wrapper. #2268 reads upstream as leaving the `ImageVolume` gate off until 1.35.
So with the gate off, a `v1.10.0` worker on 1.33 or 1.34 does not start unless the operator sets `WRAPPER_DELIVERY=init`, and the runner bump alone does not help that cluster.
Below 1.33 the AGC already picks the initContainer.

Not measured: 1.33 itself, a managed provider's gate setting, and a job through a worker the AGC created.
The fix is neither designed nor sized, and `M` is a placeholder until it is.
It has no twin on `main` to cherry-pick because Q1284's floor makes 1.33 and 1.34 unreachable there, so it lands on `release-1.10` alone; read [Patch releases and backports](../operations/release.md#patch-releases-and-backports) on what that needs.

**The cut.** Create `release-1.10` from the `v1.10.0` tag, cherry-pick #2170, take the `dogfood-e2e-runner` pin from #2268 in both `deploy/dogfood-e2e/overlays/` kustomizations, add the wrapper fix, and cut `v1.10.1` through the candidate flow.
The pin is there because `validate-release.sh` dispatches e2e from `main` on patch lines too, and `main`'s suite runs `helm template` against the 1.35 floor, which #2268 measured `2.338.1-1`'s Helm 3.16.3 refusing; that the candidate would fail this way is read from the code, not run.
Q1307 holds the same image's own runner deadline.
The `v2.0.0` window is otherwise held out of this line ([why](../plan/release-ladder.md#why-there-is-no-111-rung)).

**Done when** `v1.10.1` is tagged, and a worker the AGC created on Kubernetes 1.34 has started under the default `WRAPPER_DELIVERY`, and `docs/releases/v2.0.0.md` names `v1.10.1` under **Upgrading** with its `WRAPPER_DELIVERY` step re-read.
