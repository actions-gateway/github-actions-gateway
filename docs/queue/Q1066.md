# Registry read cannot present ECR node-role pull credentials

The registry read behind `RunnerVersionTooOld` (Q988) authenticates with `kubernetes.io/dockerconfigjson` Secrets: those the pod template's `imagePullSecrets` names, or, when it names none, those on the worker ServiceAccount.
On GKE, `ActionsGateway.spec.registryIdentity: GKEWorkloadIdentity` adds the AGC's own Workload Identity for Artifact Registry ([the plan](../plan/q1066-gke-workload-identity.md)).
An ECR repository that kubelet reaches through the node's IAM role has no Secret to read and no equivalent, so such an image pulls fine and reports `WorkerImageVersionUnknown` with an authentication failure in the message, while the tag verdict, if the tag names a version, stands; which status ECR returns to the anonymous read is unmeasured.

Closing it means an `EKSPodIdentity` (or IRSA) value on `registryIdentity`, under which the AGC calls ECR `GetAuthorizationToken` with an IAM role it assumes.
The GKE value set the shape to follow: the token goes only to ECR hosts no pull Secret covers and never to a Bearer realm on another host, and the egress the credential path needs is admitted only for an opted-in gateway.
What differs is the egress: IRSA exchanges a projected token at AWS STS over 443, which the AGC's default policy already admits, while EKS Pod Identity reaches a node-local agent on a link-local address, which it does not (from memory, unverified; read AWS's current docs); measure which the target cluster uses before choosing.
It is a dependency (the AWS SDK, or a hand-written SigV4 call) and an identity grant, and needs the operator half of [doc-update-matrix.md](../development/doc-update-matrix.md) in the same PR.
