# Measure the superseded check on a fork PR whose branch is main (M5)

The `superseded` futility check (Q1181) withholds a re-run when a newer run of the same workflow, event and branch exists from the same `head_repository`, and nothing has measured that this keeps a fork's `main` from matching upstream's `main`.
A wrong answer withholds a fork PR's legitimate re-run whenever upstream `main` builds, which is the design's M5.

- Open a pull request from a fork whose head branch is `main` against a test repository, fail its job by disruption, push to upstream `main`, and read whether the re-run is withheld as `superseded`.
- If the filter does not separate them, the check needs more than `event` and `head_repository`; the [design notes](../plan/q555-automatic-recovery-design.md#the-futility-checks-r18-in-order) say what it compares today.

Also unmeasured beside it, and cheap to read in the same session: whether a merge-group run that loses its place is cancelled by GitHub and so caught by `run_cancelled`.
Gated on 2.1 with the rest of the retry work ([release-2.1.md](../plan/release-2.1.md)).
