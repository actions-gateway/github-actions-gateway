# Start the gate deploy once the images publish, not the whole publish run

**The release gate waits for all of `publish.yml` before it deploys, but deploy needs only the image jobs, which finish 5.5 to 5.8 minutes before the run does.** The rest is `chart-publish`, measured at 5m47s for `v2.0.1-rc.1` (run 44236526788) and 5m30s for `v2.0.0-rc.3` (run 44043285692).

`chart-publish` creates the GitHub Release and attaches the signed v2 CRD manifest and the `gag-migrate` binaries.
The gate reads those in `crd_smoke` and the storage leg's `fetch_gag_migrate`, about 35 minutes after deploy; `setup.sh` installs the chart from the checkout, not from the published OCI chart.
So `wait-for-publish.sh` can return once every `publish (…)` job has succeeded, and the gate can require the run's overall success just before the CRD smoke.

The saving applies only when the `dogfood-validation` approval comes before the images: rc.1's approval took 2m30s and the gate waited 11m13s, while rc.3's took 24m18s and the gate waited 1 second.
**Cost:** Actions minutes fall by the same; node-hours are unchanged.
**Risk:** a red `chart-publish` is found after the Kata leg rather than before deploy, spending about 35 minutes of node time on a candidate that cannot ship.
How often `chart-publish` fails was not counted; count it from `publish.yml`'s run history before choosing.

**Done when** the gate deploys on the image jobs' success, refuses the CRD smoke unless the run succeeded, and `wait-for-publish-test.sh` covers a green image set with a red `chart-publish`.
Confirm first that nothing deploy reads comes from `chart-publish`.
