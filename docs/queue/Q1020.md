# The mirror recipe is single-tenant and does not say so

`deploy/registry-mirror/base/networkpolicy.yaml` names exactly one tenant namespace, twice: as `e2e-mirror-egress`'s own `metadata.namespace`, and as the mirror-side ingress policy's `kubernetes.io/metadata.name` peer.
So the shipped shape admits one tenant, and the README's adopting section lists that namespace as a value to retarget without saying what a second tenant does.
Two answers are possible and they differ in posture: a mirror deployment per tenant, or one deployment whose ingress peer names several namespaces.

**Why it matters here rather than as a sizing note.** [secure-multi-tenant-oss-ci.md](../plan/secure-multi-tenant-oss-ci.md#definition-of-done) Definition of Done #4 is that an untrusted job cannot read another tenant's cache, secrets, or job payloads "including through anything the platform provides for its convenience", and Q408 just made the mirror exactly that.
The shared variant is not obviously wrong: every byte it holds is a public upstream image, so content confidentiality is not the exposure.
What it does open is inference, since a cache hit is faster than a miss and the access log names repositories, so one tenant can learn what another pulled and when; and it widens the blast radius the residual-risk section already accepts for a compromised mirror from one tenant to all of them.

**Unmeasured**, and the measurement is the deliverable: whether the hit/miss timing gap is actually distinguishable from inside a Kata guest across a bridge NAT, on this Deployment shape.
A rejected inference channel is as good an answer as a confirmed one, and either way the recipe should state which variant it recommends and why.

Not a Q408 defect: the dogfood cluster runs one tenant, so the posture Q408 validated is the posture Q408 claimed.
This is the gap between that and the multi-tenant product the recipe is published for.
