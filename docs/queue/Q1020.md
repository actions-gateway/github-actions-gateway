# Ship both mirror topologies and the cost-versus-risk choice between them

`deploy/registry-mirror/` renders one mirror set admitting one tenant: `base/networkpolicy.yaml` names the tenant namespace twice, as `e2e-mirror-egress`'s own `metadata.namespace` and as the mirror-side ingress policy's `kubernetes.io/metadata.name` peer.
The README lists that namespace as a value to retarget and says nothing about a second tenant, so an adopter running more than one meets an undocumented fork.

**Both topologies are legitimate and the platform admin owns the call**, so ship both and write the decision rather than picking one.
The choice is cost against risk, and it is theirs because only they know their tenant count, their disk budget, and whether their tenants are mutually hostile.

**A shared set is one line.** Only the mirror-side ingress differs: the worker-side egress policy lives in the tenant namespace and is per-tenant either way.
Swapping that peer to `namespaceSelector.matchLabels: {actions-gateway.com/tenant: managed}` admits every managed tenant, using the marker the GMC's own confinement policies already key on (`api/v2beta1/shared_types.go`).
Note what that buys and costs: it admits tenants created later, automatically.
A subset needs `matchExpressions` with an explicit namespace list.

**Isolated costs a set per tenant.** Measured off the manifests: 5 Deployments, 5 Services and, on the persistent overlay, 5 PVCs, requesting 125m CPU and 320Mi memory with limits of 2500m and 2560Mi, plus 50Gi of disk the README prices at about $5/month.
Multiply by tenant count.
The cache also stops being shared, so every tenant pulls `kindest/node` cold on its own and pays that upstream bandwidth separately.

**Isolated buys two things.** No inference channel: on a shared set a cache hit is faster than a miss and the access log names repositories, so one tenant can learn what another pulled and when.
And a compromised mirror reaches one tenant rather than all of them, which narrows the residual [secure-multi-tenant-oss-ci.md](../plan/secure-multi-tenant-oss-ci.md#explicitly-out-of-scope-and-residual-risk-accepted) already accepts.
Neither is about content confidentiality: every byte a mirror holds is a public upstream image.

**One thing is unmeasured and the measurement belongs in this row**: whether the hit/miss timing gap is actually distinguishable from inside a Kata guest, across the bridge NAT, on this Deployment shape.
A refuted channel is as good an answer as a confirmed one and would make shared the easy default for most adopters; confirming it makes the guidance sharper.
Do not write the decision guide as if the answer is known.

Deliverables: the shared variant as a rendered option beside the current one; a decision section an admin can act on, naming the tenant count where the disk cost starts to bite and the tenant relationship where isolation stops being optional; the timing measurement, reported either way.
Placement follows the existing split, mechanism in [`deploy/registry-mirror/README.md`](../../deploy/registry-mirror/README.md) and the choice on the operator page.

Sits under Definition of Done #4, which covers what a job can read through "anything the platform provides for its convenience" — Q408 made the mirror exactly that.
Not a Q408 defect: the dogfood cluster runs one tenant, so the posture it validated is the posture it claimed.
This is the gap between that and the multi-tenant product the recipe is published for.
