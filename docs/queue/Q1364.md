# Bring the e2e node up during the gate deploy, not on the Kata dispatch

**The Kata leg's worker is what scales the e2e pool up from zero, so the leg's start pays the whole cold path after deploy has finished.** For `v2.0.1-rc.1` (gate run 44236535751) the dispatch-to-runner time was 3m59s: 1m42s from scale-up to node Ready, 33s until the CSI driver and scheduler placed the pod, a 37s `kata-qemu` sandbox failure, and 36s of image pulls.

Deploy and `e2e-start.sh` take about 4 minutes before the dispatch, longer than that path, so scaling the e2e pool to one node as deploy starts should hide it.
**Saving:** about 3 minutes per gate (estimate).
**Cost:** falls slightly (estimate): the e2e node starts 1–2 minutes before it is used, while the system pool's two nodes stop about 3 minutes sooner.

**Risk:** `reserve_cpu_budget` (Q631) reserves the e2e pool's ceiling out of the project CPU quota after setup, and a node raised before it draws on the same budget, the failure Q631 was filed for.
Keep the reservation ahead of the scale-up.
The node is never the Dragonfly leg's, which [Q1363](Q1363.md) guarantees.

`v2.0.0-rc.3`'s Kata wait was 9m56s, and its worker pod's first event came 5 minutes after the job was created; those 5 minutes were not read and may be a separate cause.

Not a duplicate of [Q1161](Q1161.md), which the duplicate search matched on the shared target: that row runs the legs on separate clusters, and this one only moves one node's start earlier.

**Done when** the gate raises the e2e pool to one node during deploy without breaking the Q631 ordering, and the first gate after it shows the Kata dispatch-to-runner time.
