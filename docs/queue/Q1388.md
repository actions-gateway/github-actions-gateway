# An out-of-memory raise no node can hold spends the run's whole budget

Under `Binpack` the out-of-memory class raises the memory request with the limit, and nothing asks whether any node can hold the raised request.
Measured on dogfood on 2026-11-24 (run 45326748517): a raise to 12672Mi on nodes offering 12369Mi left the re-run `Pending` for 20 minutes, first beside eight worker nodes holding no worker and then, as idle nodes were removed, with none, since none the autoscaler can add holds the request; it ran through two GitHub withdrawals and re-issues, until `pendingPodDeadline` reaped the third worker and the AGC cancelled the run.
The abandoned arm then re-ran the run because a smaller job's worker was placed on the set, which spent the second of its two slots on a third attempt at the same 12672Mi, again `Pending`.

Two separate gaps, and either can be closed alone:

- **The raise.** The class could withhold, or lower the raise, where `next` is above what the set's nodes can hold.
  The scheduling constraints are on the killed pod and a node list would answer it, but the AGC's node access has not been read, and an autoscaled pool at zero nodes shows no capacity at all; a cheaper first step is an Event naming `maxRequests.memory` when the re-run's worker is unschedulable and carries a floor.
- **The release.** The abandoned arm treats any placed worker of the set as capacity returned, so a worker of a different size releases a run whose own worker still fits nowhere.
  The placement would have to be of a worker at least as large.
  This is not the class's: any set with a per-job floor, or whose resolved size changed since, has it.

The Q1320 futility check `worker_unstartable` does not cover it: it reads workers stuck starting, and leaves placeability out on purpose, because a full cluster also reads as unschedulable.

Operators can avoid it today with `maxRequests.memory` set to what an empty node holds ([worker-rightsizing.md](../operations/worker-rightsizing.md#when-a-job-runs-out-of-memory)).
