# A signal hides the release gate's failure, or skips its teardown

**A release gate ended by Ctrl-C, `kill` or a closed terminal records no failure and dumps no diagnostics, and a closed terminal leaves its nodes billing.** `teardown` reads `$?` as the verdict, and bash runs an EXIT trap after an untrapped signal with the last command's status, 0.

Measured 2026-11-23 on `f0c7a3eda`, bash 5.3.15 on macOS, with the gate's own `teardown`, EXIT trap and progress stream around one blocked step, cluster calls and stop scripts stubbed.
No cluster was used, and bash on Linux was not run.

| Ending | Runs | Gate's status | Failure event | Diagnostics | Status file | Stop scripts |
|---|---|---|---|---|---|---|
| A step fails (control) | 1 | 1 | yes | yes | `failed` | both run |
| TERM to the gate alone, or to its process group | 10 | 143 by signal | no | no | `running` | both run |
| Ctrl-C on a pty | 4 | 130 by signal | no | no | `running` | both run |
| HUP to the gate alone, or to its group while a plain command blocks | 9 | 129 by signal | no | no | `running` | both run |
| HUP to the group while the gate is inside `$(…)`, output to a file | 8 | 129 by signal | no | no | `running` | skipped in 7 |
| Terminal closed, output to that terminal | 16 | 129 by signal | no | not readable | `running` | **skipped in 16** |
| Terminal closed, output to a file | 16 | 129 by signal | no | no | `running` | both run |

The gate's own status is never 0: it dies of the signal.
Teardown still prints `Teardown complete (exit 0)`, and the stream still reads `running` after it, so `release-sentinel.sh` can report it only as `stalled`, later, where a recorded failure would be `failed`.

Two causes of the skipped teardown.
With the terminal gone, `teardown`'s first `echo` fails and errexit ends the trap there, read from an xtrace.
Inside `$(…)` the trap was not entered at all, and why is not known.
The lease is kept either way, so the next gate or `--reclaim` finds the nodes.
`docs/operations/release.md` recommends `nohup`, which ignores HUP, so the skip needs a gate run in the foreground; the header of `validate-release.sh` says HUP self-cleans.

**What was tried.** Trapping the three signals to `exit 130`, `143` and `129` recorded the failure and the diagnostics in all ten signal cases run (a blocked command and one inside `$(…)`), and ran the stop scripts in 4 of 4 for HUP inside `$(…)`.
The closed terminal still skipped them, 8 of 8, until teardown also ran under `set +e`, then 0 of 8.
The stubs write to a file: the real stop scripts print, so a fix has to give them an output that still exists, not only survive its own `echo`.

Three things a fix has to handle:

- A trapped TERM to the gate alone waits for the foreground command, 4.7s of a 5s one, where an untrapped one ended the gate in 0.2s.
  A lost lease stops the gate with a TERM.
- `dragonfly_readings` sets these three traps and clears them with `trap -` on its way out, which would drop the gate's own.
- Ctrl-C during `wait` on a background job is swallowed (seen once on the same harness, exit 0): bash starts the job with INT ignored.
  `e2e_leg`'s two waits on `capture_pid` have that shape.

**Done when** each ending above records the failure with its status and runs both stop scripts, the gate's tests signal a real process for it, and the header and release.md say what is true.

Not a duplicate of [Q1161](Q1161.md) or [Q1025](Q1025.md), which share only the script: one runs legs in parallel, the other drives a capacity verdict.
