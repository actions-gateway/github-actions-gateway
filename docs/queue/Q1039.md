# No cluster this repo stands up runs the shared-tenants mirror topology

The component's NetworkPolicy ships enforced on operator clusters and unexercised on every cluster the repo can boot.

**Measured 2026-08-29, re-derived 2026-09-03.** `scripts/dogfood/e2e-start.sh`'s `apply_registry_mirror()` applies `deploy/registry-mirror` or, under `REGISTRY_MIRROR_PERSISTENT=1`, `overlays/persistent`.
Neither composes `components/shared-tenants`.
Nothing under `scripts/`, `.github/` or `mk/` applies the component or its two overlays to a cluster — the two gates that name them read their text and render them in CI — so no dogfood window and no e2e lane has ever driven traffic through the shared ingress policy.

**Why this matters more than the render gap.** `check-registry-mirror-render.sh` (Q1024, shipped) *renders* those overlays; this is that no cluster *runs* them.
A rendered policy proves the YAML composes.
It cannot show that the peers it admits match the pods that actually connect, which is the failure mode the shared topology has: a NetworkPolicy ingress narrowing is fail-closed and total, so a peer that misses one real client black-holes that client's every pull.

**What it already cost.** [Q1026](https://github.com/actions-gateway/github-actions-gateway/pull/1795) narrowed the shared ingress peer to worker pods and was held in draft to wait for a dogfood window to confirm no client was cut off.
That window could never confirm it: dogfood runs the isolated topology, so the narrowed policy is not applied there.
The PR merged on that reasoning rather than on a live reading.

## The venue is the Calico kind lane

Scoped 2026-09-03.
The three readings that settle it, all from the repo:

- **Only the Calico lane enforces.** kindnet accepts NetworkPolicy objects and does not reliably drop the traffic (Q7b/Q119), and that holds for ingress as well: `manager_np_test.go` gates its metrics-*ingress* specs on `egressEnforcingCNI()` for exactly this reason.
  So the venue is `e2e-calico.yml` → `e2e-reusable.yml` with `kind_cni: calico`, and a spec there skips on kindnet like its neighbours.
- **The apparatus is already built.** `manager_np_test.go` grades a `namespaceSelector`-keyed ingress peer in both directions with throwaway namespaces, and `runEgressProbe(ns, name, workloadLabeled, curlArgs)` already carries a toggle for the very label this peer ANDs in.
  This item is that file's shape pointed at a different policy, not a new capability.
- **A dogfood leg is the worse venue, not the dearer one.** `deploy/dogfood-e2e/base/resources.yaml` already marks `gag-dogfood-e2e` with `actions-gateway.com/tenant: managed`, and that cluster has one tenant, so a dogfood run of the shared overlay produces the positive and **cannot produce either negative** without namespaces the cluster does not have.
  The negatives are where the fail-closed risk lives.
  A window is also booked and event-gated, where what this needs is a check that runs on every change to the component.
  And applying the shared overlay there swaps the live `registry-mirror-worker-access` in place, leaving the cluster on the shared policy until the next `e2e-start.sh`.

## What the lane grades

Three probes against the render of `overlays/shared-tenants`, each a one-shot curl pod on 5000:

| Namespace | Pod | Expected |
|---|---|---|
| marked, **and not `gag-dogfood-e2e`** | `actions-gateway/component: workload` | admitted |
| marked | unlabelled | denied |
| unmarked | workload-labelled | denied |

**The first row's namespace choice is the control.** Under the base's isolated ingress a namespace other than `gag-dogfood-e2e` is denied, so a green positive cannot be produced by the wrong render.
An assertion run in the tenant namespace could not distinguish the two.
Rows two and three are the two halves of the AND that Q1026 introduced and nothing has read live.

Probe the real render rather than a stand-in listener, deliberately: the policy's `podSelector` is `app: registry-mirror`, and a Deployment whose pods lost that label leaves the policy selecting nothing, which is fail-**open** and invisible in a green suite.

**Not an upstream-backed pull, deliberately.** The row previously asked for "at least one real pull".
What grades the peer is whether a connection completes an HTTP exchange on 5000, and `GET /v2/` is answered by the registry's own API layer rather than by the cache behind it, which is why it is the readiness probe.
So the probe reads the admitted path and nothing downstream of it.
An upstream manifest fetch would add a Docker Hub dependency on a hosted runner, the flake the lane already mirrors curl and Vault into its local registry to avoid, and would grade the mirror's upstream path, which is topology-independent (the component's only patch replaces `spec.ingress` of one policy) and is already graded on dogfood by `e2e-mirror-validate.sh`.

## The work

1. `e2e-reusable.yml`: cache and mirror `registry:3.1.1` and `haproxy:3.2.23-alpine` into the lane's local registry, `if: inputs.kind_cni == 'calico'`, modelled on the curl and Vault steps.
   Both are Docker Hub digest pins, so they are the 429 class those steps exist for.
2. A test-only kustomization composing `deploy/registry-mirror/overlays/shared-tenants` with an `images:` override at the two mirrored refs, so the shipped overlay is what renders and only the image source moves.
3. `cmd/gmc/test/e2e/mirror_np_test.go`: a `Describe` skipping on `!egressEnforcingCNI()`, applying that kustomization in `BeforeAll`, scaling four of the five instances to zero (one running pod satisfies `app: registry-mirror`), and the three probes above with `DeferCleanup` on the namespaces.
   Keeping the apply in the suite rather than the workflow means the kindnet lane pays nothing.
4. Docs: the "What is proven, and what is not" section of `deploy/registry-mirror/README.md`, the spec list in `docs/development/testing.md`, and `e2e-calico.yml`'s header list, which that file's own comment says has drifted before, so grep the call sites rather than trusting the count.

**Size is S**, not the M it was filed at: the scoping found the whole apparatus already built, so the diff is one spec file modelled on a sibling, one small kustomization, two workflow steps and three doc edits.
Two things would make it M: if `kind load` cannot satisfy the digest-pinned refs and the image path needs rework beyond the transformer, or if the PSA labels the GMC's `NamespacePSAReconciler` stamps on a marked probe namespace reject the curl pod.
Both are cheap to probe first and neither changes the venue.

**What it does not close, by design.** The four wired clients (dockerd, the ref-rewrite `docker pull`, helm's OCI client, buildkit) are Kata-job wiring, and the kind probe is a curl pod.
So the lane grades the peer *expression*; it does not grade that a real worker's source address resolves to its workload-labelled pod under GKE Dataplane V2 across the Kata bridge.
That reading is `scripts/dogfood/e2e-mirror-clients.sh`, and nothing schedules it: [Q1048](Q1048.md).

**Done when** the Calico lane applies a shared-tenants overlay and the three probes above pass on it, with each negative confirmed able to fail (drop the peer's `podSelector`, require the unlabelled probe to go green, restore).
