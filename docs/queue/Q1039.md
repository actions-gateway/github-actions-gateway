# No cluster this repo stands up runs the shared-tenants mirror topology

The component's NetworkPolicy ships enforced on operator clusters and unexercised on every cluster the repo can boot.

**Measured 2026-08-29.** `scripts/dogfood/e2e-start.sh`'s `apply_registry_mirror()` applies `deploy/registry-mirror` or, under `REGISTRY_MIRROR_PERSISTENT=1`, `overlays/persistent`.
Neither composes `components/shared-tenants`.
Nothing under `scripts/`, `.github/` or `mk/` names the component or its two overlays except the static gate that reads their text, so no dogfood window and no e2e lane has ever rendered the shared ingress policy, let alone driven traffic through it.

**Why this matters more than the render gap.** [Q1024](Q1024.md) is that no gate *renders* those overlays; this is that no cluster *runs* them.
A rendered policy proves the YAML composes.
It cannot show that the peers it admits match the pods that actually connect, which is the failure mode the shared topology has: a NetworkPolicy ingress narrowing is fail-closed and total, so a peer that misses one real client black-holes that client's every pull.

**What it already cost.** [Q1026](https://github.com/actions-gateway/github-actions-gateway/pull/1795) narrowed the shared ingress peer to worker pods and was held in draft to wait for a dogfood window to confirm no client was cut off.
That window could never confirm it: dogfood runs the isolated topology, so the narrowed policy is not applied there and `scripts/dogfood/e2e-mirror-clients.sh` would have graded a policy the cluster was not enforcing.
The PR merged on that reasoning rather than on a live reading.

**Done when** one venue applies a shared-tenants overlay and drives at least one real pull through it.
The cheapest shape is probably a kind lane rather than a dogfood leg, since the topology's distinguishing property is which peers the policy admits and not anything about Kata or GKE Dataplane V2; that choice is the open question here.
