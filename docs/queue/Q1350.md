# Narrow FQDN-mode blob egress to GitHub's published storage accounts

Every FQDN-mode egress backend admits `*.blob.core.windows.net`, which is every Azure storage account, and the proxy's opt-in CONNECT allowlist carries the same suffix ([the residual](../design/05-security.md#worker-exfiltration-to-azure-hosted-endpoints-inside-githubs-published-ranges)).
GitHub's `/meta` publishes the accounts it uses under `domains.actions`: 140 `productionresultssa<N>.blob.core.windows.net` names on 2026-11-12 ([the plan](../plan/q1253-azure-egress-residual.md#can-the-admitted-set-be-narrowed)).

Split from Q1253, which measured and recorded the residual and closed without changing what is admitted; this row is the change.

The shape, settled on 2026-11-12, with its reasons:

- **The narrowed list is the default, and the wildcard is an explicit opt-out.** The narrowed list is the more secure option, so the secure-by-default rule puts it first.
  The opt-out exists so a platform can fall back if the published list breaks a job.
  It is a platform-owned GMC flag rendered from a chart value next to `fqdnPolicyBackend`, and a string enum per [api-review.md](../development/api-review.md#prefer-a-string-enum-to-a-bool): `Published` by default, plus a wildcard value.
  Widening it is a security relaxation, and whether the list is complete is GitHub's fact, the same for every tenant, so it is not a tenant field.
  An upgrade narrows existing FQDN-mode pools, so the release note says so.
  This reverses the usual "follow what already ships" direction on purpose.
- **Falling back to CIDR filtering already exists:** `egressPolicyMode: CIDR` on the `EgressProxy`.
  Direct mode and CIDR mode have no hostname layer, so this change cannot narrow them.
- **The GMC learns names from the `/meta` fetch it already makes** every 24 hours in `IPRangeReconciler`.
  It decodes `domains.actions`, keeps the blob entries, persists them beside the CIDRs so a restart without `/meta` still has them, and requeues FQDN-mode `EgressProxy`s on change.
  Those policies are rendered by `egressFQDNs`, not by the CIDR patch loop.
  A missing or empty key keeps the last-known list and never falls back to the wildcard.
- **A platform-owned ConfigMap adds names without waiting for GitHub's list or the next refresh.** It reuses the watched-ConfigMap pattern of the egress destination allowlist ([security-operations.md](../operations/security-operations.md#self-service-additions-via-a-watched-configmap)): a key that adds to the published list, fail-safe, and in the GMC namespace.
  Entries must be exact `<account>.blob.core.windows.net` names, so the ConfigMap cannot re-widen to the wildcard; the enum is the one way to do that.
- **The proxy's CONNECT allowlist gets the same list** in place of the `blob.core.windows.net` suffix (`proxyAllowlistEnv`), so the two enforcement layers agree.

Not measured: how often GitHub adds an account, which sets how often the refresh lag fails a job; GKE `FQDNNetworkPolicy` behaviour at 140 names; and whether any runner feature writes to an account outside the published list.
