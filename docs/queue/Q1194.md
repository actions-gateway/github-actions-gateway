# Reference-architecture profiles page: gated vs validated-once

Users choose a shape across several axes (worker isolation, egress posture, mirror topology, mirror back end, node-layer P2P, CNI), and no page says which combinations are supported or how each was tested.
The pieces are spread over [kata-dind-workloads.md](../operations/kata-dind-workloads.md#untrusted-pull-requests--the-tight-egress-posture), [p2p-image-distribution.md](../operations/p2p-image-distribution.md) and `deploy/registry-mirror/README.md`, and a user has to assemble the rest.

The deliverable is one operator page listing a handful of named profiles rather than the full cross product, which runs to roughly 288 combinations, most of them nobody's real choice.
Each profile names its validation venue in one of two tiers, decided 2026-10-23:

- **Gated every release:** what the release gate already runs, the Kata, DinD and Kata-on-Dragonfly legs.
  No new legs: the gate is already long on the dogfood cluster's mostly free GKE tier, and a new permutation joins it only on user demand.
- **Validated once:** run once on dogfood, with the date, the run and the readings recorded on the page, and re-run on demand or when something it depends on changes.
  [Q1193](Q1193.md) is the first.

Read on 2026-10-23 from the scripts, workflows and overlays, not from a run: the shared-tenants topology runs in the Calico CI lane (Q1039); the persistent and shared-persistent topologies are render-checked only; the Dragonfly back end pairs only with the per-tenant ephemeral topology, because `e2e-start.sh` refuses it with the persistent one.
