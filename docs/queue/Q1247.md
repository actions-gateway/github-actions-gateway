# Roadmap driver hands back a clean git merge that binds one ID twice

When the roadmap merge driver finds a backlog ID on two bullets of the merged `docs/roadmap.md`, it falls back to git's own three-way merge, and where that merge is clean it exits 0 with only a stderr note: the duplicate lands with no conflict.
Measured 2026-11-01 against the driver at #2198's head `8b78d52`: base `X q:Q10,Q11` and `Y q:Q20`, ours rebinds X to `q:Q10`, theirs rebinds Y to `q:Q20,Q10`.
The driver printed `the merged page lists a backlog binding more than once: Q10; the plain three-way merge resolved it cleanly` and exited 0 with Q10 on both bullets.
The same fallback-to-clean shape is deliberate for a whole bullet added to two lists (`git-merge-roadmap-test.sh` asserts rc 0 and git's output verbatim there), so this predates Q1240 and is not reachable by the shapes Q1240 fixed.
Nothing downstream catches it: on the same day `make roadmap-check` passed a real page with one bullet duplicated under overlapping IDs (16 bullets, exit 0), so the gate has no one-ID-one-bullet rule.
Two fixes, unweighed: give `devtools/docs/roadmapcheck` a uniqueness rule, which catches the duplicate however it arrived, or have the driver exit non-zero on a duplicate even when git's merge is clean.
