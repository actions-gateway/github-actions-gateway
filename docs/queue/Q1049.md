# `brokertest` strands a queued job when its session is deleted

Measured 2026-09-03 while fixing [Q1008](Q1008.md).
`brokertest.Server.EnqueueJob` keys its job queue by session ID, and `handleSession`'s DELETE leaves that queue in place with nobody polling it, so a message enqueued onto a session that then goes away is never delivered and never re-offered.

Real GitHub does not behave that way: a runner pool's queue outlives any one session, and an undelivered message is redelivered to a sibling session of the same owner.
The mismatch matters because the AGC recycles a session on **every** acquired job (single-use JIT agents, Q114), so any test that enqueues a second job for one owner is one scheduling swap away from the stranded case.
Q1008 was that, and it cost a red `main`.

Q1008's fix teaches its two call sites to exclude the spent session, and [testing.md](../development/testing.md#avoiding-shared-stub-flakes-in-the-agc-suite) states the rule, so the known instances are closed.
This row is the class: the next test to enqueue twice has to know the rule, and the stub could enforce it instead.

Candidate: on DELETE, move that session's undelivered messages to another active session of the same owner, or hold them for the next session that owner registers.
Weigh it against what per-session isolation currently buys: `sigterm_test.go` and the Q260 fan-out accounting both enqueue per session deliberately, so re-offering must not silently redeliver where a test asserts a job was dropped.
Decide that before writing it; a wrong answer here makes a test double lie in a new direction rather than the old one.
