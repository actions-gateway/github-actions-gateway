# Key a security-dashboard panel on the egress-audit attribution gauge

Q1062 shipped `actions_gateway_egress_audit_unattributed`, the series the security dashboard's own Row 1 prose says a consumer-keyed panel would have to gate on so a pool's traffic is never read under a consumer's name without the join to back it.
No panel reads it yet, so the dashboard still keys egress entirely on the pool.

The minimum is a fourth series in the existing "Egress posture per gateway" state timeline, which it fits: that panel is `1 = flagged` and so is this gauge, and it tells the audit persona which tenants' egress resolves to no job and since when.
Unfiltered, it would be near-solid `1` across a fleet that has not turned the pair on, and a band that is always lit in a `1 = flagged` row trains the eye to discount the three neighbours where a `1` genuinely is a fault.
The answer below filters it instead, which keeps the since-when a timeline gives and drops the always-lit band.

The reason this was not folded into Q1062 is the render, not the JSON: `make dashboard-render-check` fails a dashboard changed beyond its panel descriptions whose screenshot did not, so the panel needs a live Grafana + Prometheus to re-render `docs/assets/grafana-dashboard-security.png` per [`deploy/monitoring/preview/README.md`](../../deploy/monitoring/preview/README.md).
A consumer-keyed *traffic* panel, proxy series filtered to the gateways reading `1`, is the larger question behind it and needs its own decision about what a mixed pool should show.

**Ask (answered):** yes, filtered to opted-in tenants, decided by the maintainer on 2026-10-09.
The series plots only a tenant that has turned on at least one half of the pair, so a lit band is a configured pair with a gap in it, which the audit persona can act on, and a tenant that never opted in is absent rather than flagged.
How many tenants have opted in at all is a separate stat panel, if one is wanted, and not a series in this row.

The filter needs a label the gauge does not carry yet: `actions_gateway_egress_audit_unattributed` has `namespace` and `name` only, so a query cannot tell `EgressAuditDisabled` (neither half on) from a partial pair.
So key the panel on the per-`RunnerSet` gauge Q1069 shipped, `actions_gateway_runnerset_egress_audit_unattributed{namespace,runner_set,reason}`, whose `reason` is one of `EgressAuditJoined` (the one `0`), `WorkerAuditDisabled`, `ProxySourceAuditDisabled`, `WorkerAuditWithoutProxy`, `EgressAuditDisabled` and `DirectEgress`.
The reason alone says whether the tenant opted in: on a set with no pool it reads `WorkerAuditWithoutProxy` when the gateway logs `WorkerAddresses` and `DirectEgress` when it does not, so `EgressAuditDisabled` and `DirectEgress` are the only reasons for a tenant that turned neither half on.
So the filter that implements the answer above is `reason!~"EgressAuditDisabled|DirectEgress"`, and it keeps opted-in tenants whose sets egress directly.
This row rides [release 1.10](../plan/release-1.10.md).
