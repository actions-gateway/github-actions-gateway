# Nothing warns when shipped code merges during a candidate window

`v1.6.0-rc.1` was tagged 2026-08-25 and never validated: #1725, #1726 and #1674 merged on top of it, and `check-artifact-unchanged.sh v1.6.0-rc.1 origin/main` then exited 1 on 11 files of the released surface, all `go.mod`/`go.sum` across `broker`, `cmd/agc`, `cmd/proxy`, `cmd/worker`, `githubapp` and `scaleset`.
The `k8s.io/*` bump from 0.36.3 to 0.36.4 links into the shipped AGC binary, so the candidate's verdict would no longer have described what shipped.
Cost was one candidate number plus a second cut and a second dogfood run.

The freeze rule exists for exactly this window and is documented, but it is only ever evaluated by hand, by whoever promotes, after the fact.
Nothing signals it at the moment the merge happens, and the merging PRs were Dependabot's, which nobody reads as release-affecting.

Worth deciding rather than assuming: whether the signal belongs on the PR (a check that notices the newest tag is an unpromoted prerelease and that the diff touches the released surface, per `semverfloor -ships`), or on the candidate (a watcher that reports when its verdict stops covering `main`).
The first interrupts contributors during every freeze; the second interrupts only the release engineer.
Blocking is probably wrong either way -- the bumps were good changes and the right answer was a new candidate, not a held merge -- so scope this as a warning that names the candidate it invalidates.
