# `gh api` job logs exits 1 and writes nothing on escape sequences

Reading a workflow job's log to confirm a gate actually ran is the instrument [testing.md](../development/testing.md#path-gated-workflows-verify-the-heavy-gates-actually-ran) sends you to when a green check is not enough.
It has a failure mode that turns a failed read into a plausible finding, and nothing in the output marks it.

## Measured 2026-09-18

Confirming that Q1118's new assertions had run on GitHub's runner rather than only locally:

```
gh api "repos/{owner}/{repo}/actions/jobs/105392327528/logs" > st.log 2>&1
# exit 1; st.log holds:
#   the response contains terminal escape sequences; pass --allow-escape-sequences to output it anyway
```

The log is **not written**, so a grep for the assertion names over `st.log` returns empty.
That empty reads exactly like the assertions being absent, which is the conclusion under test and the alarming one — a gate job reporting green for a heavy job whose content never ran.
Re-running with `--allow-escape-sequences` returned the real 423 KB log, with every assertion present.

Both halves of the trap are ordinary practice.
The redirect is what [bash-style.md](../development/bash-style.md) and the exit-status rules ask for, and it is what routes the error message into the file a later grep reads.
And a job log is exactly where a reader has already decided the answer matters.

## What to write down

One entry under testing.md § [The status you report is a claim too](../development/testing.md#the-status-you-report-is-a-claim-too), where the neighbouring rules about an empty result already live:

- The invocation carries `--allow-escape-sequences` whenever a job log is fetched to support a claim.
- Reconcile the fetch's own exit status before grepping what it wrote, since the error lands *in* the output file rather than beside it.
- A positive control settles it in one line: grep the log for an assertion that existed before the change under test, and disbelieve the read if that one is missing too.
  The control is what separates "the read failed" from "the job did not run it", which no amount of re-reading the empty result can.

The doc's own worked example is the first site to fix: the `gh api` line under § Diagnosing failures carries no flag, so a reader following it lands in exactly this case.
