# Re-run a killed job's fail-fast siblings, not a timed-out one

The out-of-memory retry re-runs a killed leg of a fail-fast matrix alone (Q1319) and leaves the siblings GitHub cancelled for it, so the run stays failed until a person re-runs them.
Before Q1319 the retry called `rerun-failed-jobs`, which this repository has recorded as taking cancelled siblings too.

It cannot count `cancelled` as harmless, because the jobs list spells a job past its `timeout-minutes` the same way, and re-running a timeout is what 2.1 must not do.
The check run's annotations tell the two apart (the readings), but need `Checks: read`, which the App has only where the optional `Checks: Read and write` is granted, and the wording is GitHub's to change.

Where every failed job but the killed ones is `cancelled` with the fail-fast annotation, `rerun-failed-jobs` takes nothing else, so the release could make that call; without the permission, or on any other text, it re-runs the killed job alone as now.
Two readings come first: a lost runner's leg cancelling its siblings, and `rerun-failed-jobs` re-running a cancelled sibling.
Q1374 asks the same annotation of flaky-job detection, on its hot path.
