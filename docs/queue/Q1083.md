# Deprecation notice is release-count only, with no wall-clock floor

The stated policy, cited from [v1alpha1-deprecation.md](../operations/v1alpha1-deprecation.md), is that "a removal lands on a named release announced at least one release ahead".
That is expressed purely in release count.
Measured 2026-09-07 over the shipped tags — `v1.1.0` 2026-07-12 through `v1.7.0` 2026-08-30, six minor releases in 49 days — one release ahead is about **8 days** of wall-clock notice.

That is the whole guarantee an operator has, and it is far below what the project actually gives in practice: `v1.3.0` announced the `v2.0.0` removals on 2026-08-03 and `v2.0.0` still has no date, so `v1alpha1` has had over a month against a stated minimum of about a week.
A policy nobody is meeting the letter of is one that will be read literally exactly once, by whoever it inconveniences.

Upstream expresses the same idea as "9 months or 3 minor releases, whichever is longer", which pairs a release count with a wall-clock floor precisely so neither a fast nor a slow cadence can evade it.
Upstream's constant is calibrated for a project shipping three minors a year and is wrong for this one; the *shape* is what is missing here.

The deliverable is a wall-clock floor beside the release count in the roadmap's policy statement.
The number is a judgement rather than a measurement: this project has no adopters to measure an upgrade cadence from, and a window can always be lengthened later but never shortened, so erring short now is the recoverable direction.
