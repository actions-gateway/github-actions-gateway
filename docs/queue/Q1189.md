# Backport candidates run gate legs their release line never had

`validate-candidate.yml` always runs main's `validate-release.sh`, and with `legs` empty it runs every leg in main's `GATE_LEGS_ALL`, including any leg added after a release line branched.
On a backport candidate such a leg fails, because the line predates what it tests, and the legs after it in the gate's order never run.
Measured with Q1171's `storage` leg: a pre-1.10 candidate's `gag-migrate` has no `storage-version` command, and `dind` and `dragonfly` run after `storage`.

Publish is not affected: its `validated-candidate` job checks out the tag (`actions/checkout` with no `ref:`), so `check-validated-candidate.sh` reads the tag's own `gate-legs.sh` (confirmed by the #2076 review).
So the failed leg is never required, and the cost is one extra billable dogfood run to finish the remaining legs with `--legs`.

Today the only guard is a sentence in `docs/operations/release.md` ("For a candidate on a line older than 1.10, pass `legs` without `storage`"), which someone has to remember at dispatch.
No `release-1.8` or `release-1.9` branch exists (2026-10-13), so nothing has paid this cost yet; the first backport RC cut after a new leg lands will.

A mechanical fix would default an empty `legs` to the candidate tag's own `scripts/dogfood/lib/gate-legs.sh` (`git show <tag>:…`), so the gate runs exactly the legs that tag's publish will demand.
Unmeasured: whether every leg main's script runs is also defined for an older tag's list, and how a tag predating `gate-legs.sh` should resolve.

Separate from Q1162, which makes the gate wait for a candidate's images to publish, and from Q1161, which runs the e2e legs in parallel across projects: neither changes which legs a candidate runs.

Filed from the Q1171 retro.
