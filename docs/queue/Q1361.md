# An unplaceable scale-set worker is re-created every five minutes

**A job whose only worker can never start gets a fresh worker every five minutes until GitHub gives up on the job, and each one registers a runner.** The mechanism is derived from the code and one measured GitHub behaviour, and has not been reproduced.

GitHub withdraws a scale-set assignment no runner takes within five minutes, with a `JobCompleted` naming no runner, and re-issues the job under a new job ID.
Measured once, on dogfood on 2026-11-18, from the cluster's audit log; whether GitHub documents the window was not checked.
The withdrawal stamps the stuck worker `job-completed-at`, so the reaper deletes it 30 seconds later under `completed_pending`, and the re-issue gets a new worker that sticks on the same capacity.
A Pending worker's own `pendingPodDeadline` (10 minutes by default) never fires, because the withdrawal always comes first, so the abandoned-run recovery that deadline starts (Q766) never runs either.

The shape to expect is a node that accepts pods and cannot run them, such as a broken on-premises node with no autoscaler to replace it, or a runtime class the pool lacks.
The opt-in capacity gate (`spec.capacityGate`, off by default) declines intake on scheduling signals, and a pod bound to a broken node may never produce one.

This is separate from Q1360, which is an idle `Running` worker with no deadline.
Here every worker has a deadline and the loop is the cost.

**Done when** the loop is reproduced against `test/fakegithub` or a kind cluster with an unplaceable worker, and the AGC either stops re-provisioning a job whose earlier workers never started or surfaces it on the `RunnerSet`, with a test that goes red with the mechanism deleted.
