# Schedule Kata workers only onto nodes whose kata-qemu runtime is ready

**Every cold e2e node on the measured gates failed its first sandbox with `no runtime for "kata-qemu" is configured`, because the worker is scheduled before the node's Kata runtime is installed.** The failure window was 37s for `v2.0.1-rc.1`'s Kata leg, 74s for `v2.0.0-rc.3`'s, and about 52s for rc.1's Dragonfly leg ([Q1360](Q1360.md) measured that one); the kubelet's retry backoff decides when the sandbox is tried again.

Gating placement on a node label or taint that the runtime installer clears once `kata-qemu` is configured would remove the backoff part.
How much of each window is the install itself, which no scheduling change removes, was not measured; read the installer's own log on the next cold node before choosing.
**Saving:** up to the measured windows, so 1–2 minutes per gate (estimate), and the same on every cold-node Kata job outside the gate.
**Cost:** falls slightly.

**Done when** a Kata worker on a cold e2e node schedules only once its runtime is ready, and its events show no `FailedCreatePodSandBox` for a missing runtime.
