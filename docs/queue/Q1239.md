# TestResolverPendingThenDoneWakes reads the wake before it is delivered

**Event:** `TestResolverPendingThenDoneWakes` fails on `main`, in either of its wake assertions ("the caller is woken once the state changes" or "the caller is woken exactly once per state change").

Sighted once, in CI on PR #2176's unit-test job (`-race`, run 40633045071, 2026-10-28, `expected: 1 actual: 0`, "the caller is woken exactly once per state change"); that push changed only comments and docs, and the same job passed on the PR's previous head.

**Mechanism.** The resolver's completion path sets `e.state = Done` under `r.mu`, releases the lock, and only then calls the queued wakes, so a waiter can see `Done` while its wake has not run.
That order is the correct one: a wake makes the controller reconcile and call `Lookup` again, so a wake delivered before the state is visible could leave that reconcile reading `Pending` with no further wake owed.
`Wake`'s godoc states the ordering, and the test waits for the first wake with `require.Eventually` and asserts no second one arrives within 50 ms.

**Measured 2026-10-27 on a local Mac.** With a 50 ms sleep between `r.mu.Unlock()` and the wake loop, the old single-read assertion failed 5 of 5 with `actual: 0` and the waiting form passed 5 of 5.
Without the sleep, the waiting form passed 300 of 300 under `-race`.
Deleting the wake loop fails it on "woken once", and calling each wake twice fails it on "exactly once".

**Sweep.** No other test reads a `Wake` counter after `waitFor`: `TestResolverSettledEntryHoldsNoWakes` inspects `e.wakes` under `r.mu`, and the controller tests call `Wake` synchronously on a fake resolver.
