# TestResolverPendingThenDoneWakes reads the wake before it is delivered

**Top of queue per [flakes-first rule](../development/maintaining-backlog.md#flake-fixes-go-first).**

`TestResolverPendingThenDoneWakes` waits for the lookup to leave `Pending`, then asserts the `Wake` callback already ran exactly once.
The resolver does not promise that ordering: its completion path sets `e.state = Done` under `r.mu`, releases the lock, and only then calls the queued wakes, so a reader can see `Done` while `woken` is still 0.
It failed that way in CI on PR #2176's unit-test job (`-race`, run 40633045071, 2026-10-28, `resolver_test.go:41` `expected: 1 actual: 0`, "the caller is woken exactly once per state change"); that push changed only comments and docs, and the same job passed on the PR's previous head.

Measured 2026-10-27 on a local Mac: 0 failures in 300 runs under `-race`, so the window is narrow.
With a 50 ms sleep inserted between `r.mu.Unlock()` and the wake loop in `resolver.go`, the test failed 5 of 5 with `actual: 0`, which is the mechanism this row asserts.

The likely fix is in the test, since `Wake`'s godoc promises only that it is called once the state changes, not before the change is visible: wait for `woken` to reach 1 rather than reading it once, and keep the "exactly once" half by asserting it stays at 1.
Sweep the idiom across `resolver_test.go` and its package: any assertion reading a `Wake` counter straight after `waitFor` has the same race.
