# Overlay deletions never reach a cluster that already applied them

`kubectl apply -k` does not prune, and `e2e-stop.sh` deliberately leaves the tenant's NetworkPolicies standing so a window can reopen without re-deriving them.
So removing an object from an overlay under `deploy/` removes it from the manifests and from nowhere else: every cluster that applied it once keeps it, indefinitely, while the tree says it is gone.
No gate off the cluster can see the gap, because both halves are individually correct.

Measured 2026-08-28 on `gag-dogfood`, preparing the Q408 Phase 4 session: `e2e-open-egress` was still applied, 28 days old, with the manifests that create it already deleted from the branch.
The cost was nearly the whole session rather than a failed apply.
Phase 4's instrument is a battery of negatives, so a surviving allow-all policy would have reported the posture unenforced — correctly, and for a reason having nothing to do with the change under test.

[PR #1782](https://github.com/actions-gateway/github-actions-gateway/pull/1782) closed the instance: `e2e-start.sh` deletes that one policy on the Kata lane, `--ignore-not-found`, with the dind lane asserted untouched.
That is a named object in one script, and the class is every object anyone removes from any overlay.

**What the general instrument looks like.** A reconciliation that reports objects present on the cluster and absent from the rendered overlay, run where `e2e-start.sh` already applies.
`kubectl diff -k` does not answer it — it compares what the overlay declares against the cluster, and says nothing about what the cluster holds beyond it.
The readings that would: a label selector over the tenant namespaces against `kustomize build` output, or `kubectl apply --prune` with an explicit allowlist, which is the sharp option and can delete an operator's own objects if the selector is wrong.

**Three decisions this needs before it is written**, which is why it is a row rather than a follow-up commit: which namespaces are in scope (the tenant only, or `gag-registry-mirror` too), whether an unexpected object warns or fails the bring-up, and whether the tool deletes or only reports.
Warn-and-report is the safe default and probably the right one: the failure being closed is a human reading a list, not an automated delete on a prod-classified cluster.

**Not only a dogfood concern.** The same gap reaches any operator adopting `deploy/registry-mirror/` on a cluster that already ran open-egress CI, which is the population the Q408 recipe is written for.
Whatever this lands as should be reachable from [security-operations.md](../operations/security-operations.md), not only from the dogfood scripts.
