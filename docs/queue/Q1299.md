# make apply-cert-manager applies to whichever kubectl context is current

`cmd/gmc/Makefile:104:kubectl apply -f $(CERTMANAGER_MANIFEST)` names no context, and neither does the `wait-cert-manager` target beside it, so the target acts on the shared current context.
This repo's rule is to pin the target on every ad-hoc `kubectl`, because parallel sessions share that context and mutate it.

**Measured** on 2026-11-06, during Q1107: the target ran against a private `kind-q1107-gap` cluster only because `kind create` had just made that the current context, read from its `created` output and from the pods' ages there.
Nothing in the command would have stopped it landing on another session's cluster.
The guard that refuses an unpinned `kubectl` did not refuse this run, and a run with a shared cluster current was not tried.

**Done when** the two targets take the context explicitly, and `kind-iteration.md` and `local-kind-demo.md`, which call them, show how.
