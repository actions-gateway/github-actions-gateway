# Private GHCR pulls with the AGC's GitHub App token are unmeasured

The registry read behind `RunnerVersionTooOld` can present a pull Secret or, on GKE, the AGC's Workload Identity to Artifact Registry, but nothing for a private `ghcr.io` package unless a tenant stores a personal access token in a pull Secret.
GitHub's container-registry docs name only a classic personal access token and, inside Actions, `GITHUB_TOKEN`; they document no federation and no GitHub App token, so a cloud workload identity has no path to GHCR.

The AGC already holds a GitHub App credential, which would need no new identity if GHCR honoured it for pulls.
Measured 2026-10-13 with the `actions-gateway-test` App (ID 3752347, installation 135739122): `ghcr.io/token?service=ghcr.io&scope=repository:actions-gateway/agc:pull` returned 200 with the installation token as `x-access-token`, 403 with a wrong password, and 200 anonymously.
So GHCR authenticates an App installation token, but that App holds no `packages` permission and every `actions-gateway` package is public, so whether an App token with `packages: read` can pull a **private** package is unmeasured.

Closing it starts with that measurement: an App granted `packages: read`, a private package, and the same three requests plus a manifest GET.
If it works, the read could present the gateway's own App token to `ghcr.io`, under the same rule the Workload Identity login follows: only to the registry's own host and only where no pull Secret covers it.
Whether the App credential should be used for this at all is a decision for that row: the gateway's App is scoped for runner registration, and adding `packages: read` widens what a leaked AGC credential can read.
