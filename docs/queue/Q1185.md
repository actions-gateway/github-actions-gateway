# Should feature PRs stop editing a release plan's Status cell?

Every PR in a release batch rewrites the same cell, so each merge leaves the next PR conflicted and the batch can only merge one at a time.
This is a question for the maintainer, not a decided change: the alternative leaves that cell stale between releases.

## The measurement

Read 2026-10-10 off `gh pr view --json files` and `gh pr diff` for the five 1.10 pull requests of orchestrator run session-orchestrator-9d5db8:

- #2058, #2059, #2060, #2062 and #2063 each edit `docs/plan/README.md`, `docs/plan/release-1.10.md` and `docs/roadmap.md`; the four other than #2058 also edit `docs/operations/upgrade.md`.
- In `docs/plan/README.md` each one rewrites the same row, `release-1.10.md`'s, and within it the Status cell: #2063 moves Q1154 from "gate" to "landed" in `❌ Scoped 2026-10-09, no candidate cut: …`.
- They merged one after another: #2060 at 20:51Z, #2058 22:17Z, #2059 22:50Z, #2062 23:36Z, #2063 00:16Z.

Relayed from the orchestrator run, not re-measured here: each merge left the next PR `DIRTY`, costing about five rebase-and-CI cycles, and the #2062 rebase produced a duplicated `roadmap.md` bullet that `roadmap-check` rejected, by a mechanism nobody has verified.

## Why the merge drivers do not help

[`git-merge-plan-index.sh`](../../scripts/docs/git-merge-plan-index.sh) would refuse these merges even where it runs, because it hands back "a row changed on both sides" as a conflict ([the refusal rules](../development/maintaining-backlog.md#the-merge-drivers-resolve-registry-rows-by-key-not-by-line-position)); that is read from the driver's documented rules, not exercised on these PRs.
It also does not run on GitHub: the mergeability check behind `mergeStateStatus` and the merge queue's candidate both take the plain three-way merge.
So this is not [Q1130](Q1130.md)'s case, two PRs editing *adjacent* rows, which a driver resolves locally and spacing the batch avoids.
Here every PR edits *one* row, and nothing short of not editing it removes the conflict.

**Why each PR edits it now.** [The rule](../development/maintaining-backlog.md#plan-level-status-lives-in-the-plan-index) is to update a plan's Status cell when its overall status changes, and a release plan's cell names its gating rows by link.
A PR that deletes a row the cell links has to edit the cell, or `make doc-links` fails on the dead link.
`release-1.10.md`'s per-item rows carry the same obligation; whether those edits overlapped between PRs was not checked.

## The trade-off

- **Leave it to the release-closing PR.** Feature PRs stop touching the Status cell and the release doc's per-item rows, and the batch merges in parallel.
  The cell goes stale between releases, so it reads "Q1154 gates" after Q1154 has landed.
  It also needs the cell to stop linking individual rows, or deleting one still forces an edit.
- **Keep the per-PR edit.** The cell stays current at every merge, at the cost of serial merges for any batch that targets one release.

**Ask:** which of the two the maintainer wants; this is their call, and no measurement settles it.

**Measure:** before asking, whether `check-plan-index.sh` invariant 1, which needs an open-marked row backed by a live item, still holds with a cell that names no rows, and how often a release batch runs more than two PRs at once.
The deliverable is this row rewritten with a decision, not an implementation.
