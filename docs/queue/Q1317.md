# Reproduce the out-of-memory retry class on dogfood (M3, R12)

Q1183 shipped the out-of-memory retry class from source, without the dogfood reproduction R12 asks of every class, so the shape it recognises is unmeasured.
The class fires on a pod that reached `PodFailed` with the runner container terminated `OOMKilled` ([04-operational-flows.md](../design/04-operational-flows.md#out-of-memory-under-right-sizing-the-first-retry-class-scale-set-q1183)).
That rests on recall of the kubelet: on cgroup v2 an out-of-memory kill ends the container's whole process group, runner included, while on cgroup v1 or under `singleProcessOOMKill` only the largest process dies and the runner reports a failed step instead, which the class does not recognise.
This is the design's M3.

- Run a job on a `Binpack` set with `sizingProfileState: Active` that allocates past its limit, and read the pod's phase, the runner container's termination reason, and when GitHub concludes the job (the design expects about 10 minutes, when the job lock lapses).
- Confirm the re-run's pod carries the raised limit and the `MemoryLimitRaisedForRetry` Event fires.
- If the runner survives, the class fires from the wrong place: it would need to move to `JobCompleted`, as the design's [Where a class fires](../plan/q555-automatic-recovery-design.md#where-a-class-fires) allows.

The 2.1 headline is retry for more platform failures ([release-2.1.md](../plan/release-2.1.md)), and a class shipped on an unmeasured shape is the first thing it has to settle.
Same dogfood session as [Q1236](Q1236.md) where convenient.
