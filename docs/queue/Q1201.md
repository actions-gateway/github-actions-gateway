# make e2e runs against the ambient kube context, dogfood included

`make e2e` and `make e2e-cluster` never name a cluster.
The ginkgo suite, its `setup.sh` steps and its teardown all read the current context from the shared `~/.kube/config`.
Any session on this machine can switch that context, and a dogfood script does it on every run (Q1019). prod-guard inspects the agent's own Bash command, so it sees `make e2e` and nothing the suite runs inside it.

**Measured 2026-10-24** working Q1177.
Four `make e2e SUITE=live-github` runs between 00:56Z and about 01:10Z failed in setup waiting on fakegithub.
`kubectl config current-context` then read `gke_actions-gateway-dogfood_us-east1-b_gag-dogfood`.
A peer session's `scripts/dogfood/start.sh` started at 00:52:54Z, which fits the switch, though nothing recorded which call made it.
On the dogfood cluster, which is hard-classified prod, the suite did the following:

- It installed upstream metrics-server v0.8.1 into `kube-system` beside GKE's own.
  The two deployments share the `k8s-app=metrics-server` label, so GKE's Service selected both.
- It installed cert-manager v1.20.2.
  The first run's teardown then uninstalled it, and the next run installed it again.
- It created namespace `e2e-infra` and deployed fakegithub into it.
  Its images point at `127.0.0.1:5000`, so they never pulled, and that pull failure is the only reason setup failed.
- It server-side applied main's five actions-gateway CRDs with `--force-conflicts`.
  That moved storage from `v2beta1` to `v2` under a `v1.9.0-rc.2` GMC, and `status.storedVersions` now reads `[v2beta1 v2]`.
- Its teardown ran `make undeploy`, which happened to be a no-op only because dogfood's release is named `gag`.

All of it was removed or restored by hand afterwards.

The failure was loud only by luck: fakegithub's image could not pull.
A suite whose images resolved would have run its specs, tenants and all, on prod.

Fix shape, unmeasured:

- Have the `e2e` targets export a private `KUBECONFIG` from `kind get kubeconfig --name $(KIND_CLUSTER)`, so the run never reads or writes the shared context.
- Have the suite's `BeforeSuite` refuse to start unless the context it resolves is `kind-$(KIND_CLUSTER)`.
  That catches a hand-run `ginkgo` as well.

The second half is the gate; the first only narrows the window.
Q1186 is the same hazard in the dashboard preview harness.
