# A scale-set replay during its old worker's termination acks with no pod

A scale-set job replayed while its previous worker pod still exists with a `deletionTimestamp` gets no worker of its own, and the listener acks the job anyway.
`ProvisionScaleSetWorker` names the pod from the job ID, so the replay's pod create returns `AlreadyExists` for the terminating pod; that path reads as "the replayed job already has its worker" and returns nil.
`ownerPodsGone` reports the terminating pod live (it exists under the owner reference's UID), so the Secret is kept too, still holding the old runner's spent JIT config.
The runner registered for this delivery (`generateJITConfig` in `scalesetlistener/listener.go`, just before `Provision`) then never starts.

Unmeasured: read from code by the Q1174 reviewer and confirmed by reading `ProvisionScaleSetWorker` and `ownerPodsGone`, not reproduced.
Whether GitHub hands the job to another of the set's runners in the meantime is also unmeasured, and decides how much this costs.
A pod's graceful termination lasts seconds to minutes, so this window is likely wider than Q1174's, which lasted only until the garbage collector ran.

**A likely fix**: on the pod create's `AlreadyExists`, read the pod; one with a `deletionTimestamp` is not this job's worker, so fail the delivery with an error the listener retries (`provisionRetry`) until the old pod is gone.

**Reach.** Any scale-set tenant whose session is re-created while one of its workers is terminating: the replayed job's freshly registered runner never gets a pod.
