# `maxEvictionRetries: 0` reports every disruption as budget exhausted

A `RunnerSet` with automatic re-runs turned off still reports each disrupted worker as an exhausted retry budget.
Read from source on 2026-11-27, not run: with a budget of 0 the scale-set recovery calls `recordRetriesExhausted` before anything else (`cmd/agc/internal/provisioner/eviction.go:242:if maxRetries <= 0 {`), and the classic tier reaches the same call through a reservation that 0 always refuses.
That emits a Warning `EvictionRetriesExhausted` Event reading `the auto-retry budget (0) is exhausted; a manual re-run is required` and increments `actions_gateway_eviction_retries_exhausted_total`.
The shipped `ActionsGatewayEvictionRetriesExhausted` alert fires on any increase of that counter, so an operator who set 0 is alerted on every disruption.

The API reference calls 0 the way to disable auto-retry entirely, and two runbooks tell operators to set it: the read-only `Actions` permission path in tenant onboarding, and a workload that fails consistently.
The design's test plan asserts the counter increments at 0, so the behaviour is deliberate, and what it costs is that "off" and "ran out" are one signal.

**A fix:** at 0, count and report the disruption as a re-run withheld, with a reason of its own on `actions_gateway_eviction_rerun_withheld_total` and a Normal Event, and leave the exhausted counter for a budget that was spent.
That changes a documented metric's meaning at 0, so it needs an upgrade note and the test-plan line updated with it.
