# Keep the shipped cache and mirror Deployments off worker nodes

**The cache server and the registry mirrors GAG ships can still land beside a worker, where a worker that escapes its container can write the artifacts other jobs pull next.** The GMC now keeps the pods it builds (its own, the AGC and the egress proxy) off nodes running worker pods, with a required pod anti-affinity against workers in every namespace and an opt-out for single-node clusters (chart value `controllerWorkerSeparation`, GMC flag `--controller-worker-separation`).
The cache and the mirrors are not built by the GMC: they are kustomize bases an operator applies, so that change does not reach them.
Read at `b3e802656`: `deploy/gha-cache/base/deployment.yaml`, `deploy/registry-mirror/base/deployment.yaml`, and the `deploy/athens/` and `deploy/dragonfly-core/` manifests carry no `affinity` at all.

The term to copy is `workerSeparationTerm` in `cmd/gmc/internal/controller/worker_separation.go`: it selects `actions-gateway/component: workload` together with `app.kubernetes.io/component: runner`, because the AGC pod carries the component label too.

The open question is the opt-out.
A kustomize base has no chart value, so a required term in the base strands the pod on a single-node cluster unless the operator patches it out.
Options are a component the operator adds to turn it on, or the term in the base plus a documented patch to drop it; the second is the secure default and matches the GMC.
The e2e and dogfood scripts reference these bases (`scripts/e2e/mirror-timing.sh`, `scripts/dogfood/e2e-mirror-validate.sh` among others), so whichever shape is chosen has to keep those lanes scheduling; which clusters they apply them to, and how many schedulable nodes those have, was not read for this row.

**Done when** each shipped cache and mirror Deployment carries the worker separation term or a documented component that adds it, the single-node opt-out is documented beside it, and the dogfood lanes still schedule.
