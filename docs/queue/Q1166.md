# updatecli fails every run: GITHUB_TOKEN cannot write workflow files

The scheduled `updatecli` workflow has concluded `failure` on every run from 2026-06-22 through 2026-10-19, and has opened one bump PR in that time: [#1695](https://github.com/actions-gateway/github-actions-gateway/pull/1695), Karpenter.
Measured 2026-10-23 with `gh run list --workflow updatecli.yml`.

**Every pin in a workflow file is refused at push.** The job hands updatecli `secrets.GITHUB_TOKEN`, and GitHub refuses that token any write under `.github/workflows/`: run 37327993420 (2026-10-05) logs 48 `refusing to allow a GitHub App to create or update workflow … without workflows permission` lines.
The `workflows` permission is not one the job's `permissions:` block can grant `GITHUB_TOKEN`, so no edit inside the workflow fixes this.
8 of the 10 manifests under `updatecli.d/` write one of six workflows (`e2e-reusable`, `autoscaler-drift`, `integration-test`, `publish`, `security-scan`, `unit-test`), so kind, Calico, shellcheck, cosign, syft, buildkit, polaris and envtest have never been bumped by the lane that owns them.
[dependency-updates.md](../development/dependency-updates.md) tells a maintainer to watch for "a silent green with no PR for a long-stale pin", and this run is never green, so that advice does not reach it.

**Decision: move each workflow pin into a file updatecli may write; do not give updatecli a credential carrying `workflows: write`.** The bump job can already push any non-workflow file with `GITHUB_TOKEN`, and every bump still lands only through a PR a maintainer merges, so moving the pins adds no capability to any credential.
A GitHub App or fine-grained token with `workflows: write` would fix the push in one line and clear the bump PRs' `action_required` hold, at the price of a stored secret that can rewrite `.github/workflows/` on any branch; dependency-updates.md already declines a stored App token for the hold alone.

**What the move touches** (measured 2026-10-23):

- One pins file (for example `ci/pins.env`), and the 8 manifests retargeted to it.
  Pins carried by several workflows today collapse to one copy: kind and syft in two each, buildkit in three (`e2e-reusable`, `publish`, `security-scan`).
- Each job using a pin loads the file into `$GITHUB_ENV` after `actions/checkout`, since a workflow- or job-level `env:` cannot read a file; a small composite action keeps that to one line per job.
- `cosign-release` is an action input, so it reads a step output instead of a literal: `.github/workflows/publish.yml:422:cosign-release: v2.5.2` and `.github/workflows/publish.yml:586:cosign-release: v2.5.2`.
- Two gates parse pins out of workflow files and must retarget: `scripts/ci/check-cosign-pin.sh` (reads `publish.yml`), and `scripts/ci/check-tools.sh`'s `@ci:<VAR>` floor (`ci_pin`, an `awk` over `.github/workflows/*.yml`).
  `ci_pin` fails closed, so a missed retarget reddens `make doctor` rather than passing: an unresolved floor is counted as a broken registry row and added to the exit status (`scripts/ci/check-tools.sh:391:exit $(( missing_required + broken_floors ))`).
  The yamllint and kubeconform floors (`@ci:YAMLLINT_VERSION`, `@ci:KUBECONFORM_VERSION`) have no updatecli manifest and keep their pins in the workflows, so the retargeted `ci_pin` reads both the pins file and the workflows.
- The heavy jobs' path filters key on their own workflow files (for example `.github/workflows/unit-test.yml:137:- '.github/workflows/unit-test.yml'` and `.github/workflows/e2e-calico.yml:71:- '.github/workflows/e2e-reusable.yml'`), so each filter that guards a lane using a moved pin must also list the pins file.
  Otherwise a bump that touches only the pins file goes green without running the lane it bumps.
- The bump PRs' `action_required` hold stays, and the maintainer still releases them with **Approve and run**.

The first cosign bump this unblocks moves the signer in `publish.yml` from v2.5.2 to v3, since `updatecli.d/cosign.yaml` tracks the latest release with no major constraint; review that PR as a major bump.
