# updatecli fails every run: GITHUB_TOKEN cannot write workflow files

The scheduled `updatecli` workflow has concluded `failure` on all 16 of its runs, every Monday from 2026-06-22 to 2026-10-05, and has opened one bump PR in that time: [#1695](https://github.com/actions-gateway/github-actions-gateway/pull/1695), Karpenter, whose pin is the only one outside `.github/workflows/`.
Measured 2026-10-09 with `gh run list --workflow updatecli.yml`.

Two causes are live in the latest run (37327993420, 2026-10-05):

- **Every pin in a workflow file is refused at push.** The job hands updatecli `secrets.GITHUB_TOKEN`, and GitHub refuses that token any write under `.github/workflows/`: the log carries 48 `refusing to allow a GitHub App to create or update workflow … without workflows permission` lines across `e2e-reusable.yml`, `autoscaler-drift.yml`, `publish.yml`, `integration-test.yml` and `security-scan.yml`.
  The `workflows` permission is not one the job's `permissions:` block can grant `GITHUB_TOKEN`, so no edit inside the workflow fixes this.
- **The cosign manifest 404s.** `updatecli.d/cosign.yaml`'s `shaDarwinAmd64` source exits 22 on six `curl: (22) The requested URL returned error: 404` lines, so that pipeline fails before it reaches a push.
  The log does not print which URL 404'd; the bootstrap download of the pinned `v2.5.2` just before it succeeded, so the pin itself still resolves.

So kind, Calico, shellcheck, cluster-autoscaler, cosign, syft, buildkit, polaris and envtest have never been bumped by the lane that owns them.
[dependency-updates.md](../development/dependency-updates.md) tells a maintainer to watch for "a silent green with no PR for a long-stale pin", and this run is never green, so that advice does not reach it.
[Q944](Q944.md) is the neighbouring gap, that no manifest can be dry-run locally; this row owns the measurement of the scheduled runs.

**Ask:** what turns on the maintainer is which credential may write workflow files unattended.
A GitHub App token or a fine-grained token carrying `workflows: write` fixes the first cause in one line, and widens what an automated credential can change to the files that decide what runs with the repo's secrets.
The alternative keeps the token as it is and moves each workflow pin into a file updatecli may write (a `scripts/` env file, or a `vars.mk` the workflows read), which is more edits and no new credential.
The cosign 404 is a manifest defect either way and needs no decision.
