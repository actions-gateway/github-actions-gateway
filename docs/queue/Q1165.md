# render-overflow-check times out loading a page from its own local server

**Top of queue per the [flakes-first rule](../development/maintaining-backlog.md#flake-fixes-go-first).** Sighted once, on the `push main` run of `1ced9359b` (#2047, run 37403964143, 2026-10-06), which leaves `main`'s tip red on `doc-links`.
The merge-group run of the same tree passed six minutes earlier.

The `render-overflow` job built both site scopes and began measuring `site` at widths 320 and 1440, and Playwright's navigation then timed out:

```text
playwright._impl._errors.TimeoutError: Page.goto: Timeout 30000ms exceeded.
  - navigating to "http://127.0.0.1:35949/operations/velero-backup-restore/", waiting until "load"
```

The `site-dev` scope then measured 424 pages with no finding, so nothing about the page's layout failed.

**Mechanism unverified.** The server is the script's own, on loopback, so the wait is unlikely to be the server itself.
`wait_until="load"` in `scripts/docs/check-render-overflow.py:108:await page.goto(base + path, wait_until="load")` waits for every subresource, so a hung off-host subresource would produce exactly this.
The obvious two are already ruled out by `mkdocs.yml`, which sets `font: false` (fonts are self-hosted) and leaves `plausible_domain` empty (analytics off), so that reading is weaker than it looks.
Check the built page for any off-host resource before choosing a fix: if there is one, blocking off-host requests in the browser context removes the dependency; if there is none, the next suspect is the runner, and a retry on navigation is the cheaper repair.
