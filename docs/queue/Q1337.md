# Allowlist ConfigMap wait starts before the manager, not at cache sync

**The EgressProxy reconciler holds a pool for at most 30 s while the egress allowlist ConfigMap is unread, and the 30 s starts when the GMC wires its controllers, before the manager and its caches start.** If the ConfigMap reconciler's first read lands later than that, the first reconcile of a pool refuses a host the ConfigMap covers.
The pool's policy and the proxy's `PROXY_ALLOWED_HOST_SUFFIXES` lose the host, and regain it when the read lands and requeues every pool.
The host is in the proxy Deployment's environment, so that is two rollouts of the proxy, and a window in which the gateway cannot reach its GitHub Enterprise Server (GHES) appliance.

**The mechanism is a source read and is not measured.** `awaitEgressAllowlistConfigMap` calls `AwaitDynamic(time.Now().Add(egressAllowlistConfigMapWait))` from `registerControllers`.
How long a GMC takes from there to the ConfigMap reconciler's first read on a large or slow cluster is unknown, and so is whether 30 s is ever exceeded.
The ConfigMap reconciler runs on every replica without leader election, so a standby has read the list before it leads, and the exposure is a process start only.

The candidate fix, also unmeasured, is to start the clock when the manager's cache has synced instead of at wiring.

**Done when** a measurement shows whether the first read can land after the deadline, and, if it can, the wait is counted from cache sync and an envtest that delays the ConfigMap reconciler's start shows the pool's policy unchanged across the delay.
