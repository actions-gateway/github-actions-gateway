# A reaped scale-set worker leaves an unnamed job with no runner

A scale-set worker reaped `Pending` past `pendingPodDeadline` takes one runner out of its set, so one of the set's assigned jobs is left with no runner to start it.
Abandoned-run recovery (Q766) force-cancels and re-runs the run of the job the pod was created for.
Since Q1169 it skips that when another worker's runner started that job, because that run lost nothing (`cmd/agc/internal/provisioner/abandoned_scaleset.go`, `assignedJobAccountedFor`).
The job that did lose its runner is then a different one, and nothing names it, so it is recovered by nothing.
This is the open part Q1169 left: before Q1169 the same job was stranded too, and a live run was cancelled beside it.

**What becomes of the stranded job is unmeasured.** The design doc and the identity-unknown Event say GitHub cancels an unstarted job at its ~15-minute timeout, and that a manual re-run is then required; that is the expected outcome here, not one measured for this shape.

**The likely record is the listener's in-flight set** (`scalesetlistener.GuardState.InFlight`, Q606), which already holds the run identity of every job whose worker the listener built.
At the reap, the stranded job is an in-flight entry with no `actions-gateway.com/started-job-id` on any live worker and no live worker minted for it, the same reading the orphan scan's `scaleSetWorkerSet.serving` takes after a restart (Q844).
Two things make it harder than reusing that: the reconciler only reads the guard ConfigMap, once per process, and a job whose `JobStarted` has not arrived yet reads exactly like a stranded one, so the check needs a settle window or a later re-check.

Found from source while working Q1169; not observed on a cluster, and the rate is unmeasured.
It needs a worker stuck `Pending` past its deadline while another runner of the same set took that worker's job, so it shows on a set whose workers schedule unevenly (a node pool scaling up while others are warm).

**Reach.** Any scale-set tenant hitting that shape: one job's run waits out GitHub's unstarted-job timeout and needs a manual re-run, where Q766 meant it to be force-cancelled and re-run automatically.
