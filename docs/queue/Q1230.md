# Never-started preemption and eviction victims re-run instead of cancel

A worker preempted while still `Pending` goes straight to `rerun-failed-jobs` on both tiers, ahead of the abandoned handling that force-cancels a never-started worker's run first (Q691/Q766).
Read from source on 2026-10-27, not observed: on the classic tier `provision()` sets `cause = preemption` from `outcome.Preempted`, and the abandoned case requires `cause == ""`, so a preemption victim the delete path resolved with `DeletedBeforeStart` is re-run; on the scale-set tier `judgeScaleSetDisruption` tries `disruptionAwaitingRecovery`, whose `PreemptedByScheduler` arm matches, before `abandonedAwaitingRecovery`.
The classic routing is deliberate: its comment says a preemption victim most often never started and that one disruption gets one recovery, and it was written with Q628, before Q683 measured that a never-started job's run has to be concluded before a re-run is legal.
The kubelet eviction arm is ordered the same way on both tiers; whether the eviction manager ever evicts a still-`Pending` worker is unmeasured.
Q1198 moved the node-shutdown arm's never-started pods to the abandoned handling (`LostToNodeShutdownBeforeStart`) and left these two arms alone, because the preemption routing is a recorded decision and its scale-set shape (a victim deleted while `Pending`, which may never publish `Failed`) needs its own evidence.
Unverified, as on Q1198: what GitHub does with a re-run of a run whose job never started; the design table's abandoned row predicts a refusal until GitHub ends the run on its own, about as long as the 15-minute re-run window.
The likely fix routes a preemption or eviction victim with no container start record to the abandoned handling on both tiers, keeping `cause` on the metrics.
The in-flight row on futile re-runs (skip known-futile re-runs on the existing disruption arms) edits the same arms.
