# Jobs sharing one name: share a failure key and report false flakes

Flaky-job detection keys a failure by run ID and `jobDisplayName`, and GitHub accepts two jobs in one workflow with the same `name:`; measured on dogfood on 2026-11-22, the two then share one record, and the second job's success is paired with the first job's failure.
In run 45052015868 the jobs `shared-name-red` and `shared-name-green` both carried `name: shared-name`: the red one failed at 18:00:19 UTC (`82a2530d…`), the green one succeeded at 18:05:32 (`e44b9b0b…`), and the AGC logged `scale-set job re-run completed` with `trigger=other`, `flaky=true`, emitted a Normal `FlakyJobDetected` for a job nobody re-ran, and deleted the red job's record ([the readings](../plan/q555-automatic-recovery-design.md#readings-from-the-dogfood-turn-up-2026-11-22)).

So a workflow with duplicate job names inflates `actions_gateway_scaleset_flaky_jobs_total` and the manual re-run rate on `scaleset_job_reruns_total{trigger="other"}`, and loses the red job's context, whenever one twin fails and the other succeeds.
Whether matrix legs collide was not measured; their display names normally carry the matrix values, from recall.

The completion carries no attempt number, so the fix cannot simply require a later attempt.
A candidate is to pair only when the completion's job UUID was assigned after the failure was recorded, which the listener can see; whether that holds across an AGC restart is the open part.
[Q1319](Q1319.md) needs the same fact about duplicate names for a different reason, matching a classified job to its job ID for a single-job re-run.
