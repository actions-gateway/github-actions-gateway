# Manage shared in-cluster caches with a CRD and provider-side grants

**Event:** a tenant asks to share its in-cluster cache with another tenant, or a platform team asks to run one cache for several tenants, once [Q215](Q215.md) has shipped the per-tenant cache.

Q215 ships one cache server per tenant, in the tenant namespace, which the tenant's `ResourceQuota` pays for.
The two other modes in [tenancy modes](../plan/q215-worker-cache.md#tenancy-modes) are one mechanism with different owners: a server in a provider namespace, granted to the GAG tenants the provider names.
The provider is either another tenant or a cluster tenant that is not a GAG tenant, and in the second case quota, cost accounting and chargeback are the cluster administrator's.

The shape to copy is `EgressProxy`'s cross-namespace sharing ([§H.9](../design/appendix-h-v2-api-decomposition.md#h9-cross-namespace-proxy-sharing), shipped in Q166): a namespaced kind whose owner grants namespaces, consent only on the provider's side, the GMC writing NetworkPolicy on both sides, and an object in each granted namespace that carries the server's URL and whose presence is the grant.
Without the CRD an operator hand-wires both sides' policy and every consumer's `ACTIONS_RESULTS_URL`.

Two things in falcondev v9.8.0 make sharing weaker than for a proxy, read from source and not measured: `CACHE_MAX_SIZE_BYTES` is one budget for the whole server, so one tenant's saves evict another's entries, and the server accepts a token from any repository GitHub signs, so the grant's NetworkPolicy is the only caller boundary.
The design has to say whether a per-grant budget is needed, which would mean a server per grant or an upstream change.
Shared modes stay off for untrusted-PR tenants, whose isolation is the reason Q215 exists.
