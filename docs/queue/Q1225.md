# Share in-cluster caches across tenants: upstream asks, then a CRD

Blocked by [Q215](Q215.md): phase 2 of the in-cluster cache starts once phase 1, one server per tenant, has shipped.

Phase 2 adds the shared and platform-operated modes in [tenancy modes](../plan/q215-worker-cache.md#tenancy-modes): a server in a provider namespace, granted to the GAG tenants the provider names.
The provider is either another tenant or a cluster tenant that is not a GAG tenant, and in the second case quota, cost accounting and chargeback are the cluster administrator's.

falcondev v9.8.0 keeps tenants' entries apart but has no budget per tenant, no per-tenant metrics, and no owner allowlist, read from source and not measured ([the table](../plan/q215-worker-cache.md#phase-2-sharing-q1225)).
Nothing upstream asks for them yet.

The work, in [the plan's order](../plan/q215-worker-cache.md#phase-2-sharing-q1225):

1. File feature requests upstream for an owner allowlist, a budget per owner, and an owner label on the metrics, one issue each; falcondev takes no outside pull requests since v9.10.0.
2. Build a CRD shaped like `EgressProxy`'s cross-namespace sharing ([§H.9](../design/appendix-h-v2-api-decomposition.md#h9-cross-namespace-proxy-sharing), shipped in Q166): consent on the provider's side, the GMC writing NetworkPolicy on both sides, and an object in each granted namespace carrying the server's URL whose presence is the grant.
3. If upstream declines, run one stock server per granted tenant instead of forking.

Shared modes stay off for untrusted-PR tenants, whose isolation is the reason Q215 exists.
