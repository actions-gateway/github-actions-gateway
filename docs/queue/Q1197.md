# Recovery claims give up after five write conflicts with another replica

`claimDisruptionRecovery` (`recovery_claims.go`) retries a conflicting write `recoveryClaimConflictRetries = 5` times, sized as "the replica count with headroom", but each conflict is one write by another replica, and `claimMu` serialises a replica's own claims into a back-to-back burst, so one writer can lose more than five rounds while the other drains a node's worth of claims.
A claim that gives up leaves the disruption unrecovered, counted as `eviction_recovery_evidence_lost_total`, and the run needs a manual re-run.
The same bound in the failure ledger's `updateRerunLedger`, which Q1182 copied from it, lost a reservation in 10 of 200 runs of a test with two replicas writing 16 reservations concurrently against the fake client (measured 2026-10-23, `TestScaleSetBudget_ConcurrentDisruptionsOfOneAttemptMerge`), and 0 of 200 once the loop was bounded by its context instead of a count.
The claim path is unmeasured: it has the same shape, and two AGC replicas run only during a rolling update, so the exposure is a drain that coincides with a rollout.
The fix is the ledger's: retry a conflict until the caller's context ends, since every conflict is another writer's progress, with a two-replica concurrency test that goes red under the fixed bound.
