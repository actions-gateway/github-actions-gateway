# Pre-warm the Dragonfly leg's e2e node once the pool is emptied

**The gate's Dragonfly leg empties the `e2e` pool so its worker lands on a node that has not cached the runner image, then pays the whole cold start after dispatch, 5m16s from dispatch to runner on `v2.0.1-rc.1`.** The Kata leg no longer does: `prewarm_e2e_node` raises its node while `start.sh` and `e2e-start.sh` run.

Raising one node right after `empty_node_pool` succeeds would overlap the node's boot and the Kata installer's image pull with the leg's own `e2e-start.sh`.
That pull took 24–84s on the 11 cold nodes read for Q1367, and it is most of the window in which a cold Kata worker's sandbox fails.
The node still has no worker image, so `node-p2p` keeps its meaning.
It would also let `apply_dragonfly_nodes`' rollout wait cover the node client on that node, which today races the first job's pulls.
**Saving:** at most that leg's `e2e-start.sh` time after the pool is emptied, which was not measured.
**Cost:** one e2e node starts earlier by the same span.
**Risk:** GKE advises against combining `resize` with autoscaling, and the autoscaler may remove the idle node before dispatch; the leg's `e2e-pool-nodes:` line shows it.
The CPU reservation is already held by then.

`prewarm_e2e_node` returns early unless the `kata` leg is selected, so a `--legs dragonfly` run needs its own condition.

**Done when** the Dragonfly leg raises one e2e node after emptying the pool and before `e2e-start.sh`, a refused resize is a warning, and the gate's tests assert that order.
