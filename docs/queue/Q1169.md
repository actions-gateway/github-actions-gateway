# Abandoned scale-set worker force-cancels the run it was created for

When a scale-set worker is removed before its container ever ran — the reaper's `pendingPodDeadline` delete, or an external delete of a `Pending` worker — abandoned-run recovery (Q766, `cmd/agc/internal/provisioner/abandoned_scaleset.go`) force-cancels the run named by the pod's `actions-gateway.com/run-id` and `actions-gateway.com/repository`.
A worker that never ran has no `JobStarted`, so those are the identity of the job the pod was created for.
GitHub gives a scale-set job to whichever of the set's runners asks first, so that job can be running on another worker when this one is abandoned.
Recovery then force-cancels a run with a live job, and the job that actually lost a runner, if any, is a different one that nothing names.

This is the same keying Q1152 corrected for eviction and orphan recovery, on the one recovery path whose pod has no started job to read instead.
Found from source while working Q1152; not observed on a cluster, and the rate is unmeasured.
It needs a worker stuck `Pending` past its deadline while another runner of the same set took that worker's job, so it shows on a set whose workers schedule unevenly (a node pool scaling up while others are warm).

**A likely fix**: before force-cancelling, look for a live worker whose `actions-gateway.com/started-job-id` is the abandoned pod's job (the pod name is `scaleSetPodName(set, jobID)`, so the job ID needs recording on the pod or matching by name).
Where one exists the job is running and nothing is cancelled.
Which job, if any, is stranded instead is the open part: it is one assigned job that never sees a `JobStarted`, and the listener's in-flight set is the only record that could name it.

**Reach.** Any scale-set tenant whose worker is abandoned while its job runs elsewhere: a live run is cancelled and re-run, costing the run's progress and one slot of its retry budget.
