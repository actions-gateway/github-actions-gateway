## Highlights

**[`v2` is GA, and it is the only API.](https://actions-gateway.com/2.0.0/operations/upgrade/#action-required-at-v200-remove-the-crds-conversion-webhook-before-applying-them)** Every `actions-gateway.com` kind serves `v2` alone with no conversion webhook, and the `actions-gateway.github.com` group is gone.
Every `RunnerSet` acquires jobs through a scale set, so a set that asked for `Classic` moves to that protocol.
**Removals** lists what went, and **Upgrading** is the order to take it in.

**[Every `RunnerSet` refuses fork pull request jobs unless it accepts them.](https://actions-gateway.com/2.0.0/operations/upgrade/#action-required-if-a-runnerset-runs-fork-pull-request-jobs-they-are-now-refused)** A fork can edit `runs-on` to name any set, and nothing at GitHub refuses a job for coming from a fork.
A refused job gets no runner and its run is force-cancelled; `spec.forkPullRequests: Accept` restores fork CI on a set built for untrusted code.
This breaks fork CI on every set that does not set it.

**[A tenant can keep its `actions/cache` entries on a cache server in its own namespace.](https://actions-gateway.com/2.0.0/operations/in-cluster-cache/)** This matters most for a tenant that runs untrusted fork pull requests, where a cache shared between jobs is a way to plant content a trusted job later restores.
The server is [falcondev-oss/github-actions-cache-server](https://github.com/falcondev-oss/github-actions-cache-server) 10.0.0, deployed per tenant from `deploy/gha-cache/`.
It takes each job's scope from the runtime token GitHub signs for that job, so a fork pull request writes only to its own `refs/pull/<n>/merge` scope.
Jobs reach it on the new `cache-runner` worker image, the seventh first-party image, which is `build-runner` with the runner's overwrite of `ACTIONS_RESULTS_URL` disabled.
It is opt-in: a worker on any other image keeps using GitHub's cache.
Save, restore, the sibling-branch boundary and the fork pull request scope were each measured on a kind cluster, and save, restore and the sibling-branch boundary once more under Kata Containers on GKE.
BuildKit's `type=gha` cache rides the same URL and is read from source, not measured, and the release gate does not assert any of it.

**[A job killed for memory under right-sizing is re-run with a higher limit.](https://actions-gateway.com/2.0.0/operations/worker-rightsizing/#when-a-job-runs-out-of-memory)** Under the `Binpack` and `Throughput` profiles the Actions Gateway Controller (AGC) chose the limit, so on a scale-set `RunnerSet` it now re-runs an `OOMKilled` job with the killed limit times the profile's headroom, capped at `maxRequests.memory`, or at twice the killed limit where you set none.
The re-run spends the ordinary `maxEvictionRetries` budget, waits for GitHub to conclude the run (up to 24 hours, surviving an AGC restart), and emits a `MemoryLimitRaisedForRetry` Event naming both limits.
A second kill of the same job is not re-run, and more than 10 such re-runs on one set within 10 minutes pause the class for 30, reported by the `actions_gateway_auto_retry_paused` gauge and an `AutoRetryPaused` Event.

**[Scale-set re-runs that GitHub would refuse are withheld before a budget slot is spent.](https://actions-gateway.com/2.0.0/operations/observability-metrics/)** A run past GitHub's 50 re-runs, one created more than 30 days ago, and a `push` or `pull_request` run superseded by a newer commit on the same branch are no longer re-run, and count under `actions_gateway_eviction_rerun_withheld_total` as `attempt_limit`, `run_too_old` and `superseded`.
A run someone has already cancelled is withheld on every disruption cause, while GAG's own force-cancel of an abandoned run is still re-run.

**[Flaky scale-set jobs are detected, and each failed job records its platform context.](https://actions-gateway.com/2.0.0/operations/troubleshooting/#flaky-jobs-and-platform-faults-on-failed-jobs)** A failed job that later succeeds with no disruption behind its failure emits a `FlakyJobDetected` Event and counts in `actions_gateway_scaleset_flaky_jobs_total`.
A failed job whose worker snapshot shows a platform fault, colocated egress proxy readiness included, emits `PlatformFaultOnFailedJob`.
`actions_gateway_scaleset_job_reruns_total{trigger="other"}` over completed jobs is the manual re-run rate, and the new `ActionsGatewayRetryCauseMisclassified` alert fires when more than half of one cause's automatic re-runs fail again over 7 days, with at least 5 re-runs.

**[GitHub egress survives a Gateway Manager Controller (GMC) restart, and a missing allowlist pages.](https://actions-gateway.com/2.0.0/operations/upgrade/#non-breaking-the-gmc-keeps-github-egress-across-a-restart)** A restarted GMC used to give `CIDR`-mode proxy pools no GitHub egress until its first `api.github.com/meta` fetch, which a rate limit could hold off for up to an hour.
It now seeds itself from a copy of the last fetch in the `actions-gateway-gmc-ip-ranges` ConfigMap, and waits for GitHub's rate-limit reset rather than retrying into it.
While it holds no ranges at all, `EgressRulesStale` now reads `True` with the new reason `RefreshNeverSucceeded`, and a direct-egress v2 gateway, with no `defaultProxyRef`, carries the condition too, paged on by the new `ActionsGatewayDirectEgressRulesStale` alert.

**[The egress proxy counts every CONNECT by the allowlist entry that admitted it.](https://actions-gateway.com/2.0.0/operations/observability-metrics/)** `actions_gateway_proxy_connects_total{destination,outcome}` tells a failing destination from a failing proxy, and the tenant dashboard plots it.
`destination` is the configured entry, `unlisted` or `any`, never the requested host, so its values are bounded by the allowlist.

## Upgrading

**First, upgrade the cluster to Kubernetes 1.35 or later** ([why, and what happens below it](https://actions-gateway.com/2.0.0/operations/upgrade/#before-upgrading-to-v200-the-cluster-runs-kubernetes-135-or-later)).
`v2.0.0` raises both charts' floor from 1.30 to 1.35, the version CI tests, and the `v1.10.0` chart accepts 1.35 while the cluster moves.
Below the floor `helm upgrade` refuses and leaves the release where it is, but `helm template` of the CRD chart applied with `kubectl` succeeds, which leaves a `v1.10.0` control plane on `v2.0.0` CRDs for as long as the cluster upgrade takes.
So upgrade the cluster before any step below.

**If the cluster will pass through 1.33 or 1.34, or is on one now, set this first, or `v1.10.0` workers fail to start:**

```sh
kubectl -n gmc-system set env deployment/gmc-controller-manager WRAPPER_DELIVERY=init
```

A `v1.10.0` AGC delivers the worker wrapper through an image volume on any server from 1.33, and with the `ImageVolume` feature gate off, the apiserver drops the volume with no error.
The variable has the GMC tell each AGC to use an initContainer instead, and the AGCs restart to pick it up, again when you remove it.
`helm upgrade` leaves it set, so remove it once the cluster is at 1.35 or later:

```sh
kubectl -n gmc-system set env deployment/gmc-controller-manager WRAPPER_DELIVERY-
```

The failure was measured on kind with Kubernetes 1.34.11, using a hand-written Pod with the worker's volume, mount and command.
An initContainer form of that Pod reached the wrapper, and the variable reached the AGC Deployment and rolled it.
That the AGC then builds the initContainer is read from the code.
No job ran through a worker the AGC created, and neither 1.33 nor a managed provider's gate setting was measured.

**Rendering a chart with `helm template` needs Helm 3.20 or later on 3.x, or 4.1 or later on 4.x.** With no cluster to ask, Helm checks the floor against the version it was built for, so an older one refuses on any cluster; pass `--kube-version <your cluster's version>` to keep it ([install prerequisites](https://actions-gateway.com/2.0.0/operations/install/)).
The minimum is read from each release's `k8s.io/client-go` pin, and 3.20 and 4.1 themselves were not run.

**Take the newest 1.10 patch before upgrading, so the release you can roll back to still receives jobs.** `v1.10.0`'s default worker runs `actions/runner` 2.338.1, which falls outside GitHub's 30-day update window about 2026-11-25, and GitHub then stops queueing jobs to those runners with no error.

**Before upgrading, on 1.10:**

1. Migrate any `EgressProxy` still on `CiliumFQDN` or `CalicoFQDN` ([the check](https://actions-gateway.com/2.0.0/operations/upgrade/#before-upgrading-to-v200-no-egressproxy-still-names-a-deprecated-fqdn-alias)).
2. Run `gag-migrate storage-version --apply` and confirm every `actions-gateway.com` CRD reads `storedVersions: ["v2"]` ([the check](https://actions-gateway.com/2.0.0/operations/upgrade/#before-upgrading-to-v200-every-actions-gatewaycom-crd-stores-only-v2)).
   The apiserver refuses to drop a version a CRD still lists there, so `v2.0.0`'s CRD apply fails without it.
3. Migrate any tenant still on `v1alpha1` with a 1.x `gag-migrate`, and confirm no `v1alpha1` object is left ([the check](https://actions-gateway.com/2.0.0/operations/upgrade/#before-upgrading-to-v200-no-v1alpha1-object-is-left)).
   `v2.0.0`'s `gag-migrate` no longer carries that migration.
4. Replace any `RunnerSet` that still asks for `Classic`, because on 1.10 deleting it deregisters its agents and from `v2.0.0` nothing does ([the command that lists them](https://actions-gateway.com/2.0.0/operations/upgrade/#action-required-before-v200-a-classic-runnerset-now-runs-on-the-scale-set-protocol)).
5. Relabel every tenant namespace that carries only the `actions-gateway.github.com` labels, which `v2.0.0` no longer honours ([the check](https://actions-gateway.com/2.0.0/operations/upgrade/#before-upgrading-to-v200-every-tenant-namespace-carries-the-actions-gatewaycom-labels)).
6. Search your own alerts and dashboards for the [13 removed classic series](https://actions-gateway.com/2.0.0/operations/upgrade/#action-required-if-you-alert-on-or-chart-the-classic-acquisition-series-they-are-no-longer-exported) and for [`tier` on a disruption series](https://actions-gateway.com/2.0.0/operations/upgrade/#action-required-if-a-query-reads-tier-on-a-disruption-series-the-label-is-gone).
   Neither raises an error: `{tier="scaleset"}` returns nothing, so a rule reading it never fires again.

**The upgrade is one sitting, in this order:** [remove the CRDs' conversion webhook](https://actions-gateway.com/2.0.0/operations/upgrade/#action-required-at-v200-remove-the-crds-conversion-webhook-before-applying-them), apply the five CRDs in `actions-gateway-crds-v2.yaml`, `helm upgrade` with all four image digests, then apply the chart-root CRD ([the commands](https://actions-gateway.com/2.0.0/operations/upgrade/#action-required-at-v200-apply-the-crds-with-the-upgrade-because-the-agcs-watch-depends-on-them)).
Without the webhook removal, `kubectl apply --server-side` refuses all five CRDs on a default install.
Neither AGC can list its `RunnerSet`s against the other release's CRDs, so keep the gap short and restart no AGC or GMC pod inside it.
A `v2.0.0` AGC on the old CRDs reads `Ready` while it holds no session, so watch `actions_gateway_scaleset_session_open`, and treat no series the same as `0`.

**After the upgrade,** delete the two `actions-gateway.github.com` CRDs the chart left behind, and [list what still names `v2alpha1` as its owner](https://actions-gateway.com/2.0.0/operations/upgrade/#action-required-after-v200-delete-what-an-owner-deleted-during-the-upgrade-left-behind): the garbage collector cannot collect those objects once their owner goes.

**To roll back to your 1.10 release, put both sets of CRDs back before the chart, and name the Helm revision** ([the commands](https://actions-gateway.com/2.0.0/operations/upgrade/#gmc-rollback)).
The `tier` label returns on the six series, and `actions_gateway_eviction_rerun_outcomes_total` stops.
A `v1.10.0` AGC keeps the failed-job records this release writes into each scale-set `scaleset-failures-<set>` ConfigMap but cannot evict them, so they can hold up to half of its size cap, leaving the other half for re-run budgets.

**Also in this upgrade, from the work since `v1.10.0`:**

**A GMC deployed from your own manifests should set `DEPLOYMENT_NAME`** to its Deployment's name, as the chart now does.
Without it the GMC still persists GitHub's IP ranges, but writes the `actions-gateway-gmc-ip-ranges` ConfigMap with no owner, so it is left behind on uninstall.

**Anything that recreates the GMC Deployment deletes that ConfigMap with it**, including `helm upgrade --force-replace`, renaming the release, and `kubectl delete deployment`, so the next GMC start waits for its first fetch as before.

**If you alert on `EgressRulesStale` reason `RefreshPending`, match `RefreshNeverSucceeded` as well.** The no-ranges state moved from `False` / `RefreshPending` to `True` / `RefreshNeverSucceeded` ([what changed](https://actions-gateway.com/2.0.0/operations/upgrade/#non-breaking-egressrulesstale-now-fires-when-no-github-ranges-have-loaded)).

**Apply `deploy/monitoring/prometheusrule.yaml` again and re-import the dashboards.** The rules gain `ActionsGatewayScaleSetNoSession`, `ActionsGatewayMessagePollFailing`, `ActionsGatewayDirectEgressRulesStale` and `ActionsGatewayRetryCauseMisclassified`, and lose six alerts and a recording rule that read classic series.
Two proxy panels that read nothing on a v2 pool now do (#2267).
A copy of the webhook-rejection alert or the security dashboard from 1.8 or later [needs the `-v2` webhook names](https://actions-gateway.com/2.0.0/operations/upgrade/#action-required-if-you-copied-the-webhook-rejection-alert-or-imported-the-security-dashboard-both-now-see-the--v2-webhooks).

**`EgressProxy.spec.noProxyCIDRs` now rejects more ways of exempting GitHub from the proxy.** An entry that covers a GitHub host through a comma, a space, a wildcard, a port, a trailing dot or an address is refused, and a shared proxy is now compared with the gateways in the namespaces it grants.
A proxy already stored with such an entry keeps running, but a delete and re-create is rejected, which includes a restore from backup, so find [the entries](https://actions-gateway.com/2.0.0/operations/upgrade/#action-required-if-a-noproxycidrs-entry-exempts-github-through-a-comma-wildcard-port-or-address-the-entry-is-now-rejected) and [the shared-proxy pairs](https://actions-gateway.com/2.0.0/operations/upgrade/#action-required-if-a-shared-egressproxy-exempts-a-consumers-github-host-the-pair-is-now-rejected) first.

**`spec.tracing` now rejects `insecure: true` with an `https://` endpoint.** The pair exported in plaintext, and a gateway already stored with it keeps running, but a delete and re-create is rejected, which includes a restore from backup, so [find and fix them first](https://actions-gateway.com/2.0.0/operations/upgrade/#action-required-if-spectracing-sets-insecure-true-with-an-https-endpoint-the-pair-is-now-rejected).

**A `networkPolicy` peer now rejects a `cidr` that is broad, link-local or over a metadata server.** On `spec.tracing.networkPolicy` and the Vault signer's `networkPolicy`, the `cidr` can be no broader than `/16` for IPv4 or `/48` for IPv6, and cannot be link-local or cover one of four cloud metadata addresses that are not link-local.
`0.0.0.0/0` opened the peer's port from the AGC to every address, and a gateway already stored with such a value keeps running with that rule in place, but a delete and re-create is rejected, which includes a restore from backup, so [find and narrow them first](https://actions-gateway.com/2.0.0/operations/upgrade/#action-required-if-a-networkpolicy-peer-names-a-broad-or-link-local-cidr-the-value-is-now-rejected).

**`spec.tracing.endpoint` now rejects a value that does not parse as a URL.** A gateway already stored with one keeps running, but a delete and re-create is rejected, which includes a restore from backup, so [correct it first](https://actions-gateway.com/2.0.0/operations/upgrade/#action-required-if-spectracingendpoint-does-not-parse-as-a-url-the-value-is-now-rejected).

**`RunnerSet.spec.priorityTiers` now rejects thresholds that do not strictly ascend.** A tier at or below an earlier one never received a pod, and a set already stored with one keeps running, but a delete and re-create is rejected, which includes a restore from backup, so [find and fix them first](https://actions-gateway.com/2.0.0/operations/upgrade/#action-required-if-a-runnersets-prioritytiers-do-not-ascend-the-list-is-now-rejected).

**An FQDN-mode `EgressProxy` now reaches a GitHub Enterprise Server host only when the platform egress allowlist covers it.** The host came from the tenant's `githubURL` unchecked, and the upgrade takes an unlisted one out of the pool's policy with no object edited, so [add your appliance hosts to `allowedEgressFQDNs` in the same upgrade](https://actions-gateway.com/2.0.0/operations/upgrade/#action-required-if-a-gateway-names-a-github-enterprise-server-host-an-fqdn-mode-pool-reaches-it-only-when-the-platform-allowlists-it).

**A new `ActionsGateway` may not spell public GitHub `www.github.com` or `api.github.com`, and a stored one now shares scale-set names with `github.com`.** The AGC addresses all three as public GitHub.
A gateway already stored under either alias keeps running and stays editable, but a delete and re-create is rejected, which includes a restore from backup, and so is a new claim on a scale-set name held under another of the three hosts, so [find them first](https://actions-gateway.com/2.0.0/operations/upgrade/#action-required-if-a-githuburl-spells-public-github-wwwgithubcom-or-apigithubcom-a-new-gateway-is-rejected-and-a-stored-one-shares-scale-set-names-with-githubcom).

**A namespaced `RunnerTemplate` must now meet Pod Security `baseline`, on every security profile.** The webhook refused only `privileged: true`, so in a `privileged`-profile namespace a tenant could author a host-reaching worker, and a shape past `baseline` now has to be a `ClusterRunnerTemplate`.
The level is evaluated as Kubernetes 1.37 defines it, and a dependency update does not move it.
A platform whose own admission policy decides tenant pod shape can turn this rule and the next one off with the chart value `allowUncheckedRunnerTemplatePodShape`.
A template already stored keeps building workers until its `podTemplate` changes, but a delete and re-create is rejected, which includes a restore from backup, so [find them first](https://actions-gateway.com/2.0.0/operations/upgrade/#action-required-if-a-namespaced-runnertemplate-goes-past-pod-security-baseline-the-shape-is-now-rejected).

**A namespaced `RunnerTemplate` now rejects `nfs`, `iscsi` and every other volume type Pod Security `restricted` forbids.** The node mounts those, so their traffic passed neither the worker `NetworkPolicy` nor the egress proxy.
The same stored-template terms apply, and a `persistentVolumeClaim` is [the replacement](https://actions-gateway.com/2.0.0/operations/upgrade/#action-required-if-a-namespaced-runnertemplate-declares-an-nfs-iscsi-or-similar-volume-the-type-is-now-rejected).

**No template may project a ServiceAccount token, and the AGC now removes one from every worker pod.** `automountServiceAccountToken: false` never covered a `projected` volume's `serviceAccountToken` source.
The same goes for a `podCertificate` source addressed to a signer under `kubernetes.io`, a prefix Kubernetes reserves and under which it documents one signer as issuing apiserver client certificates.
Unlike the two rules above this one reaches stored templates at the upgrade: their workers stop getting the token, so [find the jobs that read it first](https://actions-gateway.com/2.0.0/operations/upgrade/#action-required-if-a-template-projects-a-serviceaccount-token-the-source-is-now-rejected-and-removed-from-worker-pods).

**A namespaced `RunnerTemplate` may no longer set `nodeName`, or a `schedulerName` other than `default-scheduler`.** Either placed the worker past the default scheduler, and with it past the rule keeping workers off the controllers' nodes, so a tenant could put a worker beside its AGC.
Like the token rule this reaches stored templates at the upgrade, since the AGC clears both, so [find them first](https://actions-gateway.com/2.0.0/operations/upgrade/#action-required-if-a-namespaced-runnertemplate-sets-nodename-or-schedulername-both-are-now-rejected-and-cleared-from-worker-pods).

**A kustomize patch on a library template has to target `version: v2`.** One still naming `v2beta1` matches nothing and [kustomize skips it without an error](https://actions-gateway.com/2.0.0/operations/upgrade/#action-required-if-you-overlay-a-library-template-deploytemplates-is-written-at-v2).

**Two `RunnerSet`s may now share a name across namespaces.** A set's [first `runnerLabel` still has to be unique](https://actions-gateway.com/2.0.0/operations/upgrade/#non-breaking-two-runnersets-may-share-a-name-across-namespaces) across its GitHub scope.

**A worker that never started is now force-cancelled and re-run.** That covers a worker deleted while still pulling its image, which was reported failed or not recovered at all, one whose node shut down before it started, and a job left without a runner when a scale-set worker is reaped after another runner took its job ([the three sections](https://actions-gateway.com/2.0.0/operations/upgrade/)).
The node-shutdown shape counts under `abandoned_run_force_cancels_total` instead of `eviction_retries_total{cause="node_shutdown"}`.
A worker deleted while pulling stops adding samples to `actions_gateway_job_duration_seconds`, so where image pulls are slow or broken that histogram's count drops and its percentiles shift.

**Check a custom `workerImage`'s runner version.** The default moves to `actions/runner` 2.338.2, and a `RunnerTemplate` pinned to its own image keeps the runner it was built on ([what to compare](https://actions-gateway.com/2.0.0/operations/troubleshooting/#worker-image-runner-version)).

## Removals

**Breaking: Kubernetes below 1.35.** Both charts' floor moves from 1.30 to 1.35 (#2268).

**Breaking: three API versions and the conversion webhook.** The chart no longer ships the `v1alpha1` CRDs (`ActionsGateway`, `RunnerGroup`), and no controller reconciles them; Helm keeps the two CRDs on the cluster until you delete them.
The `actions-gateway.com` CRDs no longer serve `v2alpha1` or `v2beta1`, and with them go the `CiliumFQDN` and `CalicoFQDN` `egressPolicyMode` values (#2241, #2243, #2261).
Four gauges left with `RunnerGroup`: `actions_gateway_worker_quota_exceeded`, `actions_gateway_worker_quota_pressure`, `actions_gateway_workers_unschedulable` and `actions_gateway_runnergroups_degraded`.
A rule of your own on one goes silent with no error, so read its twin: `actions_gateway_runnerset_worker_quota_exceeded`, `actions_gateway_runnerset_worker_quota_pressure`, `actions_gateway_runnerset_workers_unschedulable` or `actions_gateway_runnersets_degraded`.

**Breaking: Classic acquisition.** `acquisitionProtocol` and `maxListeners` went with `v2alpha1`, and the AGC has one acquisition path (#2257).
The 13 metrics only Classic wrote are no longer exported, the `AgentDeregistrationFailed`, `AgentPoolError` and `JobAcquisitionFailed` Events are no longer emitted, and a set kept through the upgrade leaves its `agentpool-rs-<set>-<n>` Secrets and offline `rs-<set>-<n>` runners [for you to remove](https://actions-gateway.com/2.0.0/operations/upgrade/#action-required-before-v200-a-classic-runnerset-now-runs-on-the-scale-set-protocol).

**Breaking: the `tier` label on six disruption series** (#2264): `eviction_retries_total`, `eviction_retries_exhausted_total`, `eviction_rerun_failures_total`, `eviction_rerun_withheld_total`, `abandoned_run_force_cancels_total` and `abandoned_run_rerun_waits_total`, whose values were `classic` and `scaleset`.
`by (tier)` keeps working with one empty group, and a filter on either value returns nothing.

**Breaking: the `actions-gateway.github.com` namespace labels no longer count.** The admission policies and the GMC honour only `actions-gateway.com/tenant=managed`, `actions-gateway.com/privileged-profile=allowed` and the `actions-gateway.com/allow-profile-downgrade=allowed` annotation (#2245).
A namespace carrying only `actions-gateway.github.com/tenant=true` stops being a tenant on upgrade: the GMC stops watching its Secrets, so its gateways lose their credentials, and `gmc-tenant-resource-guard` denies the GMC's writes there, so teardown cannot finish either.
The GMC's Secret access there ends with it, because the GMC deletes the 1.x `gmc-tenant-secret-reader` RoleBinding itself, a write the guard admits outside a tenant namespace (#2250).
A privileged grant on the old key is lost.
Tenants migrated with `gag-migrate` already carry both spellings.
Run the [pre-upgrade check](https://actions-gateway.com/2.0.0/operations/upgrade/#before-upgrading-to-v200-every-tenant-namespace-carries-the-actions-gatewaycom-labels) and relabel what it lists before upgrading.

**Also gone:** `gag-migrate`'s `v1alpha1` fan-out, leaving only `storage-version`, and the chart's `sampleGateway` value (#2241); the AGC's `--agent-key-type` flag (#2257); the `GITHUB_ORG_URL` and `GITHUB_RUNNER_VERSION` variables the GMC set on the AGC, which nothing reads once Classic is gone (#2263); and the CRD chart's `conversion.*` values, which nothing rejects if you still set them (#2261).

## API and metric surface

**Added to the API:** `spec.forkPullRequests` on `RunnerSet` (`Refuse`, the default, or `Accept`), `spec.tracing.networkPolicy` and `spec.tracing.caBundleRef` on `ActionsGateway`, and a rejection of a `spec.tracing.endpoint` that does not parse as a URL.
**Tightened in the API:** `RunnerSet.spec.priorityTiers` rejects a list whose thresholds do not strictly ascend, `spec.tracing` rejects `insecure: true` with an `https://` endpoint, `EgressProxy.spec.noProxyCIDRs` rejects a GitHub exemption written with a comma, a space, a wildcard, a port, a trailing dot or an address, in a shared proxy's granted namespaces as well as its own, and a `networkPolicy` peer rejects a `cidr` broader than `/16` (IPv4) or `/48` (IPv6), a link-local one, and one covering a listed cloud metadata address.
A new `ActionsGateway` is rejected when its `githubURL` host is `www.github.com` or `api.github.com`.
The scale-set name guard reads those two hosts as `github.com`, and `EgressProxy`'s `GitHubEgressIncomplete` condition gains the reason `GitHubHostNotAllowlisted`.
A namespaced `RunnerTemplate` rejects a `podTemplate` past Pod Security `baseline` or with a volume type `restricted` forbids, rejects `podTemplate.spec.nodeName` and a `schedulerName` other than `default-scheduler`, and both template kinds reject a projected `serviceAccountToken` source and a `podCertificate` source addressed to a signer under `kubernetes.io`.
As of 2026-11-06, no enum value or default was added or changed since `v1.10.0`, and no CLI flag or chart values key was added; since then `spec.forkPullRequests` added an enum, and one flag and one values key were added, the GMC flag `--allow-unchecked-runner-template-pod-shape` and its chart value `allowUncheckedRunnerTemplatePodShape`.
**Removals** above lists what left.

## Project and tooling

## Security

**No security advisory accompanies this release**, and no reported vulnerability in this project's own code is patched.
No Go module dependency version or toolchain changed since `v1.10.0`.

**Four changes narrow exposure.** The GMC honours only the `actions-gateway.com` namespace labels (#2245), deletes its Secret-reader binding from a namespace that stops being a tenant (#2250), and applies a proxy's NetworkPolicy before its Deployment (#2238).
The `gmc-tenant-resource-guard` policy now also confines the GMC's ConfigMap, CNI-native policy and ServiceMonitor writes to tenant namespaces, which its ClusterRole had let it make anywhere ([what changed](https://actions-gateway.com/2.0.0/operations/upgrade/#non-breaking-the-gmcs-configmap-cni-policy-and-servicemonitor-writes-are-confined-to-tenant-namespaces)).

**Fork pull request jobs are refused by default** on every `RunnerSet`, closing the path by which a fork names a trusted set's label in its edited workflow and runs on it.
A set built for untrusted code accepts them with `spec.forkPullRequests: Accept`.

**The in-cluster cache server applies GitHub's own cache-scope rule**, so a tenant that turns it on keeps a fork pull request from writing to any scope the base branch restores from.
It is opt-in and changes nothing for a tenant that does not deploy it.

A pull request that changes code runs `govulncheck` and a Trivy image scan of every built image.
The `worker`, `build-runner` and `cache-runner` scans are report-only, so a finding in one of those does not fail the pull request.
One that changes the chart runs a Polaris posture check of it.
