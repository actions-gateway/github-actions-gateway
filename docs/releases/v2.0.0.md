## Highlights

**Pending: `v2` GA and the four removals lead this section once they land.**

**[A tenant can keep its `actions/cache` entries on a cache server in its own namespace.](https://actions-gateway.com/2.0.0/operations/in-cluster-cache/)** This matters most for a tenant that runs untrusted fork pull requests, where a cache shared between jobs is a way to plant content a trusted job later restores.
The server is [falcondev-oss/github-actions-cache-server](https://github.com/falcondev-oss/github-actions-cache-server) 10.0.0, deployed per tenant from `deploy/gha-cache/`.
It takes each job's scope from the runtime token GitHub signs for that job, so a fork pull request writes only to its own `refs/pull/<n>/merge` scope.
Jobs reach it on the new `cache-runner` worker image, the seventh first-party image, which is `build-runner` with the runner's overwrite of `ACTIONS_RESULTS_URL` disabled.
It is opt-in: a worker on any other image keeps using GitHub's cache.
Save, restore, the sibling-branch boundary and the fork pull request scope were each measured on a kind cluster, and save, restore and the sibling-branch boundary once more under Kata Containers on GKE.
BuildKit's `type=gha` cache rides the same URL and is read from source, not measured, and the release gate does not assert any of it.

**[A job killed for memory under right-sizing is re-run with a higher limit.](https://actions-gateway.com/2.0.0/operations/worker-rightsizing/#when-a-job-runs-out-of-memory)** Under the `Binpack` and `Throughput` profiles the Actions Gateway Controller (AGC) chose the limit, so on a scale-set `RunnerSet` it now re-runs an `OOMKilled` job with the killed limit times the profile's headroom, capped at `maxRequests.memory`.
The re-run spends the ordinary `maxEvictionRetries` budget, waits for GitHub to conclude the run (up to 24 hours, surviving an AGC restart), and emits a `MemoryLimitRaisedForRetry` Event naming both limits.
A second kill of the same job is not re-run, and more than 10 such re-runs on one set within 10 minutes pause the class for 30, reported by the `actions_gateway_auto_retry_paused` gauge and an `AutoRetryPaused` Event.

**[Scale-set re-runs that GitHub would refuse are withheld before a budget slot is spent.](https://actions-gateway.com/2.0.0/operations/observability-metrics/)** A run past GitHub's 50 re-runs, one created more than 30 days ago, and a `push` or `pull_request` run superseded by a newer commit on the same branch are no longer re-run, and count under `actions_gateway_eviction_rerun_withheld_total` as `attempt_limit`, `run_too_old` and `superseded`.
A run someone has already cancelled is withheld on every disruption cause, while GAG's own force-cancel of an abandoned run is still re-run.

**[Flaky scale-set jobs are detected, and each failed job records its platform context.](https://actions-gateway.com/2.0.0/operations/troubleshooting/#flaky-jobs-and-platform-faults-on-failed-jobs)** A failed job that later succeeds with no disruption behind its failure emits a `FlakyJobDetected` Event and counts in `actions_gateway_scaleset_flaky_jobs_total`.
A failed job whose worker snapshot shows a platform fault, colocated egress proxy readiness included, emits `PlatformFaultOnFailedJob`.
`actions_gateway_scaleset_job_reruns_total{trigger="other"}` over completed jobs is the manual re-run rate, and the new `ActionsGatewayRetryCauseMisclassified` alert fires when more than half of one cause's automatic re-runs fail again over 7 days, with at least 5 re-runs.

**[GitHub egress survives a Gateway Manager Controller (GMC) restart, and a missing allowlist pages.](https://actions-gateway.com/2.0.0/operations/upgrade/#non-breaking-the-gmc-keeps-github-egress-across-a-restart)** A restarted GMC used to give `CIDR`-mode proxy pools no GitHub egress until its first `api.github.com/meta` fetch, which a rate limit could hold off for up to an hour.
It now seeds itself from a copy of the last fetch in the `actions-gateway-gmc-ip-ranges` ConfigMap, and waits for GitHub's rate-limit reset rather than retrying into it.
While it holds no ranges at all, `EgressRulesStale` now reads `True` with the new reason `RefreshNeverSucceeded`, and a direct-egress v2 gateway, with no `defaultProxyRef`, carries the condition too, paged on by the new `ActionsGatewayDirectEgressRulesStale` alert.

**[The egress proxy counts every CONNECT by the allowlist entry that admitted it.](https://actions-gateway.com/2.0.0/operations/observability-metrics/)** `actions_gateway_proxy_connects_total{destination,outcome}` tells a failing destination from a failing proxy, and the tenant dashboard plots it.
`destination` is the configured entry, `unlisted` or `any`, never the requested host, so its values are bounded by the allowlist.

## Upgrading

**Before upgrading, on `v1.10.0`, as `v1.10.0`'s notes required:**

1. Migrate any `EgressProxy` still on `CiliumFQDN` or `CalicoFQDN` ([the check](https://actions-gateway.com/2.0.0/operations/upgrade/#before-upgrading-to-v200-no-egressproxy-still-names-a-deprecated-fqdn-alias)).
2. Run `gag-migrate storage-version --apply` and confirm every `actions-gateway.com` CRD reads `storedVersions: ["v2"]` ([the check](https://actions-gateway.com/2.0.0/operations/upgrade/#before-upgrading-to-v200-every-actions-gatewaycom-crd-stores-only-v2)).
   The apiserver refuses to drop a version a CRD still lists there, so `v2.0.0`'s CRD apply fails without it.
3. Migrate any tenant still on `v1alpha1` with `gag-migrate` ([Migrating a tenant to v2](https://actions-gateway.com/2.0.0/operations/migration-v1-to-v2/)).

**Pending: the upgrade itself and rollback**, written once the removals land.
Whatever rollback target that leaves, an AGC from `v1.10.0` keeps the failed-job records this release writes into each scale-set `scaleset-failures-<set>` ConfigMap but cannot evict them, so they can hold up to half of its size cap, leaving the other half for re-run budgets.

**Also in this upgrade, from the work since `v1.10.0`:**

**A GMC deployed from your own manifests should set `DEPLOYMENT_NAME`** to its Deployment's name, as the chart now does.
Without it the GMC still persists GitHub's IP ranges, but writes the `actions-gateway-gmc-ip-ranges` ConfigMap with no owner, so it is left behind on uninstall.

**Anything that recreates the GMC Deployment deletes that ConfigMap with it**, including `helm upgrade --force-replace`, renaming the release, and `kubectl delete deployment`, so the next GMC start waits for its first fetch as before.

**If you alert on `EgressRulesStale` reason `RefreshPending`, match `RefreshNeverSucceeded` as well.** The no-ranges state moved from `False` / `RefreshPending` to `True` / `RefreshNeverSucceeded` ([what changed](https://actions-gateway.com/2.0.0/operations/upgrade/#non-breaking-egressrulesstale-now-fires-when-no-github-ranges-have-loaded)).

**Apply `deploy/monitoring/prometheusrule.yaml` again to get the two new alerts**, `ActionsGatewayDirectEgressRulesStale` and `ActionsGatewayRetryCauseMisclassified`.

**A worker that never started is now force-cancelled and re-run, not reported failed.** That covers a worker deleted while still pulling its image, one whose node shut down before it started, and a reaped scale-set worker whose job another runner took ([the three sections](https://actions-gateway.com/2.0.0/operations/upgrade/)).
They count under `abandoned_run_force_cancels_total` instead of `eviction_retries_total{cause="node_shutdown"}`, and stop adding samples to `actions_gateway_job_duration_seconds`, so where image pulls are slow or broken that histogram's count drops and its percentiles shift.

**Check a custom `workerImage`'s runner version.** The default moves to `actions/runner` 2.338.2, and a `RunnerTemplate` pinned to its own image keeps the runner it was built on ([what to compare](https://actions-gateway.com/2.0.0/operations/troubleshooting/#worker-image-runner-version)).

## API and metric surface

**Pending: the removed versions, fields and reasons.** As of 2026-11-01, no CRD field, enum value or default was added or changed since `v1.10.0`, and no CLI flag or chart values key was added.

<details>

## Project and tooling

**The release gate holds until a candidate's images are published** (#2217), and `make verify-release` now verifies SBOM attestations and the release's blob bundles (#2189).

**The dogfood AGC is scraped into Managed Prometheus** (#2180), and CI warns before the pinned runner ages out of GitHub's update window (#2213).

## Security

**No security advisory accompanies this release**, and no reported vulnerability in this project's own code is patched.
No Go module dependency or toolchain changed since `v1.10.0`.

**The in-cluster cache server applies GitHub's own cache-scope rule**, so a tenant that turns it on keeps a fork pull request from writing to any scope the base branch restores from.
It is opt-in and changes nothing for a tenant that does not deploy it.

A pull request that changes code runs `govulncheck` and a Trivy image scan of every built image, `cache-runner` included.
One that changes the chart runs a Polaris posture check of it.

## Verifying this release

We sign every image and both charts.

```bash
make verify-release VERSION=v2.0.0
```

The signed v2 CRD manifest and `SHA256SUMS` ship as release assets with detached cosign bundles, and the publish workflow attests build provenance.
