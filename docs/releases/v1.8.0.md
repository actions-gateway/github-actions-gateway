Zero-idle self-hosted GitHub Actions runners for multi-tenant Kubernetes.

> [!WARNING]
> **Two runner pools that derive the same agent identity are now rejected at admission.** Nothing is re-validated when you upgrade, so an existing colliding pair keeps running.
> The rejection lands whenever someone next re-applies either object, which may be weeks later and on a tenant who changed nothing.
> The most likely shape is two `RunnerSet`s of one name in different namespaces whose gateways point at the same GitHub org.
> Two `kubectl` commands find them before you upgrade: read **Upgrading** below.

> [!NOTE]
> **A worker image that reported an unknown runner version may now report a real one, and the real one can be too old.** The Actions Gateway Controller (AGC) reads the image out of its registry instead of judging it by the tag, so a digest-only or custom-tagged image that was previously unverifiable now gets a verdict.
> A pool that was always below GitHub's minimum and merely unreadable can start saying so, wherever the AGC can reach the registry.
> The AGC blocks nothing on it, but it rolls up into `RunnerGroupsDegraded`.

## Highlights

**[Two runner pools can no longer claim one GitHub runner identity.](https://actions-gateway.com/1.8.0/operations/upgrade/#agent-identity-collisions-are-now-rejected-at-admission-runnerset-name-and-derived-runnergroup-name)** The agent-identity stem is the string that both the `agentpool-<stem>-N` Secret and the GitHub runner name `<stem>-N` are built from, and two pools reaching the same stem both register `<stem>-N`.
`v1.7.0` stopped the destructive half of that, where the loser resolved each `409` by deregistering the incumbent's live record, so a pool that was serving jobs lost its registration to one that was not.
What `v1.7.0` did not do is stop the pair forming: the loser now reports `agent identity is owned by another pool` on every reconcile and never recovers, which is a blocked pool rather than a stolen one.
This release rejects the collision at admission, so the pair never forms.
Two shapes reach it: two `RunnerSet`s or two `RunnerGroup`s of one name in *different* namespaces whose gateways address the same GitHub scope, and a `RunnerGroup` named `rs-<x>` colliding with a `RunnerSet` named `<x>`.
A v1 `ActionsGateway` write is rejected on the same rule, which can block a rollback; **Upgrading** says what to do.

**[The AGC now reads a worker image's runner version out of the registry rather than trusting its tag.](https://actions-gateway.com/1.8.0/operations/troubleshooting/#worker-image-runner-version)** `RunnerVersionTooOld` judged the image by parsing a version out of its tag, so a digest-only or custom-tagged image reported `WorkerImageVersionUnknown` and stayed there.
The wrapper's own self-report could not settle it, because a tenant writes that.
The AGC now streams the image's layers topmost-first for the runner's `bin/Runner.Listener.deps.json`, honouring whiteouts and stopping at the first hit, before any pod runs it.
That reading is addressed by digest and out of reach of anything inside the container, so it is the verdict once it lands.
The tag verdict stands while the read is pending or has failed, with the state appended to the message, so an unreachable registry never costs you an answer you already had.
Measured against `ghcr.io/actions/actions-runner:2.335.1`: one inspection streams about 114 MB of a 544 MB image, once per digest per process.

**[A drained scale-set worker's run is now re-run, whether or not the gateway reaches its pod in time.](https://actions-gateway.com/1.8.0/operations/troubleshooting/#draining-a-worker-auto-re-runs-the-jobs-it-interrupts)** A drained worker is readable only in the seconds between the kubelet publishing its terminal phase and the object being removed, and two separate things used to depend on winning that window.
The recovery scan listed from the informer cache at the top of a `RunnerSet` reconcile, so it judged that worker only if a reconcile happened to begin inside the window.
A reconcile already in flight held the next one past it, since the queue runs one reconcile of a key at a time.
Measured on the sightings that filed the bug: an 8-second gap between reconcile completions swallowed a 3.4-second window, and the claim was never attempted.
The worker-pod watch now hands each disrupted scale-set worker to recovery as the event arrives, through the same judge and the same claim the scan uses, so a pod both paths see is recovered once, and the scan stays for what no event reaches.
That closes the class that was invisible, where a swallowed window left no claim, no metric, no Event and no log line naming the pod.
The other class was visible and equally unrecoverable: the pod also carried the at-most-once claim that stops one disruption spending two slots of a run's retry budget, so a claim landing after the kubelet removed the object was reported and abandoned.
The AGC now writes that claim to a per-`RunnerSet` ConfigMap before it calls GitHub, so it outlives the pod and the run is re-run normally.
The pod annotation stays as the marker you read; it is no longer the lock.

**[A gateway now reports whether its egress audit records can actually be attributed to a job.](https://actions-gateway.com/1.8.0/operations/observability-logging/#attributing-a-record-to-a-tenant-and-a-job)** `v1.7.0` shipped that attribution as two opt-ins on two different objects, and nothing said whether a given gateway had both.
The new `EgressAuditUnattributed` condition and its `actions_gateway_egress_audit_unattributed` gauge read both halves where the Gateway Manager Controller (GMC) already has them in hand, and every `True` reason names the half still off.
It is advisory and never gates `Ready`, because `Off` is the supported default on both halves, so a `True` on a gateway that never opted in is the expected state rather than a fault.
Its scope is `spec.defaultProxyRef`, so a `RunnerSet` overriding `spec.proxyRef` is not covered.

## Upgrading

**No breaking change, and nothing is removed.** The upgrade is the ordinary one:

1. Apply the chart's CustomResourceDefinitions (CRDs), as every upgrade does.
   The command is unconditional and idempotent, and the chart preflights it and fails with the same command if you skip it.
2. `helm upgrade` the release.
3. Wait for the GMC rollout to complete before applying any v2 object.
   Applying while the conversion webhook has no endpoints fails with `no endpoints available for service "webhook-service"`.
   That reads like a broken install and only means the apply came too early ([what to do](https://actions-gateway.com/1.8.0/operations/troubleshooting/#applying-any-v2-object-fails-with-no-endpoints-available-for-service-webhook-service)).

The full command and its options are in [Upgrading](https://actions-gateway.com/1.8.0/operations/upgrade/).

**Find agent-identity collisions before you upgrade.** Admission runs on create and update, so nothing is re-validated at upgrade time and an existing colliding pair keeps running exactly as it did.
There is also no condition or gauge reporting a pair carried in from an older release: the AGC's `AgentPoolError` Event is the only signal, and it fires only once a pool is already blocked.
Any stem appearing twice under one GitHub scope, or twice in one namespace, is a collision:

```bash
kubectl get runnersets.actions-gateway.com -A \
  -o jsonpath='{range .items[*]}{.metadata.namespace}{"\trs-"}{.metadata.name}{"\n"}{end}'
kubectl get runnergroups.actions-gateway.github.com -A \
  -o jsonpath='{range .items[*]}{.metadata.namespace}{"\t"}{.metadata.name}{"\n"}{end}'
```

**This can block a rollback.** Re-applying a v1 `ActionsGateway` while the v2 `RunnerSet` it collides with still exists is refused, and the rejection names which object is in the way.
Delete that `RunnerSet` first; a rollback removes the v2 objects regardless.
[Details](https://actions-gateway.com/1.8.0/operations/upgrade/#agent-identity-collisions-are-now-rejected-at-admission-runnerset-name-and-derived-runnergroup-name).

**Expect `RunnerVersionTooOld` to resolve on pools where it used to read `Unknown`.** The registry reading can turn a `WorkerImageVersionUnknown` into either `WorkerImageCurrent` or `WorkerImageBelowMinimum`, and the second one is `True` on an abnormal-is-True condition.
It does not gate `Ready` and blocks no job, but it feeds the gateway's `RunnerGroupsDegraded` roll-up and counts the set as impaired, so if you alert on either, expect new firings from pools that were always old and merely unreadable.
The fix is the same as it has always been: build or pull a `workerImage` on runner `2.329.0` or later.

**The AGC now makes an outbound registry read it did not make before.** It uses the pod template's `imagePullSecrets`, which is the only place it looks, and it reads them itself rather than through the ServiceAccount kubelet injects.
An egress policy that does not admit the AGC to your registry, or a credential only the node holds, leaves the reading `Failed` and the tag verdict standing, which is what you have today.
Nothing regresses; you just do not get the better answer.
`WorkerImageVersionUnknown` messages now name what the AGC could not do, and [the runbook](https://actions-gateway.com/1.8.0/operations/troubleshooting/#worker-image-runner-version) maps each one to a fix.

**A second small ConfigMap appears per `ScaleSet` `RunnerSet`, the first time one of its workers is disrupted.** `scaleset-recovery-claims-<set>` holds the at-most-once recovery claims that used to be pod annotations, beside the existing `scaleset-guards-<set>`.
It carries the same `actions-gateway.com/runner-set` label, is owner-ref'd to the set so the garbage collector reaps it, and is bounded by a one-hour claim TTL and a 256-entry cap rather than by history.
Nothing is asked of you; a script that lists ConfigMaps by that label and takes the first now gets two objects in no fixed order.

**`actions_gateway_eviction_recovery_evidence_lost_total` narrows without changing meaning.** It still counts disruptions whose runs will not be re-run automatically, so an alert on it needs no edit.
What changed is the cause behind it: a claim the AGC could not write, rather than a pod that went away.
Expect the rate to fall, and read a rate that does not as a question about the tenant `Role`'s `configmaps` grant rather than about the gateway's responsiveness.

**Nothing else moves.** No metric was removed or renamed, no field, enum value, default, condition reason or Event reason was removed or renamed, no existing default changed, no chart values key changed, and no command-line flag changed on any binary.

## Deprecations

**Nothing is removed in this release.** One notice is new and the other two are unchanged from `v1.7.0`.

**`v2beta1` is now scheduled for removal at `v2.0.0`**, which is new here and was not part of the original announcement in `release-1.3.md`.
Decided 2026-09-08: `v2.0.0` is a major release and dropping a served version is a breaking change a major release may make, and beta's contract is a migration path rather than permanence.
The path is the overlap release: the tag before `v2.0.0` serves `v2beta1` and `v2` together, so no object is ever unreachable.
Moving is a read and re-apply at `v2`, with the conversion webhook round-tripping the objects, except for the two deprecated `egressPolicyMode` aliases ([Before you upgrade past v2.0.0](https://actions-gateway.com/1.8.0/operations/v1alpha1-deprecation/)).

**`v1alpha1` and `v2alpha1` are both deprecated, and the apiserver warns on every apply of either.** Both are removed at `v2.0.0`, together with the Classic acquisition protocol.
Tenants on `v1alpha1` migrate with `gag-migrate` ([Migrating a tenant to v2](https://actions-gateway.com/1.8.0/operations/migration-v1-to-v2/)); moving from `v2alpha1` to `v2beta1` is a re-apply rather than a migration.

**The `CiliumFQDN` and `CalicoFQDN` `egressPolicyMode` aliases are removed at `v2.0.0` rather than `v3.0.0`.** They are aliases of `FQDN` and carry no behaviour of their own, and `v2` never defines them, so migrating off them stops being optional at the same tag that `v2beta1` goes away.

Field descriptions are in the [generated API reference](https://actions-gateway.com/1.8.0/reference/api/), which covers `v2beta1`.

<details>
<summary><b>The condition, its reasons, and the gauge</b></summary>

`ActionsGateway.status` gains `EgressAuditUnattributed`, abnormal-is-True and advisory.
`True` means one or both halves of the egress-attribution pair are off, so nothing joins an egress audit record to a tenant and a job.
Four reasons say which half:

- `EgressAuditJoined` is the `False` reason: both halves are on.
- `EgressAuditDisabled`: neither is, the default for a proxied gateway that never opted in.
- `WorkerAuditDisabled`: the pool records source addresses, but the gateway's `spec.auditLogging` is `Off`, so nothing names the tenant and job that held them.
- `ProxySourceAuditDisabled`: the gateway records worker addresses, but the resolved `EgressProxy` does not log `ConnectionsWithSource`, so no record carries an address to join on.

The polarity is what the condition can establish rather than a house preference.
A working join needs more than the two switches: the Container Network Interface (CNI) must not source-NAT pod-to-Service traffic, and something must collect both log streams and join them.
So a `False` says the pair is configured, not that anything runs the join.

`actions_gateway_egress_audit_unattributed` is `1` when that condition is `True`, labelled by namespace and name, beside its sibling condition gauges.

</details>

**No new fields, enum values, defaults, Event reasons, labels, annotations, CLI flags or chart values.** Metric names declared in the Go source went from 75 to 76, with the one addition above and nothing removed.

## Project and tooling

**The `v2` graduation's soak produced evidence that survives its window.** A dogfood window is billable and cannot be replayed, so a reading that lives only in a terminal is a reading lost.
The gate now writes one record per reading to a file the phase stream cannot truncate, and a renderer turns those records into the table the plan publishes, so what the plan claims and what the window measured cannot drift.
Two of the three readings came back positive and the third could not be graded in either window, which is recorded as *not taken* rather than as a pass.

**A near-miss worth recording.** One reading's detail string explained *why* rather than saying what was seen, and the explanation was a guess that reached a published plan table looking like evidence, because it had come out of a gate.
The rule now sits at the declaration: a reading records what was observed, never why.

## Security

**No security advisory accompanies this release**, and no reported vulnerability in this project's own code is patched.

**One dependency moved for a CVE.** `google.golang.org/grpc` goes from v1.83.0 to v1.83.2 for CVE-2026-84445 (HIGH), in which a gRPC-Go server crashes on a request carrying neither a `host` nor an `:authority` header.
It is an indirect dependency in both binaries' module graphs, and nothing in this project's own code imports `grpc` or starts a gRPC server.
The bump is what clears the scanner.
Whether the version it replaced was reachable in anything this project ships is a question the scanner does not answer, and the code that would have to be running is absent.
Minimal version selection pulled `golang.org/x/net` to 0.58.0 and `golang.org/x/text` to 0.41.0 alongside it.
The Go toolchain stays at 1.26.6.

**The agent-identity guard is the security-relevant change in this release**, and it is a tenant-isolation fix rather than a hygiene one.
Two pools under one GitHub scope reaching the same runner identity is a cross-tenant failure, because the runner name is unique per scope and the namespace boundary buys nothing there.
`v1.7.0` made the loser stop deregistering the incumbent, which stopped one tenant taking another's runner record but left the pair in place with one of them permanently blocked.
Rejecting the collision at admission is the secure default, it is what stops the pair forming at all, and the release ships no opt-out for it.

**A fourth reference dashboard, for the security and compliance reader**, carries four rows: egress attribution keyed on the pool, the apiserver's admission verdicts for the four shipped policies, one panel per rule in the security alert group, and control-plane liveness.
Building it is what found the two abuse alerts that could never fire, which are corrected here.

A pull request that changes code runs `govulncheck` and a Trivy image scan of every built image; one that changes the chart runs a Polaris posture check of it.
All three are path-gated on a pull request and unconditional on every push to `main` that touches something other than documentation, and the gate aggregating them reports on every pull request either way.
