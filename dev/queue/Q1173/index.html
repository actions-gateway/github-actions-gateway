    Gates under make check killed by a stray SIGTERM mid-run¶

    Event: a command under make check or make scripts-test ends on signal 15 (exit 143, or make's Terminated: 15) on main with nothing in its own suite sending one. Record the label, the uptime load, and how many make check runs other sessions had live at the time: the sender this row's fix removed was host-wide, not per-run.

    Two sightings, both on one branch that touched nothing they ran. 2026-10-09 16:40 PDT, load 20.75: check-artifact-unchanged: pathfilters match e2e-test.yml at bfef9dce… failed (exit 143) inside check-artifact-unchanged-test.sh, which passed 14/14 run alone straight afterwards. 2026-10-10 11:47 PDT, load 61.88: [script-docs-check] make[1]: *** [script-docs-check] Terminated: 15.

    The sender fixed here: run-parallel.sh's exit trap signalled every pid it had ever spawned, children reaped minutes earlier included. A reaped pid is free for reuse, so on a host whose pid space wraps within one fan-out that trap sends SIGTERM to whatever unrelated process holds the number by then, in any session's make check. Measured 2026-10-27 on this host with the trap instrumented to log, rather than signal, each reaped pid: the make scripts-test fan-out spawned children from pid 26886 to 96313 with uptime reading 23.52 at its start and 97.68 at its end, and when it exited 261 s later new pids were being allocated at 13171, so the pid space had wrapped once and stood about 13,700 short of the fan-out's first child. None of its 137 reaped pids was held by a live process at that moment, so a direct hit was not observed; the outer make check fan-out lives longer than that one and ran no instrumented exit. The trap now signals only children both still in idx_of and listed by jobs -rp: bash reaps an exited child from its SIGCHLD handler before wait collects it, so idx_of alone can name a freed pid, and jobs -rp read inside a TERM trap omits such a child (measured on bash 5.3.15). run-parallel-test.sh pins three halves: the original trap fails it by signalling two reaped pids, a trap filtering on idx_of alone fails 3/3 by signalling a TERM-killed child a second time after bash reaped it, and a trap that signals nothing fails the control case. Cleanup runs once, from the EXIT trap, so a signal no longer cleans up and then keeps spawning. One window stays open: a child exiting between cleanup's jobs -rp read and its kill can be reaped in between, and no bash construct closes it. check-registry-mirror-render-test.sh had the same shape over a narrower window, signalling cases it had already waited for when a killed case ends it early, and drops each pid as it waits it.

    Not the sender, by reading: check-artifact-unchanged.sh builds pathfilters into its own mktemp -d directory and sets no timeout, so it is neither Q1144's shared binary nor Q1106's probe. serialize-heavy-build-test.sh signals only processes it has just checked are inside the section, and on a pass signals nothing after they exit. The other scripts keeping pid lists signal only live or unreaped children: verify-release.sh behind kill -0 before any wait, and qos-cluster-probe.sh over infinite spinners it reaps and then forgets. Three more sightings followed, all on the branch carrying the fix, with ten other dispatch workers live whose gates run main's unfixed trap. The first, 2026-10-27 20:29 PDT (uptime 87.44 at the start, 73.57 at the kill): the outer make check runner itself took the signal, reported then as run-parallel.sh: wait -n returned 143 with no child of ours to reap and exit 1. The next two make check runs on that branch lost one suite each to signal 15: check-script-docs-test at 20:32–20:43 (uptime 79.18 then 90.11) and check-roadmap-test at 20:43–20:49 (85.26 then 51.48), each passing run alone straight afterwards. The old message is now received signal 15 (exit 143); the runner itself was signalled, not a child and exits 143, so a runner killed this way reads as KILLED rather than FAILED. None of the three counts against the fix: every other session's trap still carried the defect, so the soak starts once main does. A recurrence after that means a second sender; a bash trap is not told the sender's pid, so the next instrument is a snapshot of the process table taken in the runner's trap.
