    Name the four routed registry paths in the dispatch pre-flight checklist¶

    .gitattributes routes four paths to per-clone merge drivers: scripts/README.md, mk/gate-lists.mk, docs/plan/README.md and docs/roadmap.md. Two pull requests editing different rows of one of those files conflict on GitHub whenever their rows are directly adjacent, and the same merge resolves cleanly in any clone that has run make merge-driver. The cost lands on the host: a DIRTY pull request or a merge-queue eviction, then a rebase, a force-push and a full CI cycle. The mechanism is written down in the driver's header (scripts/docs/git-merge-script-index.sh:18:reduce merge-queue evictions, and no local driver can) and the rule that follows is in parallel-dispatch.md: space the assignment. Q1121 owns the separate defect that git merge-tree answers the driver's question rather than the queue's.

    The gap. The pre-flight checklist item is docs/development/parallel-dispatch.md:519:No two assigned Queue rows adjacent, and Queue rows no longer share a file (one file per item), so it names a shape that cannot collide and none of the four that can. scripts/README.md bites hardest because check-script-docs.sh fails a gated script with no row, so a batch adding scripts must land rows in one table. The gh pr create guard that compared colliding line ranges is retired (CONTRIBUTING.md:342:Nothing checks this for you).

    The choice: name the paths and space the assignment¶

    Do this. Replace the Queue-row checklist item with one naming the four paths: before assigning, the dispatcher lists which items will edit each (a new gated script or a new gate adds a scripts/README.md row and usually a mk/gate-lists.mk entry; a new plan or a roadmap change adds the other two) and does not hand two of them out in the same wave when their rows would sit in one table; the second waits for the first to merge, or the dispatcher accepts one rebase. The cost is a sentence in the checklist and a line in the opening assignment pass.

    Why not the other two directions, from the measurement below.

    • A row order stable under append puts every new row of a table at its end, so concurrent additions to one table collide at the same spot every time. Today's sorted order at least spreads them.
    • Splitting scripts/README.md by group removes collisions between groups, and none can be between groups in that file: two adjacent rows are always in one table, because headings and blank lines separate the tables. A per-group file would therefore collide exactly as often. The same holds for mk/gate-lists.mk and the plan index, whose collisions are between neighbouring entries of one list. It would also cost check-script-docs.sh, whose invocation takes one README path (scripts/docs/check-script-docs.sh:93:"$bin" "$README" "${scripts[@]}"), a multi-file reader, and it would move the driver's table-set merge across files. Splitting to a file per script would remove the collision, and it is a large change for about one event a week.

    The measurement¶

    Taken 2026-11-01 at origin/main f763051b9, over the squash commits since 2026-08-15 that touched the four files (400 commits listed, 237 PR-file edits by 157 of the last 600 merged PRs). Per PR the changed rows are keyed on column 1, placed at their position in the current file, and two PRs count as concurrent when their created-to-merged intervals overlap (gh pr list --state merged --json number,createdAt,mergedAt); a pair counts as adjacent when any two of their rows sit within one line. Positions come from today's file, not the base each PR saw, so the error runs both ways: a row inserted later separates a pair that did collide, and a row deleted later brings together a pair that did not (in this window 5 scripts/README.md row keys were deleted and never re-added, and 24 edited keys are missing from today's file and dropped). The counts are an estimate, not a bound; confirming each pair against its base with git merge-file is the tighter measurement and was not done. The row first asked for counts read off gh pr diff hunks; this uses each squash commit's diff instead, which is each PR's net change on the main-line file and a fair proxy.

    file PR edits concurrent pairs same row neighbouring rows
    scripts/README.md 107 117 3 4
    mk/gate-lists.mk 61 40 1 4
    docs/plan/README.md 57 11 2 0
    docs/roadmap.md 12 0 0 0

    Only the neighbouring rows column is the row's defect (different rows, directly adjacent): 8 pairs. A same row pair (6) is an ordinary conflict, and whether the set-merging driver resolves one is unmeasured. The 14 hits fall on 10 file-days in about 11 weeks, 23 distinct PRs. Control: the method finds the row's own 2026-09-19 pair (#1965/#1964/#1967 on scripts/README.md), which it was not told about. CONTRIBUTING.md:345:Two edits within six lines of each other collide over-reports the merge itself: git needs one unchanged line between two changes, so only adjacent rows (zero gap) conflict (measured in the original run on this file at base c8a323361: lines 200 and 201 conflict, 200 against 202 through 205 merge clean).

    Found by the dispatch run of 2026-09-18/19, which paid it twice on one pull request.
