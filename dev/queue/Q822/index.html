    Three unrelated suites fail under concurrent load and pass on rerun¶

    Event: a scripts-test suite fails inside a capped local fan-out and passes standalone straight afterwards, on main; or git-merge-script-index-test or git-merge-plan-index-test fails anywhere with a merge-*-index: the build failed with: line, which is the driver-build race below recurring past its fix.

    The mitigation is the cap: run-parallel.sh takes RUN_PARALLEL_JOBS, and the Makefile exports local-throttle.sh jobs as its default, physical cores minus 2 on a GUI dev shell and unbounded on CI or headless. So make check's 51-gate level and make scripts-test's 119-suite level each start at most that many at once instead of all of them. The measurement: eleven runs on 2026-09-07 beside a sibling go test -race suite, load 26 to 153 on 18 cores. Wall time cannot rank the caps, but every run capped at 16 or lower spent 2,248 suite-seconds or fewer against 2,609 or more uncapped (32 and 64 sat inside the uncapped range), and the fork+exec tail peaked at 1.8 s capped against 3.2 s uncapped. That tail is the axis Q1031 re-keyed this row onto, and it moved with the width rather than with the load.

    What the mitigation is not evidence for. No run crossed the 5 s budget Q1031's probe kills expire on, so that class is not reproduced here; it takes a second fan-out beside this one, which these runs had only from the -race suite next door. 8 against 16 is not separable in the data, so the default follows the throttle's own number, and Q966 owns whether that number is right.

    Two sightings taken during the sweep belong to Q912: check-endpoint-parity-test red with a fakegithub that never accepted within 30 s, once uncapped at load 77 and once at a cap of 16 at load 129, both green standalone. They are recorded here rather than on that row because the run that produced them is this row's, and a groom moves them.

    The original sightings: the provisioner eviction window under 8 workers on 2026-08-12, and git-merge-script-index-test at load 32.21 on 2026-09-04, the reading that showed load average was the wrong axis. The controller 2m timeout in the original set is Q823's, covered by the raise to 5m.

    A sighting on CI, outside the trigger, 2026-09-07¶

    git-merge-script-index-test failed in the merge group for #1862 (the shellcheck job of unit-test.yml), case a real git rebase resolves adjacent adds through .gitattributes, and the queue evicted the PR; the same job had passed on the PR's own run of the same head, and the group built one minute later for #1863 passed it. It does not trip the trigger above, which names a capped local fan-out on main: RUN_PARALLEL_JOBS is unbounded on CI by design, so the 119-wide burst the cap removes locally is the burst CI still runs, and the eviction cost one queue cycle. With main's own push of 301418a29 (2026-09-05, a side that adds a whole table is refused) and the 2026-09-04 local case, that is three distinct assertions from one suite across three runs, the shape of a driver that was not the driver. Every invocation of scripts/docs/git-merge-script-index.sh rebuilds .build/mergedriver with go build -o into one shared path (scripts/lib/merge-driver-common.sh), discards the build's output, and on a failed build falls through to a plain textual merge kept as-is; git-merge-plan-index-test shares that file, and on Linux writing an executable that is running is an error the wrapper would swallow. Unverified: six rounds of the two suites three-wide locally (load 38 on 18 cores) produced no failure, and macOS does not raise that error, so the local negative is weak. The cap does not address this mechanism, and the cheap discriminator is to stop discarding the build's stderr and build once per process tree (a flock on the output path, or a prebuilt binary the suites share), then watch the queue.

    A fourth CI sighting, 2026-09-10¶

    git-merge-script-index-test failed again in the shellcheck job of unit-test.yml, on #1884 (run 34462200647), case a one-sided row edit is kept alongside the other side's add. The driver reported the driver could not be built; left ordinary conflict markers in scripts/README.md, which is the swallowed-build path this row names.

    That is a fourth distinct assertion from this one suite, after a side that adds a whole table is refused (2026-09-05, main), a real git rebase resolves adjacent adds through .gitattributes (2026-09-07, the #1862 merge group) and the 2026-09-04 local case. Four assertions across four runs is the same argument this row already makes, with one more point on it: the failing case moves, so the driver is not what is failing.

    Two readings narrow the mechanism further:

    • Cases either side of it passed in the same suite run. adjacent adds from both sides both survive and a row deleted on one side stays deleted ran before it, and five cases ran green after. Each invocation rebuilds the shared binary, so a build that is broken would fail all of them; exactly one attempt failed.
    • It does not reproduce locally. make scripts-test was green twice on the identical tree, once inside make check and once standalone.

    The PR carried no Go and no shell: its diff is Makefile, scripts/README.md, two docs and three deleted rows. It edits scripts/README.md, which is this driver's own subject, so the suite is path-gated on and the sighting will recur on any PR touching scripts/ or the Makefile.

    It cost a CI cycle rather than a queue eviction this time, because the failure landed on the PR's own run rather than in the merge group. Confirmed on rerun: gh run rerun --failed on the same head, with no code change, took the shellcheck job green in 4m8s (job 102827685450), so this sighting meets the repo's own definition of a flake rather than resting on the local negative alone. The discriminator this row already prescribes — stop discarding the build's stderr, and build once per process tree — is what would turn the next one into a diagnosis instead of a fifth data point.

    The shared-build hypothesis: refuted, and the real window measured, 2026-09-10¶

    This row's mechanism was wrong, and the obvious measurement confirms it rather than refuting it. The inode of .build/mergedriver is unchanged across a cached rebuild, which reads as go build -o copied over the destination in place. The control settles it the other way: append three bytes to the output, rebuild, and the appended bytes survive, on go1.26.6/darwin-arm64 and go1.26.8/linux-amd64 alike. A cache hit writes nothing at all, so it is not a write that leaves the inode alone.

    That also disposes of an argument this row leaned on: the 2026-09-04 sighting was local, on macOS, so "no local reproduction because macOS does not raise the error" was explaining away a member of its own evidence set. The count is three CI sightings (301418a29 on main 2026-09-05, the #1862 merge group 2026-09-07, #1884 2026-09-10) and one local.

    A real window exists, and it is narrower than this row said and narrower than two attempts to restate it. The contended moment is a cache miss, where go places the binary, and how it places decides everything. Same filesystem it renames, which is atomic and safe. Cross filesystem it unlinks and streams a copy, so a concurrent execve of the path fails either way: ETXTBSY while the path is an incomplete file held open for writing, and ENOENT in the gap between the unlink and the create. Measured on go1.26.8/linux-amd64, replicating that shape against a concurrent exec: 4,106 of 4,109 execs failed, almost all ETXTBSY, with the instrument's controls confirming it distinguishes ETXTBSY from the EACCES a mode-644 file gives. It reproduced independently at 99.8% on a separately-built instrument, with a larger ENOENT share, so the split between the two moves with timing while the total does not. #1898 builds to a sibling path and renames, which takes the atomic route whichever way go placed the temp.

    So this row's original instinct, ETXTBSY, was closer than the two stories written over it: a SIGBUS claim that turned out to characterise coreutils cp truncating in place, which go never does, and a claim that unlinking closed the window, when it only changes the symptom.

    Whether anything here ever takes the copy path is unmeasured. It needs $GOTMPDIR/$TMPDIR and .build/ on different filesystems. On a dev Mac they are not, and go build -x shows mv; nobody has read the layout on the CI runners. So the fix closes a hazard by construction rather than one observed here.

    And it does not diagnose this row either way. Every sighting reports the driver could not be built, which is go build failing; both stories above kill an exec after a successful build. What #1898 also ships is the discriminator this row asked for: the build's output is relayed on stderr instead of discarded, so a fifth sighting names its cause rather than repeating the symptom. The row stays parked on the trigger above, and the next occurrence is expected to carry a merge-*-index: the build failed with: line naming what actually failed.
