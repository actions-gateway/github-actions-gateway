    No instrument answers whether the merge queue will conflict¶

    git merge-tree is the command a session reaches for, and in this repo it answers a different question than the one being asked.

    The trap, and why it reads as reassurance¶

    Four paths are routed to merge drivers by .gitattributes, measured 2026-09-16: scripts/README.md, mk/gate-lists.mk, docs/plan/README.md and docs/roadmap.md. git merge-tree --write-tree consults .gitattributes, so in a clone that has run make merge-driver it returns the driver's resolution. GitHub builds the merge queue's candidate itself and runs no merge drivers, so the queue performs the raw three-way and can reject a branch the local probe called clean.

    The failure is silent and its output is the encouraging one, which is what makes it survive a careful read: nothing errors, nothing warns, and the answer is exit 0.

    The measurement¶

    Taken 2026-09-16. The trap is already written down, at testing.md § the status you report is a claim too, in the Q828 entry, which records a merge-tree probe exiting 0 for a branch the queue then rejected and notes that the driver announced itself in the output being quoted as clean.

    Two sessions reached for merge-tree anyway that afternoon, both with that doc in their own checkout. One ran it and reported exit 0 as evidence a pull request would merge, then withdrew it on being challenged; that half is in this repository's own transcripts. The second session reported that it avoided the command only by reasoning about drivers being per-clone beforehand, and read the Q828 entry after finding the conflict rather than before — its own account, not something the tree records.

    Two independent sessions in one afternoon, both competent, both with the rule available, is the shape that says a prose rung is not holding it.

    The conflict under measurement was one row of scripts/README.md: an open pull request rewriting the dependabot-rebase-stale.sh row while the dispatch-run branch appended two rows directly beneath it. git merge-tree --write-tree exited 0; git merge-file on the three blobs exited 1 with two conflict markers, against a control with an unchanged side that exited 0 and produced none.

    Why an instrument and a hook, and not a gate¶

    Nothing lands in the tree, so a gate has no artifact to inspect and could never fail on what it targets — worse than no gate, because it would read as covered.

    An instrument under scripts/ci/ has the property the doc line already has: you must know to reach for it. That is the defect this row documents, so a fix that only adds a second thing to know about does not close it. As originally scoped the row could be satisfied by shipping the script while the next session types git merge-tree unchanged.

    Measured 2026-09-16 across this machine's session transcripts for this repository: 265 shell commands in which a session reached for git merge-tree, over 74 distinct sessions and 27 separate days from 2026-07-26 on. The busiest day is 2026-08-12 at 83 such commands across 11 sessions, with 2026-08-25 second at 50 across 9. In any clone that has run make merge-driver, every one of those runs got the driver's answer to a question about the queue. The population reaching for the wrong command is the whole batch over seven weeks rather than the two sessions this row was filed from.

    That figure is approximate in both directions, and how it was taken is the row's best argument.

    The first count filed here was a raw scan of the command string, corrected on review: it counts prose, commit messages and a drafted PR body that quote the command without running it. Read four times across two sessions in one afternoon it returned 331, 335, 337 and 340, rising because the sessions measuring it were writing the string into their own transcripts as they went. A count that moves while you look at it is measuring the looking.

    The replacement anchors the pattern to command position, which is better and is still a scan. It misses wrapper forms that are real runs, /usr/bin/time -p git merge-tree and git -C <dir> merge-tree among them, and it counts matches that sit inside heredoc bodies, which are text being written rather than commands being run. Six commands are contaminated that way, by the test that asks whether the match falls between a heredoc opener and its terminator. Two of the six were written on the day of this row by the two sessions measuring it: one drafting a PR body that quoted the command, one writing the probe script itself. So it too moved, 264 to 265, for precisely the reason the raw scan moves.

    The count is of commands rather than of matches, deliberately: a command naming merge-tree twice is one session reaching for it once, which is the event this row is about. Counting matches instead gives 285. Naming the test is not pedantry here, because looser tests for the same contamination return eleven and fifty-nine, and the difference between them is entirely definitional.

    Two sessions each wrote a carefully anchored regex and each counted its own draft as an invocation. A count that excludes prose but not quotation is not a parse, and telling a heredoc body from shell code needs a real shell parser. That is what claude-go-throttle-hook.sh does and what neither instrument here did, so the hook this row asks for is argued by the failure of both attempts to avoid needing it.

    A PreToolUse hook is the rung that reaches them, and the repo already runs two: .claude/settings.json wires claude-go-throttle-hook.sh on Bash and claude-no-subagent-workers-hook.sh on Task/Agent. go-throttle is the precedent in shape: it parses with a real shell parser rather than scanning, so the command named inside a commit message or a heredoc body is a word and not an invocation (Q624).

    The two rungs are complementary rather than alternatives: the hook has nothing to point at without the instrument, and the instrument is not reached without the hook. Build the instrument first for that reason.

    Shape¶

    A script under scripts/ci/ answering will the merge queue conflict?, taking two refs and optionally a path list. It shells git merge-file on the three blobs per overlapping path and never merge-tree, carries its own positive control so an always-conflicts or always-clean harness is visible, and says in its header why merge-tree is wrong, citing Q828. Scope and name are open; the sketch is a starting point rather than a spec.

    Then a PreToolUse hook on Bash that recognises git merge-tree in command position and answers with the fix rather than a warning: name the instrument, and say that merge-tree consults .gitattributes so its verdict is the driver's. Deny rather than ask, per the repo's own hook practice: a deny's reason reaches the model, which can then run the right command, where an ask reaches a human who has to relay it. Legitimate merge-tree use that is not about queue mergeability needs a documented override, on the shape claude-go-throttle-hook.sh already uses.

    Then the doc line points at something to run, testing.md's Q828 entry gains a use this instead rather than only a warning, and the session that never read either is told at the moment it types the command.

    Done when¶

    A session that types git merge-tree in this repository is told at that moment that the command returns the driver's verdict, and is given the one that answers the queue's, and the command it is pointed at exists and carries its own positive control.

    Shipping the instrument alone does not satisfy this row: that leaves the 74 sessions above reaching for the same command and finding the same reassurance.

    Notes¶

    The control is not optional decoration: a raw three-way that exits 1 is equally consistent with a harness that always conflicts, so the instrument is unreadable without a case that must come back clean.

    A wrong driver key name reads identically to a driver that is not installed: measured 2026-09-16, git config --get merge.<name>.driver exits 1 with empty output for a misspelling and for a driver nobody configured alike. Read .gitattributes for the name and enumerate with git config --get-regexp '^merge\..*\.driver' rather than testing a name someone handed you.

    Found by the dispatch run of 2026-09-16, which hit it twice in one afternoon.
