    7. Test Plan¶

    ← Implementation Phases | Back to index | Next: Glossary →

    Testing is structured in three layers. Each layer has a distinct scope, speed contract, and failure signal. All three layers run in CI; only unit and integration tests gate PRs. End-to-end tests run nightly against a staging cluster. Multi-tenant scenarios are explicitly covered at the integration and end-to-end layers, since tenant isolation is a correctness property of the system, not just a deployment concern.

    7.1. Unit Tests¶

    Scope: Pure logic within a single package — no network, no Kubernetes API, no real file I/O.

    Speed contract: Full suite runs in under 30 seconds. Any test requiring a sleep or external call does not belong here.

    Tooling: Standard go test ./... with testify/assert. Use go test -race in CI to catch goroutine data races.

    What to cover:

    • Broker API client — Request construction, header injection, and response parsing for sessions, message, acquirejob, and renewjob. Use httptest.NewServer to serve static JSON fixtures without hitting GitHub. Assert that acquirejob and renewjob use the run_service_url from the message body, not the broker URL.
    • RenewJob loop — Verify the per-job goroutine calls renewjob at the correct 60-second interval, stops cleanly when the job completes, and handles a non-200 response from renewjob by surfacing an error without panicking.
    • Rate-limit (429) backoff — Drive the broker API client against an httptest server that returns 429 Too Many Requests with a Retry-After: 30 header. Assert the client honors Retry-After, increments actions_gateway_message_poll_errors_total{reason="rate_limited"}, and falls back to exponential backoff capped at 5 minutes when the header is absent. Assert that sustained 429s for >10 minutes surface a RateLimited condition on the corresponding RunnerGroup.
    • Token Manager — Use a fake clock to advance time to T-5 minutes before token expiry and assert the Token Manager fetches a new token before the old one expires. Assert that session goroutines reading the token during a refresh window get a valid (old or new) token and are never blocked. Assert that actions_gateway_token_refresh_errors_total increments on each failed refresh attempt; the alerting threshold for this metric is defined in docs/operations/observability.md (> 0 for 5 minutes triggers a page).
    • Payload decryption — AES-256 decryption of the TaskAgentMessage.Body field. Test against a pre-generated key/ciphertext pair committed as a fixture. Test failure modes: wrong key, truncated payload, invalid base64.
    • Session registry — Goroutine lifecycle management: spawn N sessions, verify N goroutines are running, scale down to M, verify M remain with no leaks. Use goleak.VerifyNone(t) (from go.uber.org/goleak) as a test cleanup hook — it identifies leaked goroutines by stack trace, making failures actionable. Do not use runtime.NumGoroutine() deltas, which include Go runtime goroutines and produce unreliable counts.
    • Label-to-pod mapping — The logic that translates RunnerGroup runner labels to a target pod spec. Table-driven tests covering label matches, mismatches, defaults, and invalid configurations.
    • AGC reconciler state machine — Unit-test the AGC reconciler's desired-vs-actual diffing logic with a fake client.Client (provided by controller-runtime/pkg/client/fake). Cover create, update, scale-up, scale-down, and delete transitions.
    • GMC reconciler state machine — Unit-test the GMC reconciler with a fake client. For a given ActionsGateway spec, assert that the reconciler produces exactly the expected set of Kubernetes objects (ServiceAccount, Role, RoleBinding, NetworkPolicy, proxy Deployment, proxy Service, proxy PodDisruptionBudget, HPA, AGC Deployment) all within the CR's own namespace. The reconciler does not create a ResourceQuota — that is platform-owned (Q130); assert it leaves any pre-existing namespace quota untouched. Table-driven tests covering spec creation, proxy scaling bound changes, and deletion. For credential rotation specifically: assert that updating gitHubAppRef.Name causes the GMC to update the AGC Deployment's volume reference to the new Secret name (triggering a rollout) and does not mutate or delete the old Secret.
    • HPA spec generation — For a range of ProxyConfig inputs (explicit values, all defaults, boundary values), assert the generated HorizontalPodAutoscaler has the correct minReplicas, maxReplicas, and targetCPUUtilizationPercentage. Assert that minReplicas is always ≥ 1 and ≤ maxReplicas. Assert proxy pods always have resources.requests.cpu set (required for HPA metric computation).
    • Proxy env injection — Assert that the AGC Deployment spec produced by the reconciler contains HTTP_PROXY, HTTPS_PROXY, and NO_PROXY env vars. Assert NO_PROXY includes kubernetes.default.svc, this cluster's API server ClusterIP, and the configured noProxyCIDRs. The API server assertion runs against a non-kind ClusterIP (KUBERNETES_SERVICE_HOST set to a managed-distribution address) and asserts no hardcoded Service CIDR survives — the exact gap that let Q465 ship. Assert the same three vars appear in the worker pod template.
    • Status Conditions — Assert that the GMC sets the Ready, ProxyAvailable, and AGCAvailable conditions on ActionsGatewayStatus correctly as components become healthy or degrade. Assert conditions use standard metav1.Condition types compatible with kubectl wait --for=condition=Ready.
    • Runner version rejection — Unit-test the session goroutine's handling of a 400 Bad Request from POST /sessions containing a version-too-old message. Assert the goroutine surfaces the error as a RunnerGroup condition rather than silently retrying in a tight loop.
    • GMC RBAC boundary assertions — Enumerate the generated ClusterRole rules and assert that no rule grants * verbs on secrets, pods, or nodes at the cluster level. This is a regression guard against accidental privilege escalation during development.
    • AGC chart-RBAC drift — The AGC's permission set has two hand-maintained sources that neither generates the other: the +kubebuilder:rbac markers in cmd/agc/internal/controller/doc.go (what the code declares it needs) and the chart's files/agc-*-rules.yaml fragments (what an install grants). agc-tenant-role is read back by the GMC integration suite, which installs it straight from its fragment; agc-clusterrunnertemplate-reader had no read-back at all (Q454), and it is the role where drift is most expensive — every rule in it is a cluster-wide grant. Two unit tests close both directions: the shipped cluster-reader rules must name exactly the verbs the markers declare for the same kinds, and never a write verb; and every (group, resource) the markers declare must be shipped by one of the two chart roles, so a marker added without its chart rule fails the build rather than 403-ing in a real install.
    • gitHubAppRef namespace resolution — Unit-test the lookup: with Namespace omitted, assert the Secret resolves in the ActionsGateway CR's own namespace. Namespace is inert and admission rejects any non-empty value, so assert the webhook denial rather than a cross-namespace lookup (TestWebhook_RejectsCrossNamespaceSecretRef, TestWebhook_UpdateRejectsCrossNamespaceSecretRef).
    • Reserved namespace blocklist validation — Unit-test the admission webhook logic that rejects ActionsGateway CRs created in reserved namespaces. The static defaults are kube-system, kube-public, and gmc-system. The webhook also reads POD_NAMESPACE (downward API) at setup time and adds it to the set, so installs into a non-default namespace are protected. Tests cover the static defaults plus a custom-install namespace driven by the constructor.

    7.2. Integration Tests¶

    Scope: Multiple components interacting with real infrastructure dependencies — a live Kubernetes API server and a stubbed GitHub backend. No actual GitHub network calls. No container image builds and no real Kubernetes scheduling — pods are created in the API server but never actually scheduled.

    Speed contract: Full suite runs in under 5 minutes. Each test must complete in under 30 seconds. Tests run against a local envtest API server (from controller-runtime). kind is not used for this layer — it requires container builds and is slower than envtest.

    Build tag: all integration test files carry //go:build integration. This keeps them out of the unit-test run (go test ./...) and requires an explicit -tags integration flag. CI runs them as a separate job after unit tests pass. Tests live under cmd/{agc,gmc}/internal/controller/integration/. See docs/development/testing.md for the run commands.

    Why envtest, not the fake client: the fake client.Client cannot enforce CRD admission validation (CEL rules, x-kubernetes-validations), does not handle ownership references and garbage collection, and cannot test webhook behavior. envtest spins up a real kube-apiserver and etcd binary locally (no kubelet, no scheduler), so CRD schemas, admission webhooks, and status subresources all behave as in production.

    Tooling: controller-runtime/pkg/envtest for the Kubernetes API surface. A shared stateful httptest fake broker under internal/brokertest/ for the GitHub broker — tests control it by enqueuing job messages on demand and asserting which sessions were deleted, rather than replaying static fixtures. Standard go test with testify and gomega.Eventually for eventually-consistent assertions. Ginkgo is not used; the integration tests follow the same testing-package style as the unit tests in this repo.

    Why plain testing and not Ginkgo, measured: Ginkgo specs are closures inside a single Go test function, so the toolchain sees one test however many specs run — go test -json reports the 73-spec e2e suite as exactly 1 test (TestE2E), against 68 for one plain package's 68 tests. Everything downstream of that stream (progress reporting, per-test timing, -run selection, IDE integration) degrades accordingly, which is why the e2e suite needed bespoke reporter instrumentation to report its own progress at all. The repo is 1 Ginkgo suite against ~1,800 plain test functions; keep new suites plain. Ginkgo earns its place in e2e specifically — a shared expensive cluster fixture, Serial/Ordered constraints, and label-filtered subsets are its genuine strengths.

    What to cover:

    • CRD install and validation — Install both ActionsGateway and RunnerGroup CRD schemas into envtest. Verify valid manifests are accepted. Verify invalid specs are rejected at admission: the namespace blocklist webhook rejects reserved names; CRD CEL rules reject maxWorkers values that conflict with the last priorityTiers threshold (non-ascending tier order is a caller contract, not an admission or condition check); runnerLabels is rejected when empty (MinItems=1) or when an item contains whitespace/commas (per-item Pattern). The securityProfile no-downgrade guard is enforced by the GMC validating webhook (not CEL, since it reads metadata.annotations) and is unit-tested directly: an upgrade (baseline → restricted) and same-value update pass; a downgrade (restricted → baseline, or anything → privileged, including a dropped-field re-default to baseline) is rejected unless the allow-profile-downgrade: "true" annotation is present.
    • GMC tenant provisioning — Create a namespace, then apply an ActionsGateway CR into it. Verify the GMC creates all expected child resources within that same namespace: ServiceAccount (AGC + worker), Role, RoleBinding, NetworkPolicy, proxy Deployment (with resources.requests.cpu set), proxy Service, proxy PodDisruptionBudget, HPA, AGC Deployment (with HTTP_PROXY, HTTPS_PROXY, and NO_PROXY set), and bootstrap RunnerGroups. Verify the GMC does not create or modify the namespace itself, and does not create a ResourceQuota (platform-owned — Q130). TestGMC_TenantProvisioning_NoResourceQuotaCreated asserts a pre-existing platform quota is left untouched. Assert ActionsGatewayStatus.Conditions includes the ProxyAvailable and AGCAvailable condition types. Note: because envtest does not schedule pods, Deployment.status.readyReplicas stays at 0 — the Ready condition will not become True and tests assert the non-Ready state is reported correctly rather than asserting Ready=True. Additional provisioning cases: gitHubAppRef.namespace omitted defaults to the CR's own namespace; spec.proxy.noProxyCIDRs is merged with (not replaced by) the mandatory cluster-internal exclusions; updating gitHubAppRef.name causes the AGC Deployment to reference the new Secret without deleting the old one.
    • GMC tenant teardown — Delete an ActionsGateway CR and verify the GMC removes all associated resources, including the proxy Deployment, Service, PodDisruptionBudget, and HPA, without affecting any other tenant namespace. Assert that a second ActionsGateway CR remains fully intact. Also verify that re-applying the same CR after teardown brings all resources back cleanly.
    • v2 gateway-teardown worker reap (Q547) — The owner-reference backstop below does not reach v2 gateway teardown: worker pods are owned by RunnerSets, which deliberately survive the gateway, so the AGC reaps them itself on the gateway's deletionTimestamp and the GMC gates teardown on the counts. Verified across both tiers. envtest: TestV2_RunnerSet_GatewayTeardownReapsWorkers deletes a gateway held terminating by a finalizer — the assumption the whole design rests on, and one a fake client only imitates — and asserts a Running worker with no completion stamp and a fresh Pending worker are both deleted with completedPodTTL/pendingPodDeadline pinned to an hour, so nothing but the teardown could have reaped them; TestV2_RunnerSet_LiveGatewayRetainsWorkers is the control. Unit: the GMC's gate is table-driven over hold / release-on-zero / release-on-deadline (actionsgateway_v2_worker_drain_test.go), and both halves were settled by deleting the mechanism and requiring red.
    • Owner-reference GC backstop — After a full provisioning reconcile, sweep the tenant namespace by the managed owner labels and assert every child carries a controller owner reference to its ActionsGateway (Q394 — see §4.1.1). TestGMC_V1Provisioning_EveryManagedChildIsOwnerReferenced drives the assertion from what is actually on the cluster rather than an enumerated list, so a child added later through a new code path cannot ship un-owned. Unit-level tables in apply_helpers_ownerref_test.go pin the same contract per helper for both API versions, including the one deliberate exception (the cluster-scoped ClusterRoleBinding, which a namespaced gateway cannot own). envtest runs no garbage collector, so these verify the reference the GC keys on, not the collection itself.
    • HPA bounds update — Update spec.proxy.maxReplicas on a live ActionsGateway CR and verify the GMC patches the HPA to reflect the new bound within one reconcile cycle.
    • Proxy NetworkPolicy content — Verify the content of the generated NetworkPolicy in the API server: proxy pod egress includes the GitHub CIDR rules; AGC and worker pods have egress rules only to the proxy ClusterIP; DNS egress is always present. Verify that spec.proxy.managedNetworkPolicy: false suppresses the GitHub CIDR egress rules. Verify the IPRangeReconciler patches an existing policy when the fetched CIDR set changes. Note: envtest does not run a CNI plugin — these tests verify the NetworkPolicy spec content, not actual packet filtering.
    • AGC RBAC scope enforcement — Provision an ActionsGateway CR so the GMC creates the actions-gateway-controller ServiceAccount and its Role/RoleBinding. Impersonate that ServiceAccount via rest.ImpersonateConfig and attempt to list resources in a different tenant's namespace. Assert the API server returns 403. Assert that listing in the same namespace returns 200.
    • AGC reconciler end-to-end — Deploy a RunnerGroup, verify the AGC starts exactly one listener goroutine at rest (the permanent baseline). Enqueue jobs via the fake broker and verify additional goroutines spawn up to .spec.maxListeners. Verify idle goroutines shut down once the queue empties, leaving exactly one active listener. Update .spec.maxListeners, verify the new ceiling takes effect without restarting in-flight goroutines. Delete the resource, verify all goroutines exit and no agent Secrets or worker Pods are orphaned.
    • Secret lifecycle — Verify that a Secret is created with the correct payload labels when a job is intercepted, scoped to the correct tenant namespace, and deleted after the pod terminates. In envtest, pod phase must be advanced manually (no kubelet) — tests set the pod status to Succeeded via the status subresource client.
    • Event-driven pod completion — Verify the provisioner's InformerPodWaiter resolves a blocked session when the shared Pod informer observes the worker pod reach a terminal phase (and on pod deletion), rather than polling pod state on a timer. TestInformerPodWaiter_RealInformer runs a real manager cache against envtest, creates a pod, advances its status to Succeeded via the status subresource, and asserts WaitForCompletion returns promptly with the terminal phase.
    • Worker-Pod watch re-triggers reconciliation — Verify the RunnerGroup controller watches the worker Pods its provisioner creates, so a Pod lifecycle event (create on job acquire, terminal-phase transition, eviction, or delete) re-triggers a reconcile and refreshes the RunnerGroup's status without waiting for the next spec change or cache resync. TestAGC_Reconciler_WorkerPodEventTriggersReconcile runs a real manager against envtest, lets the controller quiesce (its reconcile count stops increasing), injects a sentinel condition into the listener-condition channel, then creates a labelled worker Pod and asserts the resulting reconcile both increments the reconcile count and flushes the buffered condition into status. The watch is deliberately Pods-only — a Secret watch would establish a Secret informer and cache credential material, violating the W3/H-2 cache-isolation property.
    • Listener-pushed condition wakes the reconciler — Verify the channel-backed source.Channel (Q333) wakes the reconciler when a listener/provisioner goroutine pushes a condition, so an otherwise-idle set drains it without a Pod event or the cache resync. TestAGC_Reconciler_PushedConditionWakesRunnerGroup (v1) and TestV2_Reconciler_PushedConditionWakesRunnerSet (v2) run a real manager against envtest, let the controller quiesce, then push a sentinel condition — creating no Pod and issuing no spec write — and assert the push alone increments the reconcile count and flushes the condition into status. TestV2_RunnerSet_ScaleSet_SessionFailureConditionsReachStatus additionally covers durability: a listener-only ScaleSet Degraded condition survives a status-write conflict with a concurrent update (the drained condition is retained and re-applied until the live object reflects it) rather than being dropped once a prompt wake lands the drain in a racing reconcile.
    • Pod provisioning — Verify that the AGC creates a Pod with the correct image, resource limits, volume mounts, and security context when a job payload is received from the fake broker. Verify controller-enforced invariants are applied unconditionally: automountServiceAccountToken: false, serviceAccountName: actions-gateway-worker, HTTP_PROXY/HTTPS_PROXY/NO_PROXY env vars injected with the provisioner's values. Verify priorityTiers tier assignment by pod count. Verify maxWorkers ceiling holds the third pod until an active pod completes. Verify the secure-by-default hardening: with SECURITY_PROFILE unset/baseline the pod gets pod-level runAsNonRoot + seccomp RuntimeDefault but no per-container privilege-escalation/capability floor; with restricted the per-container allowPrivilegeEscalation:false + drop-ALL floor is added; with privileged no SecurityContext defaults are stamped. Verify default 500m/1Gi requests+limits are stamped when the tenant container omits them, and that explicit tenant SecurityContext/resource values are preserved (gap-fill only). Verify the recommended app.kubernetes.io/* labels are present.
    • Failure recovery — Simulate a non-eviction pod failure (set pod status to Failed without reason: Evicted) and verify the AGC cleans up the associated Secret without leaking it and without triggering an automatic rerun. Simulate an eviction (set reason: Evicted) and verify the AGC calls the rerun API, increments actions_gateway_eviction_retries_total, and cleans up the Secret. Verify maxEvictionRetries: 0 suppresses the rerun call and increments actions_gateway_eviction_retries_exhausted_total instead. Simulate a namespace ResourceQuota rejection on pod create and verify the provisioner retries up to maxQuotaRetries times, increments actions_gateway_quota_retries_total on each attempt, and increments actions_gateway_quota_retries_exhausted_total when the budget is exhausted. Verify maxQuotaRetries: 0 returns an error immediately without touching any quota counter. The payload these cases pin the run identity with is the shape a real acquirejob response uses (the serialised github context), not system.github.* variables — building the identity the way only the fakes did is what let the classic tier ship unable to name a real job's run, with every one of these tests passing (Q495).
    • AcquireJob payload parsed against ground truth (Q495) — Verify the run identity and worker-pod annotations resolve from testdata/job_payload.json, the redacted capture of a live acquirejob response, rather than only from payloads the tests author. payload_groundtruth_test.go asserts owner, repo, and run_id come back non-empty from the capture, and pins the negative half — that the capture carries no top-level run_id and no system.github.run_id/.repository — so the guard fails if the parser drifts back onto a source GitHub does not populate. It is a unit test rather than an integration one because the capture is the external interface; no fake can be more authoritative about it.
    • Worker quota footprint — Verify the worker footprint behind the WorkerQuota{Pressure,Exceeded} conditions, the pre-claim quota gate, and the scale-set capacity integer matches what Kubernetes charges a pod, since all three read one calculation (Q450). Unit tests pin the four-part arithmetic against the shapes the repo ships (deploy/dogfood-e2e/overlays/{dind,kata}): regular containers and native sidecars summed, plain init containers as a max() floor raised by any preceding sidecar (KEP-753), and RuntimeClass overhead.podFixed added in full to requests but to limits only where a non-zero limit already exists. Two envtest cases prove it reaches the conditions against a real apiserver, each with a quota the regular containers alone would clear: TestV2_RunnerSet_WorkerQuota_CountsNativeSidecar (a 200m runner plus an 800m dind sidecar against a 500m quota) and TestV2_RunnerSet_WorkerQuota_CountsRuntimeClassOverhead (a 500m container plus 250m of Kata pod overhead against a 600m quota). The latter also exercises the cluster-scoped RuntimeClass read through the manager cache, which a fake client cannot demonstrate — the read is fail-open, so unit tests cover the unauthorized/missing/no-overhead paths degrading to zero overhead rather than erroring. The footprint also spans the storage keys (Q453), which Kubernetes charges through a second evaluator: ephemeral-storage is summed like CPU/memory, while each generic ephemeral volume (volumes[].ephemeral) is charged as the PVC it causes to be created — persistentvolumeclaims (a count of objects), requests.storage, and the <class>.storageclass.storage.k8s.io/… keys when the claim names a class. Unit tests pin the count-versus-quantity distinction (two volumes on one pod is two claims at any size), the partial shapes (no class ⇒ no class-scoped key; no storage ask ⇒ counted but not sized), and the negative case that matters most — a shape with no ephemeral volumes emits no claim key at all, so a namespace already over its persistentvolumeclaims ceiling for unrelated reasons cannot starve it. Two more envtest cases prove both arithmetics reach the conditions against a real apiserver, each constraining only a storage key: TestV2_RunnerSet_WorkerQuota_CountsEphemeralVolumeStorage (a 100Gi per-worker volume against a 50Gi requests.storage quota ⇒ WorkerQuotaExceeded) and TestV2_RunnerSet_WorkerQuota_CountsPerWorkerClaims (maxWorkers: 6 at 1 claim each against a 3-claim quota ⇒ WorkerQuotaPressure trips while WorkerQuotaExceeded stays False, which only holds if the claim charge is a per-pod count).
    • Pre-claim quota gate under contention — Verify the rung that refuses to claim a job the namespace ResourceQuota cannot house (#784), on both tiers it serves after Q443. Unlike the worker-quota footprint cases above, these fill the quota the way a busy namespace does — the tests own status.hard/status.used, since envtest runs no resourcequota controller — so the hard − used remaining arithmetic is what decides. TestAGC_AdmissionGate_QuotaRungSkipsAcquireUnderContention (classic) delivers three jobs against a full quota to a live listener and asserts each is skipped: acquirejob is never called (the broker stub's server-side counter, not the absence of a pod — "no pod appeared" would also pass for the claim-and-stall the rung prevents), actions_gateway_jobs_admission_rejected_total{reason="quota"} increments once per delivery, and no worker pod or per-job Secret is staged. It then proves the rung reserves nothing: with maxWorkers: 1 a single leaked reservation would close the gate forever, so freeing headroom must let the next delivery be claimed while the reason="ceiling" series stays flat. TestV2_RunnerSet_ScaleSet_PartialQuotaHeadroomSplitsTheCeiling covers the scale-set expression of the same property — under partial headroom (the case TestV2_RunnerSet_ScaleSet_QuotaHeadroomBoundsAdvertisedCapacity does not reach), the advertised X-ScaleSetMaxCapacity and the withheld gauge must sum to the declared ceiling. What envtest cannot show: status.used does not rise as worker pods are created, so neither test asserts an assignment count across more than one poll, and the sibling-AGC redelivery half of Q422 stays at live-GitHub (E2E_GitHub_QuotaBlockedJobRunsOnSibling, below).
    • Capacity gate on a cluster that cannot grow (Q405) — Verify the opt-in placeability rung on both tiers, with the gateway reporting clusterCapacity.nodeAutoscaling: Absent. The unit tests already cover the rung's ordering, its fail-open paths, and the trickle cycle; what only envtest can show is the two halves agreeing about one object — a real Pod carrying a real PodScheduled=False/Unschedulable status, aged past the scheduling grace by the reconciler's own RequeueAfter, publishing a condition the admission rung then reads back on a live listener's next delivery. TestV2_RunnerSet_CapacityGate_FixedClusterSkipsAcquire (classic) asserts acquirejob is never called (server-side on the broker stub's counter, for the same reason the Q422 case does) and that actions_gateway_jobs_admission_rejected_total{reason="capacity"} moves while reason="ceiling" and reason="quota" stay flat — maxWorkers is 3 against one in-flight pod precisely so the ceiling cannot be what refused, which is what makes the reason label meaningful. TestV2_RunnerSet_ScaleSet_CapacityGateWithholdsAdvertisedCapacity covers the integer form: it first pins the negative control (open gate ⇒ full ceiling advertised and an explicit 0 on the capacity rung's withheld series), then asserts a declining gate advertises exactly the set's own in-flight workers with the remainder withheld, the two summing to the untouched ceiling. What envtest cannot show: the gate's effect — how many wasted claims it actually removes from a burst, and whether it suppresses a cluster autoscaler that would have rescued the tenant. Both are cluster-only on a live cluster and remain unmeasured; see §9 of the plan.
    • Capacity gate on a cluster that can grow (Q406) — Verify the second signal, whose whole justification is when a signal may be trusted. The unit table (autoscaler_verdict_test.go) pins the matcher against the real messages both projects emit, including the three rows that keep it from over-gating: a FailedScheduling from default-scheduler (and from a pod's own non-default schedulerName, and one with no reporter at all) is not a declination, and a TriggeredScaleUp/Nominated newer than a declination reopens the gate. Sibling unit tests pin the load bound the mode is designed around — zero Event reads for a healthy set, none for a pod still inside the scheduling grace, one field-selected read per stuck pod up to a per-reconcile cap — and every fail-open path (no reader wired, an unreadable Event list, an unrecognized vocabulary, an unimplemented mode). The latch (Q512) has its own unit family: reaping the stuck pod latches the condition as AwaitingProbe under both signals, a post-decline container start clears it while pre-decline evidence does not, the probe's own stuck pod re-earns the live verdict, an unsupported mode still fails open through a held latch, and the two Target forms pin the probe-slot arithmetic — one slot, only while no probe pod is outstanding, on both acquisition tiers. TestCapacityGate_LatchHoldsWhileTheProbeHasOnlyBound is the negative control on the release evidence Q714 changed: a probe that has bound but run nothing must keep the latch, because binding is only a proxy for "a worker can run here" and a probe reveals that it cannot start seconds after it binds. Releasing inside that window would restore the full advertisement and reinstate the very burst the latch removed.
    • Capacity gate on a worker that schedules and never starts (Q714). Verify the third signal, whose distinguishing property is that no cluster fact selects it. TestPodStartupBackoff is the whole matcher in both directions, and its exclusions carry the weight: ErrImagePull, one failed pull rather than the kubelet's conclusion, must not gate, because refusing the pre-backoff state is this signal's entire substitute for a scheduling grace, and a CreateContainerConfigError must not either, since a per-pod config error says nothing about the next pod's shape. TestCapacityGate_DeclinesOnAWorkerThatBoundAndCouldNotStart runs the same pod against both nodeAutoscaling values, which is the assertion that this verdict is not selected the way the other two are, and asserts that WorkersUnschedulable stays False on the same object, since the two conditions read opposite halves of PodScheduled and must never both fire on one pod. TestV2_RunnerSet_CapacityGate_WorkerThatCannotStartSkipsAcquire is the envtest counterpart and deliberately uses the elastic gateway, where the autoscaler path fails open for want of an Event, so a decline there is attributable to nothing else; it asserts the skip on the broker stub's acquire counter rather than on the absence of a pod, since "no pod appeared" also passes if the AGC claimed the job and then failed to place it. What neither tier shows is the effect: envtest runs no kubelet, so every backoff status above is stamped by the test, and the shape itself was measured on a kind cluster instead (plan §9j). A sibling pair pins the Q470 split itself: TestCapacityGate_TheDangerousCombinationIsUnrepresentable asserts that no RunnerSet value produces scheduler-verdict gating where a node may still arrive — including when clusterCapacity is unset or the gateway does not resolve at all, so the DEFAULT is the safe one — and TestCapacityGate_FixedClusterReadsNoEvents asserts the two cluster facts select genuinely different paths rather than one path with different thresholds. TestV2_RunnerSet_CapacityGate_ElasticClusterDiscriminatesByReporter is the envtest counterpart, and it runs both halves against one set so the only difference between the pod that closes the gate and the pod that does not is who reported the event: a real default-scheduler FailedScheduling leaves WorkerCapacityDeclined=False while WorkersUnschedulable is True (the two conditions genuinely disagreeing is the point), then a real NotTriggerScaleUp from cluster-autoscaler closes it with reason=ScaleUpDeclined and a delivered job is left queued at GitHub. What only envtest adds over the table: the uncached, field-selected Event read works against a real apiserver, at the real API's one-second timestamp resolution. What neither can show is that upstream still says any of this — every event above is one the test stamps itself, so a reword upstream leaves all of them green while the gate quietly stops closing (an unrecognized vocabulary fails open). That class needs a real autoscaler and gets one: make test-autoscaler drives three pods through an upstream cluster-autoscaler running on kwok fake nodes in its own kind cluster, and asserts the matcher's verdict on the events that come back — a declination is still recognized (alongside kube-scheduler's own FailedScheduling on the same pod), a scale-up still leaves the gate open and really produces a node, and the node-group ceiling is still named in the message the operator docs quote. Karpenter's arm has no live counterpart yet (Q479). Still not shown by any of them: the same §9 measurement — how many wasted claims the gate actually removes from a burst, and how often a real autoscaler declines a condition it would have resolved on its next loop. See the plan §9c and testing.md.
    • Node-drain recovery boundary (Q421/Q502) — The complement of Failure recovery above, and the reason it is a separate case: a kubectl drain does not fail a pod, it POSTs to the pod's pods/<name>/eviction subresource, and an admitted eviction is a DELETE. Both sides of the Q502 boundary are pinned against that real subresource, on worker pods that came out of the real provisioning path on each tier with a complete run identity present. The unrecovered side: TestAGC_Drain_ClassicWorkerEviction_DoesNotRerun and TestAGC_Drain_ScaleSetWorkerEviction_DoesNotRecover let the eviction remove the pod with no terminal phase — envtest has no kubelet, so this is its native shape — and assert the rerun API is never called, because a worker that never ran its job to a reportable end leaves no failed job to re-run. The recovered side: TestAGC_Drain_ClassicWorkerTerminalWithMark_Reruns and TestAGC_Drain_ScaleSetWorkerTerminalWithMark_Recovers hold the evicted pod with a finalizer and then publish the status a real kubelet produces on a drained running worker — Failed with the deletion mark and a container exit the mark predates, the recorded exit being what detection orders the mark against — and assert exactly one rerun fires (with the scale-set claim stamped). The classic cases wire the production InformerPodWaiter (provisionerOptions.informerWaiter) rather than the poll fallback: the two agree on a pod that reaches a terminal phase and disagree on one deleted without ever reaching one. What a real drain actually publishes is the fake-GitHub half (E2E_AGC_WorkerNodeDrain, which drains a held-Pending worker — a transient Failed-with-mark with no container exit, which detection must and does leave alone) and the live-GitHub measurement (a running worker publishes Failed with the mark and the exit record). See the experiment and the decision.
    • Restart-safe disruption recovery (Q844). The window the two cases above cannot reach on the ScaleSet tier: preemption and drain both delete their victim, so an AGC that is down for the teardown lists no pod and has nothing to key on. The criterion is therefore a real restart rather than a pod state, and the test takes it literally: one manager generation provisions a worker and lets the guard ConfigMap record the run behind it, is stopped, the pod is deleted and the job concluded failed at GitHub as the Q385 relay would, and a second generation is started with only the ConfigMap to go on. TestAGC_ScaleSet_WorkerLostWhileTheAGCWasDownIsRecovered asserts the re-run fires; its control, TestAGC_ScaleSet_LiveWorkerSurvivesARestart, runs the identical restart with the pod left in place and asserts none does, which is what separates a lost worker from a job that is still running or genuinely failed. envtest is what makes either meaningful: the record is in a real ConfigMap and the pod is really absent, both of which a fake client would make true by construction. See archive/q844-owed-rerun-tombstone.md.
    • SIGTERM session cleanup — Start an AGC against the fake broker, burst the listener count to N sessions. Cancel the reconciler's context (simulating SIGTERM). Assert the AGC issues DELETE /sessions/{id} for every registered session before the context fully unwinds, confirmed by the fake broker. Assert no goroutine leak via goleak.VerifyNone.

    • Worker-pod reaper — Verify the RunnerGroup reconciler's reaper against a real apiserver: a worker pod advanced to a terminal phase via the status subresource is deleted once completedPodTTL elapses, driven by the real Pod watch and the reconciler's RequeueAfter timer (TestAGC_Reaper_CompletedPodDeletedAfterTTL); a pod that never schedules (envtest has no scheduler, so every pod is genuinely Pending) is deleted once pendingPodDeadline elapses, while a fresh Pending pod within the deadline survives (TestAGC_Reaper_StuckPendingPodDeletedAfterDeadline); and a pod created through the real provisioner path carries a controller OwnerReference to its RunnerGroup with the apiserver-assigned UID (TestAGC_Reaper_WorkerPodHasOwnerRef). The ownerRef cascade is not provable in envtest — there is no kube-controller-manager, so no GC controller runs — which is why the cascade hook is asserted here and the operational cleanup behaviour at cluster-only. The Running arm is proven on the v2 side (TestV2_RunnerSet_OrphanedRunningPodReaped): a worker pod driven to Running and stamped actions-gateway.com/job-completed-at past the five-minute grace is deleted, while one stamped inside the grace and one with no stamp at all (its job is still assigned) both survive (Q420). The grace is a constant, so the test back-dates the stamp rather than waiting it out. Restart recovery is measured separately (Q435): TestV2_RunnerSet_RestartReclaimsOrphanedWorkers stages all four orphan classes before starting the manager — the only thing an AGC restart means to the reaper — and asserts the three with a durable deadline (terminal, Pending, Running+stamped) are reclaimed while the unstamped Running orphan is retained and never backfilled with a stamp from cluster state alone; TestV2_RunnerSet_ScaleSet_RestartReclaimsWorkerOrphanedWhileDown then runs two managers against one scalesettest fake — provision a worker, shut the manager down, complete the job at GitHub with nothing listening, start a second manager — and asserts the replayed JobCompleted stamps the pod the new process never created. Whether the real GitHub queue still holds that completion after a multi-hour outage cannot be asked of any tier that runs against a double — the fake's queue log never expires, which is the deliberately permissive assumption — so it is a live-credential probe scenario (cmd/probe Investigation F, PROBE_RETENTION_TEST). It ran live across two rungs of one armed experiment and answered the question in the permissive direction: redelivery to a fresh session confirmed at a 29-second gap on 2026-07-28, and again at a 13 h 3 m gap on 2026-07-29 — past the 12 h maxWorkerLifetime beyond which no unstamped Running worker survives for redelivery to help, so the fake's never-expiring queue log is a sound assumption over the range that matters (Q468). It is a lower bound observed once, not a contract: LOST was never reached, so nothing here licenses deriving a timeout from it. See the plan doc. The lifetime cap that closes that residual is measured by two more tests (Q438): TestV2_RunnerSet_ScaleSet_WorkerCarriesLifetimeDeadline asserts a worker created through the real scale-set provisioning path carries the RunnerSet's maxWorkerLifetime as its activeDeadlineSeconds — against a real apiserver, so a defaulting bug producing an invalid deadline fails admission rather than a struct comparison; and TestV2_RunnerSet_RestartReclaimsWorkerKilledByLifetimeCap stages the same unstamped Running orphan the test above proves is retained forever, drives it to the Failed/DeadlineExceeded state a kubelet leaves behind, and asserts a restarted AGC reclaims it under reason="lifetime_exceeded" while a still-Running control survives. envtest runs no kubelet, so the kill itself is staged and everything downstream of it is the code under test.

    • Shared worker storage (Q719). Workers are storage-less and the provisioner provisions no volume of its own, so a ReadWriteMany volume several jobs pass files through is entirely a tenant podTemplate concern. That splits the criteria across three tiers by what each can observe, and none of them subsumes another. Unit (worker_shared_storage_test.go) pins that the tenant's claim reference survives the provisioner's own volume injection and that fsGroup survives applySecurityDefaults on every profile, with TestBuildPod_NoFSGroupIsLeftUnset as the control that the field is the tenant's rather than something GAG stamps. envtest (q719_shared_storage_test.go) adds the only thing a fake client cannot fail on: the RunnerTemplate CustomResourceDefinition is 1.2 MB of generated OpenAPI wrapping a full PodTemplateSpec, and a property it fails to publish is pruned on write, so the tenant applies a claim reference and the apiserver stores a template without one, silently. Neither can mount anything, which needs a kubelet, a Container Storage Interface (CSI) driver and two nodes: make test-rwx-storage runs the pod the provisioner really builds on both nodes of a kind cluster and requires them to exchange files through one claim, with a control asserting that without fsGroup the runner's write is refused. That control is the measurement behind the reference architecture's one hard requirement, and it is what a design-time argument would have got wrong: a freshly provisioned volume's root belongs to root, and the gap-filled UID 1001 is neither root nor in a group that owns it. See worker-shared-storage.md and testing.md.

    7.3. End-to-End Tests¶

    Scope: the full system deployed into a real Kubernetes cluster. GMC, AGC, and proxy binaries run as actual Pods. Proxy pods are scheduled and connected. Cert-manager issues TLS certificates for the admission webhook. NetworkPolicy is enforced by the CNI. HPA scaling is driven by metrics-server.

    Tier structure. End-to-end tests split into three tiers along one axis: what has to exist on the other end of the wire before they can run. The tiers are named for that, because it is the only thing that decides which questions a tier can answer — a test whose GitHub is a fake can only confirm what we already assumed GitHub does.

    Tier What it tests On the other end When it runs
    cluster-only GMC provisioning, proxy scheduling, NetworkPolicy enforcement, HPA, PDB, RBAC, teardown, GMC restart nothing — no GitHub at all every merge to main
    fake-GitHub AGC session polling, job acquisition, pod creation, eviction retry, SIGTERM cleanup test/fakegithub in-cluster every merge to main
    live-GitHub Actual workflow dispatch, log streaming, RenewJob across renewal cycles, proxy egress IP routing real GitHub, real App credentials nightly + on-demand

    These were called Tier A, Tier B, and Tier C until 2026-07-29. The letters implied a progression that was never real — they are dependency levels, not depth levels — The docs in this repo were renamed wholesale, so the letters survive only in git history — older commit messages, PR discussions, and Queue-row archaeology — where they map to the rows above in order.

    The cluster-only and fake-GitHub tiers run on a local kind cluster — fast enough for CI on every merge and for the inner dev loop. The live-GitHub tier runs against a real GitHub App and a dedicated test repository; it requires GITHUB_E2E_APP_ID, GITHUB_E2E_INSTALLATION_ID, GITHUB_E2E_PRIVATE_KEY, GITHUB_E2E_ORG, and GITHUB_E2E_REPO to be set, and is skipped at runtime when any are missing.

    What kind adds over envtest integration tests:

    Capability envtest (§7.2) kind (cluster-only/fake-GitHub)
    CRD admission + CEL validation ✅ ✅
    Admission webhook with cert-manager TLS ⚠️ requires manual cert workaround ✅
    Real pod scheduling (kubelet present) ❌ ✅
    Container images actually pulled and run ❌ ✅
    NetworkPolicy enforcement (CNI) ❌ ✅
    HPA scaling (metrics-server required) ❌ ✅
    PDB enforcement during node drain ❌ ✅
    Proxy CONNECT tunnel actually relays bytes ❌ ✅
    GMC/AGC/proxy binaries running as real Pods ❌ ✅
    Deployment rollout behavior ❌ ✅

    Speed contract: each cluster-only/fake-GitHub test completes in under 3 minutes. The two together run in under ~30 minutes. live-GitHub tests take 2–15 minutes each (the 15-minute RenewJob test is the bound). Cluster setup is a one-time BeforeSuite cost, not counted against individual test budgets.

    Build tag: all e2e files carry //go:build e2e. Tests are excluded from both go test ./... and the integration test run. Specs that need the 2-worker cluster shape to be meaningful (E2E_GMC_ProxyPodScheduledOnWorker, E2E_GMC_PDBPreventsEvictionBelowMinAvailable, E2E_GMC_GMCRestartPreservesState) carry the Ginkgo Label("multi-node"). CI runs the full suite on the default 2-worker cluster, so these run in CI; make e2e SUITE=single-node maps to --label-filter '!multi-node' to skip them for a faster local inner loop on a 1-worker cluster. The HPA scale-up spec (E2E_GMC_HPADrivesScaleUp) is deterministic and CI-safe — it patches HPA.spec.minReplicas to drive the HPA→Deployment path rather than burning CPU to trigger autoscaling. See docs/development/testing.md for run commands.

    Cluster shape. A multi-node kind cluster (1 control-plane + 2 workers) is required for pod anti-affinity and PDB tests to be meaningful. kindnet is the default CNI; it accepts NetworkPolicy objects but its bundled kube-network-policies enforcer does not drop egress traffic for the negative cases, so the runtime egress-negative specs (E2E_GMC_TenantProvisioning_WorkloadEgressBlockedToNonProxyPod, E2E_GMC_TenantProvisioning_WorkerCannotReachK8sAPI, and the direct-egress lockdown's E2E_V2_DirectEgress_NonGitHubBlocked) self-skip on kindnet.

    The make e2e-cluster KIND_CNI=calico profile (see kind-iteration.md) installs Calico instead; on that cluster the negatives assert real packet drops, each paired with an unlabelled control pod that proves the destination is reachable so a drop is attributable to NetworkPolicy enforcement.

    The per-PR e2e leg runs on kindnet (the enforcement specs self-skip there); a separate Calico CI lane runs the full suite on the egress-enforcing profile, triggered per-PR (and on push to main) whenever the diff touches NetworkPolicy/proxy code (plus manual dispatch), so those specs are a standing enforcement-regression gate (Q119) — both legs share one reusable workflow parameterized by CNI, and the Calico images are pre-pulled + cached to keep quay.io off the critical path. See testing.md § The e2e workflows.

    The fake. The fake-GitHub tier replaces real GitHub with test/fakegithub/, a standalone HTTP server deployed into the cluster as a Deployment + Service. It implements the broker protocol with stateful behaviour (session registration, controllable job-message delivery, recorded acquire/renew/rerun calls), the runner registration API (generate-jitconfig issuing real JIT blobs, list-by-name, delete, 409 on name collision), and exposes a control API used by tests to inject jobs and assert on calls.

    Single-use JIT runners. The fake simulates GitHub's single-use behaviour (Q114): with SINGLE_USE_RUNNERS=true or POST /control/singleuse?enabled=true[&owner=<prefix>], a job acquisition deletes the delivering session's runner record — the dead session then serves one empty 200 (the decode response: EOF signature) and 401s thereafter, and re-registering a surviving name returns 409 — reproducing the M4 §12 death spiral without real GitHub. It is off by default and scoped by session-owner prefix so one spec can opt in without affecting parallel suites.

    Pool-wide opportunistic delivery. fakegithub models this GitHub behaviour too (M1 Investigation C/D): a job whose session is recycled away before it is acquired is carried to the owner's pending pool and delivered to the next live session, so the post-job re-registration does not strand a job that races a session's recycle window. That carry rides the session's DELETE, which the AGC issues best-effort — so a job also ages into the owner pool on its own after 30 s undelivered (Q436).

    Without it, a DeleteSession that exhausted its retries left a session registered but polled by nobody, and any job the control API had addressed to that session was unreachable for the rest of the run: a liveness failure that reads as a slow spec, since no Eventually budget can wait it out. The real broker has no such state — work stays in the pool until a session polls for it — so the ageing restores the invariant that an enqueued job is always reachable by some session.

    The run-conclusion gate on re-runs. The fake models this GitHub behaviour as well (Q517): a run marked not-yet-concluded (POST /control/runstate?run=<id>&concluded=false) refuses rerun-failed-jobs with the measured 403 This workflow is already running answer real GitHub gives until it concludes the run — the refusal the AGC's Q503 retry loop keys on and the gap that let a fire-once-and-give-up recovery pass every fake-backed tier while failing live.

    Accepted and refused calls are reported separately on /control/reruns, so a spec asserts the refusal window and the post-conclusion acceptance without the refusals inflating its accepted count; unmarked runs conclude instantly, so only a spec that opts its own run in sees refusals.

    Pointing the AGC at it. Set AGC_EXTRA_* env vars on the GMC, which forwards them into the AGC Deployments it creates (gated by --allow-agc-extra-env=true, set only in e2e). See docs/development/kind-iteration.md for the env-var details.

    Tooling: Ginkgo-based suites under cmd/gmc/test/e2e/. A shared cmd/gmc/test/utils/ helper package wraps kubectl, kind, and the fakegithub port-forward. live-GitHub uses the GitHub REST API to dispatch workflows and poll runs to completion.

    What to cover:

    • Smoke test — single job, single tenant — Create a namespace, apply one ActionsGateway CR into it, dispatch a minimal workflow (echo "hello"), and assert the run completes green with correct log output in the GitHub UI. This is the merge gate.
    • Parallel job execution — Dispatch a matrix workflow with 10 parallel jobs against a single tenant and assert all 10 complete successfully, verifying the session multiplexer handles concurrent polling without message collisions.
    • Multi-tenant isolation — Provision two ActionsGateway CRs pointing to different GitHub repositories and different namespaces. Dispatch simultaneous jobs to both. Assert that each job runs in its own namespace, that no Secrets are visible across namespaces, and that one tenant's resource consumption does not affect the other's job throughput.
    • Proxy egress isolation — Confirm via network observation that GitHub API calls and log stream traffic from both the AGC and worker pods exit through the tenant's proxy Service address, not directly through the cluster NAT. Assert no direct egress to GitHub IPs is observed from AGC or worker pods.
    • Proxy HA under disruption — Cordon one node hosting a proxy pod and drain it. Assert the PodDisruptionBudget prevents eviction until another proxy pod is scheduled, and that in-flight jobs are not interrupted during the disruption.
    • Tenant provisioning and deprovisioning — Create a namespace, apply an ActionsGateway CR, run a job successfully, then delete the CR. Assert all GMC-owned resources (proxy Deployment, proxy Service, HPA, PodDisruptionBudget, AGC Deployment, RBAC, NetworkPolicy) are removed but the namespace itself remains intact. The platform-owned ResourceQuota is not GMC-owned and must survive CR deletion (Q130). Re-apply the CR and verify a fresh gateway and proxy pool come up cleanly and can run jobs again.
    • Job failure propagation — Dispatch a workflow with a deliberately failing step (exit 1) and assert the GitHub UI correctly reflects the failure status. Verify the worker pod exits non-zero and is still cleaned up within the tenant namespace.
    • Worker pod lifecycle cleanup (fake-GitHub, E2E_AGC_WorkerPodLifecycle) — Two tenants against fakegithub, run Serial (fakegithub session IDs carry no tenant identity, so the suite must not overlap other session-consuming suites). Tenant one uses a fast-exiting worker image and a short completedPodTTL: assert its completed worker pod and job Secret are deleted once the TTL elapses. Tenant two uses an unpullable worker image (reserved .invalid TLD) and a short pendingPodDeadline: assert the genuinely stuck-Pending pod is reaped after the deadline with a WorkerPodStuckPending Warning Event on the RunnerGroup. Also assert worker pods carry a controller OwnerReference to their RunnerGroup — this is the tier where the live GC controller makes that cascade real.
    • Single-use JIT agent self-heal (fake-GitHub, E2E_AGC_SingleUseSelfHeal) — With fakegithub's single-use simulation enabled (scoped to this spec's RunnerGroup by owner prefix), run maxListeners + 1 sequential jobs. Each acquisition consumes its agent's runner record and kills its session; assert each consumed session is torn down and replaced by a fresh one, and that the final job — the one a pre-Q114 AGC could never serve, having burned every listener slot — still produces a worker pod.
    • Pre-acquisition admission control (fake-GitHub, E2E_AGC_AcquireAdmissionControl) — Confirms the GitHub-broker contract the Q59 gate rests on, the load-bearing assumption Q154 verifies end-to-end. A maxWorkers: 1 RunnerGroup pins worker pods Pending (unschedulable) so capacity is held deterministically; fakegithub's opt-in, owner-scoped lease/redelivery model (/control/redelivery, /control/jobstats) gives the two paths distinct outcomes. (a) A Pending decoy pod manufactures the gate/ceiling divergence the post-acquire backstop exists for: the gate admits, AcquireJob claims the job, then ceilingCheck holds it — and fakegithub never redelivers the acquired job (an acquired-then-held job is cancelled, not redelivered). (b) With the slot busy, a second job is skipped by the gate (never acquired) yet redelivered repeatedly; deleting the busy pod frees the slot and the redelivered job is finally acquired (a skipped job is not lost).
    • Node drain vs. eviction recovery (fake-GitHub, E2E_AGC_WorkerNodeDrain, Q421) — Serial, multi-node. Runs a real kubectl drain against the node holding a live, AGC-watched worker pod and asserts the drain reaches no eviction recovery — its deliberately held-Pending worker never records a container exit, which since Q502 is the unrecovered side of the drain boundary (a running worker's Failed-with-mark-and-exit publish is the recovered side; this spec is what caught a mark-only rule re-running the never-ran shape, since a real kubelet publishes a transient Failed-with-mark even here): the pod never publishes PodFailed/Evicted (a phase/reason sampler runs at 200 ms across the drain and recorded Pending/ and nothing else), and fakegithub sees no rerun-failed-jobs call for the run over the following 45 s. Two things make the absence meaningful rather than vacuous: the AcquireJob payload is pinned to carry a complete run identity, without which handleEviction returns early anyway; and the spec first asserts the AGC's GITHUB_API_BASE_URL addresses fakegithub, so a rerun would have been observed had one fired. The drained pod is deliberately held scheduled-but-Pending on an unpullable image — a fake-GitHub worker running the real runner image exits by itself within seconds, and a drain aimed at it would be evicting a pod that had already failed on its own. The drain is scoped by --pod-selector to the tenant's RunnerGroup so the shared cluster's control plane is not collateral; the per-pod action (cordon, then the eviction subresource) is identical either way. Also records that the AGC's safe-to-evict: false marker does not stop a drain — it is advisory to autoscalers only. See the experiment.
    • Quota-declined job redelivers to a sibling gateway (live-GitHub, E2E_GitHub_QuotaBlockedJobRunsOnSibling, Q422) — The premise the pre-claim quota rung rests on, which no fake can be asked about: fakegithub redelivers because it was written to. A pods ResourceQuota filled to the tenant namespace's live occupancy leaves the only gateway on the org's Default runner group with zero headroom; a workflow is dispatched, and the gateway must decline each delivery with reason=quota while GitHub holds the job queued. A second gateway (its own namespace, its own runner names, no quota) is stood up only after the decline is observed — with both up at dispatch, GitHub could route the job to the sibling on the first offer and the decline would never happen. The claim is disproven by the absence of the post-claim backstop's pod creation blocked by namespace quota line rather than by the absence of a pod: a claimed job whose pod the quota rejects also leaves no pod, and that claim-and-stall is what the rung exists to prevent. The spec then asserts the sibling provisions a worker, the run concludes success, and the blocked namespace gained no worker pod. What it does not assert is the rejection counter — half A's observable — because reaching the AGC's TLS/authn-gated metrics endpoint would mean scheduling a scrape pod into a namespace deliberately filled to its pod ceiling; the decline log line carries the same reason label. Measured 2026-07-31 and the premise holds: the job was declined ≥63 times in 9s (all reason=quota, zero post-claim backstop lines), held queued by GitHub, and run green on attempt 1 by the sibling's runner — runner_name=real-ag-sib-e2e-6d8749c-0 on GitHub's own job record. The unexpected finding is the cadence: redelivery is a tight loop at ~7/s, not a backoff retry, which is why the per-delivery decline is logged at Debug. See the arrangement and the result.
    • Cross-tenant Secret opacity — After two tenants have completed jobs, assert via namespace inspection that neither tenant's namespace contains Secrets belonging to the other. Assert that the AGC ServiceAccount for tenant A cannot read Secrets in tenant B's namespace.
    • Resource cleanup under load — Dispatch 50 sequential jobs across 5 tenants and assert zero pod or Secret leaks remain after all runs complete. Checked by polling all tenant namespaces for residual resources 60 seconds post-completion.
    • Proxy HPA scaling — Dispatch a sustained burst of 50 concurrent jobs against a single tenant with spec.proxy.maxReplicas: 5 and spec.proxy.minReplicas: 2. Assert the HPA scales the proxy pool above minReplicas during the burst, and that replica count returns to minReplicas within 5 minutes of load subsiding. Assert no jobs are dropped during scale-up or scale-down.
    • GMC restart resilience — Delete and re-create the GMC pod while tenants are active. Assert that in-flight jobs are not interrupted, the GMC correctly re-derives tenant state on restart, no duplicate resources are created during reconciliation, and the proxy HPAs remain intact.
    • AGC restart resilience — Mid-run on a single tenant, delete and re-create the AGC pod. Assert in-flight jobs are not double-acquired, the AGC converges back to the correct goroutine count within one reconcile cycle, and all traffic continues routing through the proxy pool.
    • RenewJob under long-running job — Dispatch a workflow that sleeps for 15 minutes. Assert the job completes successfully, confirming the RenewJob loop correctly kept the lock alive across multiple renewal cycles without GitHub cancelling the job.
    • Rolling AGC upgrade — Start a steady stream of dispatched workflows against a single tenant, then patch the AGC Deployment image to a new tag mid-flight. Assert the upgrade completes the rolling update successfully, in-flight long polls drop and reconnect (with no duplicated job acquires observed via the broker's audit log), per-job RenewJob loops resume after the new pod starts, and total workflow success rate over the upgrade window stays above 95%. Assert that jobs whose lock expired during the blackout are redelivered and complete on retry.
    • GitHub IP range reconciliation — Simulate a GitHub meta API response with a new IP range not present in the existing NetworkPolicy. Trigger a GMC reconcile cycle and assert the proxy pod NetworkPolicy egress rules are updated to include the new range. Assert that spec.proxy.managedNetworkPolicy: false suppresses the update.
