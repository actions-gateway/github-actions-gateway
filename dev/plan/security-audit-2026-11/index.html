    Security Audit 3: November 2026¶

    Third full security audit, performed 2026-11-09 against 7b3f016ad, ahead of v2.0.0. The first audit (2026-05) is security.md and the second (2026-06) is archive/security-audit-2026-06.md; this doc records only the third audit's findings and where each one is tracked.

    Status: findings filed, the medium one fixed, the eight stricter admission rules landed (Q1322), the four egress proxy sharing leads confirmed and fixed (Q1324), six of the seven release and CI leads settled (Q1326), and the four scale-set identity leads confirmed, three fixed and one accepted as a residual (Q1325). 9 findings are confirmed from source (one medium, eight low) and 30 were leads that source alone cannot settle, 12 of which still are, one of them the release and CI lead that waits on Q1330. Nothing reached high or critical. Two rows gated v2.0.0, Q1321 and Q1322, and both have landed. The rest are Q1323 to Q1328.

    Method and limits¶

    The audit read source and ran nothing. No agent built, tested or executed anything from the repository, and nothing was sent to a cluster, to GitHub or to any other live system. That sets what each verdict means:

    • Confirmed means static text fully determines the result: a manifest, a policy expression, a constant or a pure function. No confirmed result was observed on a cluster.
    • Needs validation means source supports the path and something outside the repository decides the outcome: a Container Network Interface (CNI) plugin, the apiserver, GitHub, tenant role-based access control (RBAC) or a repository setting. These carry no severity.

    So the confirmed set is a floor, and the weight of the audit is in the leads.

    Coverage was planned as 58 units, each a surface, a trust boundary and an attack class, across two hunting waves. A reviewer that had not seen the hunting pass checked each candidate, and a second fresh reviewer checked each surviving record against source line by line. That second pass corrected wording or a citation on 15 of the 39 retained records and changed no verdict, root cause or severity. Three candidates were rejected. A coverage critic after the first wave accepted eight gaps, which became the second wave; the critic after the second wave and a separate final critic both accepted none.

    What the audit did not do:

    • Dependency vulnerability status was not assessed. No vulnerability database was consulted, and make vulncheck and make trivy-scan were not run.
    • The trust model is the documented one. Where a lead says "a tenant who can write X", whether tenants hold that permission in a real install was not established.
    • Three commits landed on main during the audit (#2286, #2288, #2289) and were not reviewed. #2286 adds an admission rule on spec.tracing, which no finding here concerns.

    The recurring theme matches the second audit's: a documented isolation property that the enforcing layer does not deliver, or delivers for fewer kinds than the doc names.

    Confinement claim¶

    The one medium finding, tracked as Q1321, which gated v2.0.0 and has landed. The design doc claimed a confinement the shipped policy did not deliver, and a General Availability release should not carry a security claim that source refutes.

    Fixed by both routes. gmc-tenant-resource-guard now matches ConfigMaps, the three CNI-native policy kinds and ServiceMonitors, in the chart template and the config copy, and 05-security.md states what stays cluster-wide: ConfigMap reads, Events, and the GMC's own API kinds. A unit test fails when the manager ClusterRole grants a write that no shipped policy matches, and a second holds each config copy to its chart template. Two ConfigMap writes are admitted outside a tenant namespace, which the finding's own fix did not anticipate in full: any in the install namespace, as it proposed, and the delete of a proxy-share or failure-attribution projection, without which neither could be withdrawn from a namespace that had lost its marker and the provider proxy's reconcile would fail there. The role was not narrowed: the GMC lists its share projections by label across namespaces, so ConfigMap get/list stays cluster-wide and is recorded as a residual. The finding below is kept as written on 2026-11-09.

    GMC ServiceAccount can write ConfigMaps (and, where the CRDs exist, CNI-native network policies and ServiceMonitors) in any namespace; tenant-resource-guard does not match those kinds¶

    gmc-tenant-resource-guard:ungated-configmap-cni-servicemonitor-writes: confirmed, medium. Starts at charts/actions-gateway/templates/rbac.yaml:17.

    The guard's resourceRules cover the original provisioning kinds and were not extended when the role gained write verbs on ConfigMaps (the egressproxy_controller.go marker widened configmaps from get to the full write set for cross-namespace proxy-share projection; ipranges_store.go adds create/update), the CNI-native FQDN policy kinds, and ServiceMonitors. Nothing compares the role's namespaced write grants against the guard's matched resources, and the envtest guard suite exercises only kinds the guard already names.

    Established by source. Derived by reading source, not by running anything. The ClusterRole authorizes configmaps create/update/patch/delete cluster-wide. No resourceRule in tenant-resource-guard lists configmaps, so its matchConstraints do not select the request and its validations are not evaluated; no other shipped policy or webhook matches the resource. A GMC-identity ConfigMap write to an unmarked namespace is therefore admitted, contradicting 05-security.md:52-54. By the same reading the guard does not select writes to ciliumnetworkpolicies, projectcalico.org networkpolicies, fqdnnetworkpolicies or servicemonitors on clusters that serve those APIs. The verifier also found the envtest copy of the guard lacks the verticalpodautoscalers rule the chart template has (chart lines 45-48), a separate drift that does not affect this result.

    Fix. Add the five kinds to tenant-resource-guard in both the chart template and the cmd/gmc/config/admission-policy copy, and admit ConfigMap writes outside a tenant namespace only in the GMC's own install namespace (the IP-range store and leader election live there). Before shipping, confirm each controller's writes of these kinds land only in marked tenant namespaces or the install namespace, since a proxy-share projection into an unmarked consumer namespace would start being denied. Add envtest cases: a GMC-identity ConfigMap create in an unmarked namespace is denied, and the IP-range store and a share projection into a marked namespace still succeed. Add a test that derives the namespaced write kinds from cmd/gmc/config/rbac/role.yaml and fails when one is missing from the guard's resourceRules. Correct docs/design/05-security.md lines 23 and 52-54 to state what is and is not gated, including that ConfigMap get/list is cluster-wide and cannot be gated by admission; narrowing the role (dropping list and patch on configmaps if the controllers allow) reduces that read. The code change below is a sketch and was not rendered or tested.

    Stricter admission rules¶

    Eight findings whose fix is a stricter admission rule, tracked together as Q1322 and gating v2.0.0 for the reason Q1283 and Q1312 were: a manifest that applies today would be refused afterwards, so only a major can take the rule, and the next major is v3. All eight have landed for v2.0.0. Three are confirmed and five are leads. For the leads the gap in the rule is visible in source; what is unsettled is whether anything gets through the layer behind it. Each rule must pass an unchanged stored value, as spec.tracing.endpoint's does.

    Tenant-authored EgressPeer accepts 0.0.0.0/0 on any port, so the AGC NetworkPolicy can be widened past the operator's apiServerCIDRs narrowing, contrary to the documented 'single scoped peer'¶

    egresspeer-unbounded-peer-agc-networkpolicy: confirmed, low. Starts at api/v2/shared_types.go:304.

    Fixed by a rule on the CIDR, with the docs corrected for what it leaves. Two CEL rules on EgressPeer.cidr refuse a value that is not a CIDR or is broader than /16 for IPv4 or /48 for IPv6, and one that is link-local or covers one of four metadata and platform addresses that clouds serve outside link-local space (Alibaba Cloud, Azure, and the IPv6 addresses of AWS and Google Cloud); each passes an unchanged stored value. That list is not complete and the docs no longer say the peer cannot name a metadata server: IPv6 forms that embed 169.254.169.254 for a translator (64:ff9b::a9fe:a9fe, 2002:a9fe:a9fe::/48, ::a9fe:a9fe) are admitted, because a NAT64 prefix is also how an IPv6-only cluster reaches a legitimate IPv4 peer, and whether any of them reaches a node's metadata server was not tested. The floor is a policy number with no measurement behind it, set at the largest network a single CIDR has to cover: an AWS VPC is at most a /16, and /48 is one IPv6 site. Three parts of the proposed fix were decided against, and 05-security.md says what each leaves open. A selector peer is not bounded, because a rule refusing {} would leave an Exists expression that selects the same pods, and a selector reaches pods only, never a node address. No operator allowlist gates the peer, since an opt-in one is additive and needs no major. The builder does not narrow a stored value, so a 0.0.0.0/0 stored before v2.0.0 keeps its rule until an operator narrows it, which upgrade.md tells them how to find. The finding below is kept as written on 2026-11-09.

    EgressPeer validation is structural only: the CEL rule at api/v2/actionsgateway_types.go:537 checks exactly-one-of, the pattern at :558 matches any prefix length including /0, the ActionsGateway webhook (actionsgateway_webhook.go:155-200) never inspects the peer, and egressPeerTo (actionsgateway_v2_builder.go:440-448) passes the CIDR straight into an IPBlock. buildAGCNetworkPolicyV2 appends the rule regardless of apiServerCIDRs, so nothing subordinates the tenant-delegated hole to the operator's scope.

    Established by source. Derived by reading source, not by running: the built AGC policy contains the egress rule {Ports:[80], To:[{IPBlock:{CIDR:"0.0.0.0/0"}}]} in addition to the apiserver rule scoped to 10.0.0.0/24, so the authored policy admits TCP/80 from the AGC pod to every IPv4 address, including 169.254.169.254, while the same gateway without the field does not. No traffic, CNI enforcement or data read was observed.

    Fix. Bound the tenant-delegated peer at admission and make it subordinate to operator scoping: reject a cidr shorter than a minimum prefix length (and ranges overlapping link-local) in the ActionsGateway webhook or with a CEL cidr() rule, decide whether an empty selector is acceptable, and optionally gate CIDR peers behind an operator allowlist when --apiserver-cidrs is set. Otherwise correct the godoc and 05-security.md so they stop claiming a single scoped peer and that apiServerCIDRs closes everything. Add an AGC-with-peer case to TestBuildNetworkPolicy_DeniesCloudMetadataServer and a webhook rejection test.

    Namespaced RunnerTemplate privilege gate checks only securityContext.privileged, so the documented 'platform-owned template pins the pod shape' property is not enforced in a privileged-profile namespace¶

    runnertemplate-privileged-equivalent-shape: confirmed, low. Starts at cmd/gmc/internal/webhook/v2/runnertemplate_webhook.go:194.

    validateReservedPodFields equates 'a privileged worker shape' with the single boolean securityContext.privileged (isPrivileged). It reads no other host-reaching field (capabilities.add, hostPath and other volume sources, procMount, seccomp or AppArmor profile, runtimeClassName), buildPod passes those fields through, applySecurityDefaults is a no-op under the privileged profile, and nothing binds a RunnerSet in a privileged-profile namespace to a ClusterRunnerTemplate.

    Established by source. Derived by reading, not running: the RunnerTemplate admission function returns no error for this spec, and buildPod returns a Pod whose spec still carries the hostPath volume, the added capabilities, the Unconfined seccomp profile and uid 0 with no runtimeClassName. Source therefore establishes that no GAG control distinguishes this tenant-authored shape from the platform's kata-dind shape, contrary to kata-dind-workloads.md:45, :176, :293 and 05-security.md:884. Whether the apiserver admits the pod is decided only by the namespace Pod Security level; admission in a privileged namespace and any node effect were not observed.

    Fix. Decide which statement is authoritative. To deliver the documented property, make the namespaced-kind gate evaluate the Pod Security Standards baseline level rather than one boolean: when rejectPrivileged is true in validateReservedPodFields, reject capabilities.add outside the baseline set, hostPath volumes, hostPort, procMount other than Default, Unconfined seccomp or AppArmor, and non-baseline sysctls on the pod and every container and init container, and add a table case per field to the existing validateReservedPodFields tests in cmd/gmc/internal/webhook/v2/runnertemplate_webhook_test.go. If the narrower check is kept by design, correct docs/design/05-security.md:884, docs/operations/kata-dind-workloads.md:45, :176 and :293 and deploy/templates/kata-dind/template.yaml:33-35 to say that a tenant in a privileged-profile namespace can author any pod shape short of privileged: true and the reserved host-namespace fields, so platform ownership of the template does not pin the worker shape there.

    Resolved in v2.0.0 by enforcing, not by correcting the docs. The namespaced-kind webhook now evaluates the whole podTemplate against the Pod Security Standards baseline level on every profile, through the upstream evaluator (k8s.io/pod-security-admission/policy v0.37.2, vendored) and not the hand-written field list sketched above, so the webhook and a baseline namespace cannot drift on what baseline means. The evaluation is pinned to Pod Security Standards 1.37 and does not use the library's latest version: at latest, a Dependabot bump of k8s.io/pod-security-admission that carried a stricter check would refuse, in a minor release, a manifest the previous one admitted. The cost is that a later upstream tightening reaches a privileged-profile namespace only when the pin is raised, which is a breaking change to schedule; TestPodShapeVersion_IsPinned fails if the pin is replaced by latest. Every baseline check forbids a set value and none requires one, so evaluating the partial template gives the verdict the built pod would get. None of the three shipped deploy/templates/ entries is refused, because all three are ClusterRunnerTemplates; TestTemplateLibrary_PodShape pins that, and that kata-dind and privileged-dind are refused as the namespaced kind.
